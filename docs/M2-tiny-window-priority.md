## 1. 让步链全表(横向 + 纵向 + 双轴)

### 1.1 横向(Row)五级——原样复述,不重开

| 级 | 动作 | 停止条件 |
|---|---|---|
| L0 | 正常求解(§2.3) | `demand(root, Row) <= 可用宽` |
| L1 | fixed 列收缩:files 从 `fixed_extent`(默认 240)线性收至 `FILES_W_MIN=170` | 收完仍不够则进 L2 |
| L2 | flex 等比压缩:全部 flex 座位按 share 等比缩,下限各自 kind 的 min(终端 260/预览 360) | 触底仍不够则进 L3 |
| L3 | 折叠非焦点座位,按离焦点最远优先的确定序 | 折到只剩焦点仍不够则进 L4 |
| L4 | 焦点最后倒下 → `LayoutError::Unsatisfiable` | — |

出处:`M2-layout-solver-spec.md` §2.6.1。

### 1.2 纵向(Col)四级——首次表格化,不新增决策

父规格 §2.7 已用一句话交代纵向退化为 `L0 → L2 → L3 → L4`(没有 L1,因为 §1.3「固定性只在
Row 轴成立」)。这里只是把那句话铺成和 1.1 对称的表,方便实现直接抄:

| 级 | 动作 | 停止条件 |
|---|---|---|
| L0 | 正常求解(§2.3 Col 分配式,`avail = h - DIVIDER`) | `demand(root, Col) <= 可用高` |
| ~~L1~~ | **空过**——Col 轴没有 fixed 类,files 在 Col 方向占满槽位、没有自己的可收缩区间 | — |
| L2 | flex 等比压缩:全部 flex 座位按 share 等比压高度,下限各自 kind 的 `min_size(kind, Col)`——终端/files/预览三者此值**相同,都是 `MIN_PANE_H=120`**(§2.1,唯一在 Col 轴不分叉的一处) | 触底仍不够则进 L3 |
| L3 | 折叠非焦点座位:沿 Col 收成 24px 横条(§2.6.3「沿被压的那根轴」的字面意思),宽仍占满槽位;离焦点最远优先——**顺序与横向 L3 用的是同一条序**(见 §1.3) | 折到只剩焦点仍不够则进 L4 |
| L4 | 焦点最后倒下 → `LayoutError::Unsatisfiable` | — |

红线 L4/W1/W2/W3 逐字成立(§2.7 原文)。

### 1.3 双轴同时不足:轴间让步顺序(本文新裁,结构澄清 + 政策位延伸)

**结论先说:两条链并行独立求解,不存在「先让哪个轴」的先后顺序——因为两个轴之间没有共享的
可变状态可以互相抢。**

依据(全部来自已裁的形式化定义,不是新假设):

- `demand(split, axis)` 的定义(§2.2)只在 `split.dir == axis` 时才求和,否则取 `max`——这意味着
  沿 Row 走一遍树和沿 Col 走一遍树是**两次独立的折叠**,一次的输出不作为另一次的输入。
- fixed/flex 分类**只在 Row 轴成立**(§1.3),`min_size(kind, axis)` 逐轴独立给值(§2.1)。
  L1 因此结构性地只能触碰 Row。
- L3 的「离焦点最远优先」按**树距离**定义(§2.6.1 第三条读法),这是一个纯树函数,**不吃任何
  几何输入**——所以横向链和纵向链在「先折叠谁」这件事上用的是**同一条序**,只是各自在这条序
  上停在不同的位置(横向可能需要折 2 个座位才够,纵向可能只需要折 1 个)。

于是双轴场景的确定性规则是:

> 同一次 `solve()` 调用内部,独立跑出 `level_row ∈ {L0,L1,L2,L3,L4}` 与
> `level_col ∈ {L0,L2,L3,L4}` 两个值,**各自**满足 W3(「对整棵树取同一个值,不逐节点贪心」)。
> 一个座位最终呈现什么,是把两次独立判定的结果**按座位取交**:
> - 两轴都判它 Full → 呈现 Full。
> - 恰好一轴判它 Collapsed → 沿那一根轴收 24px,另一根轴照旧占满槽位(§2.6.3 原文行为)。
> - **两轴都判它 Collapsed → 呈现 24×24 的方块**,两根轴各自的「占满槽位」都不再适用——这不是
>   一条额外发明的规则,是两个独立判定各自生效后的自然合取。

**这条结论要求 §3.1 的 `Presentation` 签名做一处必要的结构性修正**(不是重开折叠政策本身,
是让类型能表达它):

```rust
// 父规格 §3.1 原签名只有 Full/Collapsed,无法区分「哪根轴被压」与「双轴都被压」。
pub enum Presentation {
    Full,
    Collapsed(AxisSet),   // AxisSet ⊆ {Row, Col},非空;{Row} / {Col} / {Row,Col} 三种取值
}
```

`solve()` 仍是同一次纯调用,`level_row`/`level_col` 都是该次调用的内部中间量,不外泄
(与 §2.6.2「让步等级不落盘」同一纪律)。钉死名:
`a_seat_collapsed_on_both_axes_is_a_twentyfour_square_not_a_bar`。

**微例验算**(两座位横向 split,焦点是左边那个):窗口同时变窄又变矮到两轴都要 L3——右边座位
先在 Row 判定里因「唯一非焦点」被收成 24 宽满高的条,又在 Col 判定里(它是这个 Row-split 唯一
非焦点)被收成满宽 24 高的条,取交 = 24×24 方块;左边焦点座位两轴都停在 L0-L2 的某一级,正常
呈现。窗口边界与焦点座位的边界依旧共享同一数值(红线 L6 不受影响,取交只改被折叠座位本身)。

**双轴 24×24 方块的视觉呈现(用户裁决 2026-08-03,§5 已裁 2)**:**不复用**折叠条(§2.6.3)
「名字 + 状态图标」的样子——24×24 装不下名字,硬塞等于逼真字裁成马赛克。呈现为一个**独立于
折叠条的极简样式:纯色块 + `stateIcon`,不画边框**。与单轴折叠条共享同一枚 `stateIcon`
组件(状态语义不丢——busy/未读/等你回答等七态照样可辨),但去掉边框与文字,这个样式**只属于
双轴退化态**,不是折叠条本身缩小版。命中/Tab/展开语义与折叠条一致(点击/Enter=展开,该座位
升格为焦点)。钉死名:`a_double_collapsed_seat_is_a_color_block_with_only_a_state_icon`。

## 2. 每一级用户看到什么(banner/affordance)

| 级 | 几何表现 | 用户看到的信号 | 是否新增 chrome |
|---|---|---|---|
| L0 | 正常 | 无 | 否 |
| L1 | files 列在 240→170 间变窄 | 无——这与手动拖 divider 能达到的区间完全相同,窗口 resize 落进同一区间不构成意外 | 否 |
| L2 | flex 座位等比缩到各自 kind 的 min | 无独立 banner;逼近 min 时终端/预览内部文字开始折行/需要滚动,这是 `bt-viewport` 既有的「内容不得回改座位矩形」(红线 L10)的自然后果,不是本文新增的信号 | 否 |
| L3 | 非焦点座位收成 24px 条(单轴)或 24×24 方块(双轴) | 单轴:**折叠条本身就是信号**——名字 + 状态图标(与 tab/卡片同源 `stateIcon`,§2.6.3 已裁)。双轴:**独立的极简样式**——纯色块 + `stateIcon`,不画边框、不放名字(§1.3 已裁,§5 已裁 2) | 是,单轴样式是已裁的 §2.6.3;双轴样式是本文新裁(§1.3) |
| L4 | 连焦点座位都放不下,`solve()` 返回 `Err(Unsatisfiable)` | **fit-what-fits(§5 已裁 1)**:按能装下的数量渲染折叠条(能放几条放几条),尾行追加一句「还有 N 个装不下」;**不给操作按钮**——窗口大小是用户用鼠标/键盘拖出来的 OS 手势,应用层不越俎代庖去改它,用户自己拖大窗口即可脱离该状态 | 是,§5 已裁 1 |

L0-L2 没有独立 banner 是刻意的:这份规格里没有为「正在变窄」发过 toast(§7.1.6b 的动画/提示
纪律里也找不到这种先例),几何变化本身就是唯一的诚实说法——加一条文字反而暗示这是异常,而
L0-L2 都是「让步链正在做它该做的事」,不是异常。

## 3. 浮窗与布局的仲裁(闭合 §2.6.4 的洞)

### 3.1 浮窗不是座位——复述红线,不重开

`M2-layout-solver-spec.md` §2.6.4 原文:

> 浮窗**不是座位、不进树**,所以它不参与 §2.6.1 的任何一级;两者的仲裁发生在求解器**之外**
> (它拿到的 `viewport` 是仲裁的结果,不是仲裁的输入)。

§3.3 的编辑焦点集表也印证这一点:浮窗的开/关/移动根本不在那张表里出现——`F(浮窗任何操作)`
恒为 `∅`。补一条与该表其余各行同风格的钉死名:
`opening_or_moving_a_floating_surface_rewrites_no_ratio`。

**本文把「仲裁发生在求解器之外」这句话具体化**:浮窗的布局函数(以 `peek_box_layout` 为原型)
以 `solve()` **已经算完**的座位矩形(或整窗 `viewport`,见 §3.3)为**只读输入**,自己求交、求
clamp、求 flip,不回头改任何 `ratio`、不请求任何座位变大。这与红线 L10(内容不得回改座位矩形)
是同一纪律再高一层:**浮窗对布局也是「只读消费者」**。

### 3.2 三种浮窗体制:TRANSIENT / PINNED / MENU

现有代码实证了两套完全不同的行为,第三套(离散内容的菜单/下拉)由用户裁决(2026-08-03,
§5 已裁 4)正式确立为独立体制,不能三者共用一套规则描述:

| | **TRANSIENT**(瞬态) | **PINNED**(钉住) | **MENU**(离散内容) |
|---|---|---|---|
| 现有例子 | hover peek 缩略图(`bt-render::peek_box_layout`) | 文件树 pinned 浮窗(DESIGN §7.1.2) | 终端右键菜单、命令面板(DESIGN §7.1.6) |
| 未来例子 | tooltip、hover 一瞥卡 | 未来的可拖拽面板/工具窗(若有) | 未来的下拉/combo/子菜单 |
| 锚点 | **它所属的那个 pane** 的矩形 | **整窗内容 viewport**(§7.1.2「同窗口合成层,不出主窗口边界」;撕下后与来源 pane/tab 完全独立) | 触发它的控件(按钮/右键点/输入框)所在的矩形 |
| 放不下时的动作 | **诚实拒绝,不显示**(`peek_box_layout` 返回 `None`) | **缩到自己的诚实地板(标题条高度),不到 0**(§5 已裁 3,见 §3.4) | **几乎不拒绝**:翻转/重定位保证完整可读(§5 已裁 4,见 §3.4) |
| 主窗口几何变化时 | **消散**(下方 §3.5) | **重新钳位**:平移回视口、尺寸不变(§7.1.2「主窗口缩小自动重钳位」) | **消散**(与 TRANSIENT 同,菜单本就是打开即高优先级、关一切无关状态的短命浮层) |
| 关闭方式 | 移开/Esc/滚轮/点击/任意按键(自动) | 只被 `×`/Esc(顶层时)/Dock/再点触发器关闭(§7.1.2,几何变化不算关闭理由) | Esc/点外/选中项(既有 §7.1.5 Esc 分层路由与 owner=Menu 语义,本文不新增) |

**IME 候选窗不在这张表里**:用户裁决(2026-08-03,§5 已裁 5)v1 完全交给平台 IME 定位 API,
不进本文任何一种体制,见 §3.6。

三者的分野不是随意的:TRANSIENT 是「看一眼」,承诺本来就是「移开即散」(DESIGN §7.1 hover
原则「查询免提交」);PINNED 是用户点击撕下的一次**承诺**,几何变化让它消失等于对用户已经做
过的选择进行静默撤销——与 §2.6.3「本 UI 一贯不许有隐身状态」是同一条品味,只是从「折叠占位」
搬到「浮窗」上应用一次;MENU 的内容是**离散、有界、必须完整可读的条目列表**,不存在「按比例
缩小」这个选项——拒绝渲染一个菜单等于这个功能当场坏掉,不是一次诚实降级,所以它的默认动作是
「总能想办法摆下」而不是「摆不下就算了」。

### 3.3 clamp 目标 = 求解器已经给出的 viewport(结构)

TRANSIENT 浮窗的 clamp 目标是**它锚定的那个 pane 的矩形**(今天单 pane 窗口下这个矩形等于整个
`viewport`;M2 分屏落地后收窄为该 pane 自己的矩形,不是整窗)。PINNED 浮窗的 clamp 目标是**整窗
内容 `viewport`**(即 `solve()` 签名里那个「不含标题栏/侧栏/卡片列等 chrome」的矩形,§3.1)。
两者都**不使用原始窗口矩形**——chrome 永远被排除在浮窗可占用的空间之外,这就是「不得覆盖 chrome
到不可读」这条要求在结构上自动成立的原因,不需要额外一条「避让 chrome」的运行时判断。

`peek_box_layout` 的精确先例(`crates/bt-render/src/lib.rs:638-728`):

```rust
// peek_thumbnail_extent: 40% 上限、下取整(避免超出上限)、chrome 加不进去就整体拒绝
let fit = (avail_width * 0.4 / native_width)
    .min(avail_height * 0.4 / native_height)
    .min(1.0);
let thumb_width  = ((native_width  * fit) as u32).max(1);
let thumb_height = ((native_height * fit) as u32).max(1);
if thumb_width as f32 + chrome > avail_width || thumb_height as f32 + chrome > avail_height {
    return None;   // 诚实拒绝,不缩到看不清
}

// peek_box_layout: 优先锚在指针右下方,底部放不下就翻到上方,水平方向恒 clamp(不翻转)
let mut top = pointer_y + offset_y;
if top + box_height > avail_bottom {
    top = pointer_y - offset_y - box_height;
}
let top  = top.clamp(avail_top, avail_bottom - box_height);
let left = (pointer_x + offset_x).clamp(avail_left, avail_right - box_width);
```

这就是本文对「未来 TRANSIENT 浮窗(tooltip 等)通用 clamp 契约」的定义——**结构上照抄这个
形状**:连续尺寸的内容先按比例上限(40% 一类)算出候选尺寸;主轴(通常是竖直)不够则翻转到
反方向;次轴(通常是水平)恒 clamp 不翻转;翻转后仍不够、或候选尺寸本身放不进 clamp 目标 →
整体拒绝,不产生退化到看不清的浮窗。**MENU 体制复用同一个「主轴翻转、次轴 clamp」的定位算法,
但跳过比例上限那一步**(条目列表按自身内容量决定尺寸,不打折)——见 §3.4、§3.6。

### 3.4 完全放不下时的仲裁

- **TRANSIENT**:直接不显示,等价于 `peek_box_layout` 返回 `None` 的既有行为——用户重新悬停在
  更大的窗口里就能看到,没有承诺过要留下。
- **PINNED——诚实地板(用户裁决 2026-08-03,§5 已裁 3)**:遵循 §7.1.2 已裁的「允许临时小于
  200×150」,但这条裁决现在补上一个下限——**收缩停在只剩浮窗自身标题条(含 `×`/拖拽手柄)那
  一条高度**,`PINNED_FLOAT_MIN_STRIP`(具体像素值实现时钉,概念上与 `COLLAPSED_EXTENT` 同族:
  一条可点、可读、有真面积的最小呈现,不是零)。**永不缩到 0**——与 §7.1.2「只被 `×`/Esc/Dock/
  再点触发器关闭」的裁决因此保持一致:尺寸可以诚实地小到只剩标题条,但「消失」只能由那四个
  显式动作触发,不能由挤压几何触发。标题条本身仍可点 `×` 关闭、仍可拖拽把浮窗挪回可用空间。
- **MENU——几乎不拒绝(用户裁决 2026-08-03,§5 已裁 4)**:默认路径永远是**翻转/重定位**
  (§3.3 的「主轴翻转、次轴 clamp」),不裁剪内容、不缩小字号。只有当 clamp 目标(触发控件所在
  viewport)本身已经小到连翻转都摆不下**最短的那一种呈现**(理论上只在 §2 表格 L4 那种
  `Unsatisfiable` 场景下才会发生)时,才与下面「两者共同」那条一起处理——MENU 不为「放不下」
  单独定义一条拒绝路径,因为它不该被独立触发。
- **三者共同**:若 clamp 目标(pane 矩形或整窗 `viewport`)本身已经退化到 L4/`Unsatisfiable`
  呈现的那种极端状态(§2 表格最后一行),**浮窗一律不显示**——没有一个诚实的矩形可以锚,继续
  尝试渲染只会叠在那条「装不下」的错误态上面,制造第二层混乱。

### 3.5 几何变化时的消散规则(z-order 与 dismissal)

TRANSIENT 浮窗在**任何**改变了它锚定矩形的事件上消散,这不是新规则,是把已实现的行为点名
归纳成一条通用政策。既有触发点(`crates/bt-app/src/main.rs`):

- `resize()`(2364-2381 行)显式清空 peek,注释原文:「A resize dissolves it exactly as a wheel
  notch does; the retained thumbnail is re-derived, and resampled if the new pane asks for
  another box, on the next settled hover.」——resize 与滚轮在这条规则上是**同一等级的事件**。
- `mouse_wheel()`(2040-2042 行)、`begin_local_selection()`(1733-1734 行)、`pointer_left()`
  (1562-1564 行)、任意按键(2215-2217 行)均调用同一个 `dismiss_peek()`(1422-1427 行,
  文档注释:「idempotent; used by every dismiss gesture」)。

**本文把这条既有政策显式推广到让步链驱动的几何变化**:一个 TRANSIENT 浮窗锚定在某座位内部,
若该座位因让步链升降级(折叠/展开跨越 L3 边界)、因 divider 拖拽改变了矩形、因中心 swap/replace
换了内容、或因进出聚焦态从树上消失/重新出现,浮窗按**同一条**「锚点几何变了就消散」规则处理
——这些事件在效果上都等价于一次 resize(锚点矩形不再是浮窗算出布局时用的那个矩形),没有理由
被排除在外。

PINNED 浮窗则遵循 §7.1.2 已裁的「重新钳位不消散」:任何整窗 `viewport` 尺寸变化(含让步链把
座位折叠腾出/占用空间导致的 chrome 变化——目前 chrome 不受让步链影响,故实际触发源仍主要是
窗口 resize)只平移/收缩它,不关闭它。撕下后它与来源 pane/tab 完全独立(§7.1.2 原文),所以
**座位层面**的让步链事件(折叠/展开某个 pane)对已撕下的 pinned 浮窗**没有影响**——它根本不
在监听那些事件。

**MENU 的消散规则不是本文新定义的**:它复用 DESIGN §7.1.5 既有的 `InputOwner=Menu` 语义与
Esc 分层路由(「进行中的拖拽/divider → Menu → Dialog → pinned 浮窗 → owner=Terminal 时透传
PTY」)——菜单开启期间拥有键盘,关闭方式是 Esc/点外/选中项。本文只需要把它**摆进** TRANSIENT/
PINNED/MENU 三分类的框架里(它是几何变化即消散的那一类,§3.2 表格「主窗口几何变化时」一行),
不重新定义它的键盘/z-order 行为。

z-order 顶层规则复用 §7.1.5 已裁:「模态遮罩 z-order 高于一切弹出层与浮窗」;弹出浮层之间由
「集中控制器互斥,打开方负责关闭其余」(DESIGN §7.1 纪律③)——TRANSIENT、PINNED、MENU 都
遵守,互斥范围是「同类之间」(全窗口单例 peek、全窗口单例 pinned 浮窗,均已裁,§7.1.2;菜单
的互斥性由 owner=Menu 单值语义天然保证,同一时刻只可能有一个 owner)。

### 3.6 未来族(tooltip / 菜单 / IME 候选)怎么入座

- **tooltip / hover 一瞥卡**:内容有界且通常远小于 40% 上限,直接复用 TRANSIENT 体制与
  §3.3 的 clamp 形状(主轴翻转、次轴 clamp、放不下拒绝——一瞥卡放不下的场景理论上只在窗口本身
  已经很小时发生,届时诚实拒绝显示是正确行为)。
- **菜单/下拉(用户裁决 2026-08-03,§5 已裁 4)**:归入 §3.2 新增的 **MENU** 体制——翻转/
  重定位,几乎不拒绝(§3.4)。不套用 TRANSIENT 的「放不下就拒绝」:拒绝渲染一个菜单等于功能
  当场坏掉,不是诚实降级;离散、有界的内容几乎总能通过重定位摆下,「摆不下」只该在整个 clamp
  目标已经退化到 `Unsatisfiable` 时才和其余浮窗一起隐藏(§3.4「三者共同」)。
- **IME 候选窗(用户裁决 2026-08-03,§5 已裁 5)**:**v1 完全交给平台 IME 定位 API**,不进
  TRANSIENT/PINNED/MENU 任何一种体制——候选窗的位置由输入法框架跟随插入符,本文的浮窗仲裁
  管不到、也不该管它。归类推迟到「本产品真的要自渲染候选 UI」那一刻才重新讨论(结合内存记录
  的「搜狗不上报预编辑」等既有 IME 观察,那会是另一份独立的规格工作,不是本文现在能提前回答
  的问题)。

## 4. 绝对地板

### 4.1 `floor_demand`:形式定义(本文新增,补 §2 之缺)

父规格的 `demand()`(§2.2)算的是「每个座位都在自己 Full 状态」下的最小需求,这是 §2.6.5 计算
OS 最小窗口尺寸时用的量。但让步链真正能压到的极限,是「非焦点座位全部折叠成 24px 条」之后还
剩多少——这个量父规格从未命名,只在 L3 的停止条件里用自然语言提了一句「折到只剩焦点仍不够则
进 L4」。给它一个形式定义,方便回答「这份规格允许的最小窗口是多大」这个问题:

```
floor_demand(seat, axis, focus) =
    if seat == focus { min_size(seat.kind, axis) }
    else             { COLLAPSED_EXTENT }               // 已全折叠时的贡献

floor_demand(split, axis, focus) =
    if split.dir == axis { floor_demand(a) + floor_demand(b) + DIVIDER }
    else                  { max(floor_demand(a), floor_demand(b)) }
```

形状与 `demand()` 逐字一致,只把非焦点叶子的贡献从 `min_size(kind, axis)` 换成
`COLLAPSED_EXTENT`——这不是一个新算法,是同一个折叠(sum/max)对不同叶子取值跑一遍。

**这就是「一条折叠条 + 一个可用座位」的精确含义**:多座位树的绝对地板 = 焦点座位保留自己
kind 的诚实最小值,其余每个座位在被压的那根轴上贡献恰好 24px。单座位树(N=1,没有旁的东西可
折)没有折叠条,地板就是 `demand(root) = min_size(focus.kind, axis)` 本身——退化情形,不是例外。

钉死名:`the_floor_is_the_focus_seats_own_minimum_plus_one_bar_per_sibling`。

### 4.2 与 L12/60% 钳位的关系——一条此前没写出来的防护(结构,补 §2.6.5)

> **【2026-08-08 用户裁决:本节整节作废,保留供翻案时对照】**
> 「最小值对程序是法律,对用户是建议」。窗口最小尺寸不再由树导出——它现在是**技术地板**
> `min(一个终端叶的 min + chrome, 60% * workarea)`,见 `M2-layout-solver-spec.md` §2.6.5 与
> §7.1 表 8。本节的整个论证(下界该取 `floor_demand`,以及「只要 OS 遵守 min hint,L4 在正常
> resize 路径上永不触发」)**建立在窗口最小值应当替布局守可满足性这个前提上,而那个前提正是被
> 翻案的东西**:守可满足性的职责搬去了 `SizePolicy::Lawful` 一侧的让步链。
>
> 在手动 resize 路径上现在的答案是:**根本走不到 L4**,因为 `Sovereign` 不折叠也不拒绝(L2′,
> spec §2.6.1)。§4.3「OS 仍强制更小时诚实降级」的要求**照旧有效**,而且现在是常态而非例外——
> 分配期的夹取保证矩形永不反转,钉死名
> `no_sovereign_rectangle_is_inverted_even_under_its_own_dividers`。

§2.6.5 **原本**的公式是:

```
min_inner_size = min(demand(root) + chrome, 60% * workarea)
```

这条公式有一个没被指出的缺口:当 `demand(root)` 很大(树很大)而 `workarea` 很小(小副屏)时,
`60% * workarea` 可能**小于 `floor_demand(root) + chrome`**——也就是说 OS 允许把窗口缩到一个
连「全部折叠 + 焦点座位诚实最小值」都放不下的尺寸,让步链会被迫走到 L4。这与 §2.6.5 自己声明
的意图(「让步链是降级路径,不该是常态」)相矛盾:60% 钳制这条**上限**不该反过来变成一条会
主动把树推进 `Unsatisfiable` 的**下限缺失**。

补一条下界,formula 不变红线 L12(输入仍只来自 `demand(root)` 与工作区,不来自当前窗口尺寸,
`floor_demand` 同样是纯粹由树与焦点导出的量,不是「当前尺寸」):

```
min_inner_size = max(floor_demand(root) + chrome,
                      min(demand(root) + chrome, 60% * workarea))
```

**代价核算**:这条下界在几乎所有真实场景下是空操作——一棵中等大小的树(4 座位)的
`floor_demand` 量级在几百逻辑像素(焦点 260/360 + 若干 24px 条),而 `60% * workarea` 在任何
现实显示器(哪怕一块很小的副屏)上通常远大于这个数。它只在「树很大 + 显示器极小」这种病态组合
下才会真正把 `min_inner_size` 从 `60% * workarea` 拉高——而这恰恰是它该做的事:与其让 OS 给出
一个连折叠链都救不回来的尺寸,不如让窗口最小尺寸诚实地反映「这棵树折到底也需要这么多」。

这条补充是本文对既有让步链最有实际价值的贡献:**只要 OS 遵守 `set_min_inner_size` 的提示**,
L4/`Unsatisfiable` 在正常 resize 路径上永远不会被触发——它只在下面 §4.3 描述的、OS 没有遵守
提示的情形下才可能出现。

### 4.3 OS 仍强制更小时:诚实降级,不是崩溃

§4.2 的防护只在「OS 遵守 `set_min_inner_size`」的前提下成立。现实里存在它不成立的路径(平台
差异、某些窗口管理器忽略 min hint、编程式强制 resize、DPI 切换瞬间的中间态、多屏拖拽跨越工作
区边界的过渡帧)。这些都不是本文能阻止的输入,只能规定 `solve()` 面对它们时必须做什么:

- **绝不崩溃**、**绝不返回零面积或负尺寸矩形**(红线 L4 覆盖到这个新场景,不是新红线,是老
  红线的必然推论)。
- **绝不静默复用上一帧几何**——那是把「求解失败」伪装成「求解成功但没变化」,用户会以为窗口
  正常,实则布局与窗口尺寸已经脱节。
- `solve()` 只有两种合法输出:一个满足(哪怕已经退到 L3 折叠殆尽的)`Ok(SeatLayout)`,或者
  显式的 `Err(LayoutError::Unsatisfiable)`。上层必须处理后者并渲染一个**占满当前 viewport、
  不含任何裁剪矩形**的显式状态:**fit-what-fits**——按能装下的数量渲染折叠条,尾行追加
  「还有 N 个装不下」,不给操作按钮(§2 表格 L4 行、§5 已裁 1)。

这就是任务描述里「OS 强制更小时,honest degradation 不 crash」的完整含义:§4.2 尽力让这条路径
几乎不会被走到,§4.3 规定它一旦被走到必须长什么样子(结构上),不承诺替它设计像素。

### 4.4 `workarea` 查询失败时的兜底(用户裁决 2026-08-03,§5 已裁 6)

§4.2 的下界公式需要一个当前 `workarea` 数值才能算。多屏切换/热插拔期间这个查询有短暂失败的
可能——**具体兜底数值交给实现阶段**(这是平台集成细节,不是布局政策能替它决定的),但政策必须
说清两条边界,否则实现会各凭直觉编出不一致的行为:

1. **优先用上一次成功查询到的 `workarea`**——工作区尺寸在两次查询之间通常没有变化,复用旧值
   远比编一个假的更诚实。
2. **从未成功查询过(例如启动瞬间第一次布局就撞上失败)→ 不设最小尺寸提示**,而不是用任何猜测
   的数字去卡死用户窗口。宁可让 OS 用它自己的默认行为(通常是不限制或很小的系统级下限),也
   不要用一个可能错得离谱的数字把用户的窗口锁死——这与红线 L12「不得由当前窗口尺寸导出」是
   同一种审慎:**没有可信输入时,不产生一个假装可信的输出。**

> **【2026-08-08 修订第 2 条】** 第 1 条不变;第 2 条改为:**从未成功查询过 → 仍然给出技术地板**。
> 原文的审慎针对的是「一个可能锁死窗口的、由树导出的数」;技术地板是一个常数,不需要任何输入
> 就可信。而「完全不设最小值」恰恰是它要挡的那个荒谬矩形——157×25 的窗口没有比一个假数字更
> 诚实。60% 钳位仍然只在 `workarea` 已知时参与。
