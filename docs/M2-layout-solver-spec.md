## 0. 本文的射程(先说不做什么)

求解器**只拥有外层几何**:把一个可用矩形分给若干**座位**,输出每个座位的矩形。

| 不做 | 归谁 |
|---|---|
| 座位内部的行/列、滚动锚、公式高度树、投影失效 | `bt-viewport`(§4,一字不改) |
| 内容身份(session uid / 缓冲 / files root)与它的状态 | 法则①:状态属于内容,容器不持有 |
| 拖拽命中判定(zone/rim/角落选边)的**手势语义** | UI 层;求解器只回答「这棵树摊开是什么形状」(§3.4) |
| 极小窗口下**浮窗**与布局的冲突优先级 | 规格债 ④,§2.6.4 留洞(布局自身的让步链已裁,§2.6.1) |
| 聚焦态的卡片列几何 | 侧栏 chrome,**不进树**(§3.5,用户裁决 2026-08-03) |
| 落盘字段名与格式 | 规格债 ②,§5 只给耐久面与两条约束 |

**纪律 ④ 原文继承(结构)**:实现为**独立纯布局求解器,不模拟 CSS flex**。输入 = 树 + 可用矩形
+ DPI + 每 kind 的最小尺寸,输出 = 叶子矩形。原型的 flexbox 是**非规范性示例**,两者有差异
时以本文为准——但 §2.3 的分配公式**逐条对齐原型已验证的行为**,因为纪律 ① 要求预览与提交
是同一张图,而原型的 `rectsOf` 正是那张图的第一版实证。

## 1. 布局模型

### 1.1 座位(Seat)是唯一的叶子类型

```rust
enum SeatKind { Terminal, Files, Preview }        // 未来族员见下
struct Seat { id: SeatId, kind: SeatKind, fixed_extent: Option<LogicalPx> }
```

- **求解器只认 `SeatKind` 与几何参数,不认内容身份**(**红线 L1**)。座位不携带 session uid、
  不携带缓冲、不携带 files root。这是法则①在几何层的样子:内容搬家(swap/replace/入池)不产生
  任何布局事件,布局变更也不产生任何内容事件。
- **未来座位**按 DESIGN §7.0 七级形态里的「pane」一档扩充(web 会话、媒体、AI 对话面)。
  扩充的**唯一**接缝是 §2.1 的 `min_size(kind)` 与 §1.3 的 extent 类;树、分配公式、确定性
  规则**一行都不改**。这条是本规格的主要设计目标之一——新座位不该重开一次求解器。
- **未知 kind 必须整叶降级为占位座位**,不得让整棵树因一片叶子损坏而丢失(§7.1.4 逐叶降级原文,
  §5 复述为持久化约束)。

### 1.2 树:二叉,不是 n 叉(结构)

```rust
enum LayoutNode {
    Split { id: SplitId, dir: Axis, ratio: Ratio, a: Box<LayoutNode>, b: Box<LayoutNode> },
    Seat(Seat),
}
enum Axis { Row, Col }        // Row = 左右并置(沿 x 分配), Col = 上下堆叠(沿 y 分配)
```

**为什么留二叉**:全部既有裁决(边缘投放 = 把一片叶子劈成两半、中心 = 替换/交换、pluck 提升
兄弟)都是二叉编辑;而「一行里的窗格是平等的一行」(UI-UX §六)所需的 n 元语义由 §3.3 的
**run** 概念在二叉树上恢复——run 不是一个节点,是**同向连续 split 的传递闭包**。把 run 提升
成 n 叉节点会让「劈开某一片叶子」与「给整行加一列」两个已裁决的不同手势(UI-UX §六对照表)
失去结构区分,那是用数据结构去抹掉一条用户裁决。

**根 = 一棵树,不是一个座位**:根级 rim(48px)投放要能把整棵树劈开(原型 `splitRootOf`),
所以根必须允许是 Split。空 tab 不存在(最后一个 pane 关闭 = 关闭该 tab,§7.1.4)。

### 1.3 三种 extent 类

| 类 | 谁 | 沿 Row 轴 | 沿 Col 轴 |
|---|---|---|---|
| **flex** | Terminal、Preview | 按 ratio 分份额 | 按 ratio 分份额 |
| **fixed** | Files | **按像素**(`fixed_extent`,默认 240,可拖至 170) | **不 fixed**,占满该槽全高/全宽 |
| *intrinsic*(预留,当前无成员) | — | 按内容固有尺寸 | 同 |

**固定性只在 Row 轴成立**(DESIGN §7.1.1「Files 可拖到任意方向」裁决的直接推论):files 落在
col 切分的纵向槽位时占满该槽全宽。**col 内全固定子树 = 成员最大宽**——纵向堆叠不丢固定性,
否则两个纵向堆叠的 files 列会一起膨胀成半个窗口(原型实测过的 bug)。

**Preview 是 flex,不是 fixed(政策位)**:「固定右席」说的是**住址**不是**尺寸**——它落在
root run 的最右列,但它的宽度是份额。把住址和尺寸混为一谈会得到一条 240px 的代码预览,那不是
预览是缩略图。**它自有一个比终端更高的下限 `MIN_PREVIEW_W = 360`**(用户裁决 2026-08-03,
§2.1):260 的代码预览每一行都在折,而预览的全部价值就是「读得下去」——和 files 的 170 同族,
是「这类座位的诚实下限」,不是终端那条线的复用。

**住址在「最右列已被占」时怎么落(用户裁决 2026-08-03,政策位)**:① 优先**复用未 pin 的既有
preview 座位**(换内容,§7.1.3 单例语义,不增殖座位);② 没有则在 **root run 尾部新开一列**;
③ 但若 root run 尾部是一条 **files 固定列**,新 preview 插到那条 files 列的**左侧**——files 是
导航、preview 是内容,把内容挤到导航外侧会让「最右」这个住址名不副实。显式瞄准边缘的拖拽
**仍落所指**(§7.1.1 原文),本规则只管「默认创建」。钉死名
`the_preview_seat_lands_left_of_a_trailing_files_column`。

### 1.4 结构 vs 政策(法则③的逐项落账)

| 结构(翻案 = 换求解器,必须重跑全部不变量) | 政策(可翻案,翻案只改表) |
|---|---|
| 二叉树、Split/Seat 两型 | `MIN_PANE_W/H`、`FILES_W`、`FILES_W_MIN`、`MIN_PREVIEW_W` 的**数值** |
| divider 在分配里占实位(§2.3) | divider 视觉 1px / 命中 7px、rim 48px、边缘区 35% |
| fixed/flex 分类与 fixed 只在 Row 轴 | 谁是 fixed(今天只有 Files) |
| demand 沿同向求和、异向取 max(§2.2) | Preview **固定右席**及其让位规则(§1.3)、Preview 单例复用 |
| 入/离 run 即重新均分(§3.3) | 聚焦态 4+1+1 容量、进入门槛 |
| 纯性与确定性(§3.1、§3.2) | 让步链的**顺序骨架**(§2.6.1,已裁);折叠占位的**样子**(§2.6.3) |
| 聚焦态不改树、卡片列不进树(§3.5) | 折叠条 24px、`MIN_WINDOW_CLAMP_RATIO = 60%`(§2.6.5) |
| 落盘意图不落盘几何(§5) | Files 默认宽度、Preview 是否可 pin |

## 2. 约束系统

### 2.1 每 kind 的最小尺寸

| kind | min 沿 Row | min 沿 Col | 出处 |
|---|---|---|---|
| Terminal | `MIN_PANE_W = 260` | `MIN_PANE_H = 120` | DESIGN §7.1.1 |
| Files | `FILES_W_MIN = 170` | `MIN_PANE_H = 120` | 同上 |
| Preview | **`MIN_PREVIEW_W = 360`** | `MIN_PANE_H = 120` | 用户裁决 2026-08-03(§7 已裁 1) |

**三个数是三条独立的线,不是一条线的复用**(政策位):终端 260 是「一屏能读的命令输出」,
files 170 是「一列文件名」,preview 360 是「一行代码不折」。**最小尺寸是 kind 的常数,不是内容
的函数**——按打开的是代码还是图片去分档会把内容拉进求解器,撞红线 L1。

**红线 L2**:最小尺寸**按矩形自报的 kind 判定,不按「去真树里查这片叶子」**。中心 swap 会
把终端放到 files 原来的位置上,查真树在那一刻就开始说谎(原型实测:一个落到 files pane 上的
投放因此永远不被接受)。kind 随规划出来的矩形一起走。

### 2.2 子树需求 `demand`(结构)

```
demand(seat, axis)  = min_size(seat.kind, axis)                      // fixed 座位沿 Row 取 fixed_extent 与 min 的较大者
demand(split, axis) = if split.dir == axis  { demand(a) + demand(b) + DIVIDER }
                      else                  { max(demand(a), demand(b)) }
```

**红线 L3**:任何夹取(divider 拖拽下限、投放可行性、窗口最小尺寸)用的都是 **`demand` 子树
需求,不是单个座位的最小值**。约束是逐子树的,不是逐孩子的——外层 divider 曾因此把一个两窗格
的组挤到 260px 总宽、每个 130px。

### 2.3 fixed/flex 混合 row 的完整分配公式(规格债 ① 点名项)

先定义**沿 Row 的固有固定宽度**(判断一整个子树是否为一个固定单元):

```
fixed_w(seat)  = if seat.kind is fixed { max(seat.fixed_extent, min_size(kind, Row)) } else { None }
fixed_w(split) = match split.dir {
    Col => if both children Some { Some(max(a, b)) } else { None },   // 全固定的纵向堆叠仍是固定的
    Row => if both children Some { Some(a + b + DIVIDER) } else { None },
}
```

再定义 Row 分配(`avail = w - DIVIDER`):

| 情形 | a 得到 | b 得到 |
|---|---|---|
| a 固定、b 弹性 | `fixed_w(a)` | `avail - fixed_w(a)` |
| a 弹性、b 固定 | `avail - fixed_w(b)` | `fixed_w(b)` |
| **两侧皆固定** | `fixed_w(a)` | `avail - fixed_w(a)`(**尾侧吸收盈余**) |
| 两侧皆弹性 | `avail * ratio / 1_000_000`(§2.4 ppm 整数式) | `avail - a` |

Col 分配只有最后一行(纵向无 fixed 类):`avail = h - DIVIDER`,`a = avail * ratio / 1_000_000`,
`b = 余数`。

**「尾侧吸收盈余」是裁决不是取整细节**(DESIGN §7.1.1 原文「双固定 row 的尾侧吸收盈余——
消灭死白,与预览同语义」):当整行没有任何弹性成员而槽位大于固定和时,必须有人吃掉余量,否则
它是一块永远填不满、也永远点不到的死白。**b 恒取余数**这一条同时保证了 §2.5 的无缝性。

### 2.4 ratio 的定义域、精度与 clamp 顺序

- **规范表示 = `u32` ppm(百万分率)**(用户裁决 2026-08-03):

  ```rust
  pub struct Ratio(u32);          // 不变量:1 <= .0 <= 999_999,ppm of the flexible extent
  ```

  定义域 `ratio ∈ (0, 1)` 的两端**按类型被排除**:0 或 1 表达的是「一个零尺寸的座位」,而零尺寸
  座位应当由**关闭**或**折叠占位**表达,不是由 ratio 表达(**红线 L4**:求解器不得输出零面积
  矩形;放不下走 §2.6 让步链)。
  选 ppm 的理由是 D3 要整数,而 ppm 是整数里最省事的那个:4K 宽度上的量化误差 < 0.004px,
  远在一个物理像素之下;有理数对要约分与通分,那是自找的复杂度。分配式因此是整数运算
  `a = avail * ratio / 1_000_000`(先乘后除,`avail` 为 i64 子像素,不溢出)。
- **运行时表示与落盘表示必须同精度**——落盘就写这个 `u32`(§5 约束①)。
- **clamp 顺序是有序的,不可交换**:先判可行、后 clamp。先 clamp 后判可行会写进一个不可满足的
  值,再由下一次求解「修正」——那是把一次拒绝伪装成一次抖动。这条**结构上仍然成立**,只是
  2026-08-08 裁决之后,「不可行」的清单里**不再包含「比最小值还紧」**(见下)。
- **【2026-08-08 用户裁决修订】拖拽不再按 `demand` 设下限。** 原文是:

  > 1. 先按 `demand` 求两侧下限 `lo = demand(a, dir) / usable`、`hi = 1 - demand(b, dir) / usable`;
  > 2. `lo > hi`(已经比两侧最小值还紧)→ 拒绝这次拖拽,零副作用,不写任何 ratio;
  > 3. 否则 `ratio = clamp(requested, lo, hi)`。

  现裁为:**`ratio = requested`,只受类型定义域 `(0, 1)` 约束**;固定列按像素拖时夹取为
  `[0, usable]`(那是槽位本身,是算术不是偏好)。理由:**最小值对程序是法律,对用户是建议**。
  手拖 divider 是用户在说「我要这个比例」,用 `demand` 去否决它等于回答一个没人问的问题——而且
  实测中那条下限让 divider 在窗口不宽时**整段手势都是死的**。最小值没有失效,它们仍然否决
  **投放**(`plan_fits`,§3.3/D5)、仍然驱动**程序自选布局**的让步链(§2.6.1 `Lawful`)。
  Esc / pointer-cancel 的零副作用回滚(§3.4)**不变**,且因为回滚走的是同一个
  `Edit::DragDivider`,取消下限恰好让「从任何拖到过的位置都能回得去」成为定理而非巧合。
  钉死名:`a_drag_tighter_than_the_minimums_is_the_users_to_make`(取代原
  `a_drag_tighter_than_the_minimums_is_refused_with_zero_side_effects`)、
  `a_divider_drag_in_a_window_too_small_for_both_seats_still_follows_the_hand`。

### 2.5 单位、DPI 与取整

- **唯一权威单位 = 逻辑像素的定点表示**(`LogicalPx`,子像素分母与 `bt-doc::SUBPIXELS_PER_PX`
  同为 **1024**,但 `bt-layout` **自持**该常量、**不依赖** bt-doc,见 §4.1 红线 L7;两处以一条
  编译期一致性断言钉住)。
- **DPI 变化是相似变换,不改变布局意图**:ratio 无量纲、`fixed_extent` 与 min 都是逻辑像素,
  三者**全部与 DPI 无关**。因此:**红线 L5——DPI 变更路径上不得写任何 ratio、不得写任何
  `fixed_extent`**。DPI 变了只是同一棵树在一个新的可用矩形上重解一次。
  (工程事实:`bt-render::CellMetrics` 的 `cell_*_px` 是**物理**像素并随 `scale_factor` 重算;
  座位矩形跨到那一侧的换算发生在 §4.1 的接缝上,不在求解器里。)
- **可满足性可能随 DPI 变化**(物理窗口不变、逻辑尺寸随 scale 上升而缩小)→ 走 §2.6 让步链,
  **而不是**回过头去改 ratio。这条是 L5 的正当性:让步是**呈现**的降级,不是**意图**的丢失;
  DPI 还原时布局必须原样回来。
- **取整:边界取整,不是宽度取整**(结构)。每个座位的左/上边界各自 `round` 到物理像素,右/下
  边界取**下一个座位的左/上边界**。**红线 L6:相邻座位共享同一个边界数值**——各自 round 宽度
  会在长链上累出 1px 缝或 1px 重叠,而一条缝就是一条用户看得见的假 divider。
- divider 视觉 1 逻辑像素,**允许**取整到物理像素以保锐利(DESIGN §7.1 原文);它在分配里占的
  是 `DIVIDER = 1 逻辑像素`,取整只发生在最终边界上。

### 2.6 空间不足的让步链

上位裁决照抄(DESIGN §7.1.1 原文):

> 不可满足让步顺序:files 240→170 → 窗口最小宽由布局树需求决定 → OS 强制更小时保 focused
> pane、其余折叠占位,不静默销毁树。

**用户裁决 2026-08-03**:现在裁**顺序骨架**(§2.6.1),**浮窗与布局的冲突**仍归规格债 ④
(§2.6.4)。理由是骨架是求解器写代码就要的东西——没有它,求解器在极小窗口下不是「留洞」
而是「留 UB」;而浮窗冲突牵扯 §7.1.2 的钳位规则,那确实是另一份债。

#### 2.6.1 顺序骨架(已裁,政策位;2026-08-08 分成两种权威)

同一次 solve 内,按下表**自上而下**逐级降级,**降到刚好可满足即停**:

| 级 | 动作 | 停止条件 |
|---|---|---|
| L0 | 正常求解(§2.3) | `demand(root, axis) <= 可用` |
| L1 | **fixed 列收缩**:每个 files 座位从其 `fixed_extent`(默认 240)线性收至 `FILES_W_MIN = 170` | 收完仍不够则进 L2 |
| L2 | **flex 等比压缩**:全部 flex 座位按各自 share 等比缩,下限是各自 kind 的 min(终端 260 / 预览 360) | 触底仍不够则进 L3 / L2′ |
| L3 | **折叠非焦点座位**(§2.6.3),按**内容类优先、类内离焦点最远优先**的确定序 | 折到只剩焦点仍不够则进 L4 |
| L4 | **焦点最后倒下**:焦点座位也放不下 → 返回 `LayoutError::Unsatisfiable`,由上层显式呈现 | — |
| **L2′** | **地板等比松开**:全部座位的 min **一起**按同一个 ppm 线性松向 0,取「刚好够」的最小松开量 | 松到 0 仍不够 = 仅剩 divider,矩形退化但不反转 |

**【2026-08-08 用户裁决】「最小值对程序是法律,对用户是建议」。** L3/L4 只属于**程序自选的矩形**;
用户亲手拖出来的矩形走 L0→L1→L2→**L2′**,**永不折叠、永不拒绝**。判据随调用传参:

```rust
pub enum SizePolicy { Sovereign, Lawful }
```

| | `Sovereign`(手势) | `Lawful`(程序) |
|---|---|---|
| 谁定的矩形 | 拖窗口边框、拖 divider | 会话恢复、DPI 变化、投放可行性判定、启动 |
| L2 触底之后 | **L2′ 等比缩到底**,内容自然裁剪 | L3 折叠 → L4 显式错误 |
| 会不会出现折叠条 | 不会 | 会 |
| 会不会返回 `Unsatisfiable` | **不会** | 会 |

三条读法上的要点:

- **L2′ 与 L3 是同一根阶梯的两条岔路,不是两套几何**:两者都只改 `AxisPlan` 的一个 ppm 旋钮,
  都用同一个整数二分求「刚好够」的最小值(D3),都对整棵树取同一个值(W3)。差别只在**让什么
  先让**:程序面让**呈现形态**(pane → 条),用户面让**地板**(min → 0)。
- **L2′ 是连续的,L2→L2′ 不跳变**:松开量为 0 时 L2′ 逐 bit 等于 L2 的结果;松开量趋近满值时
  `lo/hi` 夹取全部失效,分配退化为纯 ratio。所以手动缩窗的全程没有中间夹缝、没有一次突跳。
- **W1 树守恒在 L2′ 下逐字成立**:松地板和折叠一样是**呈现态**,不动树、可逆。钉死名
  `a_squeeze_by_hand_and_release_round_trips_to_the_same_rects`。
- **DPI 变化归 `Lawful`**(本次裁量,理由见 §2.6.6)。

**三条读法上的要点**:

- **L1 先于 L2 是裁决,不是便利**:固定列有一个自己声明过的可收缩区间(240→170),那是它自带的
  让步余量;先动没有声明过余量的 flex 座位,等于拿别人的地去填自己的坑。
- **L2 等比而非逐个**:等比压缩保 share 的相对关系,逐个压缩要先回答「先压谁」,而那个问题的
  任何答案都会在对称布局上暴露遍历顺序(违反 W3)。
- **L3 的「离焦点最远」按树距离定义**(根到两座位路径的公共前缀之外的边数),距离相同时按
  in-order 位次,**再相同不可能**(id 唯一)。这是一个全序,所以 L3 是确定的。

- **【2026-08-13 用户裁决】L3 的第一把尺子是内容类,不是距离:先 preview、再 files、
  终端最后。** 真机(Preview 块切片 7 案 7)照出了旧序的代价:960 逻辑宽的窗放不下
  `preview + preview + 终端`,焦点恰在最左的 preview 上,于是「离焦点最远」选中了**终端**——
  房子里唯一跑着别人工作的那一格,被折成了 24px 的签子。折叠条本身是可逆而诚实的呈现态,
  但「谁变成条」问的是「你更愿意先看不见什么」,那不是一个树几何能回答的问题。
  裁决给出的类序:**preview → files → 终端**——preview 是对一份仍在盘上的文档的一瞥,
  files 列是回到它的路,而终端里的输出没有任何别的面能重现。**类内不变**:仍按离焦点最远
  优先,所以 L3 依旧是全序、依旧确定(类 → 距离 → in-order 位次)。
  `SeatKind::Placeholder` 排在三者之前,这一格是**推论而非裁决**:一个本 build 不认识 kind 的
  叶什么也没画,是树上最便宜的一条签子。钉死名
  `a_narrowing_window_folds_the_preview_before_the_files_column_and_the_terminal_last`、
  `within_one_content_class_the_farthest_from_the_focus_still_folds_first`。

#### 2.6.2 三条不变量(结构)

- **W1 树守恒**:任何让步**不得删除、不得重排**树上的任何节点。折叠是**呈现态**,不是编辑。
  失去空间后再获得空间,必须逐 bit 还原到让步前的矩形集合。钉死名:
  `a_squeeze_and_release_round_trips_to_the_same_rects`。
- **W2 焦点最后倒下**:焦点座位是**最后**一个被折叠的;若连它都放不下,输出的是 L4 那个**显式
  错误态**,不是一个骗人的矩形(**红线 L4** 的推论)。
- **W3 让步是全局一次决策,不是逐节点贪心**:同一次 solve 内的让步等级对整棵树取同一个值,
  否则两棵对称子树会因遍历顺序不同而降到不同等级——那正是 §3.2 的 D2 要禁掉的东西。
- 让步等级**不落盘**(§5 派生列):它是当前可用矩形的函数,存它等于存几何(红线 L11)。

#### 2.6.3 折叠占位 = 一条 ~24px 的可点标题条(已裁,政策位)

- **几何**:沿被压的那根轴收成 `COLLAPSED_EXTENT = 24` 逻辑像素的一条,另一根轴照旧占满槽位。
  **它是真矩形,有真面积**——所以红线 L4 不被违反,零面积从来不是折叠的表达方式。
- **内容**:名字 + 状态图标(与 tab/卡片共用同一枚 `stateIcon`,DESIGN §7.1.5b)。一条会呼吸、
  会亮红点的折叠条,正是「这里有个东西在跑」这句话最便宜的说法。
- **命中与焦点**:整条可点、可 Tab、可被命令面板选中;点击 / Enter = **展开**(该座位升格为
  焦点,于是按 W2 它成了最后一个倒下的那个,让步链自动把空间让给它)。
- **为什么不是零宽隐身**:本 UI 一贯不许有隐身状态——§7.1.6b ② 已经为此废止过一次「无上限
  待命池隐身存活」。一个看不见、也没有末端的座位,和一个被静默销毁的座位在屏幕上没有区别。
- **为什么不是「溢出抽屉」**:把节点临时移出树直接破坏 W1 树守恒,而 W1 是这条链唯一的安全带。
- 钉死名:`a_collapsed_seat_keeps_a_clickable_bar_and_its_place_in_the_tree`。

#### 2.6.4 【洞:浮窗与布局的冲突优先级 → 规格债 ④】

极小窗口下 pinned 浮窗(§7.1.2:最小 200×150、主窗口缩小自动重钳位、允许临时小于最小尺寸)
与布局让步链**同时**在抢同一块像素,谁先让、让到哪、浮窗是否可被推出视口——**本文不决定**。
接口是明确的:浮窗**不是座位、不进树**,所以它不参与 §2.6.1 的任何一级;两者的仲裁发生在
求解器**之外**(它拿到的 `viewport` 是仲裁的结果,不是仲裁的输入)。

#### 2.6.5 窗口最小尺寸:技术地板(2026-08-08 裁决;原「动态 + 60% 钳制」已翻案)

**原裁决(2026-08-03,现已翻案)**:

> - 默认动态:树一变就 `set_min_inner_size(demand(root) + chrome)`,让 OS 替我们守住可满足性。
> - 钳制:`demand(root)` 超过工作区 60% 时取那个 60%。
> - 红线 L12:入参只能由 `demand(root)` 与工作区导出。

**现裁**:

```text
min_inner = min(一个终端叶的 min + chrome, 60% * 工作区)
```

- **不再是树的函数**。原式让**一个**四列 tab 决定**整扇窗**能多窄——而且是对每个 tab、永久有效。
  那是把法律指向了错误的对象。树的需求没有被废除,它搬回了它该在的地方:§2.6.1 的 `Lawful`
  一侧,程序自己排的布局仍然逐条守它。**同样的数字,不同的权威。**
- **剩下的是技术地板**:一个终端叶跑得起来的最小矩形(`MIN_PANE_W × MIN_PANE_H`,与
  `sane_restored_size` 复用同源常量)。它的全部职责是让 157×25 那种荒谬矩形不可达——一个 pane
  都装不下的窗口里没有任何东西可排。
- **60% 钳制保留**,理由与原文一致(窗口拒绝被拖小 = 用户读作卡死);只是它现在**几乎永不生效**,
  而这正是要点:原式每天都要靠它兜底。
- **不再有「不设最小值」这个答案**。原式需要先知道工作区才敢信任自己(它钳的是一个可能锁死窗口
  的数);常数不需要任何输入,而「完全不设最小值」恰恰就是技术地板要挡的那个荒谬矩形。
- **红线 L12 相应修订**:见 §6。
- 工作区尺寸变化(换显示器、任务栏变化)按 §2.5 与 DPI 同类处理:重算钳制,**不写任何 ratio**。
- 钉死名:`the_window_minimum_is_one_pane_and_never_the_fleets_demand`(取代原
  `the_window_minimum_follows_the_tree_and_never_exceeds_sixty_percent_of_the_workarea`)。

#### 2.6.6 谁定的矩形:`SizePolicy` 的来源与 DPI 的归类(2026-08-08)

`SizePolicy` **随调用传参,不是求解器的字段,也不是全局标志位**——一个被求解器记住的模式,迟早
会有两个调用点对它意见不一,而分歧会以几何的形式显形(纪律①)。但**「当前 viewport 是谁定的」
本身是一个事实**,它无法从尺寸反推(900×400 由手拖出来和由会话文件要求,含义不同),所以由
**决定发生的那一处**记录、并向下传递:

| 事件 | 归属 | 一句理由 |
|---|---|---|
| 拖窗口边框 | `Sovereign` | 手放在窗框上就是「这是我的尺寸」 |
| 启动 / 会话恢复 | `Lawful` | 开窗矩形是程序选的;恢复到装不下的窗口应当折叠——那是「这里放不下」最诚实的画法 |
| **DPI 变化** | **`Lawful`**(本次裁量) | 屏幕上的**物理**窗口还是用户那扇,但求解器工作在**逻辑**矩形里,而那个矩形是由一个系统送来的 scale 算出来的、**没有任何手选过它**。用户当初的手势是对着旧 scale 做的,不随之转移。取「谁最近改变了 viewport」这条统一规则,任何例外(「DPI 保留既有主权」)都是一个会漂的状态化特例 |
| 投放可行性(`plan_drop`) | `Lawful` | 投放是程序在决定 pane 去哪,不是用户在决定窗口多大——即使用户的手正按在鼠标上 |

**主权一旦取得,只由程序交还**,不由「恰好又拖回了开窗尺寸」交还。实现上,`Resized` 事件本身
无法区分三种来源(Windows 对手拖、创建、DPI 伴随的 resize 发的是同一个事件),所以记录**本进程
主动要求过的尺寸**来区分——这不是启发式,是我们自己知道的事实。钉死名:
`a_resize_is_the_users_unless_the_program_asked_for_it`。

### 2.7 高度方向

纵向没有 fixed 类(§1.3),所以 §2.6.1 的 L1 在纵向**空过**,链退化为 `L0 → L2 → L3 → L4`。
**其余逐字相同**:等比压至 `MIN_PANE_H = 120`、折叠非焦点(折叠条同样 24px,只是横躺)、焦点
最后倒下。**红线 L4 与 W1/W2/W3 在纵向逐字成立**——纵向不是横向的简化版,它只是暂时更少一类
成员;将来若出现纵向固定的座位族,L1 原样醒来,链不需要重写。

## 3. 确定性求解

### 3.1 签名与纯度

```rust
pub fn solve(
    tree: &LayoutNode,
    viewport: LogicalRect,      // 内容区可用矩形(不含标题栏/侧栏/卡片列等 chrome)
    metrics: &SeatMetrics,      // 每 kind 的 min_size;DPI 已折进 viewport 与取整策略
    focus: SeatId,              // W2 与 §2.6.1 L3 的唯一输入
    mode: LayoutMode,           // Parallel | Focus { stage: SeatId }(§3.5)
    policy: SizePolicy,         // viewport 是谁定的(§2.6.1/§2.6.6,2026-08-08)
) -> Result<SeatLayout, LayoutError>;

pub enum LayoutMode { Parallel, Focus { stage: SeatId } }
pub enum SizePolicy { Sovereign, Lawful }   // 最小值:对用户是建议 / 对程序是法律

pub struct SeatLayout {
    rects: Vec<(SeatId, SeatKind, LogicalRect, Presentation)>,  // 顺序 = 树的 in-order
}
pub enum Presentation { Full, Collapsed }   // §2.6.3;让步等级本身不外泄,只外泄结果
```

**`SeatMetrics` 里装的是求解器量东西的全部尺子**，而不只是那张按 kind 的表。除 `scale_ppm`
外，它还带着 **divider 的宽度**（`with_divider`；窗口上永远是 `DIVIDER`）与**带宽的缩减**
（`with_band_reduction_ppm`；窗口上永远是 `RATIO_DENOM_PPM`，即不缩）。这两个旋钮存在的唯一
理由是**一个求解器要在两种尺度上回答**：DESIGN §7.1.6b′ 的卡片缩略图走的就是 `solve` 本人，
只是手里拿的是卡片自己那张表（无地板、缝 3px、带宽缩到六分之一）。**比例一字不动**，所以 L5
原样成立：设备缩放仍然不许碰任何一个 ratio 或带宽，只有调用方显式交一张别的表时才变。带宽的缩减
只在 `Seat::fixed_width` 一处落地——那是「声明宽度」与「手拖宽度」合流的唯一漏斗，两者必须
按同一个舍入缩。钉子：`a_card_sized_table_solves_the_same_shape_of_answer_as_a_window`。

**纯函数**:无 IO、无时间、无随机、无全局状态、无内部缓存。复杂度 `O(叶子数)`,`n` 在
本产品的量级是几十(聚焦态更是硬上限 4+1+1),因此**允许每帧调用**(§4.4)。

### 3.2 确定性不变量

- **D1 纯性**:同输入 → 逐 bit 同输出。钉死名 `solve_is_a_pure_function_of_its_inputs`。
- **D2 无迭代序依赖**:输出顺序 = 树的 in-order,是树的函数。**红线 L8:求解器内部不得让
  `HashMap`/`HashSet` 的迭代序参与任何几何决策**(用 `Vec` 或 `BTreeMap`)。这条是 CONVENTIONS
  §一「不要启发式」在几何层的同族:一个恰好稳定的迭代序只是没被你的样本证伪。
  钉死名 `two_structurally_equal_trees_solve_to_identical_rects`。
- **D3 定点,不浮点**:分配全程整数子像素运算,**不使用 f32/f64**。理由是 D1 要的是逐 bit
  相等,而 `avail × ratio` 一旦走浮点,同一棵树在两条代码路径(预览 vs 提交)上就可能差一个
  ULP,再经取整变成差一个物理像素——那正是纪律①要杀死的「两套几何必然漂移」。
- **D4 预览与提交同源**(DESIGN §7.1 纪律①,结构):投放预览的蓝框、拖拽期的实时几何、松手后
  的真实布局,**三者调用同一个 `solve`**,不得存在第二个「估算版」。原型的墓志铭原文照录:
  估算出来的答案必须与规则同步维护,算出来的答案不可能漂移。
  钉死名 `the_drop_preview_and_the_drop_agree_rect_for_rect`。
- **D5 可行性判据即求解本身**:「放不下」= 对**规划后的**树跑一次 solve,任一矩形低于其
  **自身 kind** 的最小值即拒绝。不得用「把目标对半砍」之类的估算——那条估算实测会拒绝掉本来
  能成立的投放(三列 359 时它算 179 < 260 而拒,重新均分后四列各 269 全部可用)。

### 3.3 增量更新:「必要」的形式定义

这是本节的核心,因为「不要移动无关座位」如果不形式化就只是一句愿望。

**run(结构)**:节点 `x` 沿轴 `d` 所在的 run,是包含 `x` 的**同向连续 split 的极大传递闭包**
的叶子集合。等价地:从 `x` 向上走,只要父 split 的 `dir == d` 就继续,一遇异向 split 即停;
该停点子树内所有沿 `d` 并置的叶子构成 run(`members(x, d)`)。

**share(结构)**:`share(x) = ∏ (沿根到 x 的路径上,每个 split 给出的那一侧份额)`。对 flex 座位,
它就是该座位在可用空间里占的比例;这是「布局意图」的唯一数值载体。

**编辑焦点集 `F(E)`**:一次结构编辑 `E` 允许改写 ratio 的**唯一**范围。

| 编辑 E | `F(E)` |
|---|---|
| 在座位 `s` 的边缘裂出新座位(dir = d) | `members(s, d)` 所在的那条 run |
| 关闭座位 `s`(兄弟被提升) | 被提升者所在的那条 run |
| **拖动重放一个已在树里的 pane**(`MoveSeat`,用户裁决 2026-08-25) | **它离开的那条 run + 它落进的那条 run**;落回同一条 run 时 `F` 收窄到那一条,落回原位则 `F = ∅` |
| 根 rim 投放 / **preview 落固定右席**(§1.3 三档落位) | **root 那条 run** |
| **preview 复用未 pin 的既有座位**(§1.3 第 ① 档) | **∅**(换的是内容,不是几何) |
| divider 拖拽 | **恰好那一个 split**(§3.4) |
| 中心 swap / replace | **∅**(占别人的座位不移动任何盒子) |
| DPI 变化、窗口 resize、工作区变化 | **∅**(§2.5 红线 L5、§2.6.5) |
| **进/出聚焦态** | **∅**(§3.5 红线 L13) |
| 让步等级升降(§2.6.1) | **∅**(呈现态,W1 树守恒) |

**必要性定理 N(可测的那条)**:

> 对任意不在 `F(E)` 中的 split `p`,`ratio(p)` 在 `E` 前后**必须逐 bit 相等**;对任意不在
> `F(E)` 中的座位 `x`,`share(x)` 的变化**只能**来自其祖先 run 内份额的变化,不得来自 `x` 自身
> 所在 run 的重新分配。

于是「不必要的移动」有了定义:**改写了 `F(E)` 之外任何一个 split 的 ratio**。这是一句可以写成
断言的话,也是一条可以设红门的话。

**必须说清的反面**:定理 N **不承诺**「run 外的座位一个像素都不动」。root 那条 run 增加一列时,
所有列都会变窄——那是几何,不是求解器多事。定理 N 承诺的是**布局意图不被暗改**。
**预览固定右席的代价必须明说**:它的 `F` 是 root run,所以「点开一个文件」会**让整行终端等比
变窄**。这是固定住址这条裁决自带的账,不是缺陷;它换来的是「单例内容配固定住址」。

**入 run 即重新均分(结构,i3/Zellij 语义)**:`F(E)` 内的 ratio 按 **`run_demand`** 重算——
`run_demand(seat) = 1`,同向求和、异向取 max。**离开 run 同样重算**:一条只在加入时均分、离开时
不均分的规则只存在一半——删掉三个里的中间那个,幸存的两个会顶着「三个一组」时的份额出来,
成为 1/3 与 2/3。
代价如实承认:**你手拖过的比例,在有座位加入/离开那一串时会被重新分配**——因为那一串已经不是
原来那组座位了。

**但「重放」不是加入也不是离开(用户裁决 2026-08-25,拖放份额结算的不变量)**:把一个**已经在
这棵树里**的 pane 拖起来重新放下,run 的成员一个没变,只是次序变了。因此它是**一条编辑**
(`Edit::MoveSeat`)而不是「关闭 + 裂出」两条,并且**不跑均分**,而是**结转份额**:

- **不变量 ①(没碰到的兄弟之间比例不变)**:每一个没动的列都保住自己在 run 里的份额;
  离开释放的空间在**它原来那条 run** 内按份额归一化(相对比例因此逐值不变),落地挤占的
  空间**只与落点相邻的那一列结算**(按 flex 列数对半),其余列一个数都不改写。
- **不变量 ②(放回原位 = 完全无操作)**:落点仍在原来那条 run 时,**run 的骨架原样保留**,
  只把「哪一列坐哪一格」重排,份额原样写回;次序没变就**连编辑都不是**——树逐 bit 相等、
  `F = ∅`。骨架不重切这一条同时保住了 divider 的身份,以及「谁在替某个触底 pane 垫最小值」
  这件事不会因为树换个方向倾斜就悄悄换人。
- 跨 run(含从纵向堆叠里拖出来)才谈得上「加入」:此时向落点那一列买份额,卖方没有份额可卖
  (rim 没有邻居、固定列只占像素)时才由整条 run 按 flex 列数出钱。

**均分只数「拿份额的列」(`flex_run_demand`)**:固定列(files)按像素先被扣掉,它**不是**
被分的那几方之一。把它当一列去数,再由分配器把它的 240px 记到「它恰好挂在树的哪一侧」头上,
正是 2026-08-25 那份实证的成因:1600px 下 `[files|mid|right]` 本是 240/679/679,把 files
拖回同一条带子后变成 **240/824/533**。

**§2.3 补齐到任意形状**:分配器过去只在「整棵子树都是固定的」时才按像素给,固定列一旦**嵌**
在 flex pane 旁边就重新变回按 ratio 分。现在改为:每个 split 先扣掉两侧的 **`reserved`**
(其中的固定列、折叠条,以及它们与其余部分之间的 divider),ratio 只分剩下的 flex 空间;
一侧没有任何拿份额的东西时它就拿 0。于是**同一条 run 无论往哪边倾斜都解出同一组宽度**,
「树的形状」彻底不再是用户能看见的东西。钉死名
`a_fixed_column_takes_pixels_wherever_it_sits_in_the_tree`。

**钉死名(实现必须存在的 pin)**:

- `opening_a_seat_rebalances_only_its_own_run`
- `closing_a_seat_rebalances_only_the_run_it_left`
- `a_re_placed_pane_leaves_its_untouched_siblings_in_proportion`(不变量 ①)
- `a_pane_let_go_where_it_was_moves_nothing_at_all`(不变量 ②)
- `a_pane_arriving_from_another_run_is_paid_for_by_the_pane_it_landed_beside`
- `a_fixed_column_takes_pixels_wherever_it_sits_in_the_tree`
- `a_center_swap_moves_no_rectangle`
- `a_dpi_change_rewrites_no_ratio`
- `opening_the_preview_seat_narrows_the_root_run_and_nothing_else`
- `reusing_the_unpinned_preview_seat_moves_no_rectangle`
- `entering_and_leaving_focus_mode_rewrites_no_ratio`

**红门**:把 `balanceRunAt` 的作用域从 run 放宽到整棵树 → 前两条立刻转红;在 `ScaleFactorChanged`
路径上加一次 ratio 归一化 → `a_dpi_change_rewrites_no_ratio` 立刻转红;把拖动重放改回
「`CloseSeat` + `SplitSeat`」两条链,或让 `flex_run_demand` 把固定列也数成一列 → 那两条
不变量当场按实证里的原始数字转红。

### 3.4 divider 拖拽是编辑,不是求解

拖拽写入的是**一个** split 的 `ratio`,或**一个** files 座位的 `fixed_extent`;`F` = 那一个节点。

- **红线 L9:拖拽期间不得触发任何 rebalance**。手拖比例的全部意思就是「我要这个比例」,而
  rebalance 的意思是「这一串成员变了」——成员没变。
- **手要落在哪里,ratio 就得是那个位置的逆**:分配器把 `reserved` 先扣掉再按 ratio 分,所以
  「指针在槽内 `leading` 处」问的是 `(leading - reserved(a)) / (usable - reserved(a) - reserved(b))`,
  由 `bt_layout::reserved_extent` 供数(`seats::requested_ratio` 收它作参数,不自己从矩形反推——
  自己反推就是 D4 明令禁止的第二套几何,症状是 divider 在手底下偏出一整条固定列的宽度)。
- 固定列**按像素拖**,不按 ratio;夹取为 **`[0, usable]`**(2026-08-08 修订,原为
  `[FILES_W_MIN, usable - demand(other, Row)]`,见 §2.4)。槽位是算术,`FILES_W_MIN` 是偏好。
- **拖拽是 `Sovereign` 的定义性场景**,所以这里没有政策位可传:程序侧没有「拖 divider」这件事。
- 一个**不是裸 files 叶**的固定子树(例如两片纵向堆叠的 files)**没有单一宽度可拖**:诚实拒绝,
  而不是往一个固定槽上写份额把布局写坏。
- 指针流异常终止(pointer-cancel、失焦)与 Esc:**零副作用回滚**到手势开始时的那一个值
  (DESIGN §7.1 原文)。回滚的是**那一个** ratio/宽度,不是整棵树的快照——快照式回滚会把手势
  期间到达的无关变更(新座位、关闭)一起撤销。

### 3.5 聚焦态是一条约束,不是第二套几何(用户裁决 2026-08-03)

**一个求解器,两种注意力形态。** 聚焦态(串行态,DESIGN §7.1.6b)**不另起一套布局**,它只是给
同一次 `solve` 加了一条约束:

```
mode = Focus { stage } ⟹ 舞台座位 stage 独占整个 viewport;树上其余座位的矩形为 None(不呈现)
```

- **红线 L13:聚焦期间树不被触碰。** 不改任何 ratio、不改任何 `fixed_extent`、不增删任何节点。
  于是「退出时并行树**原样恢复**」(§7.1.6b ⑤ 原文)不是一条需要实现的功能,而是**没做任何事
  的自然结果**——`F(Focus) = ∅`,进出聚焦态在 §3.3 的编辑表里与「DPI 变化」同格。
  钉死名 `entering_and_leaving_focus_mode_rewrites_no_ratio`。
- **卡片列是侧栏 chrome,不进树**(§7.1.6b ① 已裁「卡片列嵌入侧栏当前 tab 之下」)。它因此
  **不是座位**:不参与 demand、不参与让步链、不占 `viewport`(是它先从窗口里切走 chrome,
  求解器才拿到 `viewport`)。待命池里那些**还没上树**的会话/预览同理——它们**没有座位**,
  所以求解器根本看不见它们,直到退出聚焦态把它们物化上树(那时才是一次真的结构编辑,`F` =
  root run)。
- **4+1+1 容量与进入门槛(终端 pane > 4 不可进入)是 UI 层的政策门,不是求解器的约束**:
  求解器不数座位,它只摊开你给它的树。把容量写进求解器会让一条政策变成结构(法则③)。
- **B 案(聚焦态自有一套布局)为什么被否**:那会造出第二套几何,而纪律①的全部内容就是
  「预览与提交共用同一个布局求解器,两套几何必然漂移」。舞台是一个座位的矩形,不是一张新图。

## 4. 与 bt-viewport 投影的接缝

### 4.1 分层:求解器给矩形,投影给行

```
solve → SeatRect(逻辑像素)
      → [终端座位] 换算 (cols, rows) + cell 尺寸 → ViewportProjection / ConPTY
      → [files/preview 座位] 换算成各自的内部布局(不经本规格)
```

**红线 L7:`bt-layout` 不得依赖 `bt-viewport` / `bt-doc` / `bt-term` / `bt-render`**
(CI 可 grep 其 `use`,与 CONVENTIONS §二「policy 不进 vendor 也不进适配层」同一手法)。
判据一句话:**求解器只回答「这棵树摊开是什么形状」,不回答「那块形状里显示什么」**。
它因此**不知道** cell 尺寸、不知道 cols/rows、不知道滚动锚、不知道 `HeightTree`、不知道
`LayoutKey`。子像素常量由 bt-layout 自持并以编译期断言与 `bt-doc::SUBPIXELS_PER_PX` 对齐。

### 4.2 传导单向(结构)

```
窗口/侧栏几何 → viewport 矩形 → solve → 座位矩形 → (终端) cols/rows
   → ConPTY 200ms 静默 coalescing(§3.1 既有,原样继承)
   → projection.relayout(LayoutKey{width, dpi, font_rev, theme_rev})
```

**红线 L10:反向禁止。`bt-viewport` 与其内容永远不得回改座位矩形。** 具体地:

- 公式/图片撑高**绝不**请求更高的座位。溢出按 DESIGN §7.4 的既有裁决在**座位内部**消化:
  底部保底可见、顶部溢出由本地滚动与网格外 `N rows above` 覆盖层承接。
- 内联图片、预览内容、files 树的长文件名,一律不改变座位宽度。
- 这条堵死的是**内容改变布局的递归**——与 §7.0 界外清单「内联交互组件使会话反成容器,内容套
  内容递归」同源。一旦允许回改,`solve` 就不再是纯函数,D1/D4 同时失效。

pane divider 拖拽与 OS 窗口 resize 共用 §3.1/§3.3 的既有语义:**本地投影逐帧跟随,ConPTY 只在
200ms 静默边界接收最终尺寸**;新事件覆盖待发送值与 deadline。求解器不参与这个 debounce——它每
帧被问一次,谁把答案交给 ConPTY 是上层的事。

### 4.3 失效只经既有路径

座位宽度变化 → 该座位 `LayoutKey.width` 变化 → `bt-viewport` 既有的
`LayoutCache 键控 (span, source_gen, detection_rev, LayoutKey)` 失效路径**原样跑**。
求解器**不持有任何缓存、不参与任何 revision**(D1 的推论:纯函数没有可失效的东西)。

### 4.4 每帧求解是允许的

`O(n)`、纯整数、`n ≤ 几十`。因此 divider 拖拽期间「每帧解一次整棵树」是**首选**实现,而不是
优化对象——它比「拖拽期间直接写 DOM/纹理、松手再统一重排」少一套几何,而少一套几何正是纪律①。

## 5. 持久化钩子(→ 规格债 ②,本文只给面与两条约束)

| 耐久(必须落盘) | 派生(**绝不**落盘) |
|---|---|
| 树形状(Split 嵌套关系) | 一切矩形 / 座位像素尺寸 |
| 每 Split 的 `dir` 与 `ratio`(**`u32` ppm 原值**) | 每座位的 cols/rows |
| 每座位的 `kind` | `demand` / `fixed_w` / run 划分(全是树的函数) |
| Files 座位的 `fixed_extent` | DPI、`scale_factor`、窗口物理尺寸、工作区尺寸 |
| Preview 座位的 `pinned` 标志 | 让步等级与 `Presentation::Collapsed`(§2.6.2 明文不落盘) |
| 焦点座位 id、tab 顺序、pinned | 窗口最小尺寸(§2.6.5,是 `demand` 的函数) |
| — | 内容(转录不落盘,§8.5.2 已裁) |

**聚焦态的开关与舞台座位**是否耐久 → 归规格债 ②(DESIGN §7.1.4 的序列化面当前未列)。无论
怎么定,它都是**意图**(一个座位 id + 一个布尔)而不是几何,因此不与 L11 冲突。

**红线 L11:落盘的是布局意图,不是几何结果。** 恢复到另一台 DPI / 分辨率 / 字号的机器上必须由
`solve` 重算。存矩形等于把一次求解的**结果**冒充成**意图**,换机即错位,而且错得没法归因。

**给 schema v1 的两条硬约束**(字段名与格式仍归规格债 ②):

1. **`ratio` 的序列化精度必须与运行时表示同精度**——即**照 `u32` ppm 原样写出、原样读回**
   (§2.4),round-trip 必须闭合。钉死名 `a_saved_layout_reloads_to_the_same_rects`。
   红门:把 ratio 序列化成 3 位小数或 JSON 浮点,该 pin 在多列布局上立刻转红。
2. **逐叶降级**(§7.1.4 原文):未知 `SeatKind` → 占位座位;非法 `ratio` → clamp;整树不因单叶
   损坏而丢。**降级必须是可见的**(占位座位自报「这里原本是一个我不认识的东西」),不是静默
   把它变成一个终端。
