# M1.9 多行大块 flash 独立审因报告

审计基线：当前工作树（`efd2587` 加未提交的 M1.9q/M1.9r/M1.9s）。本次只读源码、读取真实录制、运行 oracle/既有测试；除本报告外未修改源码、测试或配置，未提交。

## 结论

1. **矮块与大块的本质差异不是“5 行阈值”，也不是 CC 把一个 repaint 拆成多个未完成的 2026 事务。** 两份录制都以完整的 DEC 2026 事务做整屏 repaint。真正差异是：CC 的可滚动输出区只占终端上半部，下面是固定的输入框/状态栏；多行大块会跨过这个**应用内部窗格边界**，于是一个已提交帧中只剩块的精确前缀或后缀可见，块的其余行被固定 UI 取代。1–2 行块在相同边界处通常是“完整可见”或“整体不可见”，没有长时间的“源码前缀可见、尾部被 UI 裁掉”状态。
2. M1.9o/M1.9q/M1.9s 的 live record 都把位置和 band 锚在**整个终端 live 网格**上，并假设 band 服从一个全局行平移。它们只认识终端 row `0..rows-1` 的上下裁切，不认识 CC 内部约 row 17 的内容窗格底。CC 实际是分段映射：上方内容区平移，下方 chrome 保持原位。没有一个 `delta` 能同时映射整个 band。
3. 具体 `frame 153` 中，当前 M1.9s 对正确候选 `delta=+4` 的前三行能精确匹配，但旧 band 后半行会分别对到空白、分隔线、prompt、分隔线。非空 UI 行不是 M1.9s 所谓 transient，故 mapping 失败。record 没有计作 invalidation，而是从 active `live_decorations` 移入 offscreen 队列；队列恢复又要求**完整 `original_source`**重新出现在网格，部分可见大块必然恢复失败，于是 active 装饰消失、源码露出。
4. 因而现有“record 锚 live 网格行 + band 每行匹配 + 原地/平移/兜底三分法”在 CC 的应用内滚动窗格下**架构上不足**。需要把“已证明公式的身份”与“本帧在 live 网格上的可见投影”分离，并在 2026 提交边界上用精确内容指纹求出分段移动区/遮挡区；band 应作为带逻辑行偏移的整体单元保存，不能把不可见行当作必须与固定 UI 行匹配的 live 行。
5. M1.9s 的改动只对“终端边缘裁切”和“同行空白/前后缀中间态”有效，所以合成测试绿、真实录制只微降。其 `>=5`、空行、delimiter、字符串前后缀启发式既没有表示真实结构边界，也弱于“源码精确相等”的安全要求，不应继续沿该方向加猜测。

## 实跑证据

### 真实录制的事务形态

只读统计结果：

- `cc-topbot.vt`：305 个 PTY chunk，其中 218 个 chunk 同时含 `CSI ?2026 h` 和 `CSI ?2026 l`；219 个含 Home。
- `cc-scrollout.vt`：340 个 PTY chunk，其中 238 个是完整 2026 事务；239 个含 Home。
- 具体 chunk 149/150/151 都从字节 0 以 `ESC[?2026h` 开始，在本 chunk 尾部以 `ESC[?2026l` 结束。chunk 150 的 close 位于 chunk 内 byte 2245；整个 chunk 长 2253。
- chunk 150 的 CSI final 统计为 `h:2, l:2, H:3, m:53, B:25, K:23`；没有 `r/S/T/L/M/@/P`，即没有设置 DECSTBM、scroll up/down、insert/delete line/char。它是 Home 后逐行写入并 `EL` 的完整整屏 repaint，不是 scroll region 指令，也不是跨 chunk 未完成的分行事务。

manifest 中 chunk 150 是 `.tmp-repaint-capture/cc-topbot.vt.chunks:152`：

```text
150 1128436570 2253
```

oracle 在处理该 chunk 前因 200 ms 稳定门完成任务而发布 `frame 152 math-ready`，随后 `feed` 发布同 elapsed 的 `frame 153 pty`；调用次序见 `crates/bt-term/src/bin/bt-repaint-oracle.rs:56-69,146-151`。因此本文的 `frame 153` 精确对应录制文件 byte offset 198782、length 2253 的 chunk 150。

### 矮块轨迹

对 `cc-scrollout.vt` 中已渲染的一行块逐源跟踪，代表性轨迹如下（`O` 表示该源码/装饰都不在可见区）：

```text
x = ...                 141 S -> 143 R -> 180 O -> 198 R -> 218 O
\hat f = ...            141 S -> 143 R -> 155 O -> 169 R -> 333 O
one-line pmatrix         141 S -> 143 R -> 154 O -> 169 R -> 333 O
zeta product             141 S -> 143 R -> 153 O -> 170 R -> 205 O -> 210 R
```

对录制中指定的 1–2 行矮块，首次 `R` 后没有 `R -> S`；它们到内部窗格边界时整体消失，之后完整源码重现时可由 offscreen 队列精确恢复。相反，多行 environment 会留下可见的 opener/body 前缀，因此会出现真正的 `R -> S`。

这说明 band 行数是**触发结构跨界的几何条件**，不是 matcher 应有的语义分类。任何足够长或恰好靠近内部边界的块都可触发；硬编码 `proven_band_rows >= 5` 只是样本相关阈值。

### 大块轨迹

当前工作树逐帧输出中，`cc-topbot.vt` 的 aligned 轨迹包含：

```text
129 S -> 131 R -> 153 S -> 156 O -> 183 S -> 186 R
       -> 187 S -> 190 R -> 210 S -> ... -> 309 S
```

pmatrix 包含：

```text
154 S -> 158 R -> 163 S -> 166 O -> 175 S -> 179 R
      -> 211 S -> 213 R -> 232 S -> 236 R -> 311 S -> 317 R
```

因此用户观察到的“大块反复 RENDERED/SOURCE 震荡”可复现；`live_invalidation_count` 在这些帧仍是 0，并不表示装饰仍 active。

当前 checkout 的 oracle 最终进程码却是 `EXIT=0`。这是因为未提交诊断改动在 `crates/bt-term/src/diagnostics.rs:113-122` 只要整帧含 `Jump to bottom` 就不记 flash，同时 binary 在 `crates/bt-term/src/bin/bt-repaint-oracle.rs:65-68,100` 又给整个 chunk 标 `source_mutated`。真实状态行仍明确显示 aligned/pmatrix 从 rendered 列表消失并进入 `source_rows`。故当前 `EXIT=0` 是豁免后的门禁结果，不能用来反证 flash 已消失；本报告以逐源状态轨迹为准。

## frame 153 的字节级根因链

### CC 做了什么

前一完整 repaint（chunk 149）中 aligned 位于 CC 输出窗格的 row 10–17：

```text
row 10  $$
row 11  \begin{aligned}
row 12  \nabla \cdot \mathbf{E} ...
row 13  \nabla \cdot \mathbf{B} ...
row 14  \nabla \times \mathbf{E} ...
row 15  \nabla \times \mathbf{B} ... \partial
row 16  t}
row 17  \end{aligned} ... Jump to bottom ...
row 19  ────────────────────────────────
row 20  ❯
row 21  ────────────────────────────────
row 22+ 固定状态栏
```

chunk 150 的关键原始字节（控制符可视化）是：

```text
<ESC>[?2026h<ESC>[?25l<ESC>[H ...
<CR><ESC>[1B ... 麦克斯韦方程组：<ESC>[K
<CR><ESC>[1B<ESC>[K
<CR><ESC>[1B  $$<ESC>[K
<CR><ESC>[1B  \begin{aligned}<ESC>[K
<CR><ESC>[1B  \nabla \cdot \mathbf{E} ... &<ESC>[K
<CR><ESC>[1B  \nabla \cdot \mathbf{B} &= 0 \      <Jump chip><ESC>[K
<CR><ESC>[1B<ESC>[K
<CR><ESC>[1B ─────────────────────────────────...
<CR><ESC>[1B ❯ ...
...
<ESC>[26;1H<ESC>[21;3H<ESC>[?25h<ESC>[?2026l
```

提交后的 grid 是：

```text
row 14  $$
row 15  \begin{aligned}
row 16  \nabla \cdot \mathbf{E} ...
row 17  \nabla \cdot \mathbf{B} ... Jump to bottom ...
row 18  空白
row 19  固定分隔线
row 20  固定 prompt
row 21  固定分隔线
row 22+ 固定状态栏
```

所以 CC 的语义是：在同一个完整 2026 事务里把输出内容向下滚了 4 行，但只在其内部输出窗格 row 0–17 绘制；越过 row 17 的公式尾部被窗格裁掉，下面的 UI 没有随内容平移。不是“先 clear 一行、下个 PTY chunk 才补完”。

### M1.9o 在哪里失败

M1.9o 基线 `efd2587` 的 `alternate_record_semantics_match` 在 `crates/bt-term/src/session.rs:3916-3947`（该提交行号）要求：

- start/end/band 全部能做同一个 `delta`；
- parser prefix 相同；
- band 每一行的 `text`、`continues`、`cell_boundaries` 都精确相等。

正确内容平移是 `delta=+4`。row 10→14、11→15、12→16 精确相等；但 row 13→17 多了 Jump chip，row 14→18 为空，row 15→19 对到固定分隔线。基线会在第一处不等立即返回 false。它也不能把 band 尾部当 bottom-offscreen，因为 `shift_live_row` 只检查无符号转换（`efd2587:3979-3981`），而 row 19–22 都仍在 33 行终端网格内。

### 当前 M1.9q/M1.9s 在哪里失败

当前事务入口在 `crates/bt-term/src/session.rs:977-1000`，事务结束后的 mapping 在 `:1003-1053`。M1.9s 把 bool matcher 改成 score（`:4190-4303`），正确 `delta=+4` 的逐行结果为：

| old→new | 结果 | 当前 M1.9s 判断 |
|---|---|---|
| 10→14 `$$` | 精确 | exact |
| 11→15 `\begin{aligned}` | 精确 | exact |
| 12→16 第一方程 | 精确 | exact |
| 13→17 第二方程 + Jump | 新行以旧行开头 | transient |
| 14→18 第三方程 → 空白 | 新行空 | transient |
| 15→19 第四方程 → 分隔线 | 无前后缀关系、均非空 | **non-transient** |
| 16→20 `t}` → prompt | 无前后缀关系、均非空 | **non-transient** |
| 17→21 `\end{aligned}` → 分隔线 | 无前后缀关系、均非空 | **non-transient** |

因此 `all_visible_rows_match=false`（`:4292-4302`）；并非“只有一行尚未画完”。即使扩大 transient 规则，它仍无法表达“旧 band 后半位于 CC 内部窗格之外”，因为 `shift_live_record` 的 `last_row` 来自整个终端的 33 行（`:4329-4358`）。

后续链路是：

1. `alternate_record_mapping` 返回 `None`，record 进入 `unresolved`（`:1028-1030`）。
2. clear/home 兜底只接受 bounded detection 中唯一 `render_equivalent` 的完整块（`:1055-1098`）。当前 grid 没有 closer/完整 source，且首次检测仍受对称 `$$` 红线约束，所以不能 reconcile。
3. rendered record 被放入 `alternate_offscreen_decorations`（`:1101-1108`），随后 `self.live_decorations = preserved`（`:1109`）。这一步使它不再进入 projection；不是 artifact 被销毁，但用户画面已经退回 source。
4. 立即调用的 restore 只用 `exact_live_source_match(&record.span.original_source, ...)` 搜索**完整原始源码**（`:1189-1211`）。frame 153 只有前缀，故 record 留在 queue。
5. projection 只同步 active `live_decorations`（`:2209-2234`），于是 aligned raster 消失、终端源码单元露出。

这也解释了为什么 invalidation telemetry 是 0：`:1103-1105` 把有 artifact 的 unresolved record 暂存，而不是走 `:1106` 的计数分支。active-presentation loss 与 record destruction 被混成了一个不易观察的状态。

## 架构判断与方向（不写实现）

### 现有架构为什么根本不足

现有模型隐含了三个在 CC 中不成立的假设：

1. **整个终端只有一个滚动/裁切矩形。** `clipped_top_rows/clipped_bottom_rows` 只表示超出终端 row 0 或 last row；viewport 也用整个 live grid 验证 band（`crates/bt-viewport/src/lib.rs:1200-1212,1220-1250`）。CC 实际有可动内容区和固定 chrome 两个区域。
2. **一个 band 在两帧间有单一 affine row delta。** frame 153 中内容区是 `+4`，固定 UI 是 `0`，跨边界 band 没有全局 delta。
3. **身份、逻辑几何和当前可见坐标是同一件事。** record 的完整 source/artifact 本可继续证明“这是同一公式”，但 matcher 一旦无法给所有 band 行分配 live row，就把它移出 active 集合；offscreen 恢复又只接受完整 source。部分可见是模型没有的第四态。

DEC 2026 边界感知本身已经存在：snapshot 在 feed 前建立，ESU 后才 finish（`session.rs:560-603,706-730`）。所以再加“等事务结束”不会解决本录制；缺的是**事务级的区域映射与遮挡语义**。

### 建议的架构级方向

保持 M1.9o 三分法，但改变 record 的身份和 placement 模型：

1. **身份独立于 live row。** 保存不可变的 proven occurrence：完整 `original_source` 字节、render source/artifact、逻辑 source-row/cell offsets、原始 band 几何及 occurrence continuity。相同源码可重复出现，故不能只以 source hash/key 定位；候选 placement 必须唯一，歧义时不复用。
2. **2026 提交后先求整个屏幕的分段 row mapping。** 用旧/新网格的精确 row/cell 内容指纹找出“上方一组行统一平移、下方一组行固定”的映射和边界；只接受由多个精确、唯一行对应证明的区域，不猜 LaTeX 前缀，不做新公式检测。frame 153 会得到内容区 `delta=+4, clip_end=17` 和 chrome `delta=0`。
3. **band 是逻辑整体，projection 是可见交集。** record 保留完整逻辑 band；每个 source segment 保留相对 band 的逻辑偏移，绝不能把多个 offscreen segment clamp 到 row 0/last row。当前帧只给 `band ∩ moving_content_region ∩ terminal` 建立 exact placement/clip；被应用 chrome 遮住的尾部标记为 occluded，而不是拿去与 prompt 行比较。
4. **只让精确字节参与身份延续。** 可见 source segment 必须与 proven record 对应 segment 的 `text/continues/cell_boundaries` 精确相等；隐藏 segment 不参与比较，重新出现前必须再次精确相等。禁止 `before.starts_with(after)`、空行、delimiter 等“可能是中间态”猜测。若精确映射不唯一或可见证据不足，则不把另一个 occurrence 的像素贴上去。
5. **offscreen/dormant record 仍是 identity，不是唯一恢复机制。** full-source exact search 可作为完全重现时的安全路径，但部分可见 prefix/suffix 应通过 proven identity + 唯一 transaction mapping 恢复其可见投影，不经过 M1.9p 首次检测，也不重算 band。
6. **失败时保持 M1.9n 红线。** 不做全局 reconcile 重装、不另算几何、不把 partial `$$` 当新块；所有已证明块继续复用原 band/artifact，首次检测仍由 M1.9k/p 的 Ambiguous/CommonMark 规则决定。

这一路径同时回答“内容指纹、事务边界、band 整体”三项：三者都需要，但事务边界已有基础；真正缺口是**以 exact content fingerprint 建立的分段区域映射**和**identity/placement 分层的整体 band**。

## M1.9s 未提交改动与未生效原因

### 改了什么

与 M1.9s 目标直接对应的未提交变化是：

- `LiveDecorationRecord`/projection 增加 `clipped_bottom_rows`，`shift_live_record` 用 virtual band 计算上下裁切，并允许 start/end/band 越过终端上下边缘后保留可见部分（`session.rs:125-133,4319-4375`；`bt-viewport/src/lib.rs:126-140,1220-1250,1672-1700`）。
- `alternate_record_mapping` 从“唯一 bool exact match”改成“遍历 virtual delta、按 exact source-row 数评分并要求最高分唯一”（`session.rs:4190-4233`）。
- 对 `proven_band_rows >= 5` 的块取消部分 parser-prefix 约束，允许空行、delimiter、字符串前后缀 mismatch 为 transient，并要求至少 2 行且不少于可见 source 行的一半精确（`:4235-4316`）。
- 新增合成测试：固定位置时擦空一条中间行再补回（`crates/bt-term/tests/repaint_flash_oracle.rs:264-335`），以及 closer 超出**终端最后一行**（`:375-426`）。本次实跑两条均 `1 passed`。
- oracle/diagnostics 增加 environment source 识别和 Jump-chip 豁免（`diagnostics.rs:113-158`，binary `:65-68,100`）。

### 为什么只微降、没有消除

1. partial-erase 合成测试的 band 不移动，异常行是空白，正好命中 `after.is_empty()`；真实 frame 153 是 band 平移后撞上非空固定 UI。
2. closer-below-last-row 测试把边界设为终端 row 7，正好命中新增 `clipped_bottom_rows`；真实边界是终端内部 row 17，而 `last_row` 仍是 32。
3. `>=5` 是按长度选择宽松 matcher，不是结构模型。它能保住若干只有空行/前缀污染的帧，所以 flash 数下降；跨内部窗格的帧仍在 `all_visible_rows_match` 失败。
4. score 仍逐旧 band 行比较，并把固定 UI 当作公式应该移动到的新行；“至少半数 exact”不能修复错误的可见域。
5. record 进入 offscreen 队列后，full-source restore 与“只剩精确可见前缀”的真实状态不相容。
6. `alternate_repaint_row_is_transient` 的前后缀/空行猜测不能证明源码精确相等，继续扩张会触碰“绝不显示错误公式”红线，同时仍无法识别应用窗格。

## 验证记录

- `cargo build --locked --offline -p bt-term --bin bt-repaint-oracle`：通过。
- `large_multiline_formula_survives_partial_erase_repaint_frames --exact`：1 passed。
- `repaint_with_closer_below_last_row_keeps_visible_formula_prefix_rendered --exact`：1 passed。
- `cc-topbot.vt`（106×33）：逐帧仍有上述 aligned/pmatrix R↔S；当前诊断豁免后进程 `EXIT=0`。

最终裁决：不要继续给“多行 band 中间态”加更多行级例外。应把下一片定义为“已证明公式 identity 与应用内滚动窗格 projection 解耦”，以完整 2026 事务的精确内容映射发现 moving region/occlusion，并让逻辑 band 整体跨该边界保持。
