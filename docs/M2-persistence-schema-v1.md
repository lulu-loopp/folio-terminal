## 1. 存储位置/格式决策空间

### 1.1 候选与取舍

| 方案 | 优点 | 缺点 |
|---|---|---|
| **单一 JSON 文件**(设置与会话状态各一份) | 原子写只需单文件 temp+rename;人可读可 diff;serde_json 零新依赖;嵌套树(`split{dir,ratio}\|leaf`)天然映射 JSON,不需要 TOML 内联表体操 | 单文件承载所有字段,一次写入覆盖粒度粗(但见下:按写入频率拆两个文件已缓解) |
| **sqlite** | 事务写入;为未来"可搜索 Recent 历史"（P1-13）留了查询接口 | 本文数据规模是"一棵树 + 一份设置 + 有界 Recent 列表",没有关联查询需求;引入 sqlite 相当于给单机 KB 级配置数据配一个关系引擎,是本项目一贯反对的"非忠实通用算法"式过度工程(`CLAUDE.md` 用户偏好);且 workspace 目前没有 sqlite 依赖,需评估静态链接与崩溃恢复语义的新增复杂度,收益不对称 |
| **目录多文件**(逐叶/逐 tab 拆散存) | 单叶写入的 blast radius 更小 | `DESIGN.md` §7.1.4 把 split 树、tab 顺序、`active tab`、`focusIndex` 当成**一次序列化的整体**来推理("未提交的重命名在序列化前提交"这类规则要求写入时刻是单一事务点);拆到逐叶文件后,崩溃可能落在"树文件已写、某叶文件未写"之间,凭空制造出 §5 本不该存在的"部分一致"状态,且需要额外的目录级完整性校验,复杂度不划算 |

**推荐：两个 JSON 文件，而非一个、也不是逐叶拆散。**

- `settings.json`——用户偏好,低频写(仅设置面板显式改动触发),小。
- `session.json`——窗口/分屏树/tab/pin/Recent,较高频写(**已裁决**:变更后 debounce 落盘,
  规则见 §5.1),体量随 tab 数增长但仍是 KB 级。

拆成两个文件而不是一个的理由是**写入频率与后果不对称**:设置改动应立即落盘(用户在设置面板
点一下就该生效并持久,丢失更痛);会话状态在正常使用中持续变化(resize、切 tab、新建 pane),
按写入时机走 §5 的策略。两类数据混在一个文件里,会强迫更痛的一类(设置)跟着更频繁的一类
(会话状态)的写入节奏走,或反过来让设置的低频写延误会话状态的及时落盘。**不进一步拆分**
(比如按每个 tab 拆): 目前只有这两种写入节奏类别,为尚不存在的第三种节奏预先拆目录是
"没有消费者的机制"(`CONVENTIONS.md` §三"只写字段=死规格"的目录版)——新的节奏类别出现时,
schema 版本化(见 §1.3)足以低成本地拆出第三个文件。

### 1.2 存储位置

`%APPDATA%\BetterTerminal\`(Roaming),文件名即 `settings.json`、`session.json`。理由:
本产品的用户画像(开发者/终端重度用户)与 VS Code 用户重叠度高,`%APPDATA%\Code\User\` 是
该人群已经建立的心智模型;域漫游场景下"设置跟着人走"是合理默认。窗口位置/DPI 这类**本机**
相关字段理论上更适合 `%LOCALAPPDATA%`,但 §3 已经把"目标显示器消失/坐标越界"钳制为安全的
降级路径(钳位回可见工作区,而不是相信旧坐标),所以把它们和设置放在一起漫游不产生正确性
风险,只是换机器时体验从"记住"退化成"钳位后的合理默认"——可接受。**不为这一个字段类目
单独换目录**,同一理由:没有第二个消费者需要 `%LOCALAPPDATA%` 语义之前,不必现在拆。

### 1.3 版本化 schema 与显式迁移规则

两份文件顶层都有整型 `schema_version`(从 `1` 起)。规则:

1. **只向前迁移,不支持降级**。读到 `schema_version < current`:依次应用
   `migrate_v{n}_to_v{n+1}` 纯函数链,每一步独立可测——且**必须**用非默认值的 fixture 测试
   (`CONVENTIONS.md` "默认值会掩盖 bug"这条铁律在这里同样成立:只喂全默认值构造的旧版
   文档去跑迁移,测不出字段错位)。
2. **读到 `schema_version > current`**(用户装过更新的 BetterTerminal 又降级回旧版本运行):
   **不尝试部分解析**——按 §5 的"读取失败"路径整体回退到默认值并显式告警,**绝不猜**
   哪些字段在新旧之间兼容。这是 `CONVENTIONS.md` "不要启发式"用在 schema 演进上的直接
   推论:猜对几个字段不代表猜对了全部不变量。
3. **迁移函数只做结构升级,不做语义修复**。发现旧版本数据本身不满足新不变量(例如 ratio
   越界)不是迁移函数的职责,交给 §5 的逐叶降级路径统一处理——两个关注点不要焊在一起。
4. **未识别字段**(同版本内、来自用户手改或第三方工具)——**已裁决(2026-08-03):静默丢弃**。
   解析时按标准 serde 语义忽略未识别字段(不设 `deny_unknown_fields`),不捕获、不透传;这些
   字段本来就没有进入内存,下次写入时自然不再出现。**显式记为"不支持手动扩展 schema"**:
   手改配置文件添加自定义字段不是受支持的工作流,写死这条比暗示"你的自定义字段会被保留"更
   诚实,也省去 `#[serde(flatten)]` opaque map 的实现与测试成本。真出现"需要在版本间保留手改
   内容"的实测需求时,走 §1.3 的迁移机制升级为显式透传——不是现在就为假想需求买单。

## 2. 设置(`settings.json`)

设置的 v1 字段集合遵循一条纪律:**只收录已经在 DESIGN/M2 文档里落定的用户可见项**,不为
"将来大概率要做"的功能预留占位字段。理由直接来自 `CONVENTIONS.md` §三"只写字段=死规格":
一个 schema 里存在、却没有任何代码读它的字段,是"死规格",要么接线要么删除;既然迁移机制
(§1.3)本来就能在功能真正落地时用一次 `schema_version` bump 便宜地引入新字段,现在占位除了
制造死字段没有别的好处。以下逐项覆盖任务列出的五个话题:

| 话题 | v1 状态 | 理由 |
|---|---|---|
| **主题**(`theme_mode: System \| Light \| Dark`) | **v1 字段** | `DESIGN.md` §7.1.6/§7.1.5c 已裁决"主题 System/Light/Dark 跟随系统"且命令面板/设置项双向同步,是已定型的用户可见功能,不是占位 |
| **BT_BG** | **不进 settings.json** | 现状是渲染缺陷复现用的启动前环境变量(`docs/M1.7-scroll-selection.md`),不是产品设置;若未来要做"自定义背景色"作为主题的一部分,那是一次新的产品裁决,应作为独立字段在那次裁决时加入,不该借 BT_BG 的壳蒙混升级 |
| **字体大小/zoom level** | **不进 v1** | 代码里没有任何 zoom/字体大小的用户交互实现(`Ctrl+滚轮`/`Ctrl±` 均未落地);现在占字段是纯粹的死字段 |
| **wheel 偏好** | **不进 v1**(已裁决 2026-08-03,§7#3) | 当前实现(`crates/bt-platform/src/lib.rs::wheel_scroll_amount`、`crates/bt-app/src/main.rs::recoverable_wheel_scroll_amount`)完全读 Windows `SPI_GETWHEELSCROLLLINES`,失败时回退常量 3 行,**没有任何用户可覆盖的入口**;裁决维持纯系统透传,v1 不加覆盖项 |
| **`detect_image_paths`** | **不进 settings.json**,维持编译期默认(bt-app 显式开、headless/回放显式关)(已裁决 2026-08-03,§7#2) | 这是 `bt_math::MathLayoutOptions` 的一个 session 政策位(`docs/M2-preview-matrix-and-verbs.md` §6),目前只在代码里以布尔常量存在;裁决维持内部政策位,不升级为设置面板项 |
| **`FORCE_HYPERLINK`** | **不进 v1**(已裁决 2026-08-03,§7#1) | `docs/reviews/cc-hyperlink-gate-probe.md` 的产品建议明确反对"无条件给所有子进程注入",主张"应做成显式用户选项或 app 级 profile 覆盖";但 profile 系统本身尚未落地(workspace 里没有 `ProfileId`/`Profile` 类型),没有挂载点;裁决挂靠该未来机制,v1 不设任何字段 |

**settings.json v1 的完整字段表**(目前只有一项,故意如此):

```
{
  "schema_version": 1,
  "theme_mode": "System" | "Light" | "Dark"
}
```

## 3. 窗口状态与布局求解器持久态(`session.json` 的一部分)

### 3.1 窗口几何

- 字段:`bounds{x, y, width, height}`(逻辑像素,配 `dpi` 记录捕获时的每显示器 DPI,供
  恢复时判断是否需要重新布局)、`maximized: bool`、`monitor_id`(尽力标识符,如设备名+
  工作区矩形指纹,不保证跨驱动更新稳定)。
- **恢复策略**:优先按 `monitor_id` 命中同一显示器并按记录的逻辑坐标复位;命中失败(显示器
  拔掉/换了驱动/坐标越出当前虚拟桌面)**钳位**到最近可见工作区而不是相信旧坐标,与
  `DESIGN.md` §7.1.2 浮窗"主窗口缩小自动重钳位"同一纪律的窗口级版本。**不崩、不弹到屏幕外**
  是硬底线,精确复位是尽力而为。
- v1 只有单一主窗口概念(`DESIGN.md` §7.0 把"OS 窗口"列为 M2+ 平台项,尚未定型)。字段命名为
  `window`(单数、非数组),不预先套一个 `windows[]` 数组——与 §2 同一条纪律:多窗口落地时
  用 `schema_version` bump 把 `window` 升格为 `windows[]`,现在不为假想中的形状买单。

### 3.2 布局求解器的持久态

`session.json` 持久化的是**求解器的输入**(树形状 + `ratio`),不是求解器本身的任何内部
状态——求解器按 `DESIGN.md` §7.1.5 是"独立纯布局求解器",给定同一份树与同一块可用矩形必须
确定性地产出同一份叶子矩形,因此它没有需要跨会话保留的内部状态,持久化到此为止:

```
split { "dir": "row" | "col", "ratio": number, "children": [node, node] }
leaf  { "kind": "term" | "files" | "preview", ...见 §3.3/§3.4/§3.4b }
```

> **【批注 2026-08-13 · 已落地,补上 `preview` 叶】**
>
> 本节原文只列 `term` 与 `files`,因为它写在布局求解器的座位家族被裁决之前。
> `docs/M2-layout-solver-spec.md` §5 随后把「preview 座的 `pinned` 标志」直接写进了持久列,
> 而**一条写不下去的字段就是一条守不住的裁决**;本节自己也说 `session.json` 载的是「求解器的
> 输入」,那么它的叶种就是求解器的叶种。`crates/bt-persist/src/layout.rs` 的
> `LeafNodeV1::Preview` 早已按这个方向补上,本节现在与代码对齐。**additive**:写在它之前的
> 每一份 v1 文档照读不误,不 bump `schema_version`。

`id` 字段(`DESIGN.md` §7.1.4:"split{dir,ratio}（id 复活时重铸）")**不持久化**——它是运行时
句柄,恢复时按树形状重新铸造,序列化只需要形状与 `ratio`。`ratio` 的取值范围、序列化精度、
超限 clamp 算法**属于 `docs/M2-layout-solver-spec.md`**(§7.1.7①原文列出的规格项),本文只
承诺:无论精度/clamp 规则最终是什么,`session.json` 里 `ratio` 就是一个 JSON number,读到
不满足求解器不变量的值时走 §5 的"逐叶降级→clamp"路径,不属于本文裁决范围。

### 3.3 term 叶

```
term {
  "kind": "term",
  "profile_id": "<稳定标识符,非展示对象>",
  "cwd": "<路径或 URI>",
  "manual_name": "<string?>"
}
```

`profile_id` 是**稳定标识**而非标题(`DESIGN.md` §7.1.4 原文强调"不是标题、不是展示对象")。

> **【批注 2026-08-10 · 已落地,本节上一段的"可执行路径"条被推翻】**
>
> 原文(保留于下方引用块,便于对照旧文件)规定 v1 的过渡取值是「启动该 pane 时实际使用的
> shell 可执行路径」,并预告 profile 系统落地时做一次 bump + 一次性迁移。**profile 系统已于
> 本次落地(P1),迁移已写:`SESSION_SCHEMA_VERSION` 5 → 6,`migrate_session_v5_to_v6`。**
> 但迁移的**方向与原文相反**:
>
> - **裁决(用户,2026-08-10,Q3):`profile_id` 取值为稳定 slug**,当前四值
>   `pwsh` / `wsl` / `gitbash` / `cmd`,与 `crates/bt-app/src/profiles.rs` 的 `Profile::id` 同源。
> - **理由:可执行路径既不稳定也不是身份。** 同一个 `pwsh.exe` 会因 MSI / winget / Store 别名
>   落在不同目录,`BT_SHELL` 能把它指到任何地方,用户什么都没改路径就变了;反过来,两个不同
>   档案完全可以跑同一个二进制(本块的 PowerShell 档案与将来「参数不同的 PowerShell」档案就是
>   这种关系),路径无法把它们区分开。
> - **实现早已与原文分叉**:应用侧自始至终写的是短 id `"pwsh"`,而本仓夹具里存的是全路径,
>   **盘上同时存在两种拼写**。这正是必须做迁移而不是读时猜测的原因。
> - **迁移规则**:按可执行文件名(大小写不敏感、忽略目录)映射 ——
>   `pwsh.exe` / `powershell.exe` → `pwsh`(两者从来是**同一个档案的解析顺序**,不是两个档案)、
>   `wsl.exe` → `wsl`、`cmd.exe` → `cmd`、`bash.exe` / `git-bash.exe` → `gitbash`;
>   已经是 slug 的原样保留;**认不出的值逐字保留、绝不映射成默认档案**——读时的 §5.4
>   逐叶降级(见 §5「未知 `profile_id` → 落到默认 profile」)是可逆的、每次启动重来一遍的,
>   而迁移写下去就是永久的。
> - **`recent[].key` 不迁移**:它是只写字段(`SeedVault::from_persisted` 从不读它,
>   `to_persisted` 每次保存都按 seed 重算),盘上过期的 key 不影响任何行为,且 §3.5 明说本
>   crate 不计算也不校验该键格式。
>
> 原文存档:
>
> > profile 系统尚未落地时,v1 的过渡取值是**启动该 pane 时实际使用的 shell 可执行路径**
> > (如 `powershell.exe`、`pwsh.exe`、`wsl.exe` 的规范化路径),这是当前唯一"稳定且不依赖
> > 尚不存在的 profile 系统"的标识来源。profile 系统落地后,这个字段的语义升级为真正的
> > `ProfileId`,是一次 `schema_version` bump 加一次一次性迁移(把可执行路径映射到新建的
> > 默认 profile)。

**另:本字段是 per-leaf 的,现在名副其实。** 字段自 v1 起就长在每片 `term` 叶上,但在 P1 之前
应用只有 tab 级的一个答案可写,于是一个 tab 的每片叶都被写成同一个 shell —— 从 Git Bash 分屏
存下的两格,回来是两个 PowerShell。`docs/UI-UX.md` §425(「树上每个叶子存 profile + cwd +
名字 + 自动化」,例子正是 `[claude in mpc | git bash]`)要的就是这一条,P1 已把运行时的
`profile` 从 `TabState` 移到 `LeafSession`,读写两侧都按叶走。

```
files {
  "kind": "files",
  "root": "<路径>",
  "open": ["<稳定 ID>", ...],
  "sel": "<稳定 ID>?",
  "width": number
}
```

`open`/`sel` 的"稳定 ID"格式复用 `docs/DESIGN.md` §7.1.3 已经裁决的节点稳定 ID 机制
("重命名/目录删除后选中与展开按 ID 尽力恢复,失败则就近降级")——本文不重新发明一套 ID,
直接引用该节点标识符的当前取值序列化,读回时用同一套"尽力恢复,失败则降级"逻辑,失败不是
本文的错误路径,是既有裁决本就承诺的正常路径。

### 3.4b preview 叶

```
preview {
  "kind": "preview",
  "pinned": bool
}
```

**只有一个字段,而且它是几何。** `pinned` 决定的是「下一个被打开的文件复用这个座,还是在它
旁边开一列」(`DESIGN.md` §7.1.3:「pane 增殖只经显式图钉」),这是求解器输入的一部分,所以它
在树里。

**没有内容字段,这是红线 L1 而非遗漏。** 「这个 pane 正在看哪个文件」是内容,不是几何;它与
tab 的共享缓冲池一起,存在 §3.5 的 `tab.preview` content 段里。理由见 `DESIGN.md` §7.1.3
的 2026-07-17 裁决:缓冲属于**文件**,池属于 **tab**,一个文件在两个 pane 打开必须是同一份
缓冲——一个挂在叶上的内容字段会让「同一文件两份缓冲」在盘上就成立。

### 3.5 顶层会话结构

```
{
  "schema_version": 1,
  "window": { ...见 §3.1 },
  "tabs": [
    {
      "root": <split 或 leaf, 见 §3.2>,
      "pinned": bool,
      "focused_leaf": "<叶稳定 ID>",
      "preview": {                          // 可选,见下方批注
        "panes": [ { "leaf": "leaf-N", "cur": "<路径>?" }, ... ],
        "pool":  [ { "path": "<路径>", "name": "<显示名>" }, ... ]
      }
    }
  ],
  "active_tab": number,
  "recent": [
    {
      "key": "<profile_id+cwd+manual_name>",
      "seed": {...},
      "timestamp": "<ISO-8601>",
      "previews": ["<路径>", ...]           // 可选,见下方批注
    }
  ]
}
```

> **【批注 2026-08-13 · 已落地,补上 tab 级 content 段与 Recent 的 previews】**
>
> **`tab.preview` —— preview 的内容身份住在 tab 层,不进布局树(裁决 11,2026-08-12)。**
> 红线 L1 把内容挡在布局树之外,而「这个 preview pane 正在看哪个文件」正是内容;`DESIGN.md`
> §7.1.3 又把缓冲池的归属定在 **tab** 上(一个 tab 一个池,一个文件恰好一份缓冲)。两条合起来
> 只剩一个位置:树旁边的 tab 层。
>
> - `panes` —— 每片 preview 叶一行,树序。`leaf` 用与 `focused_leaf` **同一套 `leaf-N` 位置
>   令牌**指回树里:`term`/`files` 叶坐在树里,位置本身就是地址;content 段站在树外,没有位置
>   可读,只能指名道姓——而磁盘上不该出现运行时座位 id(§3.2),树的中序下标是唯一既指得准
>   又完全由文件自身形状决定的地址。`cur` 为 `null` 表示这个 pane 什么都没显示,**写出来而
>   不是省略**:空 pane 是一种状态,靠"少一行"表达的话读者分不清它与写漏了。
> - `pool` —— tab 的共享缓冲池,最旧在前,即文件名切换器列出的那份**历史**。它是 `panes` 的
>   超集:浏览过又切走的缓冲仍在池里,丢掉它会让切换器每次重启后变短。
> - **只存路径与名,不存正文、不存脏位。** 与本 schema「不存输出历史」同一条诚实:恢复出来的
>   pane 显示磁盘现状,不假装什么都没发生过。未保存的编辑不会无声消失——§7.1.3 的三道脏门
>   (关最后一个 preview pane / 关 tab / 关应用)在此之前按名点过。`name` 存而不是从 `path`
>   现算:本 crate 不拥有路径文法,一条会漂移的切分规则会让同一行在重启后换个名字。
> - **恢复顺序**:池先复活(全新、无正文、无脏),各叶再按 `cur` 指进池里,`cur` 在池里找不到
>   就现造一份补进去;令牌指到别的叶种(手改过的文件、或新版本写的树)只让那一行落空,pane 照常
>   回来,这就是 §5.4 的逐叶降级。
> - **浮窗不落盘。** 浮窗是一个手势的产物而不是一个场所:它的 pane 在树里、它的缓冲在池里,
>   唯一没带回来的是「曾经撕下来过」。
> - 字段可选,**additive**:整段缺席即"没有 preview",写在它之前的每一份文档照读不误,
>   `schema_version` 不因它 bump;无 preview 的 tab 一个字节都不多写。
>
> **`recent[].previews` —— 关掉的 tab 把它的页面一起带进库(裁决 10,2026-08-12)。**
> `DESIGN.md` §7.1.4 记着同一个坑的第一次:files 叶被 `recordRecent` 静默跳过,于是纯 files
> tab 经 shut→restore 能回来、经 Ctrl+Shift+T 却回不来——**同一个库两扇门,坏了一扇**。
> `tab.preview` 一落地,不带 previews 的 Recent 条目就是这个坑第二次。只存路径:不存池(按需
> 从磁盘重生)、不存图钉(没人向一个已关闭的 tab 许诺过它的排布)——**Recent 恢复的是你去过的
> 地方,不是一套布局**。同样可选、additive、空则不写。

- `active tab`/`focusIndex` 直接对应 `DESIGN.md` §7.1.4 列出的序列化面,字段名取
  `active_tab`/`focused_leaf` 以避免与运行时 `InputOwner`(§7.1.5)的命名混淆——两者是
  不同的概念,一个是磁盘上的"上次哪个 tab/pane 活跃",一个是运行时"当前键盘焦点在哪",
  不应共用类型或命名。
- `recent` 的去重键、内容来源见 `DESIGN.md` §7.1.4 原文("Recent 条目 = 终端 seed 或
  files 场所...去重键 = profile_id+cwd+手动名")。**容量上限与过期策略已裁决(2026-08-03,
  §7#6)：容量优先淘汰 + 时间窗兜底清理**——超过容量上限时先淘汰最旧条目;条目即使未超容量,
  超过时间窗也定期清扫。具体条数/天数留给实现按原型实测手感定,不在本文钉死。
- **未提交的重命名在序列化前提交**(`DESIGN.md` §7.1.4 原文,blur 语义)——这是写入时刻
  的行为规则,不是字段,本文只在此处复述以确保实现者不会漏看。

## 4. v1 明确不持久化的内容

| 内容 | 不持久化的理由 |
|---|---|
| **转录/scrollback** | §0 已重述的既有裁决;另有独立论据——转录一旦落盘就成为第二个"这是不是真实终端输出"的真相来源,而 `DESIGN.md` R13'/G1 的整套"不得以内容相等去重、trace 确定性回放"论证都建立在**转录只活在一次进程生命周期内**这个前提上。把它落盘意味着下次启动时要回答"磁盘上这份转录是不是当前 vendor grid 状态的忠实延伸",而 resize/reflow/repaint 的整套不确定性(R13')使这个问题在协议层面不可判定——持久化转录会把一个"运行时可以诚实说不知道"的问题变成"启动时必须假装知道"的问题 |
| **解码后的富内容产物**(公式渲染位图、图片解码纹理、SVG 光栅结果) | `DESIGN.md` §3.4 Attachment 语义是"打开时快照+显式刷新",且 `docs/M2-preview-matrix-and-verbs.md` 的图片管线是"按内容哈希复用纹理身份"的运行时 LRU 缓存,不是持久层的东西。持久化解码产物会制造一份可能与源文件/源转录字节脱钩的缓存,下次启动时需要额外的失效判断(文件改了吗?检测器版本变了吗?——即 `DetectionRevision`);这正是 corpus/G1 回放依赖的"确定性可重建"公理想要避免的第二份状态。解码永远从源字节按需重算,磁盘上不留副本 |
| **进程**(shell/agent 本体) | §0 已重述;这是 M4+ 的开放架构项(常驻服务/tmux-Zellij 路线),不在 v1 范围 |
| **命令历史标记轨、OSC 133 区域元数据** | 属于转录的附属数据,转录本身不持久化,附属数据同样不持久化;下次启动是一个干净的新 shell,没有"上次的命令历史"可言(`docs/UI-UX.md` §8.5.2:"一个新 shell、一屏新的空白") |

## 5. 损坏/部分写入策略

### 5.1 写入时机(debounce)——已裁决(2026-08-03,§7#5)

`session.json` 在**有意义的变更后 debounce 约 1-2 秒**落盘(新建/关闭 tab、resize 结束、
pin 变化、切 tab 等触发计时器重置,静默窗口到了才写一次),不是每次事件立即写、也不是只在
退出时写一次。理由:立即写在高频操作(如连续拖 divider)下会产生大量无意义的磁盘 I/O 与
潜在的写失败告警噪音;只在退出时写会让崩溃丢失自上次退出以来的全部布局变化,与 §5.5 的
"崩溃恢复"路径本就要给用户一个可信的最近状态相矛盾。`settings.json` 不适用本条——它在
设置面板显式改动时立即写(§1.1 已定,低频、每次都是用户主动确认的动作,没有 debounce 的
必要)。

### 5.2 原子写

统一模式:在目标文件同目录下写一个随机后缀的临时文件、`fsync`、再用平台原子替换
(Windows 上 `ReplaceFile`/`MoveFileEx` 的 `MOVEFILE_REPLACE_EXISTING`)覆盖到最终文件名。
**同目录**是必要条件——跨卷的"写临时文件再 rename"不是原子操作,这条本身不是待裁项,是
实现正确性的前提。

### 5.3 写失败

**显式告警,绝不假装成功**(`DESIGN.md` §7.1.4 原文)。具体到 v1:写入失败(磁盘满、权限
被拒、路径被外部程序占用)时,对用户可见的后果是"这次的窗口/tab 改动这次不会被记住"的
非阻塞提示,而不是静默吞掉错误——用户此刻仍然在正常使用终端,不能因为持久化失败而中断
工作,但也不能让用户带着"pin 已经保存了"的错误信念继续操作。

**告警节奏——已裁决(2026-08-03,§7#5 的配套决定):按失败连续段(failure streak)告警一次,
不按尝试次数告警。** §5.1 的 debounce 写入在磁盘持续不可写期间(例如磁盘满一直没解决)会
反复重试,若每次重试失败都弹一次提示,持续失败的场景会变成告警轰炸,反而掩盖了"这是同一个
原因"这件事。规则:进入失败状态时告警一次;此后同一原因的连续失败不再重复告警;下一次写入
成功后重置计数,若后续又失败则视为新的失败段,重新告警一次。

### 5.4 读失败

三类读失败,统一**不崩溃、回退默认值**:

1. **文件不存在**(首次启动、被用户手动删除):视为空默认值,不告警(这是正常状态,不是
   错误)。
2. **文件存在但不可解析**(JSON 语法错误、来自未来 `schema_version` 见 §1.3)：整份文件
   回退默认值,并显式告警指出具体是哪个文件、失败原因;**原文件不覆盖、不删除**(用户可能
   想手动修复或联系支持,覆盖掉证据是二次伤害)。
3. **文件可解析但字段不满足不变量**(单个 tab 引用了不存在的 profile、`cwd` 已被删除、
   `ratio` 越界、`leaf.kind` 是本版本不认识的取值):**逐叶降级**,不因单叶损坏丢整棵树
   (`DESIGN.md` §7.1.4 原文)——

| 损坏 | 降级 |
|---|---|
| 未知 `profile_id` | 落到默认 profile |
| 无效 `cwd`(路径不存在/不可访问) | 落到 `HOME`,并在恢复出的 tab 首行提示(与 §3.5 的"new shell in \<cwd\>"横幅同一机制) |
| 未知 `leaf.kind`(来自更新版本引入的新叶类型,当前版本不认识) | 占位 pane(可见但不可用,而不是让整棵树解析失败) |
| 非法 `ratio`(超出求解器允许区间) | clamp 到合法区间(具体区间由 `M2-layout-solver-spec.md` 定义) |

### 5.5 三条退出路径的措辞区分

正常退出、崩溃、系统关机三条路径在**恢复提示的措辞**上必须可区分
(`DESIGN.md` §7.1.4:"崩溃恢复的提示措辞不暗示进程还活着")。

**判定机制——已裁决(2026-08-03,§7#7):哨兵/锁文件。** 启动时在存储目录创建一个哨兵文件
(如 `session.lock`,内容不重要,存在性即信号);正常退出时删除它。下次启动若发现哨兵文件
残留,判定上次是崩溃,走"崩溃恢复"文案(不暗示进程还活着)。**系统关机路径**通过监听
`WM_QUERYENDSESSION`/`WM_ENDSESSION` 在收到关机通知时执行与正常退出相同的清理(§5.1 的
debounce 写入立即 flush、删除哨兵文件),因此**系统关机计入"正常退出"分支**,不产生"崩溃"
措辞——用户主动关机不是程序失败,不该被当成崩溃对待。三条路径对应的用户可见文案本身仍是
本文未逐字拟定的实现细节(`DESIGN.md` §7.1.4 只要求"崩溃恢复的措辞不暗示进程还活着"这一条
约束),本条只把"怎么知道该走哪条文案"钉死为一个可实现的机制。

- 本文没有引入任何与 `DESIGN.md` §7.1.4 冲突的字段或行为——每个字段名尽量复用该节原文用词
  (`profile_id`、`cwd`、`manual_name`、`pinned`、`active tab`、`focusIndex`),偏离处
  (`active_tab`/`focused_leaf` 的 snake_case 与运行时命名的区分)已在 §3.5 注明理由。

  `CONVENTIONS.md` "只写字段=死规格"规则的直接结果,而不是遗漏——§2 表格逐项写明了理由。
- 迁移机制(§1.3)存在的意义之一就是让"现在明确不做"的决定**足够便宜地可翻案**:任何一个

  重新设计整份 schema。
