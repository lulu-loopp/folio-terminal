档位 high。基线 = 提交 `20846b1`(M1.9m)。**可以改代码**(只加测试/诊断能力,
不碰公式产品逻辑),做完停下等审、不提交。

## 要解决的"测不出来"问题

协调者的验收 oracle 是**静态**的:`BT_PROBE_INPUT`(一段 VT 字节喂进 Term 启动)
+ 抓**一张**稳定后的截图。它抓不到**交互重绘时的瞬态闪回**——M1.9n 的 reconcile
把块 band 算错、`$$` 露成源码,**静态首帧全对、门禁全绿**,只有真机在 Claude Code
里点/滚才现。协调者需要一个能在**开发环内**复现并回归这类 bug 的能力。

## 造三样(名字/形式你定,要实用)

### A. 抓真实字节流(把 Claude Code 一次点击/滚动录下来)
终端从 ConPTY 读到的**原始 VT 字节**就是 Claude Code 真实发的。加一个诊断开关
(如 `BT_PTY_DUMP=<path>`),把 bt-pty 收到的字节**原样落盘**(带到达时刻/分帧
标记更好)。这样协调者可以:开着 dump 跑 Claude Code → 在里面点一下/滚一下/双击
公式行 → 得到一段**真实重绘字节**,再用现有 `BT_PROBE_INPUT` 回放,**确定性复现**
那次重绘。注意:dump 不得改变字节、不得影响性能路径(仅旁路写)。

### B. 抓瞬态(不是只抓稳定帧)
现在只看稳定后一帧。要能观察**重绘→稳定这段里每一帧**公式是不是退成了源码。
两条路择优或都做:
- **headless 帧序列**:一个测试/诊断入口,喂一段字节序列,把**期间发布的每一帧**
  的"某逻辑块是渲染态还是源码态(有无 `$$`/show_source)"记录成序列,供断言;
- **逐帧截图**:让 ui-probe 能在回放一段字节后**连拍 N 帧**(而非单张),协调者
  肉眼/像素比对能看到中间那帧的闪。
关键是**能捕获"上一帧渲染、这一帧源码、下一帧又渲染"的中间那一帧**。

### C. 一条会红的交互重绘回归(证明工具有效)
用 A 录的真实重绘字节(或忠实构造的"原地重绘 / 平移重绘"字节序列),写一条
headless 回归:公式先 Ready → 回放重绘字节 → **断言期间没有任何一帧把该块显示为
源码**。用 M1.9n 的 stash(`git stash list` 找 reconcile 那条)或临时制造闪回来
**证明这条回归确实会红**(即它能抓到闪),再说明正常 M1.9m 下它的表现。
