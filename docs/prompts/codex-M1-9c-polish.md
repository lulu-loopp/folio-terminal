## 1. 重复右键把可恢复竞态升级成致命错误(先修,这是崩溃面)

复审低危,但用户视角是崩溃:`main.rs:1105-1110` 把 "already pending"
用 `?` 传播,最终在 `:1764-1767` 走 `self.fail()` **终止整个应用**——
用户手快点两下右键,程序就没了。

**修法**:菜单已 pending 时的第二次右键是**正常的 UI 竞态**,应当被
安静忽略(或替换 pending 请求),绝不进入致命路径。审一遍这条链路上
还有没有别的"可恢复状态用 `?` 升级成 fail" 的地方,一并降级。
回归:连续两次右键请求不产生 Err、应用不终止、菜单状态机保持自洽。

## 2. worker 结果的时效检查过严,持续丢弃已完成光栅

`session.rs:962-980` 的 `inputs_are_current` 要求**全部 1024 行历史 +
整屏逐字节不变**才接受 worker 结果。而 Typst 光栅约 42ms/式、spinner
约 100ms 跳一次——**光栅化期间 spinner 跳一次,已渲染完的结果被整批
丢弃**,靠重试落地,期间每秒浪费约 5 次光栅化。这是本片目标场景
(Claude Code)的常态。

**修法**:时效性只应绑定**该块自身的输入**(块所覆盖的行的内容与
revision),不应绑定屏幕上无关行的逐字节相等。围栏上下文的正确性
仍需保证——若围栏状态因无关行变化而可能改变,那部分必须重判,但
不得因"屏幕上任意一行动了"就丢弃结果。给出你的判定粒度设计与论证。
回归:模拟"块内容不变 + 邻近 spinner 行每 100ms 变一次"的场景,
断言光栅结果被接受(不重试风暴),且块内容真变时仍然正确失效。

## 3. live 块在行带内垂直居中(用户实拍 + 复审低危 E)

现状顶对齐,行带剩余空间全堆在下方,视觉上"公式下面空一大块"
(用户 2026-07-19 实拍)。**修为在行带内垂直居中**(上下空白均分,
差值 ≤1px);与 §7.4 的"上下等距"精神一致。
回归:栅格顶到行带顶、栅格底到行带底的距离差 ≤1px。

## 4. 借用紧邻空行扩展行带(用户需求 2026-07-19)

**动机**:单行 `$$x$$` 的行带只有一行,几乎必然低于 0.65 地板 →
用户手敲的单行公式在 live 区永远不渲染。而块**紧邻的空行**没有内容,
纳入行带既不遮挡任何东西,又能让公式获得空间。

**规则**:
- 块行带可向**下**(必要时也向上,论证是否需要)扩展至紧邻的**完全
  空白**行;扩展行数上限自定(建议 ≤2,写明依据),避免吞掉大片留白;
- 被借用的行必须是**真正空白**(无任何非空白单元);
- **借用行一旦被写入任何内容 → 立即失效回源码**(复用现有 revision/
  generation 机制,借用行要纳入该块的输入集);
- 借用后重算缩放与地板判定(更多空间 → 更多公式过关);
- alt 与 primary live 同规则。

回归:单行块 + 下方 1 空行 → 借用后过地板并渲染;借用行被写入 →
下一帧失效回源码;无空行可借时仍按地板保持源码;借用不得越过
非空行。
