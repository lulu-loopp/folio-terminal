## 症状(用户实测,c29b5b9 构建,真实 Claude Code 会话)

上一片(m1.8c/S13)做了 CSI S 显式滚动豁免,回归里 512 帧从 11.13ms 降到 0.885ms。但用户回来报告:

1. **向上收起仍然慢**(S13 声称要治的正是它)。
2. **向下收起现在也时快时慢**——出现了新的不稳定。
3. **同一个区块,有时快有时慢**(同内容、不同次操作,表现不同)。
4. 新的差分信号:**慢的都是中文密集的输出**(整段 CJK 文本、CJK 混排的 pytest 输出);**快的是纯 ASCII 代码块**(带语法高亮颜色,行数相当)。

## 关键事实:S13 的门禁测的是什么

`lifecycle_matrix.rs` 那个 11ms→0.885ms 基准跑的是 **term 解析/转录捕获路径**(纯 CPU,vendor term 处理字节),**从未测量渲染路径**(bt-render 的整形/合成/上传/呈现)。也就是说:S13 修掉的那部分开销是真的,但它可能根本不是用户感知延迟的大头。渲染路径到今天为止没有任何一个数字。

## 差分指向的嫌疑清单(逐一证实或排除,不许只挑一个)

按嫌疑度排序:

1. **每帧全量字形整形 + CJK 回退路由**。m1.5(5712448/e34e078)与 m1.5b(3023c5c)引入了 primary-coverage 字体路由:每个字形要探测主字体覆盖、走 Segoe Fluent→Noto 回退链。若每帧重绘都对全屏可见单元格重新整形(没有行级/帧级缓存),CJK 重的屏每帧成本远高于 ASCII 屏——**这直接解释差分 4**。检查 `crates/bt-render/src/lib.rs` 与 `procedural.rs`:整形结果有没有缓存?缓存键是什么?命中率如何?(挂账 P2-17「行级合成缓存」正是为此预留的,浏览器同款课题。)
2. **图集(atlas)冷热**。同一内容时快时慢(差分 3)符合"图集驻留与否"的特征:字形已上传则快,被驱逐/首次见则慢。查图集容量、驱逐策略、CJK 大字符集是否造成反复驱逐。
3. **重绘范围 × 帧数**。Claude Code(Ink)底部锚定,收起大区块时整屏重绘、小区块只重绘下缘——"向上/向下"很可能只是**重绘范围大小的表象**,方向本身不是变量。确认它实际发出的字节:除了 CSI S,是否走绝对定位 + EL/ED 重写、CSI T、IL/DL?这些路径是否还在逐帧进转录捕获(S13 只豁免了 ScrollOperation 的哪些枚举)?
4. **分块边界依赖**。同字节流、不同 PTY read 分块 → 不同帧数与不同的 coalescing 命中(200ms 合帧、帧匹配呈现门禁是 m1.8 加的)。这同样能解释差分 3。检查:一次收起产生多少次 present?每次 present 的间隔分布?
5. **同步更新(DEC mode 2026)**。Claude Code 会用同步更新包裹重绘。BT 是否尊重 2026 批帧?若不尊重,中间态帧全部被呈现,帧数翻倍。
