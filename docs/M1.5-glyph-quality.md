# M1.5: color emoji and fallback glyph quality

## Result

The renderer now makes presentation routing explicit per terminal slot. Default emoji presentation and VS16 enter a mixed color-emoji route that prefers `Segoe UI Emoji` and uses the embedded `Noto Color Emoji` for missing clusters; VS15, default-text emoji characters, and text symbols select `Segoe UI Symbol`; ordinary terminal text retains the Consolas/CJK chain. This avoids cosmic-text's internal name-sorted fallback order and keeps `☆` and `│` away from the emoji face. No glyphon, cosmic-text, swash, or other vendor source was changed.

## Capability reconnaissance

The pinned stack is glyphon 0.12.0, cosmic-text 0.19.0, and swash 0.2.9. cosmic-text's swash raster path requests `ColorOutline(0)`, then `ColorBitmap(BestFit)`, then a normal outline. glyphon maps a returned color image to its color atlas instead of tinting it as a mask. Therefore the stack supports both the COLR/CPAL route used by Segoe UI Emoji and the bitmap-color route used by the supplied Noto asset.

`assets/fonts/NotoColorEmoji_WindowsCompatible.ttf` contains CBDT/CBLC bitmap color strikes plus GSUB. The delivered fixture sequences shape through that face as one nonzero glyph each, including the family ZWJ sequence, skin-tone sequence, and US regional-indicator pair. Raster tests observe `SwashContent::Color`; VS15 through Segoe UI Symbol observes `SwashContent::Mask`.

Windows font discovery remains bounded. The database loads the existing fixed Consolas/CJK files plus `seguiemj.ttf` and `seguisym.ttf`; it never enumerates the Fonts directory. Noto is loaded from `include_bytes!` at compile time. Embedding adds the supplied 10,682,364-byte font to the executable, but makes both `cargo test` and a standalone copied executable independent of their current working directory or a sidecar asset installation. The OFL license remains at `assets/fonts/NotoColorEmoji-LICENSE`.

## Routing, normalization, and clipping

The routing order is: primary-font coverage remains first; for text not covered by the primary font, the last explicit VS15/VS16 selector wins; otherwise Unicode `Emoji_Presentation` enters the color-emoji route; otherwise default-text emoji characters and characters in the terminal symbol block select Segoe UI Symbol; everything else uses the terminal monospace family. ASCII keycap components remain terminal text unless a selector requests emoji. Thus `☂️` is color, `☂︎` is monochrome, and ambiguous `☆`/`│` remain monochrome text. The non-primary presentation classification is a pure deterministic function of `text`; primary coverage, VS15/TextSymbol behavior, and `☆` normalization are unchanged from `381e069`.

## 混合路由

进入 ColorEmoji 分支后，渲染器先用 `Segoe UI Emoji` 对整簇做一次候选 shape。只有候选结果实际来自 Segoe、恰好包含一个 glyph、`glyph_id != 0`，并且 swash 光栅结果为 `SwashContent::Color`，才采用该候选；任一条件不满足便用内嵌的 `Noto Color Emoji` 重新 shape。因而本机的 `👍🏽`、`☂️` 使用 Windows 原生 Fluent 风格，而国旗和 Segoe 不支持的 ZWJ 组合（如 `🇺🇸`、`👨‍👩‍👧‍👦`）仍使用 Noto 的单个彩色 glyph。

`seguiemj.ttf` 仍以可选文件方式加载。若系统没有 Segoe UI Emoji，字体数据库探测失败后会直接让所有 ColorEmoji 簇走 Noto，不做候选 shape、不 panic，整体行为退化为 `381e069`。这是有意的可移植性边界：Noto 仍是随程序内嵌且始终可用的正确性后备。

候选决定和最终 Buffer 一起放入按 `(text, bold, italic)` 建键的整形缓存。命中只复用缓存 Buffer，既不重复字体可用性查询，也不重复候选 shape 或光栅探测；DPI/字号变化会清空缓存。miss 的额外代价仅限 ColorEmoji：Segoe 可用时至多多一次 Segoe 整形和一次 glyph 光栅检查；候选通过时该 Buffer 直接成为最终结果，没有第二次 Segoe 整形；候选失败时再做原有的 Noto 整形。系统没有 Segoe 时只做轻量的字体库可用性检查，随后成本与全 Noto 基线相同。窄/宽缓存分别有 1024/256 个 LRU 条目，颜色和网格位置不进入键。

已知观感是同一行可能出现风格混搭：Fluent 的人物或物件会邻着 Google/Noto 风格的旗帜或复杂家庭组合。这是“原生 Segoe 优先、覆盖缺口由 Noto 补齐”的预期取舍，不代表颜色或占格退化。

Wide glyphs retain M1's two-cell slot: cosmic-text receives a two-cell monospace em target and glyphon clips the `TextArea` to exactly those two cells. In mode 2027 the four acceptance emoji sequences each occupy one two-cell lead/spacer pair. Legacy continues to obey its scalar grid accounting.

For a narrow slot, the first shape pass records the actual layout font IDs and raster ink/advance span. Normalization is allowed only when every visible glyph resolves away from the primary Consolas family; any primary-font glyph leaves the entire slot at its natural em, preserving italic and accent bearings. A fallback slot whose ink or advance exceeds one cell is reshaped at a proportional em that fits inside the cell with a 5% (minimum one physical pixel) side bearing, then baseline-aligned as before. Narrow text remains row-clipped rather than cell-clipped; containment comes from em normalization, while primary-font overhang remains possible.

The fallback scale is not a separate cache-key input. For a live renderer, `(text, bold, italic)`, the fixed database, and current metrics determine both font IDs and scale; DPI/font-size changes already clear the cache. Color and grid column still do not affect shaping.

## Automated and visual acceptance

Renderer tests pin explicit routing, embedded Noto presence, optional Segoe degradation, the Segoe/Noto mixed-family decision, cache-hit probe suppression, nonzero single-glyph shaping, color versus mask raster content, the two-cell em, narrow fallback ink/advance containment, ambiguous width 1, and the unchanged primary italic em. The app test parses `glyph-probe-input.vt` and pins family/skin/flag/VS16 at two cells, VS15 at one, and `☆`/`│` at one cell each. Existing M1 flag/mixed rows and their fourteen-row direct-grid baseline remain unchanged.

For coordinator pixel review, follow `scripts/dev/glyph-probe-input.md`. The visual verdict remains: color is visible, bars align with rulers, the flag is the US flag, and `☆` ink does not cross its one-cell markers.
