# BetterTerminal UI/UX 设计

> 可交互原型：`design/ui-mockup.html`（浏览器打开即可）。
> 原型是**代码**，这份文档是**为什么**——决策的理由只活在这里。
> 需求编号见 `docs/PROBLEM-LIST.md`；架构见 `docs/DESIGN.md`。

## 一、定位

**行为层原生 Windows，视觉层自有风格。**

- **行为必须原生**（这层是肌肉记忆，不是审美）：标题栏可拖拽/双击最大化/右键系统菜单、Snap Layouts（悬停最大化键弹出的分屏面板）、DWM 圆角与阴影、窗口动画、任务栏预览、Alt+Tab。做好了用户感觉不到；做坏了每天硌手。
- **视觉自定义**（VS Code / Discord / Spotify 都是全自定义，用户完全接受）：**Typora / Notion 的极简干净风**。
- 度量沿用 Fluent（标题栏 40px、窗口控制键 46px、关闭键悬停变红）——**用户不陌生**，但配色和质感是我们自己的。

## 二、设计语言

| | 亮色 | 暗色 |
|---|---|---|
| 窗面 | `#FFFFFF` | `#202020` |
| 面板（标签条 / 侧栏 / 缝） | `#F7F7F5` | `#252525` |
| 终端底 | `#FFFFFF` | `#1B1B1B` |
| 墨色 | `#37352F`（Notion ink） | `rgba(255,255,255,.87)` |
| 主题色 / 提示符 | `#5E6AD2`（Linear 靛蓝） | `#828FFF` |

- **字体**：UI 用 **Inter**，终端用 **JetBrains Mono**（行距 1.55）。产品里字体**内嵌进二进制**，原型阶段走 CDN。
- **主题**：Light / Dark / **System**（跟随系统实时切换）。
- **绿色被否决**（老气）。语义色（红=错、琥珀=等待）与主题色分开，不算作 accent。

### 主题色只说"那边有事"，不说"你在这儿"

**accent = 注意力，不是位置。** 这条不是审美，是一次真实的冲突：未读圆点是 accent（意思是**"那边有事，快看"**），而聚焦窗口的头曾经也是 accent（意思是**"你已经在这儿了"**）——**同一行里，同一个蓝色同时说着两个相反的意思**，而这个产品的全部主题就是"决定该看哪儿"。改成中性之后，那一行里唯一的蓝色只剩未读点，眼睛直接被它抓走。

> **暗色先暴露它，但两个主题都病着**，只是响度不同：暗色的 accent 又亮又饱和，拿它染深底会**同时改明度和色相**，正好落进 Windows/VS Code"选中高亮"的语汇——那不是这套设计说的话。

**判据**：

| 用途 | 能不能用 accent | 为什么 |
|---|---|---|
| 未读 / 需要你处理 | **✓** | 这就是 accent 的意思 |
| 焦点环、拖拽落点预览、分隔条拖动 | **✓** | **转瞬即逝的交互反馈**，跟着你的手走，不是常驻状态，不参与扫视 |
| 聚焦的窗格 / 活动标签 / 当前项 | **✗ 用明度** | "你在这儿"，与"那边有事"抢同一个通道 |

**"你在这儿"一律用对比度台阶**。而且通常根本不用额外说——**活动标签已经和下方终端连成一体，那比任何颜色都清楚**；聚焦的窗格里有光标，那是终端四十年的答案，且就在你正在看的地方。

#### 聚焦的窗格：不填充。亮色下**没有位置可填**

试过三种填充，全部撞墙，这个过程本身就是结论：

| 试过 | 亮色下合成 | 为什么不行 |
|---|---|---|
| `--active`（通用"按下"色） | **237** | **比 `--panel`（247，这套设计拥有的最深表面）还深**。掉出色阶的色不属于任何梯级，铺在白色内容上就是一条脏灰带。 |
| `--panel`（色阶里已有的 chrome 灰） | 247 | **`--panel` 已经名花有主 = chrome**。窗格头正好长在真标题栏底下，两者粘成一片灰；**更糟的是活动标签本来是白的、要和下方终端连成一体，这么一改它连到的是一条灰带——圆角连体的设计被打断了。** |
| 247~255 之间 | — | 新造一个色阶值，为了一个次要信号 |

**亮色的色阶是 247→255,一共 8 级，而 247 已经被 chrome 占了。中间没有位置。** 所以：**不填充**。

> 感知校验（说明这从来不是"台阶大小"的问题）：亮色 ΔL\*=6.3、暗色 ΔL\*=9.9——**RGB 台阶几乎相同（18 / 21），但暗色那步在感知上更大**，而暗色恰恰是看着对的那个。差别在**落点**，不在**步长**。

**信号交给本来就在扛的那一半**：标题 `--ink3` → `--ink` + 字重 500（沿用侧栏活动标签已有的词汇），非聚焦窗格的图标标记降到 50% 不透明度（**透明度是独立通道**，不与 accent 或呼吸动效抢）。四方案对照图证明了这点：**即使底色几乎看不出差别，也能一眼分辨——信息层级本身就是信号。**

再说一遍那个更强的答案：**聚焦的窗格里有光标，其余没有。** 那是终端四十年的答案，且就在你正在打字的地方。

#### 提示条是我们的，不是系统的

**不用原生 `title=`**。那个框是浏览器画的，**它不遵守这里的任何东西**——不认主题、不认字体、不认圆角，还按平台自己的节奏出现在平台想放的地方。

- 用**挂在 `<body>` 上的 fixed 单例**，不用各自的 `::after`：伪元素会被任何祖先的 `overflow` 裁掉，而**最需要提示的东西（公式工具条、标签关闭键）恰恰都住在那种容器里**。
- 原生 `title` 在**首次悬停时**剥离，不在启动时扫一遍：`render()` 频繁重建 innerHTML，一次性扫描会在第一次重渲染后**悄悄失效，而且失效是看不见的**（系统提示会若无其事地回来）。懒剥离不会腐坏。
- 剥下来的文本**移进 `aria-label`**——`title` 本来在承担无障碍名称，直接丢掉是拿一个视觉瑕疵换一个真实的回归。
- **延迟 380ms**：提示条**真的**属于那条 300–500ms 规范说的情况——它盖在你正在读的内容之上，误触发的代价是挡住视线。（公式工具条相反：出现在空白处，误触发代价≈0，见 §7.6。）

#### 光标：**手要留，但只留食指那只**

**这是两只不同的手，只有一只是老的**：

| 光标 | 形状 | 判定 |
|---|---|---|
| `grab` / `grabbing` | **摊开的手掌 / 攥紧的拳** | **Maps 与 Photoshop 时代的语汇，不用** |
| `pointer` | **食指** | **留**——每个浏览器的标签条都用它，能被拿起来的东西**该在你伸手之前就说出来** |

可拖动的东西（标签、窗格头）用 `pointer`。**一开始砍掉全部小手是矫枉过正**：手本身是个有用的交互提示，古老的是那只手掌。

> **拖动期间必须把光标钉住**（`body.dragging * { cursor: pointer !important }`）：不钉的话，指针每划过一次终端就变 I 形、划过按钮又变回手，**一路上闪三种形状**。钉的是**你抓起它时的那只手**——拖到一半光标变形，等于在说"发生了什么事"，而并没有。

> 已按此清理的（同一个 bug 的三处）：`.pane.focused .panehead`、`.tab.active .panecount`（徽标只数窗格数，那是它唯一的意思，不该在活动标签上改说"你在这儿"）、`.mini-leaf.focused`（悬停预览里同样会出现未读点）。

## 三、窗口结构

```
┌─ 标题栏 40px ─────────────────────────────┐
│ [侧栏键] [标签…] [＋][⌄]      [⚙][─][□][✕] │   横向：标签嵌在标题栏里
├───────────────────────────────────────────┤
│ 侧栏 │  内容区（小窗的分屏树）             │
└───────────────────────────────────────────┘
```

- **没有 app 图标**。它长得像按钮却不可点，而横向模式下标签就在旁边、身份靠任务栏就够了（Chrome/Edge 同）。
- **面板灰 = chrome，白 = 内容。** 标题栏在两种标签布局下**都是 chrome**，不因为一个标签设置而变色（横向模式曾单独染灰，因为那里需要衬出白色的活动标签——但那是局部理由，不足以让同一块 chrome 两种颜色）。纵向模式下标题栏与侧栏连成一片灰，终端是白的。
- **profile 图标是「标记」不是字符**。等宽字符（`❯` `$` `%`）让每个 profile 长得一样重、一样黑，图标列不携带标题以外的任何信息；换成带品牌色的标记后，**认出 PowerShell 靠的是那块蓝，不是读字形**。标记内嵌绘制，不依赖 CDN——身份不该因为网络而消失。
- **⚙ 设置**放在窗口控制键左边，同样 46×40 的度量。

## 四、标签模型

### 两种模式（设置项 "Clicking a tab"，两者共存）

**标签 = 工作区，各自拥有一棵分屏树。** 两模式共用同一数据结构，**只有"点击标签"这一个行为不同**：

| 模式 | 点标签时 | 适合 |
|---|---|---|
| **Switch view**（默认） | 整个内容区换成那个标签的布局；每个标签保留自己的分屏 | Windows Terminal 的心智 |
| **Swap focused pane** | **只替换聚焦的那个小窗**；被顶掉的会话退回标签条，其他小窗不动 | 用户原本设想的；单窗时自然退化成普通切标签 |

**标签数 = 未并入的标签数 + 1**（那个 1 = 你当前所在的布局）。这是模型的自然结果，不是特例。

- 布局标签的**标题/图标跟随聚焦的小窗**（"点哪个窗就显示谁"）。
- **数量徽标两种模式都出现**——它是**标签的属性，不是模式的属性**。曾经在 swap 模式下藏起来，理由是"布局始终可见，数字是在告诉你已经看得见的事"——**那话只对活动标签成立，对其余每一个都是错的**：标签条里的标签照样持有整棵分屏树，而 swap 模式下点它会把那棵树整个塞进聚焦窗格。**"这个标签里有 3 个终端"恰恰是你点之前最该知道的，也恰恰是你唯一看不见的。**
- **切换标签永远不移动标签。** swap 模式下若活动标签只有**一个**窗格，"替换聚焦窗格"会退化成"两个标签互换内容"——**看上去就是两个标签在标签栏里换了位，而你只是切了个标签**。规格早就写了"单窗时自然退化成普通切标签"，代码没实现，已修。**标签条是肌肉记忆瞄准的地方，它的相对位置只能由你亲手拖动来改变。**
- **等宽标签**：各占等份、上限 200px、多了一起缩、下限 46px（图标+关闭键）。好处是**位置稳定**，肌肉记忆能记住"第二个标签在哪"，不会因为某个标题变长就全体移位。

### 纵向侧栏的三个状态

**收起 / 图标 / 展开**——注意前者与后两者是**正交的两个轴**：`railCollapsed`（用户按了收起）和 `railMode`（静止时长什么样）。把它们揉进一个条件会造出死区（见原则 12）。**在设置里挑"侧栏该怎么待着"本身就说明你想要它**，所以选图标模式会自动取消收起状态。

- **图标模式下没有收起按钮**——它已经是停靠状态了，再给一个收起键是让按钮声称能控制一个看不见的东西。
- **展开是长出来的，不是浮出来的。** 早期版本是一张四边内缩的卡片，它因此必须把自己声明成一个独立物件（自己的圆角、四面阴影），**那正是"割裂感"的来源**。现在标题栏在两种布局下都是面板灰，侧栏就是**同一种材质在共享边上与它相接**——两者读作"一块变宽了的 chrome"，只有面朝终端的那条边需要画（1px 边 + 只朝右的投影）。
- **展开不重排窗格**：图标模式下侧栏**全程脱离文档流**，终端固定留出 46px。停靠时占流、展开时脱流会让终端在展开那一刻凭空拿回 46px（原则 9）。

### 悬停看多窗标签里有什么

停留 350ms → 弹出**按真实分屏结构画的缩略图**（连拖过的比例都还原，聚焦窗有主题色框），**下面补一行完整名单**——因为窄窗在缩略图里名字会被截断，而你要的恰恰是看清是哪几个终端。

## 五、拖拽语法（一套，四条路径）

| 拖什么 | 拖到哪 | 结果 |
|---|---|---|
| 标签 | 小窗**边缘** | 该标签的布局**并入**那个位置，它的标签条目消失 |
| 标签 | 沿标签条 | **实时换位** |
| 小窗标题条 | 另一个小窗边缘 | 布局内**重排** |
| 小窗标题条 | 标签条 | 脱离布局、**变回独立标签**（落点跟随光标，任意位置可插） |

- **投放区**：**离哪条边最近就分哪边**，只要在该边外侧三分之一内就触发（不必拖到边缘）。正中间是**取消区**——总得有个"我不想分屏"的落点。
- **落点预览**：显示**标签本体**（带主题色描边的标签形状，写着图标和名字），就在它将要出现的位置；此时光标上的浮动幽灵自动隐藏——预览已经在标签条里了，再跟一个幽灵是重复。
- **递归分屏**：投放区相对于鼠标下的那个小窗算，可形成任意嵌套。**上限由最小可用尺寸（260×120px）决定，不是任意的窗口数上限**。
- **换位用中线交换规则**（进邻居 35% 就换），**不是重算插入位置**——后者会来回抖：换过去后布局变了、光标底下的标签也变了，插入位置算出来又想换回来。中线规则天然有迟滞。

## 六、分屏与调整

### 一行里的窗格是**平等的一行**

**新窗格加入某个同方向的"行/列"时，那一串重新等分。**

**旧行为不是任何人选的比例，是二叉树的形状漏进了界面**：三列出来是 539/269/269。而且它**会复利**——第四列变成 539/269/**134**/134，而 134 低于最小宽度，于是**几何形状把布局逼到没地方了，分割被拒**。等分之后：三列 359，再从外缘加第四列 → **269 四个全部可用**。

> **等分不只是眼睛期待的样子，它是换来下一个窗格的东西。**

**代价说清楚**：你手动拖过的比例，在有新窗格加入那一串时会被重新分配——**因为那一串已经不是原来那组窗格了**。(i3 / Zellij 这么做；tmux 不做，所以 tmux 才要你事后手敲 `even-horizontal`。)

**注意两个手势的区别**（它们现在都对，且含义不同）：

| 落点 | 含义 | 三列 359 时再放一个 |
|---|---|---|
| **某一列的边缘** | 把**那一列**劈成两半 | 359/2 = 179 < 260 → **拒绝**（对的：179 不是一个能用的终端） |
| **整体的外缘** | 给**这一行**再加一列 | 四列各 269 → **可用** |

### 拖动时分隔条静默

**拖动期间分隔条不亮。** 按住不放时"调整大小"根本不在选项里，而它偏偏用 **accent 发出这个邀请**——那正是拖动时"松手落这儿"的颜色。**于是指针底下唯一什么都不会发生的那条线，冒充了唯一会发生的那件事。**

- **静止时小窗完全贴合**，只有一条发丝线。
- **手按到分隔线上，两个小窗同时四周缩进 5px、圆角 8px、浮起阴影**——从"撑满自己那半边"变成"略小的圆角卡片"，缝是**窗缩小的结果**。松手闭合。
  > 这解决的是一个真实的知觉问题：一条共享的边界只能提供**一个**移动的东西，眼睛会转而抓住画面上真正在动的大色块（生长中那一侧），读成"谁盖住谁"。**两条边一进一退**，意图才可见。（Windows 贴靠调整就是这么做的。）
- **不做毛玻璃**。Windows 那个是**应用来不及重绘时的兜底**，不是设计意图。我们能实时重排，把内容糊掉反而让你看不见文字重新折行——而那正是调整分屏时你要看的东西。

## 七、富内容渲染（核心卖点）

**渲染是视图，不是替换。**（DESIGN.md 的"文本永远是真相"）

- 每个公式块**自带源码**。悬停出工具条：**Show source** 变回程序真正写的 `$$...$$`，**Copy LaTeX** 复制源码而非图片。
- **渲染失败就显示源码**，不是消失。排不出来的公式仍是可读的文本——这是诚实的兜底。
- **左对齐**。居中是文档的规矩，不是终端的（第一版居中，宽公式直接被裁）。org-mode 和 Distill 都主动反转了上游的居中默认值——`d-math.css` 全文只有两条规则，其一就是 `text-align: left`。
- 原型用**真 KaTeX**——所见即真渲染器会产出的东西。**这是引擎选型的质量基线**（spike 03）。

### 7.1 "这是渲染过的"怎么标记：**靠渲染本身**

**左竖线已删除，且不再加回来。** 竖线在它所有既有用法里（blockquote、markdown `>`、GitHub alerts、Obsidian embed）表达的都是同一件事：**这段内容的出处不是当前作者**。而渲染公式要说的恰好相反——**每一个字符都是程序说的，我们只改了呈现形式**。用竖线表达它是**语义反转**，不是语义扩展。而且等我们渲染 markdown 时 `>` 本身就是竖线，同一个图形在同一屏上会有两个互斥含义。

**不需要替代品**：一个用衬线数学字体、带真分数线的排版结果出现在 JetBrains Mono 的列里，**是 pty 另一端的任何程序都产不出的东西**。这个信号零墨水、100% 可靠、且完全诚实。Jupyter 就是这么干的——等宽 13px/1.3 ↔ 无衬线 14px/1.6，不加任何边框、背景、图标、徽标。

**若将来产品上一定要一个常驻显式标记：用 gutter，不要用 rule。** Jupyter 的 `Out[n]:` 模式（固定宽 + 右对齐 + `user-select:none` + 去饱和色）天然表达"输入/输出配对"，而且它在内容列之外，不与任何边界争夺语言。

### 7.2 一个区域只用一种语言说

**背景色块 = 用「面」界定区域；边框 = 用「线」界定区域。二者在知觉上是同一个操作**（Palmer 1992, *common region*，该因素强到可以压过邻近性和相似性）。所以"背景 + 边框 + 竖线"不是更清楚，是**对同一个感知单元下达三次冗余指令**——实测那条 1px 灰边框与 2px 靛蓝竖线之间**间距为 0**，合成一条 3px 的复合条纹，这就是"很不和谐"的物理来源。

> 冗余编码在别处是被推荐的，但**它的正当性条件是冗余通道彼此正交**（颜色+形状+文字）。边框/背景/竖线全在同一个通道上：区域界定。重复三次不增加鲁棒性，只增加噪声。

**规则：hover 只给背景，不给边框，不给竖线。** GitHub alerts 是这条判据的正例——它有竖线色 + 图标 + 文字标签（三个正交通道），但**只有一个区域界定手段**（完全没有 background）。

### 7.3 块贴合内容，不贴合窗口

**块 = `width: max-content`。** 全宽块的代价实测：一个 86px 的公式坐在 1040px 的框里——**91.7% 是空的**，hover 底色圈住的是一片虚空，工具条锚在离最后一个字符 **755px** 的右边缘上，而且**指着公式右边 900px 的空白也会弹出工具条**。收缩之后，右边缘变成内容的属性，三个问题一次消失。

### 7.4 垂直定位：贴合 TeX 盒，上下等距，**不做轴居中**

> **规则：块贴合 `[baseline − h, baseline + d]`，上下等距 8px。不做数学轴居中，不加光学偏置。**

**"公式偏上"是几何缺陷，不是视觉错觉**：终端的 `line-height: 1.55` 被继承进公式，给行盒设了 20.15px 的**地板**，而半行距是围绕**字体**的升降部对称分摊的，与这条公式真实的深度 d 无关。实测 `e^{i\pi}+1=0`：对称的 8px padding 渲染成了**上 9.6 / 下 14.3**。修法是 `line-height: 0`——**必须同时写在 `.katex-display` 和 `> .katex` 上**，行盒在 `.katex` 内部生成，只写外层无任何效果。修完全部收敛到 8/8。

**为什么不用数学轴**（axis height = 0.25em，`tex.web` 第 13832 行，KaTeX 内部用的是同一个常数）：轴的参考系是**数学行本身**，它保证 `\sum`、`\left(`、分数线与周围的数学对齐；而我们的问题参考系是**一个矩形**，眼睛在这里做的是"墨迹离上边框 vs 离下边框"的邻近性判断。**用轴去解矩形内边距问题，是把正确的工具用在错误的场合。** 实测三栏对照：轴居中让 `e^{iπ}` 顶到上边框、让 `\frac` 的分母压在下边框上——**恰好重演了要修的那个观感**。而且 TeX 已经替我们做完了轴的工作（`\frac`/`\sum`/`\int` 的 bbox 中心与轴仅差 0~3.1px）；**剩下的不对称来自上标下标，那是内容本身，不该被"修正"**。

> 光学中心上移 5% 的说法：量化来源全部是**招牌/裱框行业经验**，针对大幅面。外推到 35px 的小块，5% = 1.7px，无证据无收益。**k = 0。**

### 7.5 装不下的公式：**跟着"折行"设置走**

**这不是公式自己的开关，是终端的 `Line wrapping`（P2-9 / WT #1860，252👍 最高呼声）。公式的行为从它推导出来，不新增设置项。**

| 折行 | 长文本行 | 窗格 | 公式装不下时 |
|---|---|---|---|
| **开**（默认） | 在窗格边缘折 | **永远不会横向溢出** | **块自己滚**——除了它自己没人能滚它 |
| **关** | 一直延伸 | **本来就在横滚** | **块让位**（`overflow-x: visible`），公式**汇入窗格已有的那条滚动** |

**为什么必须这样分**：折行关的时候窗格已经有一条横滚条，块再给一条，**才是真正的"横滚套横滚"**——两条同轴的滚动条嵌在一起。**我最初担心的"嵌套滚动"在这个模式下是真的**（只是我当初把它安在了错误的模式上）。

> 实测校验：两个模式下 `bothScrollX` 都为 false——**任何时候都不会同时出现两条横滚条**。

**块默认完整显示，不给自己滚动条。**

> 这条推翻了先前的"让窗格横滚，一个滚动容器不是两个"。那个决定错了两次：
>
> 1. **"嵌套滚动会吃掉滚轮"只对纵向成立。** 一个**只能横滚**的盒子没有纵向溢出可吃，浏览器会把纵向滚轮直接冒泡给背后的终端（scroll chaining）。**实测**：光标停在能横滚的公式上、纵向滚轮 200 → 终端滚了 200，公式 `scrollLeft` 保持 0。我拿一个纵向的毛病否决了一个横向的方案。
> 2. **把滚动交给窗格有真代价。** 终端文本是折行的，**窗格永远不会因为文字而横向溢出**——那条横滚条会是**那一条公式独自造成的**，而拖动它会把满屏折好行的文字一起拽走，留下空白。

**所有先例都一致**：Typora `.md-math-container`、Notion `.notion-equation-block`、Obsidian `.math-block > mjx-container` —— **每一个都是块自己滚，没有一个滚页面**。三家一致是因为**没有别的选择**：KaTeX 设了 `white-space: nowrap`，而 TeX 不会自己折断一条 display 公式。

**唯一的纵向滚动**：设置里给内嵌块设的**最大高度**（默认无限制）。**你主动设了上限、内容又超了**，才滚——唯一一种"裁剪不意外"的情况，因为那是你自己要的。

> 工程注记（两条都会咬人）：
> - **垂直 padding 必须在滚动容器里面**，不能在外层。`overflow-x: auto` 会让 CSS 把 `overflow-y` 算成 `hidden`，而 **KaTeX 的 h/d 是排版度量、不是墨迹包围盒**——积分号的下限会画到它声明的深度之外约 2.7px。padding 在滚动容器内，这点墨迹落在 padding box 里是安全的；padding 在外层就会被剃掉。**Typora 的 `.md-math-container` 带着同样的 padding，正是同一个原因。**
> - **`width: max-content` 不受父级约束**，必须显式写 `max-width: 100%`；而且**flex 子项默认 `min-width: auto`，缩不到内容以下**——不写 `min-width: 0`，里面的滚动容器永远不会开始滚。

### 7.5c 【未决】自动折行 —— 这是**引擎选型的硬指标**，不是 CSS

你问的"或者合理地自动换行"是**更适合终端的那个答案**：终端是一个**窄的、处处折行的介质**，一条要横滚的公式会是**整个窗格里唯一一个你必须动手才能读完的东西**。

但**正确的数学折行是真功能，不是 CSS**：要在**顶层关系符**（`=`、`≤`）优先断开，其次是二元运算符（`+`、`−`），续行还要缩进对齐。这决定了它**是引擎的能力，不是我们能贴上去的**：

| 引擎 | 能否自动折行 |
|---|---|
| **KaTeX** | **不能**（`white-space: nowrap`，官方已知限制）→ 走 QuickJS+KaTeX 这条路就**继承这个残疾** |
| **MathJax** | 能（`linebreaks`） |
| **Typst** | 有自己的断行 |

**已加进 spike 03 的评估项**（`docs/prompts/codex-M-1-spikes.md`）。在引擎定案前，原型按横滚做——那也是三家参照物的做法。

> 工程注记：KaTeX 的 h/d 是**排版度量，不是墨迹包围盒**——字形 span 带着字体的完整降部，下标会挂在盒子外 ~4px（无墨迹），而积分号的 `−∞` 下限**真墨迹**又会超出 strut 声明的深度 2.7px。任何按 TeX 盒做的滚动容器都会因此长出幽灵滚动条。原型用 `overflow-y: clip` + 8px `overflow-clip-margin` 在源头切掉：**必须是 `clip` 不能是 `hidden`**（`hidden` 会让另一轴计算为 `auto`，正是要避免的横向滚动条，而 `visible + clip` 是合法组合），而宽裕的 clip-margin 保证**切掉的只可能是空白，永远不会是字形**。自研渲染器掌握自己的盒子，不需要这一条。

### 7.5b 【未决】块高要不要按终端行网格量化 —— 做 SourceMap 之前必须定

终端一行是 20.15px（13 × 1.55）。修完 line-height 后 euler 那条块高 33.4px = **1.66 行**——**公式块打破了终端的行网格**。

- **它不是 CSS 问题，是架构问题。** BetterTerminal 有 canonical transcript + SourceMap，而 **scrollback 本质是一个 cell 网格**；非整数行高的块会让渲染视图与文本模型的行对应关系失配（选区、锚点、搜索命中定位全都建在这个对应上）。
- **先例**：termtex 的做法是 `--display-rows 4` + 显式 `--cell-h 20`，**把 display math 量化到整数个终端行**。这是等宽网格内嵌变高内容的常见解法。
- 若采纳，规则是 `H = ceil((h + d + 2p) / rowHeight) × rowHeight`，**多出来的余量按 §7.4 等分**。
  > 注意：**只有在这种情况下，§7.4 否决掉的数学轴才重新有意义**——H 被外部固定时，才需要决定公式在这个盒子里的落点。轴解决不了"矩形内边距"，但能解决"给定盒高、公式落在哪"。
- **依赖 spike 03**：引擎必须能交出 h/d（见 `docs/prompts/codex-M-1-spikes.md` 任务 03 的一票否决项）。没有 h/d 就既做不了等距、也做不了量化。

**登记为 M2（块模型 + SourceMap）开工前的必答题**，不是可以顺手做的 CSS 调整。原型暂不实现。

### 7.6 工具条挂在公式右侧，不在头顶

**图标按钮，贴公式右缘，垂直居中。** 不用文字按钮：块收缩后短公式只有 ~108px 宽，而 "Show source" + "Copy LaTeX" 要 ~180px——**工具条比块还宽**。不挂头顶（Typora 的 `top:-16px`）：**文档里没问题，但终端行距只有 20px，悬挂标签会盖住上一行输出**。

**出现走 ≤0.1s 档，消失给 0.5s 宽限。** 那条 300–500ms 的延迟规范针对的是"在你正读的内容之上展开隐藏**内容**"，误触发代价高；而工具条出现在**空白处**，误触发代价≈0、延迟代价却很高（用户已经决定要操作了）。Notion 实测是 `transition: background 20ms`（≈无动画）。

**这些是「标签的状态」，不是「agent 的状态」**——报错来自 `cargo`/`git`/任何东西，问 y/n 的是 `apt`，要密码的是 `sudo`。

| 状态 | 怎么知道 | 诚实度 |
|---|---|---|

| 运行中 | OSC 133 C 来了、D 还没来 | ✅ |

| **失败·未读** | OSC 133 D，**退出码非 0** | ✅ 所以报错该独立成态 |
| **等你**（输入/权限） | ⚠️ **一般情况下无法知道** | 见下 |

**OSC 9;4 本身就带状态机**（`1`=进度值、`2`=错误、`3`=不确定、`4`=警告）——程序**已经在用一套标准词汇**跟终端说自己怎么样了，我们的状态直接映射，一个字都不用猜。

**"等你"这一态的诚实处理**：

- **一般程序**：判断 `apt` 是在问 y/n 还是只是在打印，只能读文本。这时"静默等你输入"看起来就是"运行中"——**因为那确实是我们知道的全部**。这不是缺陷，是诚实。
- **能配合的程序**（Claude Code）：它**主动告诉我们**（DESIGN 的"显式 side-channel 优先"），这时才亮"等你"——因为这不是猜，是它说的。

**"等我输入 = 未读"？一半同意**：共同点是"这个标签有事找你"，但**忽略的代价不同**——完成了没看损失为零；卡住没看，agent/下载**一直冻在那儿**。所以保留区分，但只在有可靠信号时才亮。

### 关于"读文本算不算启发式"（规范第一条的边界）

`CONVENTIONS.md` §1 禁启发式，但那条禁的是**明知有真相却抄近路**（`infer_removed_top` 猜被移除的行、字节嗅探绕过 VT 状态机——那些都有正确答案可查）。

**"这行是不是在问我 y/n"不存在协议真相**——`apt` 从不告诉终端"我在提问"。读文本是**唯一可能的机制**，它不是抄近路，它是唯一的路。DESIGN 的 P1 早就给它留了位置：信号优先级的**最后一档**，"规则数据文件化、可更新、**明确标注为最低可信度，UI 上不确定状态如实显示为不确定**"。

**所以规矩不是"不许猜"，是"猜完要老实承认自己在猜"。**

## 十、交互原则（做出来的，不是想出来的）

这些是原型迭代中**踩出来**的，每条都对应一个真实的 bug：

1. **悬停展开的东西，展开后的范围必须完整包含触发它的范围。** 否则触发器会从光标底下溜走 → 关 → 又碰到 → 开 → 每秒几十次抖动。（图标侧栏内缩 6px 就是这么炸的。CSS `:hover` 表达不了"离得近就别关"，得用带**滞回**的区域：靠近 54px 开，离开 232px 才关。→ 更根本的说法：`:hover` 只能说"光标在这个元素上"，而我们要说的是"**光标还在跟这个元素打交道**"，两者在每一条边上都不一样。）
2. **一组相互咬合的几何量，必须由同一个变量导出。** 标签圆角 / 间距 / 邻居填充内缩三者各写各的 → 圆角压在邻居高光上。现在 `--tabr` 一个变量导出全部。
3. **弄清是谁盖住了谁，再决定改什么。** 上面那个"圆角伸进邻居"其实是**圆角被邻居盖住**（DOM 里邻居在后面，后画的压先画的）。让活动标签浮上来（z-index）就好了——不需要内缩，不需要撑开缝，代码还更少。
4. **`display` 不能动画。** 侧栏展开时标题用 `display:none/revert` 切换 → 面板还在滑，文字和图标位置已经瞬间跳完。改用透明度，**两个状态的布局完全一样**，图标全程不动。
5. **布局动画用 FLIP + 内层反向缩放。** 直接缩放 pane 会把里面的文字一起拉变形（200ms 的橡皮泥）。外层动画、内层反缩放 → 框在收拢，文字始终清晰。
6. **弹出层要对着「真正裁剪它的那个东西」算空间**，不是对着窗口。（设置里的下拉框：有滚动容器就算容器。）
7. **主体 = 默认动作，箭头 = 变体选择。** ＋ 开默认 profile，⌄ 选类型；横向纵向**同一个语义**，不许一处有一处没有。
8. **有疑问就实测，别读代码猜。** 原型每次改动都用 Playwright 跑一遍再交付——"标签跟随和 z-index 都对，唯独顺序纹丝不动"这类 bug，读代码是看不出来的（命中检测把手里的标签也算进去了，光标永远"在自己身上"）。
9. **同一个东西不能一半在文档流里、一半不在。** 图标侧栏停靠时占流、展开时转绝对定位 → 展开那一刻终端凭空拿回 46px，所有窗格往左弹——**恰好违背了那条规则自己注释里写的"展开不该让窗格重排"**。要么全程占流，要么全程脱流+给它留位置。
10. **"觉得偏了"先量，再谈审美。** 公式在框里偏上被当成视觉权重问题讨论了很久，实测发现是继承来的 `line-height` 给行盒设了地板、半行距按**字体**降部而非**内容**深度分摊——对称的 8px padding 实际渲染成 9.6/14.3。**用户的眼睛是对的，我的归因是错的。** 能测的东西不要猜。
11. **一个视觉符号在产品里只能有一个含义。** 左竖线在 blockquote / markdown `>` / GitHub alerts 里都表示"出处在别处"，拿它标记"终端渲染的公式"是**说了事实的反面**——而且等我们渲染 markdown 时，`>` 就是竖线，同屏两义。**先查这个符号在生态里已经说了什么，再决定用不用它。**
12. **两个正交的状态不要挤进一个条件里。** `railCollapsed`（用户收起了）和 `railMode`（静止时长什么样）被 `&&` 揉成一个类，结果"收起状态下选图标模式"两条 CSS 都不生效——侧栏隐形，而那个收起按钮还杵在那儿声称能控制它。
13. **设置一个属性会牵动另一个。** `overflow` 在一个轴上非 `visible`，另一个轴的 `visible` 就会被 CSS 计算成 `auto`——于是"只想纵向裁一下"会静默地长出横向滚动条。（`clip` 是唯一能和 `visible` 配对的值。）
14. **拖拽换位比的是「两个东西」，不是「指针和一个东西」。** 标签换位一度用指针位置判定，那注定不稳：① 指针停在**你抓它的那个点**上，所以同一个标签**抓左边和抓右边行为完全不同**——阈值跟着你的握法跑；② 它让判定取决于"指针在哪"而非"标签在哪"，标签会被推过一个它视觉上还没够到的邻居。
    **改成比较两者的中心，稳定性来自几何本身，不需要任何模糊系数**：中心一越过就换，换完之后它的中心**按定义**已在邻居新中心的另一侧，反向条件除非你真的往回拖否则不可能成立。**滞回是几何给的，不是调出来的百分比。**
    并且要用 `offsetLeft` 而不是 `getBoundingClientRect()`：**rect 含 transform**，而每次换位后邻居都在 FLIP 动画里飞 160ms——rect 会告诉你"它此刻飞到哪了"，而不是"它的槽位在哪"。**offsetLeft 是布局量，动画骗不了它。**
    > 附带收获：早先那个"命中检测把手里的标签也算进去 → 光标永远在自己身上 → 永不换位"的 bug（原则 8），**根本不会在这个模型里存在**——它是指针式判定的衍生病。
