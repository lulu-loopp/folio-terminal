## 2. 骨架级差距(四条,建议逐条补裁后再开工)

### 2.1 G1 — 活网格展平让「行」成为「列」的函数,而方案明文禁止两轴混用

**方案原文**(§2 渲染侧换算全名单):

> **列走 `ContentColumn→ViewportColumn`;行走既有的纵向映射,与横轴转换无涉**,两轴不得混用一个转换。

同一份方案又把光标、IME 候选窗、preedit 折行列进「必须做横向换算」的名单(§2),而光标与 IME 只存在于**活网格**。
换句话说:方案要求活网格参与横向取景。活网格参与横向取景,就必须先把它的 WRAPLINE 行展平——否则 `x_origin`
在活平面上滚过的就是网格宽度以外的空无(这正是 §7.1.6g ② 对整个横滚的原始否决理由)。

**现状**(展平活网格会撞上的、方案一个字都没写的纵向契约):

- `continuous_frame` 要求 `live_rows.len()` 恰等于 PTY 行数,否则 `FrameProjectionError::RowCount`(`bt-viewport/src/lib.rs:1946`)。
- `ViewportFrame::grid_rows` 的定义是「PTY 网格高度」,`validate_shape` 拒绝 `rows < grid_rows`(`:528`)。
- `FrameVisualRow::live_grid_row: Option<u32>`(`:240`)是**一对一**的呈现行→网格行。
- `ViewportFrame::live_point_at(row, column)`(`:700`)读 `row_map[row].live_grid_row`,**列原样透传**;
  它的唯一调用者 `live_viewport_mouse_hit`(`bt-app/src/main.rs:10398`)也把 `column` 原样交给协议编码
  (`bt-app/src/input.rs:70` / `:103`)。这正是 Codex 一轮点名的泄漏点(方案里记作 `main.rs:6902→7001`)。
- `MathBlockAnchor::Live { band_start_row, band_end_row }`(`:357`)与 `occluded_visible_rows: Vec<(u32, Vec<(u32,u32)>)>`
  (`:422`)都以**网格行**+列区间记账,`validate_shape` 在 `:566`–`:589` 校验它。

一条跨 3 个网格行的活逻辑行展平后是 **1 个呈现行**。于是:

1. 呈现行数 < `grid_rows`,`validate_shape` 直接拒;
2. `live_grid_row` 从「一个行号」变成「一段行号」,而**具体是哪一个由内容列决定**:
   `grid_row = first_grid_row + content_column / viewport_columns`。这就是「行成为列的函数」;
3. `live_point_at` 必须同时产出网格行**和**网格列(今天它连列都不产出),鼠标上报因此是一次**两轴耦合**换算,
   而不是方案说的「列走横轴、行走纵轴」;
4. 活公式块的 band 记账、遮挡记账、光标行、选择跨行,全部跟着变。

**判**:方案的 §1a 契约只定义了横轴,而它自己要求的活平面展平必然改写纵轴契约;四轮审阅只核对了措辞,没有人核对这一条。
这是**方案的内部矛盾**,不是仓库漂移。

**建议改法(供裁决,二选一)**:

- **A. 台阶一只展平冻结+staging 两个平面,活带保持逐网格行。** 契约不动,代价是活带顶部与其上的历史之间出现一道
  「上面展平、下面还折」的可见接缝,且正在打印的长行要等它滚进历史才展平。需要产品裁决这道接缝可不可接受。
- **B. 台阶一同时展平活带,并在 §1a 里补一条纵向契约**:`FrameVisualRow::live_grid_row` 由 `Option<u32>` 变为
  `Option<LiveRowSpan { first: u32, count: u32 }>`,`live_point_at` 改签名为 `(ViewportRow, ContentColumn) -> GridPoint`,
  `grid_rows` 与 `rows` 的关系由「呈现行 ≥ 网格行」改为「呈现行 ≤ 网格行,且两者由 row_map 显式桥接」。
  活公式块 band、遮挡、选择的行区间一并改读 span。**这是一条实打实的新契约,应当由 Codex 复审后再写进 §1a。**

我不替这条做主:A 是产品裁决,B 是架构裁决,两者都超出「照方案施工」的授权。

### 2.2 G2 — 每逻辑行的横向索引今天没有户口也没有预算(与今天落地的淘汰模型相撞)

**方案原文**(§1b):

> 每条逻辑行缓存累计 cell-width checkpoint,`x_origin` 二分定位首个可见 grapheme

**现状**(方案定稿后 5 天落地,今天):

- `TranscriptStore` 的 doc 是「**The only owner and quota authority for frozen terminal history**」(`bt-transcript/src/lib.rs:821`);
- 行数配额之下多了一层**由行数推导的字节顶**:`FROZEN_BYTES_PER_LINE = 2048`(`:50`),
  `frozen_byte_budget() = frozen_quota × 2048`(`:897`),`frozen_bytes` 是每次 push/pop 维护的滚动和(`:839`、`:886`),
  `enforce_frozen_limits`(`:1195`)取行数溢出与字节溢出的大者交给 `evict_oldest`;
- `resident_bytes`(`:763`)是这条顶的算术本身,它的 doc 明写贵的大头是 `text` 与**每 grapheme 一枚 u32 的 `grapheme_boundaries`**
  ——4,000 列的行是 4,000 + 16,004 字节,这正是「32 倍而不是 50 倍」的成因,也是这条顶被造出来的直接原因
  (DESIGN §7.1.6g ③:一个 pane 一分钟吃 2 GB)。

**冲突**:一枚**每 grapheme 的**累计宽度 checkpoint 就是又一枚 u32/grapheme,即把今天字节顶要压的那个主导项**再翻一倍**。
方案写这条时,这条顶还不存在。而且方案没说这块索引**归谁所有**:

- 放进 `FrozenLine` → 必须进 `resident_bytes`,等于把读者选的 `Scrollback` 容量凭空砍掉近一半;
- 放进 `ViewportProjection` → 那里确有每行缓存的先例(`cache: HashMap<LayoutCacheKey, MeasuredLayout>`,`lib.rs:1394`),
  但那是**每行 O(1)**(12 字节)的先例,不是每行 O(行长) 的先例;而且它必须自己处理 `take_evictions`(`:1002`)、
  tombstone 与 `SourceGeneration` 的失效,今天没有任何一条这样的通路。

**建议改法(供裁决)**:

1. checkpoint **稀疏化**:每 `S` 个 grapheme 一枚(S 取 64 量级),二分到块再块内线扫。摊销后仍是 O(视口),
   而每行增量降到 `4 × ceil(len/S)` 字节(4,000 列的行由 +16 KB 降到 +250 B)。这一步是纯工程,不改方案骨架;
2. 户口二选一,需明裁:(a) 进 `FrozenLine` 并**计入 `resident_bytes`**,同时 DESIGN §7.1.6g ③ 的「2 KiB/行」
   要么重量要么明写「展平模式下每行贵 X%」;(b) 留在投影侧,但必须新增一条随 `take_evictions`/tombstone/
   `SourceGeneration` 失效的通路,并自带**独立的字节上限**——否则就是在刚刚被封死的那个洞旁边开第二个。

### 2.3 G3 — `content_extent` 的定义域与维护方式未定,而它直接骑在今天的淘汰模型上

**方案原文**(§1a):`HorizontalProjection { content_extent, viewport_columns, x_origin }`。

**现状**:方案从头到尾没说 `content_extent` 是**谁的**最大宽度——整份冻结历史?当前可见的若干逻辑行?一个 pane 的一生?

三种取法的后果完全不同:

- 取**整份历史的最大宽度**:横条的行程由历史里最宽的那一行钉死。一条十万 grapheme 的行会把横条压成一根针,
  直到它被淘汰;而它被淘汰的那一刻,`content_extent` 需要重算——`evict_oldest` 今天不知道任何横向事实,
  重算就是 O(历史) 全扫,除非另建一个宽度的多重集/计数器,**又是一份要进字节账的每行结构**(与 G2 同源);
- 取**可见窗口内的最大宽度**:横条的行程会随竖向滚动跳变,读者手里的滑块会自己变长变短;
- 取**每逻辑行各自的宽度**(即横向取景是逐行的):横条语义从「一个 pane 的横轴」变成「当前行的横轴」,
  这与方案「pane 级显示能力」的定位冲突,也与竖条语言不对称。

**判**:这是契约里一个**已命名但未定义**的字段,而它的每一种定义都要么改动淘汰路径、要么改动横条语义。
不能由施工者顺手选一个。

**建议**:方案补写 `content_extent` 的定义域;若取整份历史,则同时裁决它在 `evict_oldest` 上的维护方式,
并与 G2 的户口一并计账。

### 2.4 G4 — §7.1.5f–k 划线体系晚于方案落地,它的两道判据在展平后**不存在**

划线体系(§7.1.5f–k,2026-08-21/23)在方案定稿后长进了 `layout_frozen_line` 的正中央。两条硬碰硬:

**(a) §7.1.5k ① 末列截断门的判据是「物理行的最后一格」,展平后这一格不存在。**

- DESIGN §7.1.5k ① 原文:「候选触到**物理行最后一个 visual cell** = `edge-suspect`,压住不画」,
  理由是「刚好写满一行的完整引用」与「被程序切成两半的前半截」**在一行之内是同一张图**;
- 实现是 `frozen_line_end_cell(line, columns)`(`bt-viewport/src/lib.rs:4302`):它**按当前 pane 宽重放折行**,
  只对**最后一行**判「是否恰好写满 `columns`」,doc 明写「上面每一行都是这一层已经重接过的软折,门绝不能看见它们」;
- 展平后,布局宽度是 `content_extent` 而不是 pane 宽,「恰好写满」这个条件对某一条随机的最宽行成立、对其余行永假。
  这道门要么全程哑火,要么在错误的行上开火。

正确的判据在数据里但没被读:`FrozenLine::fragments: Vec<PhysicalFragment { byte_start, byte_end, soft_wrapped }>`
(`bt-transcript/src/lib.rs:728`、`:742`)记着**捕获当时**的物理边界。但 fragment 只记字节范围与是否软折,
**不记当时的宽度**,而门问的恰恰是「最后一格是不是当时的最后一列」。所以展平路线要么给 fragment 补一个捕获宽度,
要么改由 `soft_wrapped == false && 该 fragment 的 cell 宽度 == 捕获宽度` 判定——**两种都是对一条 2026-08-23 裁决的语义改写**,
不是改名。

**(b) 链接身份今天是从帧格子里重建的,而帧格子将被横向裁切。**

- `hyperlink_at`(`:731`)→ `link_span`(`:758`)→ `link_group_run`(`:794`)→ `rejoined_across_break`(`:877`)
  这条链在 `self.cells` 上左右游走,`run_label`(`:928`)直接**读格子的文字**去比对目标;
- §7.1.5h ① 的立论原话就在 `implicit_hyperlinks` 的 doc 里(`:3896` 附近):只读一个可见行会把
  `…> https://support.cla` 解析成一个**别人拥有的合法主机**——「点击去了读者从没打过的地方」,2026-08-20 才修掉;
- 横向窗口是**同一刀**。只要链接推断/重接在窗口上跑,这个 bug 就原样复活。

好消息:`HyperlinkHit::uri` 取自格子上已经盖好的 `CellHyperlink::uri`(`:741`),不是现场重解析,所以**只要推断仍在整行上跑**,
目标就不会错——错的只是 run 的两端(哪些格子亮、hit 的 start/end 锚点)。这与方案「链接 run 的归属以内容坐标为准而非可见范围」
是同一句话。

**判**:(b) 是一条**必须写死不许绕的红线**(链接与路径推断永远在整条逻辑行上跑,首次建索引时 O(行长),
绝不允许为了帧预算改到窗口上跑),它与方案自洽,可以直接写进实现单;
**(a) 是真的要补裁**——它改的是一条四天前刚定的划线裁决的判据。

另外两条属于同一族、可在实现单内解决但必须明说的:

- `PrintedPathPass` 的探询副作用(`:1482`–`:1494`,每帧 256 个上限,`main.rs` 侧有 worker 回填)必须跟着「整行一次」走,
  否则读者横滚到的路径要等一次探询往返才亮;
- `layout_frozen_line` 的入参今天带 `Option<&mut PrintedPathPass>`,`None` 表示「只要行数」(`:4332` doc)。
  展平后行数恒为 1,这条快路径的存在理由消失,`frozen_visual_line_count`(`:4250`)整个退化——是化简,不是障碍。
