# One Folio driving another — research for 0.4

2026-09-10. Branch `docs/remote-research` off `main` at `c9f25c6`. This is
research, not a design: no product code is touched, nothing is built, nothing is
launched, and nothing here is decided. Every claim about this codebase carries a
`path:line`; every claim about another product carries a source, and the list is
§10.

The order is ruled — **0.4 = remote**, **0.5 = the macOS GUI port**. One Folio
drives shells and agents that live on another machine, sees their history, and
puts the files column and the previews on the remote disk: *as if one computer
were using another*. Two things asked for earlier fold into it — an agent
session that survives the client closing, and a second computer attaching to the
same history and taking over.

The framing given with the ticket was: a headless Folio **server** on the remote
owns the PTYs, the terminal model, the transcript and file access; the local
Folio opens a **remote tab**; rendering, mouse, IME and clipboard stay local;
the transport is SSH. **This document confirms it, and refines the one clause
that decides everything else: the server owns a *canonical* terminal — headless,
metrics-free, the authority for terminal replies, pty size and the checkpoint an
attaching client is given — while the *presentation* model, with reflow,
detection, inline images, typeset math and layout, stays on the client and is
fed the session's original bytes.** §3 is the evidence, §8.2 is the shape, and
§9's first three questions are what the owner has to rule on.

## 0. The short answer, before the evidence

> **Revised 2026-09-10, after an independent read-only review (Codex,
> gpt-6-astra, 18 findings, 8 blockers).** The review's central objection is
> upheld and this document's recommendation has changed: **the first version of
> this document said the server must own no terminal state at all, and that was
> wrong.** Every one of the review's twenty-seven code citations was checked
> against the tree and every one holds. §3 now says what the evidence actually
> supports, §8 is rebuilt around a two-model split, and §9 is rewritten. The
> places where the review is answered rather than accepted are marked
> **[reviewed]** and carry their own evidence.

Six facts decide the shape of this work.

**The server is nearly free, and the port is not.** `bt-platform` is the only
crate carrying a Windows-only dependency row, and its library has no
dependencies at all off Windows; `bt-pty` is already a unix crate. What blocks
macOS is the 79 `bt_platform` entry points `bt-app` calls for a window, a
compositor, a web host and pickers
(`docs/plans/port/macos-spike-2026-09-07.md:47-49`). **A server has no window**,
so it needs none of that (§1, §2).

**Two terminal models, not one, and not zero.** The *presentation* model —
Folio's `DualPlaneSession` as `bt-app` builds it — is welded to the renderer:
`create_leaf_session` opens `renderer: &WindowRenderer, body:
bt_render::SeatViewport` (`crates/bt-app/src/main.rs:30560-30561`) and sets cell
height, cell width and ASCII baseline in subpixels before the session sees a
byte (`main.rs:30778-30780`). That model must stay on the client. But a
*canonical* one need not: `DualPlaneSession::new(columns, rows)`
(`crates/bt-term/src/session.rs:1530`) already constructs a session from a
constant, `SPIKE_CELL_HEIGHT_SUBPIXELS`, and no renderer at all. The first draft
of this document read the first fact as forbidding the second. It does not
(§3).

**And the server needs the canonical one for three things it cannot fake.** A
detached session must answer `CSI 6n`, `CSI c` and colour queries or the program
asking them hangs — today those replies are minted in `bt-term` and written back
by the client (`main.rs:32305, 32340`). An attaching client must be handed a
*checkpoint*, because a retained suffix of a byte stream cannot reconstruct a
terminal: the scrollback setting is in **lines** (`bt-persist/src/settings.rs:829`),
and a byte cut can land inside an escape sequence or after the alternate-screen
entry that gives the following bytes their meaning
(`vendor/alacritty_terminal/src/term/mod.rs:1111`). And the pty has exactly one
size, so somebody has to own it (§3.4, §8.2).

**The byte stream is still what crosses, and the client still parses it.** The
client receives the session's original bytes and feeds them to its own
`DualPlaneSession` exactly as it feeds a local pty today — so detection, marks,
reflow, inline images, typeset math and the whole rendering pipeline are
unchanged code. This is tmux's shape, not WezTerm's: WezTerm ships rendered
delta state and its client is a proxy with no model of its own [S1][S2]; tmux
owns a canonical terminal and hands its client bytes, which is why iTerm2 can
build native scrollback, selection and search over it [S7][S8].

**The journal is new work, honestly budgeted. [reviewed]** The first draft
claimed the live recorder already writes `bt-corpus`'s `BTCRP002` format. It
does not: `bt-pty`'s recorder writes **raw bytes** to one file and a **textual
sidecar** (`# BT_PTY_DUMP_CHUNKS_V1 sequence elapsed_us bytes`, and `# RESIZE
<cols> <rows> <us>`) to another (`crates/bt-pty/src/lib.rs:182-184, 219, 250`),
with no exit status and no crash-tail rule. And `bt-corpus`'s decoder allocates
straight from file-supplied lengths and counts
(`crates/bt-corpus/src/lib.rs:103, 115, 123`) — the WezTerm CVE-shaped bug
[S25], and a decoder that must never be pointed at hostile data. What survives
is the *shape*, which is proven and portable: timestamped `Output` / `Resize` /
`Exit` with a deterministic reader. The journal itself is a ticket (§8.8 T3).

**The transport should open no socket.** `crates/bt-platform/src/http.rs` is the
only network code in the tree and is a WinHTTP wrapper for one `GET`
(`docs/DESIGN.md:6911, 6915`); there is no async runtime and no TCP anywhere.
Spawning `ssh` and framing its stdio leaves that record intact. **But not with
`ControlMaster`: Windows OpenSSH lists "Client ControlMaster" as out of scope
[S31]**, which is the platform the client runs on, so Folio multiplexes its own
sessions inside its own framing over one long-lived `ssh.exe` per host (§8.3).

## 2. The PTY layer

**The vendored `portable-pty` still carries its Unix backend, intact.**
`vendor/conpty/portable-pty/src/` holds `cmdbuilder.rs`, `lib.rs`, `serial.rs`,
**`unix.rs`** — 414 lines of `UnixPtySystem` over `libc::openpty` — and `win/`.
`unix.rs` is declared `#[cfg(unix)] pub mod unix;` at
`vendor/conpty/portable-pty/src/lib.rs:54`. In its `Cargo.toml`, `libc`, `nix`
(features `term`, `fs`), `filedescriptor`, `anyhow`, `log`, `serial2` and
`shell-words` are unconditional `[dependencies]`; only `bitflags`,
`lazy_static`, `shared_library`, `winapi` and `winreg` sit under
`[target."cfg(windows)".dependencies]`. **Enabling the Unix backend takes
nothing at all** — it is already enabled by `cfg`, and
`docs/plans/port/macos-spike-2026-09-07.md:121-124` says so in as many words.
`vendor/conpty/portable-pty/CHANGES-FOLIO.md` records that every Folio change to
this tree is Windows-only: the ConPTY sidecar loader, a job object with
`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` around each child, a registry-string NUL
fix, and the environment-block grammar guard in `cmdbuilder.rs`. One pleasing
coincidence, worth stating once: `portable-pty` is Wez Furlong's crate, and
WezTerm's own multiplexer is built on it. Folio has already vendored the PTY
layer of the closest prior art.

**`bt-pty` is already a unix crate.** It calls
`portable_pty::native_pty_system()` and never names ConPTY directly. Twelve
`#[cfg(windows)]` sites (`crates/bt-pty/src/lib.rs:29, 46, 658, 1128, 1363,
1449, 2994, 3037, 3062, 3095, 3304, 3385`); the last six are tests, and every
one of the first six already has a `#[cfg(not(windows))]` arm beside it:
`ConPtySource::NotWindows` (`:32-44`), `conpty_source()` (`:51`),
`environment_key_eq` (`:663`), `quoted_for_cmd` — whose comment reads "so that
this module goes on compiling off Windows" (`:1144`) — the interpreter-line
application inside `spawn` (`:1363`), and `clear_host_buffer`, which answers
`Ok(false)` off Windows and documents that as not an error (`:1455`). Its
public API is the exact surface a server needs and nothing more: `PtyCommand`
(`:511`) with `new`/`arg`/`working_directory`/`env` (`:525-559`),
`PtySession::spawn` (`:1340`), `write` (`:1412`), `resize` (`:1421`),
`read_output` (`:1472`), `try_wait` (`:1502`), `shutdown` (`:1516`). Its Cargo
dependencies are `bt-term`, `bt-transcript`, `portable-pty`, `thiserror`; none
is Windows-only.

**One thing in it is genuinely Windows policy and a server has to answer it:**
the default shell. `crates/bt-pty/src/shell.rs:96` `resolve_default_shell`
implements the 2026-08-04 ruling — `BT_SHELL` wins, else `pwsh.exe` if the probe
finds one, else `powershell.exe`. On a Linux or macOS server the equivalent is
`$SHELL`, then the login shell from the password database, then `/bin/sh`. That
is a ticket (§8.8 T2), not a research question.

## 3. Two terminal models — which one goes where

The first draft of this document argued that the terminal model cannot leave the
client at all. The review's first blocker is that the argument proves something
narrower than it claimed, and it is right. Here is what the evidence actually
supports.

### 3.1 What is welded to the renderer is `bt-app`'s call site, not `bt-term`

`create_leaf_session` (`crates/bt-app/src/main.rs:30560`) takes
`renderer: &WindowRenderer` and `body: bt_render::SeatViewport` as its first two
parameters (`:30560-30561`), derives the grid from
`renderer.metrics().grid_for_pixels(body.width, body.height)` (`:30591`),
constructs the session with `renderer.metrics().cell_height_subpixels()`
(`:30778`), and immediately sets `cell_width_subpixels(renderer.metrics())` and
`ascii_baseline_subpixels()` (`:30779-30780`) plus `MathLayoutOptions` derived
from the same metrics (`:30781-30784`). `bt-doc` exports `SUBPIXELS_PER_PX` for
the purpose.

**But `bt-term` offers a constructor with no renderer in it.**
`DualPlaneSession::new(columns, rows)` (`crates/bt-term/src/session.rs:1530`)
calls `with_cell_height(columns, rows, SPIKE_CELL_HEIGHT_SUBPIXELS)` — a
constant. The metrics are a *product* decision made by the caller, not a
structural requirement of the type. **[reviewed]**

So the honest division is not "model on the client, bytes on the server". It is:

* **The presentation model stays on the client**, and it must, because
  everything the metrics feed is a question about *this window*: where an inline
  image sits in the grid, how tall a display-math band is, how a long line
  reflows at this pane's width, and which detection blocks that reflow produces.
  Two clients on one session have two fonts, two DPIs and two widths, and there
  is no single right answer for them.
* **A canonical model belongs on the server**, metrics-free, with inline images
  and math off, because §3.4 lists three jobs nothing else can do.

### 3.2 Nothing below `bt-persist` derives `serde`, and the generations reset per session

A grep for `derive(...Serialize` across `crates/` hits `bt-app/src/update.rs`,
`bt-math/src/lib.rs` and every file under `bt-persist/src/`. It hits **nothing**
in `bt-term`, `bt-doc`, `bt-detect`, `bt-viewport` or `bt-transcript`; `serde`
is not in those crates' manifests at all.

The counters are per-*session*, not per-process: `grid_generation`
(`session.rs:1108`), `screen_revision` (`:1110`) and `view_generation` are set
to their starting values inside the constructor (`:1613-1615`), and
`DetectionRevision`, `GridGeneration`, `ViewGeneration`, `LayoutKey` and
`VersionStamp` are `Copy` newtypes over `u64` in
`crates/bt-doc/src/versions.rs`. **[reviewed]** — the review is right that this
does not preclude a wire representation or an epoch-qualified revision; it
prices one. The cost is real and it is the argument that stands: a checkpoint
schema has to be *designed and versioned*, and it must not be produced by
sprinkling derives on live types whose fields are internal
(`adapter.rs:220` holds an `Arc<dyn Fn(Rgb) -> String>`, `:252-254`
`Arc<Mutex<…>>` channels, `:364` a `RefCell` capture ring; `inline_image.rs`
holds `Arc<[u8]>` decoded pixels at `:98, 117, 132, 491`; `BoundedCache`
(`bt-term/src/bounded_cache.rs:83`) is documented single-thread-only at `:31`).
**A checkpoint is a declared document, not a struct dump** — §8.2.

`bt-pty` already depends on `bt-term` (`crates/bt-pty/Cargo.toml:10`), so a
server that links `bt-pty` links the canonical model whether or not it wants it.
That removes the last reason to keep it out.

### 3.3 Byte replay is not whole-pipeline replay, and must never claim to be

**[reviewed — accepted in full.]** `bt_corpus::replay`
(`crates/bt-corpus/src/lib.rs:146`) never reads `at_micros`; it plays events at
full speed. Three of the client's derived facts are timer-dependent and would
come out wrong:

* **Command durations.** `CommandMark::duration` (`command_marks.rs:185`) is the
  difference between `executed_at` (`:346`) and `finished_at` (`:392`), both
  supplied `Instant`s. Full-speed replay collapses every command to zero.
* **Detection stability.** Live math and block detection wait on
  `LIVE_MATH_STABLE_INTERVAL = 200 ms` (`session.rs:64`) advanced by
  `advance_live_stability(now)` (`:3471`).
* **Synchronized updates.** DEC 2026 commits on a client frame timer,
  `finish_synchronized_update_if_due(now)` (`main.rs:75716`), independently of
  when bytes arrive.

(`settling.rs:41`'s "the fade is never the state" is about presentation tweens
and was cited in the first draft as if it bore on semantic settling. It does
not.)

**The consequence is a rule, not a caveat.** Replay exists for one purpose —
reconstructing the canonical terminal inside the server, from its own journal,
after a crash — and it runs in **virtual time**: the journal's `at_micros` drive
the clock the canonical session is advanced with, timers fire in recorded order
relative to bytes, and worker completions are awaited rather than raced.
**Replay is never the attach path**, because attach gets a checkpoint (§8.2),
and it never reaches the client's pipeline at all. What a replay test asserts is
not "the same output bytes" but **the same terminal**: identical screen and
scrollback lines, identical modes and cursor, identical mark ledger, identical
cwd and title.

### 3.4 The three jobs a canonical server-side terminal is for

**① Answering the terminal's own questions while detached.** Today a `CSI 6n`,
a `CSI c` or an OSC 11 is parsed by `bt-term`, minted as a reply, and written
back to the pty by the client — `for reply in leaf.session.take_pty_writes()`
(`main.rs:32305` and `:32340`), the same door DSR, DA and colour answers all
leave by (`docs/DESIGN.md:1595`; `adapter.rs` tests DSR at `:2121`). With no
client attached and no parser on the far end, a program that asks waits until it
times out — and the programs most likely to be in these panes are exactly the
ones that ask. **[reviewed — this is the strongest argument in the review and
the first draft had no answer to it.]**

**② Handing an attaching client a bounded, correct starting point.**
**[reviewed — accepted; the first draft's Q3 was unsound.]** The first draft
proposed capping the journal by the pane's scrollback quota and trimming from
the front. Three things are wrong with that. The setting is
`scrollback_lines: u32` (`bt-persist/src/settings.rs:829`; the offered values
are 25k–200k **lines**, `bt-app/src/settings.rs:1007`), so a byte budget is not
the setting the user set. A cut at an arbitrary byte can land inside a UTF-8
sequence or inside an escape sequence. And even a cut at a clean sequence
boundary loses cursor position, every mode, the palette, the title, the cwd
(`session.rs:1158, 1306, 9208`) and — the case that decides it — the
alternate-screen entry (`swap_alt`, `vendor/alacritty_terminal/src/term/mod.rs:1111`)
without which the following bytes of a `vim` session mean something else
entirely. **A checkpoint produced by a live canonical terminal is the only
bounded thing that is also correct**, and it is what the server hands over.

**③ Owning the pty's size.** A pty has one size. `bt_corpus::replay` calls
`resize` for every recorded resize (`lib.rs:179`) and neither initialises from
the header nor touches a live pty, so replaying cursor-addressed output at a
different width changes what it says. **[reviewed — accepted.]** The canonical
session is the size authority; resizes are epoch-numbered; and bytes carry the
epoch they were produced under, so a client never reflows output that was
written for a different width (§8.2).

## 4. What already crosses a process boundary in this product

### 4.1 The attention wire, and the three rules it established

`crates/bt-app/src/attention_wire.rs` owns the grammar and
`crates/bt-platform/src/attention_pipe.rs` owns the kernel object; the split is
deliberate, because "the unsafe boundary should not have to be reopened to
change a field name" (`attention_wire.rs:3-5`). The message is one flat struct —
`attention_wire.rs:93` `Message { capability, family, event, id: Option<String>,
text: Option<String> }` — encoded at `:113`, decoded at `:135`, behind
`const WIRE_VERSION: u64 = 1` (`:108`). Three rules come out of it and **all
three transfer to a remote protocol unchanged**.

**A capability, not an address.** `FOLIO_PANE` says `<window>.<tab>.<seat>`, is
diagnostic, and is not in the message; what is in the message is 128 unguessable
bits minted when the pane was born (`attention_wire.rs:7-18`): "Coordinates can
be *guessed*, incremented, and walked… A capability cannot be walked, so a hook
that inherited one pane's environment can raise a hand for **that** pane and has
no way to name another — not because it is refused, but because it cannot say
the words."

**The payload never crosses** (`attention_wire.rs:20-27`): "the only things it
ever sends onward are the **two fields the mapping table declared**… Both are
bounded and checked; everything else in a payload stays in the hook process and
dies with it. That is not an optimisation: a channel that carried payloads would
be a channel worth attacking."

**Everything is bounded; failure is silent and counted.** `WAIT_TTL = 600s`
(`:77`), `INBOX_BOUND = 256` (`:84`), `MAX_QUOTED_CHARACTERS` (`:181`),
`MAX_PAYLOAD_BYTES = 64 KiB` (`:571`), `STDIN_BUDGET = 200 ms` (`:586`); and
below it `MAX_MESSAGE_BYTES = 4096` (`attention_pipe.rs:118`),
`MAX_FRAMES_PER_SECOND = 512` (`:135`), `MAX_INSTANCES = 4` (`:582`). The
six-clause security contract is written out at `docs/DESIGN.md:1606`. The pipe
itself refuses the network by construction (`PIPE_REJECT_REMOTE_CLIENTS`,
`attention_pipe.rs:14-16`), so the *transport* is not reusable and the
*discipline* is the part worth carrying.

There is also a shape precedent for how a server subcommand is reached.
`fn main()` (`crates/bt-app/src/main.rs:104350`) answers two doorbells before it
builds anything — `cli::attention(...)` at `:104369` and `cli::explorer_command`
at `:104379`, each exiting without a window, "because a `folio.exe` that built a
swap chain in order to write forty bytes down a pipe would be measurably the
slowest part of somebody else's program" (`main.rs:104363-104368`). A server is
that idea taken all the way: a process that never builds a window at all.

### 4.2 `bt-corpus` is the shape, and the shipped recorder is not it

**[reviewed — the first draft overstated this and the correction matters,
because a ticket was sized on it.]**

What exists and is right: `crates/bt-corpus/src/lib.rs` defines a framed binary
format — magic `BTCRP002`, initial columns and rows, an optional source string,
a count, then `CorpusEvent { at_micros: u64, kind }` where
`EventKind = Output(Vec<u8>) | Resize { cols, rows } | Exit { code }`
(`:10-32`), written by `write_to` (`:61`), read by `read_from` (`:92`), played
by `replay` (`:146`) with a choice of chunking (`:35-39`) so a byte boundary can
be moved without changing the result. It is on the portable-core list and CI
compiles it on macOS every push (`.github/workflows/ci.yml:412-418`). **The
vocabulary a session journal needs — output, resize, exit, with a timestamp — is
therefore already designed, already tested, and already portable.**

What does **not** exist, and was claimed in the first draft:

* **The live recorder does not write this format.** `bt-pty`'s `PtyDump` writes
  raw bytes to one file and a *textual* sidecar to another —
  `# BT_PTY_DUMP_CHUNKS_V1 sequence elapsed_us bytes` at
  `crates/bt-pty/src/lib.rs:184`, one line per chunk from `write_chunk` (`:219`),
  and `# RESIZE <cols> <rows> <us>` from `write_resize` (`:250`). There is no
  exit-status event; the end of the file is the end of the file.
* **The reader is not safe on hostile input.** `read_from` allocates
  `vec![0; len]` from an unchecked `u32` for the source string (`:103`),
  `Vec::with_capacity(event_count)` from an unchecked `u64` (`:115`), and
  `vec![0; len]` per output event (`:123`). This is precisely the WezTerm PDU
  bug [S25]. **`bt-corpus`'s decoder must not be pointed at anything a remote
  machine wrote**; the journal gets its own bounded reader, and the wire gets a
  third (§8.5).
* **A journal is not a recording.** It has to be appendable, crash-tail
  recoverable (a torn last record is discarded, not fatal), ordered so a resize
  cannot be observed before the bytes that preceded it, and carry the child's
  exit status. None of that is in the recorder today.

So the honest budget is: **the format's shape is free, the journal is a
medium-sized ticket** (§8.8 T3), and the decoder is written new with bounds
rather than reused.


### 4.3 The only socket in the tree

`docs/DESIGN.md:6911` records the state of the world when the update check was
built: no HTTP client in a lock file of 569 packages, and first-party code that
had never opened a socket. `crates/bt-platform/src/http.rs` is what was added,
and `docs/DESIGN.md:6915` calls it the product's only socket opened by this
process — deliberately *not* a client: no redirects, no keep-alive, no POST, no
body, no caller-supplied header, no `http://`. Its one caller is
`crates/bt-app/src/update.rs:378`. A fresh grep confirms it is still the only
one: `tokio`, `reqwest`, `ureq`, `hyper`, `TcpStream`, `TcpListener` and
`UdpSocket` return zero hits across every manifest and every `.rs` under

### 4.4 The WSL namespace is the nearest existing "another machine's paths"

`crates/bt-transcript/src/paths.rs` declares
`PrintedPathNamespace { Windows, Msys { home }, Wsl { distro, home } }`
(`:61-106`) and translates a printed path in two steps (`to_local_path`, `:134`): a drive mount `/mnt/d/…` becomes a drive-rooted path
(`drive_mount_to_local_path`, `:218`), and anything else becomes
`\\wsl.localhost\<distro>\…` (`distro_path_to_local_path`, `:255`) — the
only producer of a UNC path this crate admits. A `~` is resolved against a home
the *shell reported over OSC 7*, folded in by `with_shell_home` (`:169`),
because the launcher cannot know it. Which namespace a pane is in is assigned at
spawn by `bt_app::profiles::printed_path_namespace`
(`crates/bt-app/src/profiles.rs:2897`) and is **never inferred from the printed
text**.

Nothing in `paths.rs` touches a disk (`:10-12`): "A candidate is a **shape**, and
the only thing that turns a shape into a link is `PrintedPathLinks`, which is
told the answers by someone who did the reading off the event thread"
(`PrintedPathLinks` at `:2418`; the `.exists()` calls live in `bt-app`, e.g.
`main.rs:78062`). And the trust rule, verbatim from `paths.rs:562-563`:

> "So: **drive-rooted, and nothing else, unless the pane itself is standing in
> the distribution the path names.**"

`may_read_unasked` (`:584-622`) enforces exactly that: a `\\wsl.localhost\` root
is admitted only when the asking pane's own namespace is `Wsl { distro:
Some(same) }`, compared case-insensitively.
`may_read_unasked_through_links` (`:644-680`) is the one function here that
touches disk, and it does a single `symlink_metadata`/`read_link` hop against
the link itself, never the target.

**This is the model for a remote namespace, in three transferable parts**: the
namespace is assigned at spawn and never sniffed; a path from a remote pane is
reachable only while that pane is still standing in that remote; and the
sentence becomes *local, and nothing else, unless the pane itself is standing on
the host the path names*.

## 6. Persistence

`SESSION_SCHEMA_VERSION` is **15** (`crates/bt-persist/src/session.rs:51`; the
`windows[]` promotion was v9, `session.rs:213`). `SessionV1` (`:135`) carries
`windows: Vec<SessionWindowV1>` (`:162`); a window (`:222`) carries `placement`,
`tabs`, `active_tab`, `quake`, `quake_placements`; a tab (`:476`) carries
`root: LayoutNodeV1`, `pinned`, `focused_leaf`, `preview`; and the terminal leaf
— `crates/bt-persist/src/layout.rs:108` `TermLeafV1` — carries exactly
`profile_id`, `cwd`, `manual_name`, `card_skip` and `last_command`. Bounds are
`MAX_RESTORED_WINDOWS = 32`, `MAX_RESTORED_TABS_PER_WINDOW = 128`,
`MAX_RESTORED_PANES = 512` (`session.rs:379, 383, 392`), applied by
`degrade_in_place` (`:330`). `layout.rs:100-106` says `cwd` and `profile_id`
are carried **unvalidated** on purpose, because whether a directory exists is a
filesystem question and not this crate's.

**No output history is persisted** (`session.rs:503`). A restored pane
re-spawns a shell at `cwd` and starts blank.

A remote tab's persistence is therefore small, and its shape is already right: a
leaf gains a host handle and a server-side session id — both non-secret, both
unvalidated here for the same reason `cwd` is. Nothing about the connection
belongs in this file, and under an SSH transport nothing about the connection
*exists* for it to hold. What changes at restore is the answer to a question the
file already asks: this leaf wants a shell — on which machine.

**Six things carry over.**

**① The one product that put the terminal model on the server is the one that
has not finished it.** WezTerm's own open issue #106, "Revised mux/scrollback
model", is the maintainer saying the mux model "too closely mirrors the raw
terminal state API, but that isn't ideal for mux'd terminal sessions", and
listing what it costs: no local selection over text already on screen, no
keyboard selection, no proper searchable scrollback [S4]. The symptom list is
concrete — scrollback corruption when scrolling inside `less` or `man` under the
mux, mouse scroll not reaching alternate-screen applications, `ClearScrollback`
not honoured [S22][S23][S24] — and the docs still say multiplexing "is still a
young feature" [S3]. Note what the complaint actually is: not that the *server*
has a terminal, but that the **client does not**, so selection, search and
scrolling all become round trips. That is the half Folio must not copy.

**② The product Folio is trying to be keeps a terminal on *both* sides.**
tmux `-CC` sends structured control messages that *carry each pane's bytes*
[S7], and iTerm2's stated motivation for consuming them is exactly Folio's
pitch: without it you are stuck with "tmux's text-mode interface: its
scrollback, its copy mode, its keybindings fighting with local ones", and with
it every tmux window is a native tab with native scrollback, copy and search
[S8]. But tmux did not stop owning a terminal in order to do that — it owns the
canonical one, which is why a detached session keeps working and an attaching
client is given a screen rather than a replay. **That pair is the model this
document now recommends** (§8.2), and reading tmux as "no server-side model" was
the first draft's mistake.

**③ mosh is the standing proof of what shipping rendered state costs.** It is
the most sophisticated screen-state protocol anyone has written, and the price
printed on the tin is that there is no history [S11]. Folio's 0.4 exists in
order to have history from another computer.

**④ Everybody delegates auth to SSH, and the two most recent products deliver
their server binary the same way.** VS Code and Zed both prefer letting the
remote download it and both keep a *local-download-then-upload-over-SSH*
fallback [S5][S14]. For Folio the fallback is the only option and that is a
feature, not a limitation: §4.3 says this product has no HTTP client outside a
Windows-only update check, so asking a remote machine to fetch a binary from the
internet is not a thing it can do or should learn to do. What neither of them
can lend Folio is the *mechanism*: both push the binary through a connection
they already have, and §8.3 explains why an absent server cannot receive an
upload over the very channel it was supposed to be serving.

**⑤ Two concrete cautions.** WezTerm has an open crash where the PDU decoder
allocates from a peer-supplied length field with no bound [S25] — the exact
failure mode a hand-rolled framed binary protocol invites, and the reason §8.5
puts a hard cap in the grammar rather than in the reader — and the reason §4.2
refuses to point `bt-corpus`'s own reader at foreign bytes, since it has the
same shape (`bt-corpus/src/lib.rs:103, 115, 123`). And Zed's one `ControlMaster`
per project buys cheap extra channels at the price that when the master dies
every channel dies at once, plus a stale control socket blocking a new master
and a `ControlPath` directory OpenSSH will not create [S26][S21].

**⑥ And the one thing nobody can lend us: the client platform.** Every product
above that multiplexes over SSH does it with `ControlMaster`, which **Windows
OpenSSH lists as out of scope** [S31] — Zed carries a Windows-specific path for
precisely this [S32]. Folio's client is a Windows program, so it multiplexes
inside its own framing over one connection (§8.3). This is the single place
where the prior art stops applying.

## 8. The proposal

### 8.1 The split — a broker, a frontend, and a client

**[reviewed — the first draft said "`ssh host folio-server --stdio`" and stopped
there, which does not survive the client going away.** An `ssh` command's stdio
*is* the connection; when the ssh child dies the stdio dies with it, and nothing
can hand the same descriptors to a later connection. `PtySession` also kills its
child on drop (`crates/bt-pty/src/lib.rs:1569`), so whatever owns the sessions
must outlive every connection.**]**

Three processes, and the middle one is new:

**① The broker**, on the remote. A daemon owning the pty sessions, the canonical
terminals, the journals and the file service. It listens on a **private local
endpoint** — a Unix domain socket in the user's runtime directory, in a
directory created `0700`, path stamped with the server's version. It has no
network socket of any kind. Its trust boundary is the account, which is the same
boundary SSH already gave away, so the endpoint carries no second
authentication; what it carries is *permissions*, and the check on connect is
the peer's uid.

**② The frontend**, on the remote: `folio-server --stdio`, short-lived, spawned
by `ssh` for each connection. It connects to the broker's socket and pumps
frames between the socket and stdin/stdout. If the broker is absent it starts
one, detached from the ssh process group so it survives the connection, and
retries with a bounded backoff. **The startup race is settled by the socket
itself**: bind is exclusive, the loser connects to the winner, and a socket file
whose owner is gone is only removed after a lock is taken on a sibling file.
A broker with no sessions and no clients exits after a grace period; a broker
with live sessions never exits on its own.

**③ The client**, this product, with everything it has today plus one new
module: the transport, the remote leaf, and the dispatch point of §8.4.

**The server's I/O list, complete:** stdin and stdout (frontend), one Unix
socket (broker), one pty per session, one journal file per session, a directory
watcher, and the files it is asked to read, write or run `git` in. No listening
network socket, no HTTP client, no async runtime.

**What links into the broker:** `bt-pty` (which brings `bt-term`,
`Cargo.toml:10`), `bt-corpus`'s vocabulary, `bt-persist` for `atomic_write`, and
a new portable `bt-remote` for the grammar. `bt-platform` arrives as an empty
shell off Windows (§1). No `bt-render`, no `bt-app`, no window.

**The seams to cut in the client**, with sizes:

1. **`main.rs:30560` `create_leaf_session`** — a second source of bytes for a
   leaf, alongside `PtySession`. Its terminal-model construction is unchanged,
   which is what §3.1 buys. **M**.
2. **`main.rs:75494` `drain_pty`** — drain remote frames beside local rings,
   without the Win32 placement sample (`:75541`) becoming a precondition for
   remote bytes arriving; and **suppress the reply path for remote leaves**
   (§8.2). **L**, the largest item.
3. **`files.rs` / `preview.rs` / `git.rs`** — each has an isolated read that
   gains a remote arm; the worker threads stay. But see §8.4: this cannot be
   done by adding an arm to a function that returns a `PathBuf`. **M** each,
   *after* the reference type exists.

### 8.2 The wire model

**Recommendation: two models, one byte stream, and a checkpoint between them.**

* **The server** runs a canonical `DualPlaneSession`, built metrics-free by
  `DualPlaneSession::new` (`session.rs:1530`) with inline images and math off.
  It is the **reply authority**, the **size authority** and the **checkpoint
  source**. It renders nothing and is never seen.
* **The client** runs its own `DualPlaneSession`, built exactly as it is today,
  from the renderer's metrics. It owns the transcript, detection, reflow, marks,
  inline images, typeset math, layout and the glass.
* **What crosses** is (a) declared control messages, (b) a **checkpoint** on
  attach, and (c) the session's **original bytes** from the checkpoint's offset
  onward. Not rendered state, not a screen diff, not a re-encoded stream.

**Why the bytes and not the server's screen.** Because the client's pipeline is
then unchanged code: remote bytes enter the same `feed_at` that local pty bytes
enter, and every feature above it — blocks, marks, `$$…$$`, images, links,
reflow — works remotely on the day the leaf exists, with no second
implementation. This is tmux's arrangement, and it is why iTerm2 gets native
scrollback, selection and search out of it [S7][S8], where WezTerm's client is a
lazy proxy over server-computed render deltas and its maintainer has an open
issue saying that model "too closely mirrors the raw terminal state API"
[S2][S4].

**The double parse, named honestly.** The bytes are parsed twice: once headless
on the server, once for real on the client. Ghostty's author calls that the
central flaw of today's multiplexers [S17][S18] — but his complaint is
specifically about *re-encoding*: tmux parses escape sequences and then emits **a
different set** for the outer terminal, which the outer terminal must parse
again, losing whatever tmux did not re-emit. Here the client receives the
**original** bytes, so nothing is lost in a re-encode and the second parse is the
only one whose output anybody sees. The cost is CPU on the remote for a parse
nobody renders, which is what tmux has always cost.

**The checkpoint, and what it is.** A declared document, versioned with the
protocol — never a struct dump (§3.2). It carries:

| Field | Why |
|---|---|
| `epoch`, `offset` | where in the journal this checkpoint stands; the byte stream resumes here |
| `size` + `resize_epoch` | the pty's authoritative size and which epoch produced the bytes that follow |
| screen lines, with attributes and hyperlinks | the visible terminal |
| scrollback lines, bounded by the pane's `scrollback_lines` setting | history, in the unit the setting is actually in (`settings.rs:829`) |
| cursor position, shape, visibility | — |
| every mode: alt screen, wrap, origin, bracketed paste, mouse, focus, DEC 2026 | without these the following bytes mean something else (§3.4 ②) |
| palette and the two default colours | a program that set them will not set them again |
| title, cwd, and the shell's reported home | `session.rs:1158, 1306, 9208`; `paths.rs:169` learns `~` from OSC 7 |
| the OSC 133 mark ledger, with the **server's** timestamps | so command durations that elapsed while detached are real rather than zero (§3.3) |
| `exited: Option<code>` | a session whose child is gone but whose history is not |

**What the checkpoint does not carry, stated so nobody expects it:** detection
blocks (the client re-derives them from settled lines, and a checkpoint is by
definition settled), synchronized-update batching, inline image rasters, or
anything in subpixels.

**Ordering, and the one rule that makes it safe.** On attach the client (i)
receives the checkpoint, (ii) builds its model from it, (iii) then receives live
bytes from `offset` onward — buffered by the broker in the meantime, never
dropped, and refused past a bound with a re-checkpoint instead. **While the
client is applying a checkpoint or a backlog, its own reply path is suppressed
entirely**; and for a remote leaf it stays suppressed for ever, because:

> **Exactly one live reply authority per session, and it is the server's
> canonical terminal.** For a remote leaf the client drains
> `take_pty_writes()` (`main.rs:32305, 32340`) and **discards** it. Nothing the
> client's parser mints is ever written to a remote pty.

That rule has one consequence worth spelling out: focus reporting (`CSI I` /
`CSI O`) is a fact the *client* knows and leaves by the same door. So focus
becomes a declared control message, and the server's canonical terminal decides
whether the mode is on and writes the bytes. User input — keystrokes, mouse
reports, bracketed paste, IME commits — is not a reply and travels as input.

**Resize.** The client requests a size; the broker sets it on the pty, bumps the
resize epoch, and stamps subsequent output with it. A client never reflows bytes
whose epoch is not the one it asked for; it waits for the epoch boundary. In v1
one client is attached at a time, so the request is always granted.

**What this costs, plainly.** A canonical parse on the remote per session. A
checkpoint schema to design, version and test. And two implementations of "what
this terminal is" that must not drift — mitigated by both being the *same crate*
(`bt-term`) driven by the same bytes, and by a red test that feeds one corpus to
both and compares screen, scrollback, modes, cursor, marks, cwd and title.

**Not chosen, one line each.** Rendered screen diffs (mosh): the history is the
feature and mosh's stated price is the history [S11]. A server-side model with a
proxy client (WezTerm): §3.1's presentation coupling is real even if it is not
structural, and the second parse is cheaper than porting reflow, detection,
math and inline images to a headless box [S2][S4]. A pure byte broker with no
terminal (the first draft): §3.4 ① and ②.

### 8.3 Transport, bootstrap, and the endings

**One long-lived `ssh.exe` per host; Folio multiplexes inside its own framing.**
**[reviewed — accepted; the first draft's ControlMaster recommendation is
unavailable on the platform the client runs on.]** Windows OpenSSH's own project
scope lists **"Client ControlMaster"** among the things that will not work
[S31], and Zed, which uses one control master per project elsewhere, carries a
Windows-specific path for exactly this reason [S32]. So the connection is one
`ssh.exe` per host, and every session and every RPC rides inside Folio's frames
on it: request ids, per-session queues, fair scheduling so one session's `cat`
cannot starve another's keystroke, and backpressure that stops reading a pty
rather than growing a queue. A second connection is a second authentication, and
is used only for the bootstrap (below).

**Invocation.** `ssh -T -o BatchMode=… <host> <path>/folio-server --stdio`,
with:

* **`-T`**, so no pty is allocated for the transport itself and nothing echoes.
* **The ssh executable resolved through the trusted lookup**
  (`bt_platform::handoff`'s `program_on_path`), not a bare name —
  `quiet_command`'s own neighbouring documentation warns against running a
  program named rather than located (`bt-platform/src/lib.rs:2024`).
  **[reviewed]** `quiet_command` (`:2014`) is the right door and gives a
  `Command` with `CREATE_NO_WINDOW`; it is **not** a transport, and supplies no
  readers, no writer queue, no cancellation and no authentication UI. Those are
  the ticket.
* **All three pipes drained, always.** A blocked stderr blocks ssh.
* **A bounded handshake wait**, after which the connection is failed with what
  stderr said, not with a hang.
* **Contaminated stdout diagnosed, never parsed.** A non-interactive `ssh` can
  still run `~/.bashrc` — bash runs it for non-interactive shells when it
  believes it is being run by a remote daemon [S33] — so a login banner or an
  `echo` in an rc file can land on the channel. The first frame is a magic; if
  the bytes before it are not the magic, the connection fails with *"the remote
  shell printed something before the server started"* and the first bounded
  chunk shown as text. It is never fed to a terminal parser.
* **Authentication and host verification are ssh's**, and their output is
  surfaced: unknown host key, password prompt, passphrase prompt and permission
  denied each get a distinct, cancellable surface. Folio stores no key, no
  password, and makes no trust decision.

**Bootstrap and delivery.** **[reviewed — the first draft said "upload over the
same connection", which cannot work: an absent server cannot receive an upload
message, and an incompatible one cannot be assumed to understand it.]** The
recommendation is **a separate, short-lived provisioning connection**:

1. The client opens `ssh -T <host> sh -s` and writes a small POSIX script on
   stdin, then the binary's bytes, then closes stdin — EOF terminates the
   transfer, which is why this is a *separate* connection and not the framed
   one.
2. The script creates a temp file in the **same directory** as the install
   target with a name of the client's choosing, reads the bytes into it,
   verifies a SHA-256 the client stated, `chmod 0700`, and `mv`s it into a
   **version-stamped path**. `mv` within a directory is atomic, unique temp
   names make concurrent installers safe, and a version-stamped path means an
   install never overwrites a binary a live broker is executing.
3. Prerequisites are `sh`, `mkdir`, `cat`, `chmod`, `mv` and a SHA-256 tool
   (`sha256sum` or `shasum -a 256`); their absence is a named failure, not a
   crash. Quoting is fixed by the script being sent on stdin rather than
   composed into an argv.
4. Then the framed connection is opened against the newly installed path.

**Upgrades with live sessions fall out of the version stamp.** The socket path
is version-stamped too, so a new client can install and start a new broker while
an old broker keeps the sessions it owns. The client talks to both, marks the
old sessions as *on the previous server*, and the old broker exits when its last
session does. Nothing is migrated and no session is killed by an upgrade.

**Handshake.** First frame each way: magic, protocol version, product version,
and the broker's session list. **Refuse a mismatch and say so** — WezTerm's rule
[S3], Zed's rule [S14] — with one action: provision the matching server.

**Platform contract. [reviewed]**

* **Linux**: `x86_64` and `aarch64`. **musl is the candidate** and the open work
  is validation, not existence — the vendored backend calls `libc::openpty`
  directly (`vendor/conpty/portable-pty/src/unix.rs:36`) and musl implements it
  [S34]. A static libc does not remove kernel requirements, so the gate is a
  real link plus a runtime pty check on both architectures: `/dev/ptmx` and
  devpts present, resize delivered, `SIGWINCH` seen by the child, child reaped.
  `cargo-zigbuild` with a pinned glibc floor is the fallback [S29].
* **macOS**: `aarch64`. Apple Silicon requires *a* signature to execute, but the
  linker's ad-hoc signature suffices — "unsigned" here means **without a
  Developer ID**, not literally unsigned [S35]. A file delivered by `ssh`/`scp`
  gets **no** `com.apple.quarantine` attribute, so Gatekeeper is not in the path
  [S36]. The concrete risk is a cross-linker that emits no ad-hoc signature at
  all: **build the macOS server on the macOS runner CI already has**, and verify
  the signature on the artifact after release processing.
* **Windows as a remote: deferred, explicitly.** It is not impossible —
  `portable-pty` selects ConPTY on Windows
  (`vendor/conpty/portable-pty/src/lib.rs:407`) — but it needs three things this
  milestone does not have: the ConPTY sidecar delivered beside the exe, because
  the loader reads only `current_exe()`'s own directory (`docs/DESIGN.md:6178`);
  a bootstrap with no POSIX `sh`; and the whole of §8.4 in Windows spelling on
  both sides. It is a milestone of its own and is named here so it is not
  mistaken for an oversight.

**The endings.**

| What ends | What happens |
|---|---|
| the `ssh` child dies | the broker keeps running; children keep running; journals keep growing. Remote leaves go to *detached* with a mark and a Reconnect action. The canonical terminal keeps answering the shell's questions (§3.4 ①). |
| the client process exits | identical; the broker never learns the difference |
| the broker dies | its children die with it. On reconnect there is no session: the leaf offers a new shell at the same remote cwd, which is what restore already does (§6) |
| the child exits | `Exit { code }` is journalled and sent; the session stays attachable until it is closed, so its history is still readable |
| a second client attaches | v1: it takes over, and the first is told. Multi-client is v2 |
| the user closes the tab | detach. **Kill is a separate, explicit verb** and is the only thing that ends a session's child |

### 8.4 The remote namespace, and typed references

**[reviewed — accepted in full; the first draft's answer was a namespace variant
and that does nothing.]** `may_read_unasked`'s non-WSL arm returns
`drive && RootDir` **irrespective of the namer** (`paths.rs:608-616`), so a new
`PrintedPathNamespace` variant would not stop a remote pane's printed `C:\…`
from being admitted as a local read. Worse, existing consumers manufacture
client paths from remote-derived strings today: `files::full_path(root, key)`
returns a `PathBuf` built from string segments (`files.rs:676`), and
`git::repo_root(text)` turns git's stdout into a `PathBuf` (`git.rs:2350`).

**The rule: a remote location is a typed, host-bound reference, and it has no
`PathBuf` spelling.**

* One type — a host id plus an opaque remote path held as **bytes**, because a
  Unix filename is bytes and may contain a backslash, which no Windows spelling
  survives.
* It is threaded through cwd, listings, previews, the git panel, every cache
  key, the command palette's file section, and persistence.
* **One dispatch point** stands before every client filesystem call, `PathBuf`
  construction, URL mint and program launch: local goes to the existing gates,
  remote goes to the wire, and there is no third answer. `may_read_unasked` and
  `may_read_unasked_through_links` are asked **on the side that owns the disk**.
* Red tests: a remote `C:\Windows\System32\…`; a remote UNC and a device path;
  `..` in every position; a Unix filename containing `\`; and a local pane
  offered a remote path.

`PrintedPathNamespace` still gains a `Remote` variant, but for what it is
actually for: deciding how a *printed* path in that pane's output is spelled and
resolved. It is assigned at spawn (`profiles.rs:2897`), and `~` is still learned
from OSC 7 (`paths.rs:169`) — which works remotely because it is the shell that
reports it. **Local WSL translation is untouched**, and a remote `/mnt/c` stays
on that remote host: the namespace says how to read the text, the reference says
which machine it lives on, and conflating them is the bug this section exists to
prevent.

**Previews of remote images and PDFs.** **[reviewed — the first draft said "a
client-side scratch file" and that is only safe with a boundary.]** WebView2
checks every resource (`bt-platform/src/webview.rs:1831`) and the app admits
file resources **inside the minted document's own folder**
(`webnav.rs:506, 596`). So a remote file dropped into a shared temp directory
would grant the page access to its siblings. The rule: **one isolated directory
per preview buffer, created for it and removed with it; the filename is
generated by the client and never derived from the remote name; only the
intended URL is minted; the navigation and resource gates are unchanged.** Tests:
an SVG with subresources, an HTML file with a relative `img`, and a sibling file
that must not load.

**The three verbs that mean nothing across a wire.** *Open in Explorer* becomes
**Copy remote path** plus opening the containing folder in the files column.
*Drag a remote file out* is refused in v1 — a drop target expects a path that
exists. *Drag in* is a copy, also v1-refusable. And **`folio-here` from a remote
shell** gets a real answer: it is a small remote helper that **cannot write into
the broker's framed stdout**, so it speaks to the broker over the same private
local endpoint, holds a **per-pane capability minted at spawn** exactly as
`FOLIO_PANE`'s capability is (`attention_wire.rs:7-18`), and may say only two
things: *preview this remote path* and *open this remote folder in the column*.
No local path, no launch, no command.

**And the single-instance interaction. [reviewed]** The in-flight
single-instance work hands a second launch's command line to the running
process, and a launch request carries local `PathBuf`s (`cli.rs:66`;
`bt-platform/src/instance.rs` supplies the directory-ownership primitive). **A
local second launch must never land in a remote tab**: the routing decision is
"this request names local paths, therefore a local window and a local leaf",
made before a tab is chosen. An explicitly remote launch is host-qualified and
is a v2 verb.

### 8.5 Security and the bounds

*What a hostile client can do to a server*: it holds SSH to that account and
already owns it. The broker must not pretend otherwise. Said once.

*What a hostile server can do to a client* is the whole surface, and the rule is
the attention wire's: **declared fields only, everything bounded, failure silent
and counted** (`attention_wire.rs:20-27`; the six-clause contract at
`docs/DESIGN.md:1606`).

1. **A hard cap in the grammar, checked before allocation** — the length prefix
   is refused before a byte is reserved. `bt-corpus`'s reader is the specimen of
   getting this wrong in our own tree (`bt-corpus/src/lib.rs:103, 115, 123`) and
   WezTerm's open PDU crash is the specimen in someone else's [S25].
2. **Control responses have schemas and aggregate limits.** **[reviewed —
   accepted; the first draft only bounded a frame.]** Directory entries, preview
   bytes and git output do not pass through the terminal's OSC caps at all, and
   a per-frame bound permits an unbounded *listing*. So: a declared schema per
   response; a cap on entries per listing and on total bytes per request;
   pagination with a cursor; cancellation; and **decoded** image dimensions
   bounded, not only compressed bytes.
3. **Every response is bound to a request id, a host and a session, and a stale
   response is dropped and counted.** A reply that arrives after its request was
   cancelled, or that names a session the client has closed, is not applied.
4. **Filenames are bytes.** They are never assumed to be UTF-8, never
   round-tripped through a Windows path, and are rendered with the replacement
   character rather than being made lossy in the model.
5. **Saves get conflict detection and a defined answer after an ambiguous
   disconnect** — the existing mtime `SaveOutcome::Conflict` moves server-side,
   and a save whose acknowledgement was lost is re-checked, not blindly retried.
6. **Terminal bytes stay terminal bytes.** Remote output goes through the same
   parser, the same 64 KiB OSC bound and the same OSC 52 refusal as local output.
   A remote pane is not a softer door into the same window.
7. **A capability, not an address.** Session ids are unguessable, minted by the
   broker, never walked.
8. **The client never runs what the server names.** No auto-run, no
   server-supplied argv, no server-chosen profile.
9. **Replay never speaks.** Replies, notifications, attention deliveries and
   automatic file reads produced while applying a checkpoint or a backlog are
   discarded (§8.2), with a red test that a replayed `CSI 6n` reaches no pty.

### 8.6 Latency

Over a WireGuard-based mesh on a home network the round trip is roughly
10–40 ms. mosh's measured case was a 3G link at a median of 503 ms, where
prediction moved it under 5 ms [S12], and mosh itself shows predictions
adaptively on high-delay links rather than always [S11].

**Recommendation: no prediction and no local echo in v1.** A predicted character
is a lie the client tells about a program it is not running, and the panes most
likely to be here — a full-screen TUI, an agent's approval prompt — are exactly
where it is wrong.

**The measurement that would overturn it** (T13): stamp the keystroke on send
and the first byte attributable to it on arrival, over a real working session on
the user's own two machines. Median past ~80 ms, or a tail past 200 ms above a
few percent, means revisit — with mosh's adaptive rule, not unconditional echo.

### 8.7 Scope

**v1**: a remote tab; full-control remote shells with the client's whole
pipeline on them; transcript blocks, marks, detection and formulas for free; the
files column, previews and text editing on the remote disk; the git panel on the
remote repository; a session that survives the client and can be reattached; and
persistence of which host a leaf belonged to.

**Out of v1**: agent state and notifications over the wire; more than one client
on one session; server-side search; remote video first frames; drag-and-drop of
remote files; port forwarding; a remote web pane; Windows as a remote (§8.3);
and any transport that is not `ssh`.

**v2**, in the order they become possible: agent state and notifications — the
attention wire's `Message` grammar gains a second transport and its one new
declared field `tool_name`, which is what the 2026-09-09 agents research was
written for (`docs/plans/agents/state-and-notifications-research-2026-09-09.md`
§6.2); several clients on one session, which the canonical terminal makes
answerable because there is one authority for size and replies; server-side
search over the canonical scrollback, which is now merely an API on something
that already exists; and named instances, which turn out to be the natural name
for "the agent that lives on that box".

## 9. Open questions

**Ruled 2026-09-10 (owner, after the Codex review):** Q1 yes — the server runs a canonical terminal; Q2 T8 is the first release step, with an explicitly labelled attached-only prototype after T5/T7 and T6 before any automatic cwd handling; Q3 a checkpoint plus the bytes after it, the journal retained as a crash-recovery artifact. **Ruled later the same day (owner):** Q6 is overturned for v1 — when two clients attach to one session both see it update live and both may type (a shared view, not takeover); a machine that is also a server sees a session another machine started as a background session with a "connected from elsewhere" mark and attaches to it with one click, through its own local broker without ssh. Two questions the owner asked the same day are recorded for the design: whether the local Folio on a machine that is also a server should run its own sessions through the broker so both machines see one list (see §9 Q19 and the named-instances note in §8.7), and what a second client sees while another is attached (Q6: takeover in v1, shared view in v2).

**Three of these change everything below them. They are Q1, Q2 and Q3, and they
are first for that reason.**

---

### Q1. Does the server run a terminal? — **Yes, a canonical one.** *(reversed from the first draft)*

The first draft said no, on the grounds that a `DualPlaneSession` cannot be born
without a rasterizer. That is true of `bt-app`'s call site
(`main.rs:30560-30561, 30778-30780`) and **false of `bt-term`**, which offers
`DualPlaneSession::new(columns, rows)` over a constant
(`crates/bt-term/src/session.rs:1530`). Three jobs need it and nothing else can
do them:

* **A detached session must answer.** `CSI 6n`, `CSI c` and colour queries are
  minted in `bt-term` and written back by the client today
  (`main.rs:32305, 32340`). Detached, with no parser, the asking program waits
  until it times out.
* **An attaching client must get a checkpoint, not a byte suffix.** The
  scrollback setting is in **lines** (`bt-persist/src/settings.rs:829`), a byte
  cut can land inside a sequence, and losing the alternate-screen entry
  (`vendor/alacritty_terminal/src/term/mod.rs:1111`) changes what everything
  after it means.
* **The pty has one size**, and `bt_corpus::replay` resizes without owning
  anything (`bt-corpus/src/lib.rs:179`).

**What does *not* move**: the presentation model. Reflow, detection, marks
rendering, inline images, typeset math and layout stay on the client and receive
the session's **original bytes**, so every feature above the parser works
remotely with no second implementation.

**The cost, so the ruling is informed**: the bytes are parsed twice (§8.2 names
this honestly against Ghostty's author's objection [S17]); a checkpoint schema
must be designed, versioned and kept from drifting; and the server links
`bt-term`, which `bt-pty` already depends on anyway (`bt-pty/Cargo.toml:10`).

**If this is overturned** — if the owner wants a pure byte broker — then
detached sessions cannot answer terminal queries, attach must replay from a
journal boundary that cannot be made correct, and §8.2, §8.3's endings, T4 and
T5 all change. Say so and this document is rewritten again.

---

### Q2. Is T8 the first release step, or is there an earlier prototype? — **Recommend: T8, and no earlier promise.**

The first draft's first-usable ticket proved only that remote bytes reached a
terminal model. That is a prototype: no host UI, no ssh discovery, no
authentication surface, no namespace-safe cwd, no remote shell integration. T8
now carries all of it and depends on T4, T5, T6 and T7, which makes the first
usable thing later and honest rather than early and false.

**The alternative, if the owner wants something to touch sooner**: declare an
explicit *attached-only prototype* — one host typed into a settings box, no
detach, no files column, no persistence, behind an environment gate — after T5
and T7, and do not call it a release step. Recommend taking it, because the
owner tests on their own machines and a prototype that is labelled as one costs
nothing; **but T6 must still land before any automatic cwd handling**, because a
remote `cwd` that becomes a client `PathBuf` is the bug class of §8.4 and it is
easier to prevent than to unpick.

---

### Q3. What does an attaching client receive, and what is retained? — **A checkpoint plus the bytes after it; the journal is retained by time and total size, not by scrollback.**

**[The first draft's answer was unsound and is withdrawn.]** It proposed capping
the journal by the pane's scrollback quota and trimming from the front. The
setting is `scrollback_lines` (25k–200k **lines**,
`bt-app/src/settings.rs:1007`), and a byte trim cannot preserve a terminal
(§3.4 ②).

The recommendation, in three parts:

* **The scrollback the user set is honoured by the canonical terminal**, in
  lines, exactly as it is locally — it is the same crate doing it.
* **The checkpoint carries those lines**, plus modes, cursor, palette, title,
  cwd and the mark ledger with the server's own timestamps.
* **The journal is a crash-recovery artifact, not the history**, so it is
  retained by a total-size budget and an age, trimmed at whole records from a
  point at which a checkpoint has been written — never at an arbitrary byte.
  Losing the whole journal costs a crashed broker its sessions, which they were
  going to lose anyway.

Withdraw the first draft's promises of "exactly as much history as a local pane"
and "show the tail first": the first is now true for a different reason, and the
second described an unbounded replay that no longer exists.

### The rest

4. **What must replay reproduce?** — **The terminal, in virtual time; never the
   client's derived facts.** The journal's `at_micros` drive the clock, timers
   fire in recorded order relative to bytes, worker completions are awaited. The
   test asserts screen, scrollback, modes, cursor, mark ledger, cwd and title —
   not identical output bytes. Command durations, detection stability
   (`session.rs:64, 3471`) and DEC 2026 batching (`main.rs:75716`) are *not*
   reproducible from bytes and are not asked to be: durations come across in the
   checkpoint's ledger, the other two are live-rendering concerns.
5. **Who may write to a remote pty?** — **The broker's canonical terminal, for
   replies; the attached client, for input.** For a remote leaf the client
   drains `take_pty_writes()` and discards it. Focus reporting becomes a
   declared control message rather than an exception to the rule.
6. **Two clients, one session — v1?** — **No: takeover, with the loser told.**
   The canonical terminal makes real multi-client answerable later (one size
   authority, one reply authority, one checkpoint source), which is exactly what
   WezTerm lacks and has a filed crash for [S4]. It is v2 work, not a v1 corner.
7. **Is `bt-corpus` reused?** — **Its vocabulary, yes; its decoder, never on
   foreign bytes.** `read_from` allocates from unchecked lengths and counts
   (`bt-corpus/src/lib.rs:103, 115, 123`). The journal and the wire each get a
   bounded reader.
8. **musl or glibc?** — **musl is the candidate; the question is validation, not
   existence.** The vendored backend calls `libc::openpty`
   (`vendor/conpty/portable-pty/src/unix.rs:36`) and musl implements it [S34]. A
   static libc does not remove kernel requirements, so T9 gates on a real link
   plus a runtime pty check on both architectures — `/dev/ptmx` and devpts,
   resize delivered, `SIGWINCH` seen, child reaped. Fall back to
   `cargo-zigbuild` with a pinned floor [S29].
9. **What exactly is required of a macOS remote?** — **A signature, which the
   linker's ad-hoc one satisfies; "unsigned" here means without a Developer ID**
   [S35]. An `ssh` upload sets no quarantine attribute [S36]. The real risk is a
   cross-linker emitting no ad-hoc signature: build on the macOS runner CI
   already has, and verify the artifact after release processing.
10. **Windows as a remote?** — **Deferred, explicitly, and it is not
    impossible**: `portable-pty` selects ConPTY
    (`vendor/conpty/portable-pty/src/lib.rs:407`). It needs the sidecar
    delivered beside the exe (`docs/DESIGN.md:6178`), a bootstrap with no POSIX
    `sh`, and §8.4 in Windows spelling on both sides. Its own milestone.
11. **How does the server get onto the remote?** — **A separate short-lived
    `sh -s` connection**, script on stdin, bytes after it, EOF ending the
    transfer; SHA-256 verified remotely; atomic `mv` into a version-stamped
    path. Not "over the same connection" (the first draft), which an absent
    server cannot receive. Upgrades keep live sessions because the socket path
    is version-stamped too.
12. **`ControlMaster`?** — **No, and not by choice**: Windows OpenSSH lists
    "Client ControlMaster" as out of scope [S31], and Zed carries a
    Windows-specific path for the same reason [S32]. One long-lived `ssh.exe`
    per host, Folio's own multiplexing inside its framing.
13. **What stops a remote path becoming a local one?** — **A type, not a
    namespace.** `may_read_unasked` admits any drive-rooted path irrespective of
    the pane's namespace (`paths.rs:608-616`), and `files.rs:676` and
    `git.rs:2350` build `PathBuf`s from strings today. §8.4's host-bound
    reference and single dispatch point are the answer; T6 lands before T8.
14. **Where do remote image bytes go for WebView2?** — **An isolated directory
    per preview buffer, with a client-generated name.** WebView2 admits file
    resources inside the minted document's folder (`webnav.rs:506, 596`), so a
    shared temp directory would grant a remote page its siblings.
15. **Do control responses get the terminal's defenses?** — **No, they need
    their own**: schemas, entries-per-listing and bytes-per-request caps,
    pagination, cancellation, request/host/session binding, stale-response
    rejection, filenames as bytes, decoded-image bounds, and save conflict
    detection after an ambiguous disconnect.
16. **Does a remote pane get shell integration?** — **Yes**, and the text is
    portable, but `shell_integration.rs:350` writes *local* files, so the remote
    copy is **staged by the broker** at spawn. It is inside T8 because a first
    usable remote shell without marks is not the product.
17. **Does `folio attention` work from a remote agent in v1?** — **No**, and it
    is the most valuable thing v2 adds. The grammar exists
    (`attention_wire.rs:93`) and the discipline exists
    (`docs/DESIGN.md:1606`); what is missing is a second transport. Doing it in
    v1 would ship the agent surfaces the owner deliberately paused on
    2026-09-10.
18. **What does `folio-here` become?** — **A broker client, not a stdout
    writer.** It cannot share the frontend's framed stdout, so it connects to
    the broker's private endpoint with a per-pane capability minted at spawn
    (`attention_wire.rs:7-18`'s rule) and may say only *preview this remote
    path* and *open this remote folder*.
19. **How does this meet the single-instance work?** — **A local second launch
    must never land in a remote tab.** Launch requests carry local `PathBuf`s
    (`cli.rs:66`); routing decides "local paths, therefore a local leaf" before
    a tab is chosen. Host-qualified remote launches are v2.
20. **Does the server need a settings file?** — **No.** Everything arrives in
    the session-open message. A file on the remote is a second place for an
    answer to live and a thing to migrate.
21. **Is there a management CLI on the remote?** — **No.** List and kill are
    verbs on the same protocol, driven from the client. A CLI on the remote is a
    second product with a second grammar to keep compatible.
22. **Does the update check learn about servers?** — **No; the client is the
    version.** The handshake refuses a mismatch and offers provisioning, which
    makes the server's version a consequence rather than a thing anyone
    maintains.
