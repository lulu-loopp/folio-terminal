# One Folio driving another — research for 0.4

2026-09-10. Branch `docs/remote-research` off `main` at `c9f25c6`. This is
research, not a design: no product code is touched, nothing is built, nothing is
launched, and nothing here is decided. Every claim about this codebase carries a
`path:line`; every claim about another product carries a source, and the list is
§10.

The order is ruled — **0.4 = remote**, **0.5 = the macOS GUI port**. One Folio
drives shells and agents that live on another machine, sees their history, and
puts the files column and the previews on the remote disk: *as if one computer
were using another*. Two things asked for earlier fold into it — an agent
session that survives the client closing, and a second computer attaching to the
same history and taking over.

The framing given with the ticket was: a headless Folio **server** on the remote
owns the PTYs, the terminal model, the transcript and file access; the local
Folio opens a **remote tab**; rendering, mouse, IME and clipboard stay local;
the transport is SSH. **This document confirms all of that except one clause,
and the clause it overturns is the important one: the server must not own the
terminal model.** §3 is why, §8.2 is what to do instead.

---

## 0. The short answer, before the evidence

Five facts decide the shape of this work; each is evidenced where it is named.

**The server is nearly free, and the port is not.** `bt-platform` is the only
crate carrying a Windows-only dependency row, and its library has no
dependencies at all off Windows; `bt-pty` is already a unix crate. What blocks
macOS is the 79 `bt_platform` entry points `bt-app` calls for a window, a
compositor, a web host and pickers (`docs/plans/port/macos-spike-2026-09-07.md:47-49`).
**A server has no window**, so it needs none of that (§1, §2).

**Nothing in the terminal model can be serialised today**, and its sequence
numbers reset every process start, so they cannot be resume tokens (§3.1,
§3.2).

**And the model is born out of the renderer's font metrics.**
`create_leaf_session` opens `renderer: &WindowRenderer, body:
bt_render::SeatViewport` (`crates/bt-app/src/main.rs:30560-30561`) and
constructs the session from cell height, cell width and ASCII baseline in
subpixels (`main.rs:30778-30780`). A terminal model on a headless box would
have to be handed a rasterizer to exist, and would have one answer for however
many clients were attached (§3.3). **This is why the framing's one clause
about the server owning the terminal model has to go.**

**The byte log is already built, already portable, already replayed.**
`crates/bt-corpus/src/lib.rs` is a framed binary format of timestamped
`Output` / `Resize` / `Exit` events with a deterministic `replay`, and `bt-pty`
already writes it from a live pane behind `BT_PTY_DUMP`. The durable artifact a
remote session needs is a format this product already ships (§4.2).

**The transport should open no socket.** `crates/bt-platform/src/http.rs` is
the only network code in the tree and is a WinHTTP wrapper for one `GET`
(`docs/DESIGN.md:6911, 6915`); there is no async runtime and no TCP anywhere.
Spawning `ssh` and framing its stdio leaves that record intact and leaves keys,
host verification and encryption to OpenSSH (§4.3, §8.3).

`#[cfg(windows)]` gate: `bt-unicode`, `bt-doc`, `bt-detect`, `bt-layout`,
`bt-persist`, `bt-winres`, `bt-math`, `bt-transcript`, `bt-viewport`,
`bt-render`, `bt-term`, `bt-pty`, `bt-corpus`. The `core-macos` CI job compiles

The dependency graph makes the cut cheap. **`bt-platform` is the only crate in

### 1.2 Where the two are entangled — the cost list

1. **`main.rs:30560` `create_leaf_session`** — the worst of them, and the one
   that settles §8.2. Its signature opens `renderer: &WindowRenderer, body:
   bt_render::SeatViewport` (`main.rs:30560-30561`); the grid comes from
   `renderer.metrics().grid_for_pixels(body.width, body.height)`
   (`main.rs:30591`); the session is constructed with
   `renderer.metrics().cell_height_subpixels()` (`main.rs:30778`) and then told
   `cell_width_subpixels(renderer.metrics())` and `ascii_baseline_subpixels()`
   (`main.rs:30779-30780`) before it has seen a byte. **A terminal model in this
   product cannot be born without a rasterizer.**
2. **`main.rs:75494` `drain_pty`** — one pass over every tab that, in the same
   loop and under one `Instant`, feeds bytes into the model, delivers OSC
   attention (`main.rs:75569`), schedules focus-card thumbnails
   (`main.rs:75614` `panes_spoke`), sets repaint flags (`main.rs:75636`
   `unpainted_pane_output`), raises OS attention (`main.rs:75631`) and dirties
   the session file for a changed cwd (`main.rs:75637`) — having first sampled
   Win32 window placement (`main.rs:75541`). Cutting a seam here means
   separating "bytes arrived" from "this window should repaint", which is
   exactly the seam a remote pane needs and the largest single refactor in this
   plan.
3. **`profiles.rs`** — one 23,180-line file that is both the profile picker and
   the spawn-resolution data. The data half has to be reachable from a
   server-facing request builder without dragging the menu behind it.
4. **`git.rs`** — 7,087 lines mixing the panel's state machine with the argv
   builder at `git.rs:2121-2139`. Only the second half goes remote.
5. **`preview.rs`** — 12,320 lines, but here the split is already clean *by
   function*: the worker thread reads, the WebView2 hand-off displays.

## 2. The PTY layer

**The vendored `portable-pty` still carries its Unix backend, intact.**
`vendor/conpty/portable-pty/src/` holds `cmdbuilder.rs`, `lib.rs`, `serial.rs`,
**`unix.rs`** — 414 lines of `UnixPtySystem` over `libc::openpty` — and `win/`.
`unix.rs` is declared `#[cfg(unix)] pub mod unix;` at
`vendor/conpty/portable-pty/src/lib.rs:54`. In its `Cargo.toml`, `libc`, `nix`
(features `term`, `fs`), `filedescriptor`, `anyhow`, `log`, `serial2` and
`shell-words` are unconditional `[dependencies]`; only `bitflags`,
`lazy_static`, `shared_library`, `winapi` and `winreg` sit under
`[target."cfg(windows)".dependencies]`. **Enabling the Unix backend takes
nothing at all** — it is already enabled by `cfg`, and
`docs/plans/port/macos-spike-2026-09-07.md:121-124` says so in as many words.
`vendor/conpty/portable-pty/CHANGES-FOLIO.md` records that every Folio change to
this tree is Windows-only: the ConPTY sidecar loader, a job object with
`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` around each child, a registry-string NUL
fix, and the environment-block grammar guard in `cmdbuilder.rs`. One pleasing
coincidence, worth stating once: `portable-pty` is Wez Furlong's crate, and
WezTerm's own multiplexer is built on it. Folio has already vendored the PTY
layer of the closest prior art.

**`bt-pty` is already a unix crate.** It calls
`portable_pty::native_pty_system()` and never names ConPTY directly. Twelve
`#[cfg(windows)]` sites (`crates/bt-pty/src/lib.rs:29, 46, 658, 1128, 1363,
1449, 2994, 3037, 3062, 3095, 3304, 3385`); the last six are tests, and every
one of the first six already has a `#[cfg(not(windows))]` arm beside it:
`ConPtySource::NotWindows` (`:32-44`), `conpty_source()` (`:51`),
`environment_key_eq` (`:663`), `quoted_for_cmd` — whose comment reads "so that
this module goes on compiling off Windows" (`:1144`) — the interpreter-line
application inside `spawn` (`:1363`), and `clear_host_buffer`, which answers
`Ok(false)` off Windows and documents that as not an error (`:1455`). Its
public API is the exact surface a server needs and nothing more: `PtyCommand`
(`:511`) with `new`/`arg`/`working_directory`/`env` (`:525-559`),
`PtySession::spawn` (`:1340`), `write` (`:1412`), `resize` (`:1421`),
`read_output` (`:1472`), `try_wait` (`:1502`), `shutdown` (`:1516`). Its Cargo
dependencies are `bt-term`, `bt-transcript`, `portable-pty`, `thiserror`; none
is Windows-only.

**One thing in it is genuinely Windows policy and a server has to answer it:**
the default shell. `crates/bt-pty/src/shell.rs:96` `resolve_default_shell`
implements the 2026-08-04 ruling — `BT_SHELL` wins, else `pwsh.exe` if the probe
finds one, else `powershell.exe`. On a Linux or macOS server the equivalent is
`$SHELL`, then the login shell from the password database, then `/bin/sh`. That
is a ticket (§8.8 T2), not a research question.

## 3. The terminal model, and why it must stay on the client

### 3.1 Nothing in it derives `serde`

A grep for `derive(...Serialize` across `crates/` hits `bt-app/src/update.rs`,
`bt-math/src/lib.rs` and every file under `bt-persist/src/`. It hits **nothing**
in `bt-term`, `bt-doc`, `bt-detect`, `bt-viewport` or `bt-transcript`; `serde`
is not in those crates' manifests at all.

The types are not *hostile* to it. `bt-transcript`'s `TranscriptId`,
`StagingId`, `SourceGeneration` and `GraphemeOffset`
(`crates/bt-transcript/src/lib.rs:378-387`), `FrozenLine` (`:897`),
`FinalizedLine` (`:975`), `CapturedRow` (`:818`), `StyleSpan` (`:861`),
`CellHyperlink` (`:485`) and `TranscriptStore` (`:988`) are plain
`String`/`Vec`/`u32`/`u64` composites, and `FrozenLine::resident_bytes()`
(`:925`) already accounts for every allocation — a promising sign for anything
that would need a wire budget. `bt-doc`'s `HistoryDocument`
(`crates/bt-doc/src/document.rs:27`) is four `BTreeMap`s, an
`Option<Selection>` and two counters. Adding derives is possible. It is the
next two facts that say not to.

### 3.2 The generations reset, and some of the model does not travel at all

`DualPlaneSession` (`crates/bt-term/src/session.rs:1091`) carries
`grid_generation` (`:1108`) and `screen_revision` (`:1110`). Both are bumped on
every mutation and every resize (`:2769, 3045, 3049, 3201, 3261, 3265`); both
start from their `Default` at every process start (`:1614-1615`); neither is
persisted anywhere. `DetectionRevision`, `GridGeneration`, `ViewGeneration`,
`LayoutKey` and `VersionStamp` all live in `crates/bt-doc/src/versions.rs` and
are `Copy` newtypes over `u64`. **They work as an in-session delta cursor and
not at all as a resume token**: a client returning tomorrow cannot say "send me
everything after revision 41,203", because the server restarted and its counter
is 12.

And parts of the model are process-local by construction:
`crates/bt-term/src/adapter.rs:220` holds an `Arc<dyn Fn(Rgb) -> String>`,
`:252-254` `Arc<Mutex<…>>` event channels, `:364` a `RefCell<…>` capture ring;
`inline_image.rs` holds `Arc<[u8]>` decoded RGBA buffers (`:98, 117, 132, 491`);
and `BoundedCache` (`crates/bt-term/src/bounded_cache.rs:83`) is documented as
single-thread-only — "there is no thread sharing: every one of these caches
lives on one thread" (`:31`) — with three consumers
(`inline_image.rs:565`, `main.rs:18639`, `main.rs:24361`), all decoded-pixel
stores.

### 3.3 The decisive fact

§1.2 ① again, because it is the whole argument: the session is constructed from
the renderer's cell height, cell width and ASCII baseline **in subpixels**, and
`bt-doc` exports `SUBPIXELS_PER_PX` for the purpose. Inline images are placed in
that grid; `MathLayoutOptions` is set from the same metrics
(`main.rs:30781-30784`). A server-side `DualPlaneSession` would have to be
handed the client's font rasterization at birth, told again on every DPI change
and every font-size change, and — the part more numbers cannot fix — would
produce **one** answer for however many clients were attached, each of which has
its own font, its own DPI and its own pane width.

**So, against the framing: the server must not own the terminal model.** What it
owns is the PTY, the byte log, the process lifetime and file access. §8.2 says
what to do with that, and §7 says who else learned it the hard way.

## 4. What already crosses a process boundary in this product

### 4.1 The attention wire, and the three rules it established

`crates/bt-app/src/attention_wire.rs` owns the grammar and
`crates/bt-platform/src/attention_pipe.rs` owns the kernel object; the split is
deliberate, because "the unsafe boundary should not have to be reopened to
change a field name" (`attention_wire.rs:3-5`). The message is one flat struct —
`attention_wire.rs:93` `Message { capability, family, event, id: Option<String>,
text: Option<String> }` — encoded at `:113`, decoded at `:135`, behind
`const WIRE_VERSION: u64 = 1` (`:108`). Three rules come out of it and **all
three transfer to a remote protocol unchanged**.

**A capability, not an address.** `FOLIO_PANE` says `<window>.<tab>.<seat>`, is
diagnostic, and is not in the message; what is in the message is 128 unguessable
bits minted when the pane was born (`attention_wire.rs:7-18`): "Coordinates can
be *guessed*, incremented, and walked… A capability cannot be walked, so a hook
that inherited one pane's environment can raise a hand for **that** pane and has
no way to name another — not because it is refused, but because it cannot say
the words."

**The payload never crosses** (`attention_wire.rs:20-27`): "the only things it
ever sends onward are the **two fields the mapping table declared**… Both are
bounded and checked; everything else in a payload stays in the hook process and
dies with it. That is not an optimisation: a channel that carried payloads would
be a channel worth attacking."

**Everything is bounded; failure is silent and counted.** `WAIT_TTL = 600s`
(`:77`), `INBOX_BOUND = 256` (`:84`), `MAX_QUOTED_CHARACTERS` (`:181`),
`MAX_PAYLOAD_BYTES = 64 KiB` (`:571`), `STDIN_BUDGET = 200 ms` (`:586`); and
below it `MAX_MESSAGE_BYTES = 4096` (`attention_pipe.rs:118`),
`MAX_FRAMES_PER_SECOND = 512` (`:135`), `MAX_INSTANCES = 4` (`:582`). The
six-clause security contract is written out at `docs/DESIGN.md:1606`. The pipe
itself refuses the network by construction (`PIPE_REJECT_REMOTE_CLIENTS`,
`attention_pipe.rs:14-16`), so the *transport* is not reusable and the
*discipline* is the part worth carrying.

There is also a shape precedent for how a server subcommand is reached.
`fn main()` (`crates/bt-app/src/main.rs:104350`) answers two doorbells before it
builds anything — `cli::attention(...)` at `:104369` and `cli::explorer_command`
at `:104379`, each exiting without a window, "because a `folio.exe` that built a
swap chain in order to write forty bytes down a pipe would be measurably the
slowest part of somebody else's program" (`main.rs:104363-104368`). A server is
that idea taken all the way: a process that never builds a window at all.

### 4.2 `bt-corpus` — a PTY byte log with timing and resize, already shipped

`crates/bt-corpus/src/lib.rs` defines a framed binary format: magic `BTCRP002`,
`initial_cols`, `initial_rows`, an optional source string, then a count and a
sequence of `CorpusEvent { at_micros: u64, kind }`, where
`EventKind = Output(Vec<u8>) | Resize { cols, rows } | Exit { code }`
(`:10-32`). `write_to` (`:61`) and `read_from` (`:92`) are hand-written — no
serde, no derive — and `replay` (`:146`) plays a corpus back deterministically
with a choice of chunking (`Chunking::{Recorded, Fixed, Pattern}`, `:35-39`), so
a byte boundary can be moved without changing the result.

`bt-pty` already writes that format from a **live** pane: `PTY_DUMP_ENV`
(`crates/bt-pty/src/lib.rs:81`), the recorder at `:162`, one file per pane with
an ordinal (`:103-110`), and a companion ledger headed
`# BT_PTY_DUMP_CHUNKS_V1 sequence elapsed_us bytes` (`:184`).

So the durable artifact a remote session needs — *what this shell printed, in
order, with its resizes and its exit* — is a format this product already writes,
already reads, already replays deterministically, already tests against, and
already compiles on macOS in CI (`.github/workflows/ci.yml:412-418`). That is
not a small coincidence. It is the strongest structural argument in this
document.

### 4.3 The only socket in the tree

`docs/DESIGN.md:6911` records the state of the world when the update check was
built: no HTTP client in a lock file of 569 packages, and first-party code that
had never opened a socket. `crates/bt-platform/src/http.rs` is what was added,
and `docs/DESIGN.md:6915` calls it the product's only socket opened by this
process — deliberately *not* a client: no redirects, no keep-alive, no POST, no
body, no caller-supplied header, no `http://`. Its one caller is
`crates/bt-app/src/update.rs:378`. A fresh grep confirms it is still the only
one: `tokio`, `reqwest`, `ureq`, `hyper`, `TcpStream`, `TcpListener` and
`UdpSocket` return zero hits across every manifest and every `.rs` under
`crates/`. There is no async runtime in this product.

### 4.4 The WSL namespace is the nearest existing "another machine's paths"

`crates/bt-transcript/src/paths.rs` declares
`PrintedPathNamespace { Windows, Msys { home }, Wsl { distro, home } }`
(`:61-106`) and translates a printed path in two steps (`to_local_path`, `:134`): a drive mount `/mnt/d/…` becomes a drive-rooted path
(`drive_mount_to_local_path`, `:218`), and anything else becomes
`\\wsl.localhost\<distro>\…` (`distro_path_to_local_path`, `:255`) — the
only producer of a UNC path this crate admits. A `~` is resolved against a home
the *shell reported over OSC 7*, folded in by `with_shell_home` (`:169`),
because the launcher cannot know it. Which namespace a pane is in is assigned at
spawn by `bt_app::profiles::printed_path_namespace`
(`crates/bt-app/src/profiles.rs:2897`) and is **never inferred from the printed
text**.

Nothing in `paths.rs` touches a disk (`:10-12`): "A candidate is a **shape**, and
the only thing that turns a shape into a link is `PrintedPathLinks`, which is
told the answers by someone who did the reading off the event thread"
(`PrintedPathLinks` at `:2418`; the `.exists()` calls live in `bt-app`, e.g.
`main.rs:78062`). And the trust rule, verbatim from `paths.rs:562-563`:

> "So: **drive-rooted, and nothing else, unless the pane itself is standing in
> the distribution the path names.**"

`may_read_unasked` (`:584-622`) enforces exactly that: a `\\wsl.localhost\` root
is admitted only when the asking pane's own namespace is `Wsl { distro:
Some(same) }`, compared case-insensitively.
`may_read_unasked_through_links` (`:644-680`) is the one function here that
touches disk, and it does a single `symlink_metadata`/`read_link` hop against
the link itself, never the target.

**This is the model for a remote namespace, in three transferable parts**: the
namespace is assigned at spawn and never sniffed; a path from a remote pane is
reachable only while that pane is still standing in that remote; and the
sentence becomes *local, and nothing else, unless the pane itself is standing on
the host the path names*.

| favicon decode | `favicon.rs:330+` | — | client |

| git | `git.rs:2121` `git_command` → `bt_platform::quiet_command` (`bt-platform/src/lib.rs:2014`) | — | **server** for the subprocess; the panel stays |

The pattern is the same in every row: **the read is the server's, the decode is
the client's**. The preview worker already says what it is — "this thread is a
disk" (`preview.rs:6810`) — and a disk on another machine is still a disk.

Two rows want naming. `DirWatch` is the single largest piece of genuinely new
platform code the server needs, because there is no portable watcher anywhere in
the workspace and no `notify` dependency in any manifest. And the WebView2
hand-off is the one place where "the client decodes" is not enough: a remote
image is shown by handing WebView2 a `file:` URL, and there is no local file to
hand it (§8.4).

## 6. Persistence

`SESSION_SCHEMA_VERSION` is **15** (`crates/bt-persist/src/session.rs:51`; the
`windows[]` promotion was v9, `session.rs:213`). `SessionV1` (`:135`) carries
`windows: Vec<SessionWindowV1>` (`:162`); a window (`:222`) carries `placement`,
`tabs`, `active_tab`, `quake`, `quake_placements`; a tab (`:476`) carries
`root: LayoutNodeV1`, `pinned`, `focused_leaf`, `preview`; and the terminal leaf
— `crates/bt-persist/src/layout.rs:108` `TermLeafV1` — carries exactly
`profile_id`, `cwd`, `manual_name`, `card_skip` and `last_command`. Bounds are
`MAX_RESTORED_WINDOWS = 32`, `MAX_RESTORED_TABS_PER_WINDOW = 128`,
`MAX_RESTORED_PANES = 512` (`session.rs:379, 383, 392`), applied by
`degrade_in_place` (`:330`). `layout.rs:100-106` says `cwd` and `profile_id`
are carried **unvalidated** on purpose, because whether a directory exists is a
filesystem question and not this crate's.

**No output history is persisted** (`session.rs:503`). A restored pane
re-spawns a shell at `cwd` and starts blank.

A remote tab's persistence is therefore small, and its shape is already right: a
leaf gains a host handle and a server-side session id — both non-secret, both
unvalidated here for the same reason `cwd` is. Nothing about the connection
belongs in this file, and under an SSH transport nothing about the connection
*exists* for it to hold. What changes at restore is the answer to a question the
file already asks: this leaf wants a shell — on which machine.

**Five things carry over, and they are unusually unanimous.**

**① The one product that put the terminal model on the server is the one that
has not finished it.** WezTerm's own open issue #106, "Revised mux/scrollback
model", is the maintainer saying the mux model "too closely mirrors the raw
terminal state API, but that isn't ideal for mux'd terminal sessions", and
listing what it costs: no local selection over text already on screen, no
keyboard selection, no proper searchable scrollback [S4]. The symptom list is
concrete — scrollback corruption when scrolling inside `less` or `man` under the
mux, mouse scroll not reaching alternate-screen applications, `ClearScrollback`
not honoured [S22][S23][S24] — and the docs still say multiplexing "is still a
young feature" [S3]. Folio's §3 reason for not doing it is different from
WezTerm's problem, but the outcome is the same one, arrived at twice.

**② The product that did it the other way is the one Folio is trying to be.**
tmux `-CC` sends structured control messages that *carry each pane's bytes*, and
iTerm2's stated motivation for consuming it is exactly Folio's pitch: without
it you are stuck with "tmux's text-mode interface: its scrollback, its copy
mode, its keybindings fighting with local ones", and with it every tmux window
is a native tab with native scrollback, copy, and search [S8]. Eternal Terminal
makes the same trade at a lower level and gets the same headline: "every byte
gets transferred… so you have local scrollback and all that jazz" [S13].

**③ mosh is the standing proof of what shipping rendered state costs.** It is
the most sophisticated screen-state protocol anyone has written, and the price
printed on the tin is that there is no history [S11]. Folio's 0.4 exists in
order to have history from another computer.

**④ Everybody delegates auth to SSH, and the two most recent products deliver
their server binary the same way.** VS Code and Zed both prefer letting the
remote download it and both keep a *local-download-then-upload-over-SSH*
fallback [S5][S14]. For Folio the fallback is the only option and that is a
feature, not a limitation: §4.3 says this product has no HTTP client outside a
Windows-only update check, so asking a remote machine to fetch a binary from the
internet is not a thing it can do or should learn to do.

**⑤ Two concrete cautions.** WezTerm has an open crash where the PDU decoder
allocates from a peer-supplied length field with no bound [S25] — the exact
failure mode a hand-rolled framed binary protocol invites, and the reason §8.5
puts a hard cap in the grammar rather than in the reader. And Zed's one
`ControlMaster` per project buys cheap extra channels at the price that when the
master dies every channel dies at once, plus the standard operational traps: a
stale control socket blocking a new master, and a `ControlPath` directory
OpenSSH will not create for you [S26][S21].

## 8. The proposal

### 8.1 The split

**A new binary crate, `folio-server`, plus a new portable library crate,
`bt-remote`. Nothing moves out of `bt-app`.**

That last clause is the surprising one and it is what §3 buys. Because the
server does not own the terminal model, it does not need `bt-term`,
`bt-detect`, `bt-viewport`, `bt-doc`, `bt-render` or any part of `bt-app`. It
needs:

* `bt-pty` — the PTY, unchanged but for the default-shell rule (§2, T2).
* `bt-corpus` — the byte-log format, unchanged (§4.2).
* `bt-persist` — `atomic_write`, for saving a remote file.
* `bt-remote` (new, portable) — the frame grammar, the declared message set,
  the version handshake, and the session log. Pure data and pure functions, no
  I/O, no platform call; it joins `scripts/check-portable-core.ps1`'s list.
* `folio-server` (new, a binary) — sessions, the file service, the process
  lifetime. Its only I/O is stdin, stdout, a pty, a directory watcher and the
  files it is asked for.

On the client the seams to cut are three, and the sizes are honest:

1. **`main.rs:30560` `create_leaf_session`** — today it spawns and constructs
   in one body. It has to grow a second source of bytes: a leaf whose `write`,
   `resize` and `read_output` go to a remote session id instead of a local
   `PtySession`. The terminal model construction beneath it does not change at
   all, which is the point of §3. **Medium** — a trait or an enum over the two,
   and the renderer-metrics half is untouched.
2. **`main.rs:75494` `drain_pty`** — must learn to drain a remote leaf's frames
   alongside a local ring, and to do it without the Win32 placement sample at
   `main.rs:75541` becoming a dependency of remote bytes arriving. **Large**, and
   the largest single item in the plan.
3. **`files.rs` / `preview.rs` / `git.rs`** — each has a small, already-isolated
   read function that has to gain a remote arm: `read_directory`
   (`files.rs:1072`), `read_head` and the worker's four `PreviewWant` arms
   (`preview.rs:6816-6832`), `git_command` (`git.rs:2121`). The worker threads
   stay; what changes is where the bytes come from. **Medium** each.

### 8.2 The wire model — recommended, with what v1 loses

**Recommendation: a declared control protocol whose terminal payload is the PTY
byte stream. The server is a PTY broker with a durable, replayable byte log and
a bounded file service. The client keeps its whole pipeline — terminal model,
transcript, detection, reflow, marks, layout, render.** This is tmux `-CC`'s
shape and Eternal Terminal's trade, not WezTerm's and not mosh's.

Five arguments, in order of weight.

**It is the only model that can be born.** §3.3: a `DualPlaneSession` is
constructed from a rasterizer's subpixels. Server-side state would have to be
told the client's font, and would have to pick one client's font when two are
attached.

**It costs nothing to serialise.** §3.1: zero serde derives exist below
`bt-persist`. Byte-log framing costs one new crate of hand-written encode and
decode in `bt-corpus`'s own style — and `bt-corpus` is the crate that already
holds the exact shape (`Output` / `Resize` / `Exit` with microsecond stamps).
Snapshot-plus-delta costs derives on `DualPlaneSession`, `HistoryDocument`,
every detection type and every transcript type, *plus* a compatibility story for
all of them across a client and server at different versions.

**It answers the owner's two requirements directly.** *History from a second
computer*: the second client attaches and the server replays the log from its
start; the client builds its own model from the same bytes that built the
first's. *An agent session that survives the client closing*: the shell is the
server's child and the log is the server's file — closing the client closes a
pipe. Neither needs a serialisable grid.

**Two clients with different window sizes stop being a bug and become an
answer.** WezTerm has a filed crash for exactly this [S4], and its docs' own
position is that the server's logical size is whatever the last client said.
With a byte log, each client reflows the same bytes into its own width. The pty
still has one size — that is `TIOCSWINSZ`'s truth, not a design choice — so
multi-client size remains a policy question (§9 Q6), but the *rendering* stops
being shared state.

**It keeps the security posture the product already has.** §8.5.

**What v1 loses by this choice**, stated plainly:

* **A cold attach replays.** A client attaching to a long-running session
  replays that session's log rather than being handed a screen. The log is
  capped by the pane's own scrollback quota (§9 Q3), the replay path is
  `bt_corpus::replay` and is already exercised by the corpus tests, and this
  work is the same work the client does when a shell prints a lot at once. It is
  not free, and it is the honest cost.
* **The server cannot answer questions about the screen.** Server-side search
  over history, a server-side "what is on this pane right now" for a headless
  tool, and any agent state derived by *parsing* rather than by a hook, are all
  out until v2 puts `bt-term` on the server as an optional second reader of the
  same log. It can be added later without changing the wire, which is the
  property that makes this the right first move.
* **Bandwidth is the shell's, not ours.** `cat` of a large file sends a large
  file. That is exactly what ssh does today and what the owner already lives
  with; §8.6 says why it is not worth pre-optimising.

**Not chosen, and why, in one line each.** Rendered screen diffs (mosh): the
history is the feature and mosh's price is the history [S11]. Server-side
terminal model (WezTerm): §3, plus the maintainer's own unfinished-business
issue [S4]. A dumb ssh pipe with no control protocol: it cannot carry a file
service, cannot survive the client, and is what a pane running `ssh` already is.

### 8.3 Transport, delivery, handshake, and the four ways it ends

**Transport: `ssh <host> folio-server --stdio`, framed on stdin and stdout.**
The client spawns `ssh` through `bt_platform::quiet_command`
(`bt-platform/src/lib.rs:2014`) — the workspace's only permitted
`Command::new`, and already the gate every subprocess passes. No socket is
opened by this process, so §4.3's record stands and `PRIVACY.md`'s claim that
Folio has no network client of its own stays true in the only sense that
matters: the bytes go where the user's own `ssh` sends them, under the user's
own keys and known-hosts.

Four transport rules, each from prior art:

* **stdout is protocol and nothing else; every diagnostic goes to stderr**
  [S27]. The remote command is invoked non-interactively so no rc file, MOTD or
  banner lands on the channel.
* **One connection, several channels, and one failure.** Zed's `ControlMaster`
  per project is the right model for a host with several remote tabs [S14]; the
  cost is that when the master dies all of them die at once [S26], so the client
  treats the master as the unit of connection health, and a stale control socket
  or a missing `ControlPath` directory is a diagnosable startup error rather
  than a hang [S21].
* **Keepalives are ssh's job.** `ServerAliveInterval` decides how long a dead
  peer takes to be noticed; the protocol does not invent a second heartbeat.
* **Framing carries a hard cap in the grammar.** WezTerm's unbounded
  length-prefix crash [S25] is the specimen; §8.5 is the rule.

**Delivery of the server binary.** Cross-compiled per target and **uploaded over
the same SSH connection** — never fetched by the remote, for §4.3's reason.
Targets: `x86_64-unknown-linux-*` and `aarch64-unknown-linux-*` (the user's
Linux GPU box is aarch64), and `aarch64-apple-darwin` (the user's Mac mini).
The client checks a version-stamped path on the remote — Zed's `~/.zed_server`
check is the model [S14] — and uploads if it is absent or the version differs.
Two decisions inside that:

* **musl over glibc, if `openpty` is there.** A static `*-linux-musl` binary has
  no libc floor at all, where VS Code's prebuilt server needs glibc ≥ 2.28 and
  has broken connections to older distributions as a result [S5][S28]. musl
  provides `openpty`, but this must be *verified in the ticket*, not assumed —
  and `cargo-zigbuild` can pin a glibc floor instead if it is not [S29][S30].
* **Cross-compilation is new to this CI.** Every job today builds natively for
  its own runner and there is no cross build anywhere
  (`.github/workflows/ci.yml`). A Linux runner cross-building aarch64 and a
  macOS runner building arm64 is the least-new-machinery answer.

**Handshake.** First frame each way: a magic, a protocol version, and the
product version. **Refuse a mismatch and say so** — do not negotiate down. This
is WezTerm's stated rule ("a compatible version must be installed" [S3]) and
Zed's ("version-checked, then re-uploaded" [S14]), and it is much cheaper than a
compatibility matrix for a protocol nobody outside this product speaks. A
mismatch is a notice with one button: upload the matching server.

**The four endings.**

| What ends | What happens |
|---|---|
| **The ssh child dies** (network drop, laptop sleep, master killed) | the server keeps running; its shells keep running; its log keeps growing. The client's remote leaves go to a *detached* state with a visible mark and a Reconnect action. This is the whole point of the milestone. |
| **The client process exits** | identical to the above; the server never learns the difference, and does not need to. |
| **The server dies** (box rebooted, OOM, killed) | its children die with it. On reconnect the client finds no session; the leaf shows what it showed and offers to start a new shell at the same `cwd` — which is exactly what session restore already does today (§6). |
| **A session's shell exits** | `EventKind::Exit { code }` is appended to the log and sent; the leaf behaves as a local exited pane does. |

Detached servers must not accumulate: a server with no client and no live child
exits; a server with live children keeps them and reaps its log by the same
scrollback quota a pane already has (§9 Q3).

### 8.4 The remote namespace

**A fourth variant beside the three that exist:
`PrintedPathNamespace::Remote { host, home }`, assigned at spawn, never
sniffed** — `profiles.rs:2897` already assigns the namespace, and
`with_shell_home` (`paths.rs:164`) already learns `~` from OSC 7, which works
identically over a remote shell because it is the *shell* that reports it.

**The trust rule extends by substitution, not by exception.** `paths.rs:562-563`
becomes: *local and drive-rooted, and nothing else, unless the pane itself is
standing on the host the path names.* A path printed by a remote pane is
readable unasked only through that pane's own server, and a local pane can never
be induced by printed text to read across the wire. `may_read_unasked`
(`:584-622`) gains one arm; `may_read_unasked_through_links` (`:644-680`) has to
be answered **by the server**, because a symlink hop is a question about the
remote's disk.

**Files column, previews, git panel** follow §5's rows: the reads go to the
server, the decode stays. **Images and PDFs are the one hard case**, because
today they are shown by handing WebView2 a `file:` URL (`preview.rs:226, 242`)
and there is no local file. Two honest options, and the recommendation is the
first: **fetch the bytes to a client-side scratch file under the same 8 MiB cap
and hand WebView2 *that***, deleted with the buffer — which keeps one code path
and one security gate; or refuse remote images in v1 and show the placeholder
the product already shows for an unreadable body. Video first frames use Media
Foundation on a local path and should simply be refused remotely in v1.

**Three verbs need answers because they mean nothing across a wire.**
*Open in Explorer* becomes **Reveal on the remote** only if something there can
reveal it, which on a headless box is nothing — so it is replaced by **Copy
remote path** and by opening the containing folder in the files column, which is
the action people actually wanted. *Drag a remote file out of the column* is
refused in v1: a drop target expects a path, and handing Windows a path that
does not exist is worse than not offering the gesture. *Drag in* is a copy —
also v1-refusable. And **`folio-here` from a remote shell** is the one that
should exist: a tiny remote-side helper (VS Code's `code` command from a remote
terminal is the pattern) that speaks the same declared protocol back up the same
channel and asks the client to open a preview or a folder — with the attention
wire's rules on it, because it is the same kind of thing.

### 8.5 Security

**The founding rule applies verbatim, and the threat model is asymmetric.**

*What a hostile client can do to a server.* It holds SSH to that account. It
already owns the account. Nothing the protocol does can make that better or
worse, and the server must not pretend otherwise by adding permission checks
that a shell would sail past. Say it once and stop.

*What a hostile server can do to a client.* Everything interesting is here. The
remote machine's administrator — or anything that has taken it — chooses every
byte the client receives. **So server messages are treated exactly as terminal
output is treated: attacker-controlled bytes, bounded, declared, and never
promoted into a path or a command on the client.** Concretely:

1. **Declared fields only, no free payload.** `attention_wire.rs:20-27`'s rule
   is the law: a field exists in the grammar or it cannot be said. No
   general-purpose string that becomes a local path, a local command, a URL to
   open, a settings value, or a file to write.
2. **A hard cap in the grammar, checked before allocation.** A length prefix is
   refused above `MAX_FRAME_BYTES` before a byte is reserved — WezTerm's open
   OOM is precisely the absence of this [S25]. Per-second frame and byte budgets
   in `attention_pipe.rs:118-135`'s style; overflow drops and counts, silently,
   as that module already does.
3. **Paths from the server are remote paths and can never be local ones.** A
   `Remote { host }` path has no local spelling; the type system should make the
   mistake unspellable rather than the review catch it. This is the same move
   `PrintedPathNamespace` already made for WSL.
4. **A capability, not an address.** Session ids are unguessable and minted by
   the server; the client never walks them, exactly as `FOLIO_PANE` may not be
   walked (`attention_wire.rs:7-18`).
5. **Terminal bytes stay terminal bytes.** Remote output goes through the same
   parser, the same OSC caps and the same clipboard refusals as local output —
   including the OSC 52 refusal and the 64 KiB OSC bound from the 2026-09-08
   audit. A remote pane must not be a second, softer door into the same window.
6. **The client never executes anything the server names.** No auto-run, no
   "the server suggests this profile", no server-supplied argv.

One more, and it is the trust boundary people forget: **connecting to a host is
a decision, and it is SSH's to record.** Folio does not manage keys, does not
store passphrases, does not implement host verification, and shows what `ssh`
says when `ssh` refuses. A host that fails verification fails in the terminal,
where the user can read it.

### 8.6 Latency

Over a WireGuard-based mesh on a home network the round trip is roughly
10–40 ms. Typing feels wrong when the echo of a keystroke is late, and the
threshold where humans reliably notice is far above that: mosh's own measured
case was a 3G link with median 503 ms, where prediction moved it under 5 ms
[S12], and mosh *itself* only shows predictions adaptively on high-delay links
[S11]. Meanwhile the client-side pipeline this product already runs — parse,
detect, reflow, shape, present — costs a frame or two of its own on every
keystroke locally.

**Recommendation: no prediction in v1, and no local echo.** A predicted
character is a lie the client tells about a program it is not running, and the
one class of program most likely to be in these panes — a full-screen TUI, an
agent's approval prompt — is exactly the class where prediction is wrong.

**The measurement that would overturn this**, and it should be taken in T12
rather than argued: instrument the client to stamp a keystroke on send and stamp
the first byte of output attributable to it, and record the distribution over a
real working session on the user's own two machines. If the median
keystroke-to-glass exceeds about 80 ms, or the tail past 200 ms is more than a
few percent, revisit — and revisit with mosh's rule, not with unconditional
echo: predict only when the measured RTT says to.

### 8.7 Out of scope for v1, and what v2 adds

**v1 is:** a remote tab; full-control remote shells with the client's whole
terminal pipeline; the transcript blocks, marks, detection and formulas that
follow from it for free; the files column on the remote disk; previews and
editing of remote text files; the git panel on the remote repository; a session
that survives the client and can be reattached; and persistence of which host a
leaf belonged to.

**Out of v1:** agent state and notifications over the wire; more than one client
on one session; server-side search; remote video first frames; drag-and-drop of
remote files; port forwarding of any kind; a remote web pane; anything that
requires a GUI on the remote; and any transport that is not `ssh`.

**v2 adds**, in the order they become possible: agent state and notifications
(the attention wire's `Message` grammar gains a transport, and the hook on the
remote reaches the local window through the same declared, bounded channel —
this is the milestone the 2026-09-09 agents research was written for, and it
needs `tool_name` as its one new declared field, `agents research §6.2`);
several clients on one session, which the byte log makes cheap because each
client reflows for itself; an optional `bt-term` on the server, reading the same
log, purely so that headless questions can be asked of it; and the named
instances idea, which turns out to be the natural name for "the agent that lives
on that box" and should be designed *with* remote rather than before it.

## 9. Open questions

Each with a recommendation.

1. **Does the server own the terminal model?** — **No** (§3). This is the one
   place this document departs from the framing it was given, and the evidence
   is `create_leaf_session`'s signature (`main.rs:30560-30561, 30778-30780`),
   zero serde below `bt-persist`, and WezTerm's own open issue about the model
   it chose [S4]. If it is overturned, everything else in §8 changes with it, so
   this is the ruling to take first.
2. **Is the server a separate binary or a `folio` subcommand?** —
   **Separate.** `bt-app` does not compile off Windows and will not until 0.5
   (`macos-spike:47-49`); a subcommand would mean the server could only ship on
   the one platform it will never run on. A single binary becomes possible after
   the port and is not worth waiting for.
3. **How much log does a session keep?** — **The pane's own scrollback quota,
   in bytes, trimmed from the front.** It is a number the product already has an
   opinion about, a person already sets, and the alternative — an unbounded file
   on somebody's server — is the kind of thing that is discovered at 3 a.m.
   Trimming from the front means a cold attach shows exactly as much history as
   a local pane would.
4. **What does a cold attach cost?** — **Measure in T4**, before T5 depends on
   it. Replaying a full quota through `bt_corpus::replay` into a
   `DualPlaneSession` is the same work as a shell printing that much at once,
   and the product already has a budget test for that shape
   (`main.rs:95401 mod pty_drain_budget_tests`). If it is too slow, the fix is
   to replay in the background and show the tail first, not to change the wire.
5. **Does the client fetch remote image bytes for WebView2?** — **Yes**, to a
   capped client-side scratch file deleted with the buffer (§8.4). The
   alternative refuses a whole class of file for an implementation detail of the
   pane, and the cap is already `PREVIEW_EDIT_BYTES` (`preview.rs:76`).
6. **When two clients attach, whose window size does the pty get?** — **The
   last one to resize**, with a visible mark on the others, which is WezTerm's
   answer [S1] and tmux's. v1 has one client, so this is a v2 ruling — but the
   byte log means the *rendering* is per-client regardless, which is the half
   that usually hurts.
7. **musl or glibc for the Linux server?** — **musl, if it provides `openpty`
   for the vendored backend; verify in T6, do not assume.** A static binary has
   no libc floor, where VS Code's prebuilt server needs glibc ≥ 2.28 and has
   broken real connections because of it [S5][S28]. Fall back to
   `cargo-zigbuild` with a pinned floor [S29].
8. **Does the client ever let the remote download its own server?** — **No**
   (§4.3, §8.4). This product has no HTTP client outside a Windows-only update
   check, and a remote machine fetching a binary from the internet on Folio's
   instruction is a supply-chain surface the product does not currently have.
   Upload over the connection that is already open.
9. **Does `folio attention` work from a remote agent in v1?** — **No**, and it
   is the single most valuable thing v2 adds. The grammar already exists
   (`attention_wire.rs:92`), the discipline already exists
   (`docs/DESIGN.md:1606`), and what is missing is a second transport for a
   message type that was designed to have one. Doing it in v1 would mean
   shipping the agent surfaces the owner deliberately paused on 2026-09-10.
10. **What replaces "Open in Explorer" on a headless box?** — **Copy remote
    path, and open the containing folder in the files column** (§8.4). Not a
    remote file manager, and not silently doing nothing.
11. **Does a remote pane get the shell-integration scripts?** — **Yes**, and it
    is nearly free: `shell_integration.rs` is portable text, and bash and zsh
    integration already exist and were hardened in the 2026-09-08 audit. The
    server installs nothing; the scripts ride the spawn, exactly as they do
    locally.
12. **Does the WSL namespace survive?** — **Yes, untouched.** A remote pane on a
    Linux box and a local WSL pane are different things that happen to print
    similar paths, and §4.4's rule keeps them apart by construction: the
    namespace is assigned at spawn, so a pane can only ever be in one of them.
13. **Does the server need its own settings file?** — **No.** Everything it
    needs arrives in the session-open message. A configuration file on the
    remote is a second place for an answer to live and a thing to migrate.
14. **Is there a `folio server` management surface?** — **Minimal in v1**:
    listing sessions and killing one, over the same protocol, from the client's
    UI. Not a CLI on the remote — a CLI on the remote is a second product with a
    second grammar to keep compatible.
15. **What happens to the update check for a remote server?** — **Nothing; the
    client is the version.** T6's handshake refuses a mismatch and offers to
    upload, which makes the server's version a consequence of the client's
    rather than a thing anybody maintains.
