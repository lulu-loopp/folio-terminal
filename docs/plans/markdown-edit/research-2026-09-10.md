# Editing a Markdown file in place — research for 0.3

2026-09-10. Branch `docs/md-edit-research` off `main` at `7153668`. This is
research, not a design: no product code is touched, nothing is built, and
nothing here is decided. Every claim about this codebase carries a `path:line`;
every claim about another product carries a source, and the list is §11.

The order for the next two releases is ruled — **0.3 = editing a Markdown file
in place**, **0.4 = the macOS port** — and the framing accepted for 0.3 is the
*live-preview* model: the block under the caret shows as source, every other
block stays rendered, leaving the block renders it again. Two constraints are
hard. Everything must live above the platform boundary, because 0.4 ports
`bt-platform` and the modules that consume it and nothing else. And the edited
file must stay **byte-identical outside what the person changed** — encoding,
BOM, line endings, trailing whitespace, the missing final newline.

---

## 0. The short answer, before the evidence

Three facts decide the shape of this work.

**The source face is already an editor.** `crates/bt-app/src/preview_edit.rs`
(1,072 lines) is a complete plain-text edit model — caret as a byte offset,
selection, wrapped-row Up/Down, CRLF-safe boundaries, tab stops, clipboard, IME
— and it is wired to a real save with atomic write and mtime conflict
detection. A `.md` file flipped to its source face is editable today
(`crates/bt-app/src/preview.rs:519`).

**The rendered face is already caret-precise on the glass.** `preview_place_at`
(`crates/bt-app/src/main.rs:53064`) turns a pointer position into
`preview_select::Place { block, piece, offset }` by re-shaping the paragraph
under the pointer with the very shaper that drew it
(`crates/bt-render/src/lib.rs:10565`). Selection, word grain, highlight bands
and copy all work over it (§7.31, `docs/DESIGN.md:5254`).

**The bridge between them does not exist.** `parse_markdown`
(`crates/bt-app/src/preview.rs:2062`) discards every source position it walks
past, and neither `MarkdownBlock` (`preview.rs:903`) nor `Span`
(`preview.rs:772`) carries a byte range, a line number or an offset. A `Place`
names a byte in *rendered* text — a heading without its `#`, a quote without
its `>`. `docs/DESIGN.md:1470` states the consequence as settled fact:
「渲染后的 markdown 没有第 573 行——它的块不带源行号」, which is why a
`file:573` hyperlink flips the pane to source instead of scrolling the page
(`main.rs:72733`).

So this feature is not "write an editor". It is **give the parse a memory of
where it came from, and then let the editor that exists work one block at a
time.**

## 1. The Markdown pipeline

### 1.1 The parser is ours

There is no Markdown crate in the workspace — no pulldown-cmark, no comrak, no
markdown-rs. Every manifest was grepped; the only `markdown` string in any of
them is a prose comment at `crates/bt-app/Cargo.toml:54`. Two entry points, both
in `preview.rs`:

* `parse_markdown(src: &str) -> Vec<MarkdownBlock>` — `preview.rs:2062`
* `parse_inline(line: &str) -> Vec<Span>` — `preview.rs:1111`

`parse_inline` is a real CommonMark implementation: two claiming scans for
backticks and math producing `ClaimedRun` byte ranges of the line
(`preview.rs:1266`, `:1280`), one left-to-right walk with a bracket stack
(`preview.rs:1301`, `:1323`), then a delimiter-stack pass `resolve_emphasis`
(`preview.rs:1863`) that cites CommonMark §6.2/§6.3 and uses
`unicode-properties` for the flanking rule.

`parse_markdown` has exactly one product caller — `main.rs:55030` — plus one
that will surprise a reader: `crates/bt-app/src/attention_words.rs:91` uses it
to pull the first prose block out of an agent's last message. Any change to its
signature touches the attention work.

### 1.2 The block model

A document is a **flat `Vec<MarkdownBlock>`**. No tree, no nesting. Ten
variants at `preview.rs:903`: `Heading{level,spans}` (:904),
`List{ordered,items}` (:913), `Code{lang,text}` (:923),
`Table{rows,alignments}` (:936), `Quote` (:950), `Rule` (:952), `Paragraph`
(:953), `Math{source}` (:975), `Image` (:990). Inline is
`Span { text, style, target }` (`preview.rs:772`) with eight styles
(`preview.rs:718`).

Not modelled at all, verified by grep: task-list checkboxes, footnotes, YAML
front matter, nested lists, indented code blocks, setext headings (refused on
the record, `preview.rs:2679`), reference links, generic HTML blocks — only
`<img>` and `<picture>`.

### 1.3 Source byte ranges — the crux

**No block and no span carries a source position of any kind.** The only
`Range` in the pipeline is `ClaimedRun` (`preview.rs:1266`), scoped to one line
inside `parse_inline` and discarded before a `Span` is built.

The good news is that the walk has the index in hand: `parse_markdown` collects
`lines: Vec<&str>` (`preview.rs:2063`) and steps a `let mut index = 0usize`
(`:2069`). Every branch advances `index` by whole lines and every
`blocks.push(...)` happens at a known one — the fence (`:2075`), display math
(`:2100`), the bracket spelling (`:2150`), the HTML image (`:2166`), the table
(`:2177`), the heading (`:2199`), the rule (`:2211`), the quote (`:2226`). For
those, emitting a range is mechanical. Three things still have to change:

1. **A line index is not a byte offset.** `str::lines` strips the newline *and*
   a trailing carriage return, so a CRLF file's line length is not `line.len()`.
   What is needed is a vector of line starts — and it exists already, as the
   editor's own `preview_edit::line_starts` (`preview_edit.rs:42`), which
   additionally counts the trailing empty line that `str::lines` denies.
2. **Two accumulators have already destroyed their source when they flush.**
   `paragraph: Vec<&str>` (`preview.rs:2068`) holds slices of the source and is
   flushed through `join_source_lines` (`preview.rs:2586`), which trims each
   line and joins with a space; `list: Vec<String>` (`:2067`) stores each item
   with its marker stripped and lazy continuations appended with a space
   (`:2218`–`:2225`). Each needs a parallel vector of the lines it consumed.
3. **The range has to live somewhere.** `MarkdownBlock` derives `Eq, PartialEq`
   (`preview.rs:902`) and is compared by value in dozens of assertions across a
   4,200-line test module, and it is shared with the terminal —
   `crates/bt-app/src/table_block.rs:63,76` builds terminal table blocks out of
   `preview::TableRow`. Adding a field to the enum makes every one of those
   comparisons range-sensitive. §9.2 recommends a parallel vector instead.

How faithful could a range be? Every payload is a *normalised* rendering, never
the source bytes: a fence loses its markers, its info string and every carriage
return (`preview.rs:2091`); display math loses its delimiters and trims each
line (`:2110`); a heading loses its hashes (`:2645`); a list item loses its
marker and indent (`:2654`); a quote loses its angle bracket (`:2672`); a table
loses its pipes and its separator row (`:2726`); a paragraph loses per-line
indentation and its newlines (`:2586`). A blank line belongs to no block at all
— it is consumed by the flush arm at `:2205`. So a block range is the *span the
block was parsed from*, and the bytes between block ranges are the document's
own connective tissue. A save that rewrote one block must therefore splice, not
rebuild.

### 1.4 Re-layout: the whole document, every time

The single entry point is `rebuild_preview_document` (`main.rs:54838`). It
computes a two-level key (`main.rs:2358`, `:2379`):

* same `PreviewParseKey`, different width or art → **reflow only**; the blocks
  and intrinsics are moved out with `std::mem::take` and only `lay_markdown_out`
  re-runs (`main.rs:54873`–`54945`). This was the fix for the 2026-08-13
  resize-stutter report (`main.rs:1450`).
* different parse key → **full re-parse** of the whole 64 KB head, then math
  resolution, picture resolution, intrinsic measurement and layout
  (`main.rs:55028`–`55060`).

`PreviewParseKey.revision` is a whole-buffer counter (`preview.rs:3830`) bumped
by `edit_content` (`:4365`), by `accept` (`:4544`) and by `decline` (`:4520`).
**One keystroke bumps it, so one keystroke re-parses, re-highlights and
re-measures the entire document.** Caching that exists: `MarkdownBlockIntrinsic`
(`main.rs:1462`), the width-free per-block measurements including a fence's
syntax highlighting — cached per whole-document content and thrown away on any
edit; `highlight.rs:33` says so in as many words. The one cache that *survives*
an edit is `PreviewMathKey` (`main.rs:1494`), content-addressed on the LaTeX
text, so every unchanged formula re-finds its raster after a re-parse. There is
no shaped-glyph-run cache: shaping happens in `measure_markdown_block`
(`main.rs:55478`) and again per frame in `build_preview_markdown_body`
(`main.rs:4324`), which lays out **only visible blocks** (`main.rs:4386`).

### 1.5 Per kind

* **Display math** — `MarkdownBlock::Math{source}` with delimiters stripped
  (`preview.rs:975`, `:2100`, `display_math_block` `:2299`, 23 environments at
  `:1646`). **Inline math** — `SpanStyle::Math` stored *with* its delimiters
  (`preview.rs:742`), collected by `document_formulas` (`main.rs:3580`) and
  handed to `crates/bt-math` (`MathEngine`, `bt-math/src/lib.rs:178`) which
  returns an RGBA raster asynchronously; arrival bumps art, not parse
  (`main.rs:2364`).
* **Tables** — recognised only under a separator row (`preview.rs:2177`,
  `:2701`), alignments read by `bt_detect::table::delimiter_row` (`:2715`), the
  same parser the terminal's own detector uses.
* **Code fences** — three-backtick only, and an unclosed fence still renders
  (`preview.rs:2075`, `:2087`). Highlighting is syntect + two-face in
  `crates/bt-app/src/highlight.rs`, seven token classes onto palette inks, with
  a line cap and a byte cap past which it is silently empty
  (`highlight.rs:673`).
* **Images** — a picture is always its own block: an inline image becomes a span
  and is then cut out of its paragraph by `push_prose` (`preview.rs:2610`), so
  prose with a picture in the middle of it is three blocks. Sources stay
  unresolved strings.
* **Links** — `Span::target` verbatim and unresolved; resolution is
  `link_action` (`preview.rs:5655`), which needs the document's own path.
* **Task lists, footnotes, front matter** — not implemented. A leading rule
  spelling is read as `Rule` (`preview.rs:2683`) and the YAML under it becomes
  paragraphs.

### 1.7 `bt-doc` is a false friend

`ContentAnchor` (`crates/bt-doc/src/anchor.rs:26`) addresses a `TranscriptId`
plus a `GraphemeOffset`, or a row and column in a terminal grid. `VersionStamp`
(`bt-doc/src/versions.rs:165`) carries four generations; `LayoutKey` (`:111`) is
measured in `width_cells`, a monospace notion. Four reasons it does not apply:

1. `preview.rs`, `preview_edit.rs` and `preview_watch.rs` reference `bt_doc`
   **zero times**. The pipeline has never used it.
2. The coordinate is wrong. `preview_select.rs:5` says so directly: a rendered
   Markdown page "is neither" of this window's two selection models — "there is
   no grid to count and there is no one string to index".
3. The lifecycle is append-only by construction: `SourceLifecycle::transition`
   (`versions.rs:73`) accepts exactly one move, live to frozen, and
   `HistoryDocument` (`document.rs:27`) is frozen lines plus tombstones. An
   editable document is the opposite shape.
4. `LayoutKey`'s identity is a cell width; a rendered page's is a float pixel
   width and a measure box (`preview.rs:3073`).

What *is* worth stealing is the discipline, not the types: the two-level split
and "every field participates in cache identity" is what `main.rs:2358`–`2385`
already copies. An in-place editor extends that key; it does not adopt `bt_doc`.

## 2. Selection on the rendered face

The unit is the **piece** — `preview_select.rs:14`. `Place { block, piece,
offset }` (`:50`) derives `Ord` with the fields in reading order (`:44`), so
"which end is first" is a comparison rather than arithmetic. `Selection {
anchor, head, grain }` (`:103`) with `Grain::{Character, Word, Piece}` (`:82`).
`Piece { at, lead, prefix, text, atomic }` (`:247`) where `text` is "what is
read here, exactly as it is set on the glass" (`:262`).

**The mapping does not reach source offsets.** `offset` indexes `Piece::text`,
which is assembled from span texts by `span_text` (`:450`): a quote has dropped
its angle bracket (`:329`), a fence line is tab-expanded to what was drawn
(`:343`), a heading has no hashes. The one place two byte-spaces are reconciled
is glass against rendered document, not document against file: `PreviewTextAtom
{ shaped, doc }` (`main.rs:3382`) exists solely because an inline formula with a
picture is shaped as one no-break space (`bt-render/src/lib.rs:10637`).

What lands on the clipboard is **what was read**, with three declared
exceptions: a list marker (`preview_select.rs:442`, written only when the
selection reaches the item's start), display math with its delimiters (`:375`),
and an image as its full inline spelling (`:401`). Separators come from `Lead`:
a blank line between blocks, a newline between lines, a tab between cells
(`:232`).

§7.31 (`docs/DESIGN.md:5254`–`5289`) rules the rest, and two of its clauses are
directly load-bearing here. ③ (`:5269`): the unit is the piece because only
visible blocks are laid out, so `PreviewBody::paragraphs` renumbers on every
wheel notch — any caret model must be document-anchored, never glass-anchored.
⑩ (`:5289`): a selection survives scroll and `reflow_document` and **dies on
`show_document`**, that is, on every re-parse (`main.rs:2725`), because the
commonest reason for a re-parse is the file changing underneath and a kept
selection would highlight somebody else's sentence. An editor that re-parses on
every keystroke would drop its own selection on every keystroke.

And the keyboard clause (`:5283`) is a forward reference to this very ticket:
Shift with an arrow is refused on the record because 「在一页不能打字的文档里
移动 caret,是块级编辑那一片的开头」 — restated in code at `main.rs:18924`.

Hit-testing exists at three grains. To a block box: `PreviewTextBox { piece,
rect, clip, paragraph }` (`main.rs:3507`), stored per frame as `pane.md_text`
(`main.rs:2648`), resolved by `preview_text_box_at` (`main.rs:5080`) with exact
containment, then nearest-on-row, then nearest-vertically, so it never answers
nothing for a page with any text. To a link: `preview_link_at`
(`main.rs:52918`) over run boxes from `measure_preview_run_boxes`
(`bt-render/src/lib.rs:6498`). To a character: `preview_place_at`
(`main.rs:53064`) into `measure_preview_hit` (`bt-render/src/lib.rs:6512`) into
`preview_hit` (`:10565`), which **re-shapes the paragraph** and asks cosmic-text
for the cursor index. Layout is deliberately not retained per glyph — only the
paragraph description, its drawn rect and its clip — and every glyph-level
question re-shapes one paragraph lazily (`bt-render/src/lib.rs:6492`).

So the glass-to-document half is finished and caret-precise. The
document-to-file half is the work.

## 3. Text input we already own

**Three editors, not one.**

`TextField` (`crates/bt-app/src/text_field.rs:57`) is the capable single-line
one: byte caret on a character boundary, anchor-and-caret selection (`:119`),
word-wise motion (`:41`, boundary at `:303`), `delete_word_back` (`:218`), Home
and End with shift, and a real IME split — a separate `preedit` field (`:74`)
spliced at the caret by `composed()` (`:156`) without touching the committed
buffer. No undo, no mouse, no scroll offset. Used by the palette
(`palette.rs:1496`), in-pane search (`search.rs:346`), the commit-graph search
(`main.rs:16467`), the git prompt (`main.rs:6166`) and every settings text row
(`settings.rs:5167`, `:5186`).

`TabRename` (`main.rs:17015`) is the second and weaker one — the tab, files-row,
breadcrumb and address rename field, with its own scroll offset, no word verbs,
no clipboard, no undo, and IME commit only with no pre-edit drawn
(`main.rs:86840`). `text_field.rs:19` records it as debt: it "should migrate to
this, and is deliberately not migrated by this slice".

`preview_edit` is the third, and it is not a widget — it is a **pure multi-line
arithmetic model** over a mutable `String` and a byte offset. It already solves
what a block editor needs most: `line_starts` (`:42`), `WrapLayout` with
`row_of`/`row_span`/`line_of_row` (`:198`–`:297`) so Up and Down work on wrapped
rows, `eol_of`/`with_eol` (`:300`, `:315`) so a CRLF file stays a CRLF file,
`normalize` (`:332`) as the single place a caret is kept off the seam inside a
CRLF pair, `EditCaret { anchor, caret, desired_column }` (`:360`), ten
`Motion`s (`:422`), and a **total** `EditCommand` mapping (`:443`, `command` at
`:473`) — every key that reaches the surface has a verb, including `Ignore`,
because "the editor owns the keyboard outright while it is focused" and a key
with no verb is swallowed rather than sent to a shell nobody is looking at.

What none of the three has: **undo and redo**. Zero occurrences in any of them,
and `preview.rs:3818` says it outright — "the undo history a real editor would
compare against does not exist here", which is why the dirty bit is set by the
first change and cleared only by a save. `preview_edit` also has no word-wise
motion (`Motion` has no `WordLeft`), which `TextField` does; that is a port of
one function.

## 4. Files in and out

**The read.** `read_head` (`preview.rs:5296`) checks
`bt_transcript::paths::may_read_unasked_through_links` *first* (`:5304`) so a
blocking open never lands on a named pipe, then opens the file and takes
`PREVIEW_HEAD_BYTES + 1` bytes (`:5320`) — one byte over the cap so truncation
is known without a second stat. `may_read_unasked`
(`bt-transcript/src/paths.rs:584`) permits a drive-rooted local path and a WSL
share only when the pane asking stands in that distribution, and refuses UNC
shares, device namespaces and verbatim spellings.
`files_a_tab_stands_on` (`main.rs:32253`) collects every path a tab's preview
state depends on so the folder-watch set can be derived.

**The cap is 64 KiB, not 16 MiB.** `PREVIEW_HEAD_BYTES = 64 * 1024`
(`preview.rs:56`). The 16 MiB figure belongs to `MAX_DOCUMENT_BYTES`
(`bt-persist/src/migrate.rs:1298`), which guards the settings and session
documents, not previewed files. Past the cap a buffer is `truncated`, and
`PreviewBuffer::is_editable` refuses (`preview.rs:4345`) — the comment at
`:4335` says why: "an edit surface over the head of a file is a save button
wired to `truncate`". **`docs/DESIGN.md` is far over 64 KB, so the document that
motivates this feature cannot be edited in the pane today.**

**Encoding.** `HeadEncoding::of` (`preview.rs:5089`) recognises a byte-order
mark and nothing else, by ruling, because "a mark is the file saying what it is"
and a wrong guess is worse than a refusal (`preview.rs:5064`). UTF-16 is read
because Windows PowerShell 5.1 writes it. CRLF, trailing whitespace and a
missing final newline are all preserved on read: `decode_head` (`:5378`) only
decodes bytes to characters.

**But the encoding is then thrown away, and this is a live defect.**
`PreviewBuffer` (`preview.rs:3802`) has no encoding field; `accept` (`:4547`)
takes the already-decoded string with the mark stripped by `HeadEncoding::body`
(`:5119`); and `save_atomically` (`:5269`) writes the content as UTF-8 bytes. So
**editing a marked UTF-8 file or a UTF-16 file today silently rewrites it as
UTF-8 without a mark**, and a body that decoded through `from_utf8_lossy`
(`:5393`) would write its replacement characters into the file. There is a
correct precedent one module over: `shell_integration::add_to_profile`
(`shell_integration.rs:1273`) is a genuine round-trip of a user's own file, and
it explicitly refuses UTF-16 (`:1283`) and detects the line ending from the
existing bytes (`:1303`) before writing. That is the guard the preview save is
missing.

**The watcher.** `preview_watch.rs` subscribes one shallow directory watch per
containing folder, kernel-driven and never polled, and re-checks metadata only
when the kernel names the entry, debounced by a 300 ms quiet window
(`watch_clock.rs:33`). `note_disk_moved` (`preview.rs:4257`) decides in order:
gone, so `DiskNews::Deleted`; **dirty and moved, so `DiskNews::Changed`, edits
stand, no re-read** (`:4270`); clean and moved, so a quiet re-read that does not
make the body on screen flash away (`:3872`). So "the file changed under us
while we hold unsaved state" is already a modelled state with two answers,
`take_the_disks_copy` (`:4291`) and `keep_this_body` (`:4306`), and a later save
still returns `SaveOutcome::Conflict` on mtime (`:4392`).

**The write.** Two parallel implementations of the same algorithm exist:
`bt_persist::atomic_write` (`bt-persist/src/atomic.rs:25`) and
`preview::save_atomically` (`preview.rs:5269`). Both stage a same-directory
sibling, sync it, then rename. The `bt-persist` one is *not* welded to the
config directory — `temp_sibling_path` (`atomic.rs:82`) derives from the
target's own parent, and it already writes the PowerShell profile
(`shell_integration.rs:1341`) and an agent hook file
(`attention_hooks.rs:496`). Neither handles a read-only or hidden target
attribute, an ACL, or a symlinked target — a rename replaces the link, not what
it points at, and nothing on the write side asks the question the read side asks
with `may_read_unasked_through_links`. `write_tracker.rs` and `debounce.rs` are
generic and would serve an autosave unchanged.

## 5. Keyboard and mouse

The table is `BINDINGS` (`shortcuts.rs:768`–`1303`), **41 rows**, a struct per
row rather than an enum dispatch (`Binding`, `:514`), looked up by one linear
find guarded by scope (`:1707`). Overrides go to `keybindings.json` matched by
stable id, never index (`bt-persist/src/keybindings.rs:49`, applied
`main.rs:32459`). The generated reader's table is `docs/shortcuts.md`, held by
`scripts/check-shortcuts-table.ps1`.

`Scope` (`shortcuts.rs:302`) is the load-bearing part: `Window`, `Preview`,
`TerminalPrimary`, `SearchOpen`, `WebPage`, `SearchHost`. Discipline ① — never
take a bare Ctrl-and-a-letter from the terminal — is what makes `Scope::Preview`
exist: Ctrl+S is `Action::SavePreview` scoped to a focused preview
(`shortcuts.rs:1061`), because "there is no terminal in a page".

The chord space an editor needs is unusually free:

| Chord | Status |
|---|---|
| Ctrl+S | **Taken**, `save-preview`, `Scope::Preview` (`shortcuts.rs:1061`) — and already in force over a focused *rendered* page, because `Focus::preview` is `preview_keyboard_surface().is_some()` (`main.rs:53675`) |
| Ctrl+Z, Ctrl+Y, Ctrl+I, Ctrl+K, bare Ctrl+B, bare Ctrl+D | free — no row; bare control letters are left to the shell (`shortcuts.rs:765`) |
| Ctrl+Shift+Z | **Taken** by Cards (`shortcuts.rs:955`), so redo cannot be the usual Ctrl+Shift+Z |
| Tab, Shift+Tab, Ctrl+Backspace, Ctrl with an arrow, Home and End | free at window level, answered per surface |
| Enter, Ctrl+Enter | **unbindable by rule** — no row may be keyed on Enter in any combination, measured twice and enforced by a test (`shortcuts.rs:788`, `:3548`) |
| Ctrl+Alt with anything | **the AltGr forbidden zone** — refused because Windows reports AltGr as that pair (`docs/DESIGN.md:1245`, enforced `shortcuts.rs:2224`); `preview_edit.rs:477` already treats it as typing |
| Ctrl+F | scoped `SearchHost`, meaning a terminal or a web page (`shortcuts.rs:441`), so it is **not** live over a rendered document |
| Ctrl+Home, Ctrl+End | taken outside the table, hardcoded scrollback keys on a focused terminal (`main.rs:86598`) |

Routing is a ladder in `keyboard_input` (`main.rs:85901`): files tree
(`:86670`), then `preview_key` (`:86680`), then the search field, then the PTY
encoder. `preview_key` (`main.rs:53864`) hands everything to
`preview_edit::command` when the source face has focus, otherwise falls to
`preview_browse_key` (`:53951`) — "one key with the preview seat focused and
**nothing to type into**" — whose last arm returns having consumed the key
(`:54080`). **A plain letter pressed on a rendered Markdown pane today does
nothing and is swallowed**, deliberately, so it cannot reach a shell nobody is
looking at.

IME arrives straight from winit into `bt-app` (`main.rs:97524` into `ime_input`
`:86809`) and is routed by `ImeOwner` (`:14900`) to nine surfaces. The preview's
own is `preview_ime` (`:54099`): pre-edit into `window.preedit`, commit through
`insert_into_preview` — the same door a typed character uses. Candidate
placement is per surface, and it is **monospace grid arithmetic**:
`preview_ime_cursor_area` (`:54142`) builds the rect from
`preview_caret_position` and `mono_advance`, then `apply_ime_cursor_area`
(`:73621`) calls winit's `set_ime_cursor_area` and
`bt_platform::ImeSystemCaret::update` (`bt-platform/src/lib.rs:5524`).
Clipboard is raw Win32 inside `bt-platform` (`:4664`, `:4708`) — no `arboard`,
no winit — and the preview's copy goes through the wrapper the terminal
selection uses (`main.rs:97878`, called from `:53264`).

## 6. Where the preview pane lives

**A buffer belongs to a file; a pane is a view** (§7.1.3,
`docs/DESIGN.md:932`; `preview.rs:4` restates it). Each tab owns one
`PreviewPool` (`preview.rs:4616`) keyed by `PreviewSource`, capped at eight
clean buffers, with dirty and on-screen buffers never evicted. **A file open in
two panes is the same buffer, so edits cannot fork**, while each surface keeps
its own caret and scroll in `PreviewViewState { caret, scroll }`
(`main.rs:2398`) — ruling 8⑧, "a buffer belongs to a file; a caret, a selection
and a scroll offset belong to the view looking at it". `pane.md_source` is per
surface too (`main.rs:2684`, flipped at `:51507`), so one document can be source
in one pane and rendered in another at the same instant.

There are three surfaces: `PreviewSurface::Seat` (docked), `Float` (the tear-off
window, second tenant of the floating chassis, `main.rs:2459`), and `Peek` (the
hover glance card, read-only by the 2026-08-13 ruling, `:2461`). §7.31 ⑥
(`docs/DESIGN.md:5630`) already ruled that a float selects exactly as a pane
does, by **one dispatch line, not a second model** — the precedent an editable
face should follow.

The focus-card projection never fetches: `focus_thumb.rs:421` — "a thumbnail
must not put a question to the disk" — and `document_head` (`:1334`) slices only
what the buffer already holds. An editable document changes nothing there; a
card already draws a dirty pool buffer, because a glance that showed the disk's
copy would be a glance that lies.

**The WebView2 route is out of scope, and this is the once it is said.** An
`.html` name routes to `PreviewFtype::Web` (`preview.rs:431`) and is drawn by
the composition-hosted engine (`bt-platform/src/webview.rs`), a wholly separate
path from the Markdown renderer. Its source face is already this window's own
editor by §7.32 (`docs/DESIGN.md:5324`), and that is a different face of a
different engine. Nothing proposed here touches it.

## 7. Portability

`scripts/check-portable-core.ps1` forbids the Win32 crates and
`std::os::windows` inside thirteen named crates unless the item is under a
`#[cfg(windows)]` gate; **`bt-app` is deliberately not in that list** (`:36`),
because it is what has not been ported yet.
`scripts/check-adapter-boundary.ps1` is the other half — the terminal's vendor
seam may not import a policy crate — and does not bear on this work.

Every platform call an in-place editor needs already has an adapter:

| Need | Adapter | Where |
|---|---|---|
| Clipboard get and set | yes | `bt_platform::clipboard_text` / `set_clipboard_text`, `bt-platform/src/lib.rs:4664`, `:4708` |

fidelity on the write side (§4), and that is pure Rust.

**What carries over.** Four things. (1) The rule everyone who does this has
converged on is the same rule: *the marks come back when the caret is inside the
element*, and nothing else — Obsidian's own predicate is literally "does any
selection range intersect this node" [S1]. (2) Everyone who tried to keep a
table rendered while it was edited ended up building a second editor for it, and
Obsidian's own users then asked for the plain text back [S3][S4]; a table that
shows its source under the caret is the cheaper and more honest answer. (3)
There are two families — hide the marks per element (Obsidian, Bear) and hide
them all with a whole-document escape (Typora, MarkText, Zettlr) — and Folio
**already owns the escape**: `md_source` is Typora's Source Code Mode, shipped,
per surface. What it is missing is the first family. (4) iA Writer is the
standing reminder that this is a preference and not progress; the flip stays.

One thing does *not* carry over: continuous save. Obsidian's two-second autosave
is the behaviour its own users wrote a plugin to defeat [S5], and it lives
inside a vault the app owns. Folio edits other people's repositories, where a
save fires a watcher, a formatter or a hook.

## 9. The proposal

### 9.1 The editing model for v1

**One rule, and it has no exceptions: the block whose source range contains the
caret is drawn as source; every other block is drawn rendered.**

Nothing is "not editable in place". A table under the caret shows its pipes; a
fence shows its markers, still syntax-highlighted, because the highlight is
already computed per content; display math shows its delimiters and its raster
disappears until the caret leaves; an image shows its inline spelling. This is
the only rule the codebase can hold consistently, and it is why: a rendered
block is proportional, wrapped and sometimes a picture, while `preview_edit`'s
entire arithmetic — a column is x over the monospace advance, wrapped rows, tab
stops, the IME caret rect — assumes a monospace grid, and `docs/DESIGN.md:5260`
says this is exactly why the source face's arithmetic cannot be ported to the
rendered one. Turning the block under the caret into a monospace body is not a
compromise; it is the one move that lets the existing editor be *reused
unchanged* instead of rewritten.

**The caret stays a byte offset into the file.** `EditCaret`
(`preview_edit.rs:360`) already is one, over `PreviewBuffer::content`, which
already is the file's bytes. So typing, Backspace, Enter, wrapped Up and Down,
IME commit and the clipboard all work with no new arithmetic. What is new is
only knowing which block the caret is in, and landing the caret where a person
clicked on rendered text.

**Block boundaries need no special case.** Enter at the end of a paragraph
inserts the file's own line ending (`eol_of`, `preview_edit.rs:300`, already
wired at `main.rs:53886`); whether that makes a new block is the parser's
answer, not the editor's. Backspace at the start of a paragraph deletes the
preceding newline and the re-parse merges the blocks. Arrow-Up out of the top
row of the source block moves the caret into the previous block's source range,
that block becomes source, this one becomes rendered, and `desired_column` is
carried in monospace columns — which is honest, because the destination will be
drawn in monospace too. There is no "leaving a block" event to write. There is a
caret, a parse and a render, in that order.

### 9.2 The document buffer

**Keep the flat string that `PreviewBuffer::content` already is.** Not a rope
and not a vector of lines. Three reasons: every primitive in `preview_edit` is
written against a mutable string at a byte offset; a rope buys asymptotics that
matter at megabytes while the editable cap is 64 KiB (a few MiB at most after
§9.6 T2), and an insert into 64 KiB is a memory move that disappears next to the
re-parse beside it; and "blocks own their source slices" is precisely the design
that would stop the file being byte-identical outside the edit — the file is the
truth and the blocks are a projection of it, which is the invariant this feature
must not invert.

**Source ranges ride beside the blocks, not inside them.** A second entry point
returning the blocks and a parallel vector of ranges, with `parse_markdown` kept
as a thin wrapper. `MarkdownBlock` derives `Eq` and is compared by value across
a 4,200-line test module and shared with the terminal's table renderer
(`table_block.rs:63`); a new field makes every one of those assertions
range-sensitive for no gain, and `attention_words.rs:91` wants the blocks and
not the ranges.

**Undo lives on the buffer, not on the pane.** A coalescing log of a range, what
was removed and what was inserted; granularity is a typing run, broken by a
caret jump, a newline, a direction change, a save, or the arrival of a disk
copy. On the buffer because two panes on one file share the buffer by ruling
(`preview.rs:4640`) and an undo stack on the pane would fork the one thing the
pool exists to keep unforked. Not persisted.

**No new crate.** A portable `bt-edit` sounds tidy, but the parser it would have
to serve is two thousand lines inside `preview.rs`, and moving the parser is a
larger and riskier change than the feature. The portability gate does not ask
for it either — `bt-app` is not in the portable list, and nothing proposed here
adds a platform call. If a module is wanted for testability, it is
`crates/bt-app/src/preview_live.rs` in `preview_edit.rs`'s style: pure functions
from the blocks, the ranges and a caret to the block that is source, answerable
in a test with no window.

### 9.3 Save policy

**Explicit Ctrl+S with a dirty mark. This is not a new decision** — §7.1.3
(`docs/DESIGN.md:932`) already ruled it: 「显式保存(Ctrl+S/按钮,原子写)、脏
标记」, and it ships. The prior art supports keeping it: only Obsidian saves
continuously, inside a vault it owns, and its users wrote a plugin to slow it
down [S5].

**External change while dirty is already answered and should not be re-opened.**
`DiskNews::Changed` (`preview.rs:4974`), the two answers `take_the_disks_copy`
(`:4291`) and `keep_this_body` (`:4306`), and `SaveOutcome::Conflict` on mtime
(`:4392`). No three-way merge: that is a git feature, and Folio has a git panel.

**Preserving bytes outside the edit needs three fixes, and they are the whole of
the byte-identity constraint.** (1) Remember the encoding on the buffer and
write the file back in it, mark included — or, if that is judged too much for
0.3, **refuse to edit a body whose encoding is not plain UTF-8**, which is the
line `shell_integration.rs:1283` already draws for the PowerShell profile. (2)
Refuse to edit a body that decoded lossily, because a save would write
replacement characters into somebody's file. (3) A truncated head is already
refused (`preview.rs:4345`) and stays refused unless §9.6 T2 lands the
whole-file read. Line endings, trailing whitespace and the missing final newline
already survive.

### 9.4 Surfaces

**Entering: a click in the body.** The rendered face already takes a press
(`press_preview_text`, `main.rs:53118`) and already runs the six-pixel drag
latch that decides click against drag for links (§7.31 ⑦). The same six pixels
feed a third mouth: no travel and no link means a caret. No pencil in the head,
no double-click gate — a document you can type into is one you type into.

**Knowing you are in it: the block under the caret is source.** That is the
whole affordance and every product in §8 relies on it. The dirty dot and the
head's Save box already appear on their own (`main.rs:50262`).

**Leaving:** Esc, already `EditCommand::Release` (`preview_edit.rs:459`); a
press in another surface's body, which already drops edit focus
(`main.rs:81280`); or the flip to whole-file source.

**The flip stays and keeps its name.** `md_source` becomes Folio's Source Code
Mode; the rendered face becomes live preview; there is no third state, because
Obsidian's Reading view is live preview with nothing focused.

**The files column's second batch.** Rename exists (`profiles::file_menu`,
`profiles.rs:6737`, row at `:6743`); `bt_platform::recycle`
(`bt-platform/src/lib.rs:6237`) exists and is already in use for colour schemes.
What is new is two rows, New file and New folder, a Delete row wired to the
existing adapter, and a name to type into — which is the moment to pay the debt
`text_field.rs:19` records and put `TabRename` onto `TextField`.

### 9.5 Out of scope for v1, and what v2 adds

Out: editing a table cell by cell; typing directly into rendered proportional
text; bold and italic chords and any formatting toolbar; find-and-replace in the
document (Ctrl+F is `SearchHost`-scoped and a preview is not a host,
`shortcuts.rs:441`); spell check; folding; multiple carets; link autocomplete;
pasting an image into the document; and every parser feature the parser does not
have — task lists, footnotes, front matter, nested lists. Adding Markdown
dialect is a different slice from adding editing. And the hosted page, said once
in §6.

v2 is Typora's model: the caret in proportional text with the marks absent, a
pair of asterisks typed becoming bold as it closes, a real table editor. It
needs §9.6 T6's inline provenance *plus* its inverse — a source offset back to a
glyph — and a rich-text caret. T6 is the half that is worth building now either
way.

Seven, in dependency order. Four can start on day one.

## 10. Open questions

1. **Does any block refuse to become source under the caret?** — **No.** One
   rule, no exceptions (§9.1). A table with an exception would need a second
   editor, which is what everyone in §8 who tried it ended up building.
2. **Does the 64 KiB cap move?** — **Yes**, on demand: the head read stays the
   glance, and asking to edit buys a whole-file read (T2). Without it a Markdown
   editing release cannot edit `docs/DESIGN.md`. The alternative — leave the cap
   and keep large files read-only — is honest but it puts an arbitrary size in
   front of the feature's own use case.
3. **One selection model on the rendered face, or two?** — **One.** Today
   `md_select` is a `preview_select::Selection` in piece space, and a caret would
   be an `EditCaret` in file-byte space; two anchors on one surface is two
   answers to "what is selected". Recommend the caret becomes the single model
   once T6 lands, with the copy still walking pieces so §7.31 ⑥ — copy what you
   read — is unchanged; only the range's origin moves.
4. **Does a source range go in `MarkdownBlock` or beside it?** — **Beside it**
   (§9.2): the enum is compared by value across some 4,200 lines of tests and is
   shared with the terminal's table renderer.
5. **Does the whole-document re-parse survive a keystroke?** — **Measure first**
   (T4). 64 KiB through a hand-written line parser is probably far inside
   budget; the expensive parts are the intrinsics and the fence highlighting,
   and keying those per block content fixes them without an incremental parser.
   Do not build an incremental parser on a guess.
6. **Undo granularity and depth?** — a typing run, broken by a caret jump, a
   newline, a direction change, a save or an incoming disk copy; no depth cap
   below a few thousand entries; not persisted, because a session snapshot that
   restored an undo stack would let a person undo past a save they cannot see.
7. **Does the flip survive?** — **Yes**, as Source Code Mode. It is `md_source`,
   it is per surface, and it is the escape every product in §8 has.
8. **Does the float get the same behaviour?** — **Yes**, by one dispatch line,
   which is the precedent §7.31 ⑥ set for selection (`docs/DESIGN.md:5630`).
9. **Does the focus card change?** — **No.** The red line "a thumbnail must not
   ask the disk" (`focus_thumb.rs:421`) is untouched; a card draws the buffer's
   head, and a dirty buffer's head is the truth about what is open.
10. **Three-way merge on an external change?** — **No** (§9.3).
11. **A new crate?** — **No** (§9.2). A module, `preview_live.rs`, if one is
    wanted for testability.
12. **Does Ctrl+F become live over a document?** — **Not in this slice.** It
    would need a widened `SearchHost` and a match model over rendered pieces,
    which is a feature of its own.
13. **Do the bold and italic chords ship?** — **No** in v1. T6 makes them
    possible; they are v2's toolbar, not v1's caret.
14. **What happens to today's two atomic writers?** — recommend T2 folds
    `preview::save_atomically` (`preview.rs:5269`) into
    `bt_persist::atomic_write` (`atomic.rs:25`), which is already used for user
    files elsewhere, so there is one algorithm and one place to fix the
    read-only-attribute and symlink gaps named in §4.
15. **Does a keystroke drop the selection, as a re-parse does today?** — it must
    not, and question 3 is why: once the caret is the model, `show_document`'s
    clearing rule (`main.rs:2725`) has to distinguish *our own* re-parse from a
    re-parse caused by the disk. That is one boolean at the call site, and it is
    the single most dangerous line in T4.
