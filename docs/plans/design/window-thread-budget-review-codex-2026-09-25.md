## R1 — High: the guard checks spellings and lexical owners, not execution on the window thread

**Exact paragraphs:** §5.1, “Its universe is bt-app's product code (`Index::of_package("bt-app")`, `in_the_product`).”; the `# lanes` paragraph, “Each one is pinned: it either contains a `spawn_at_priority` call, or a spawn names it as the worker body.”; assertion 4, “every list owner's body names `Station::<its station>`”. These do not establish §1.7's promise that every wait is listed and wrapped.

**Concrete failure sequences:**

1. Add `bt_platform::new_probe()` which calls `std::fs::metadata`, then call it from a `Runtime` method. No vocabulary spelling appears in bt-app; its enumerated file set is unchanged. Both guards pass. Adding a new wait inside an existing unlisted cross-crate API has the same effect. A file-set equality check proves the chosen universe was read, not that the universe covers this property.
2. A declared function spawns a worker closure. Move its `fs::rename` from inside the closure to immediately before the spawn. Its lexical owner, occurrence count, and spawn pin remain the same; the call now runs synchronously. Conversely, a function named by a spawn can acquire a second, direct window-thread caller. The lane exemption remains valid under the proposed check.
3. Change `during(Station::RenameDisk, || rename(...))` to `during(Station::RenameDisk, || ()); rename(...)`. The owner still names the station and contains one rename, so the guard stays green while the wait is charged elsewhere. Returning a closure from `during` and invoking it afterward is another version of the same mistake.
4. Put a blocking implementation behind `dyn Trait`, an imported function pointer, or a helper in another crate. The caller invokes `operation.run()` or `f()`, not a vocabulary path. In particular, lexical `Receiver::recv` matching does not resolve `receiver.recv()`. The current `bt_source::Pattern::{Path,Call}` API describes token shapes, not receiver types, call-graph reachability, or trait dispatch.

**Change that fixes it:** Narrow the promised invariant to a checked set of effect doors, then make those doors the enforceable boundary. Inventory raw blocking effects across first-party production crates and platform configurations; pin their authorized implementations and callers; give external APIs explicit blocking/thread-affinity contracts. Require worker execution context at worker-only doors, and structurally tie each admitted owner-thread call to its measurement wrapper. A runtime thread-identity assertion at those doors can complement the source checks without attempting to interrupt an OS call. Ban or explicitly inventory escapes through callbacks, aliases and trait implementations where the lexical checker cannot prove them. Do not claim arbitrary Rust blocking behavior is statically recognized.

Expand the mutation set to cover all four sequences, cross-crate additions, method syntax, and a direct caller of an existing worker. Keep the existing identifier view and exact multiplicities: they are useful, just insufficient. Define how imports are resolved or prohibited; “both spellings” and “no occurrence outside an item” currently leave that mechanism ambiguous.

## R2 — High: 16/8/4 ms is an observational target, with no aggregate admission argument

**Exact paragraphs:** §1.2, “The reference interval is `pace::DEFAULT_FRAME_INTERVAL`, 16 ms. Every existing allowance was derived from it.”; §1.6, “Work that overruns is already stopped by its own slice.”; §1.7, “Nothing is refused at run time. An overrun reopens its row.”

**Concrete failure sequence:** A turn spends 8 ms draining, 4 ms searching, and twice 4 ms in admitted waits. Every individual allowance is respected, but the turn costs 20 ms before composition, event handling and publication. Exact *source* call counts do not constrain dynamic repetition in a loop or invocation once per window. At 120 Hz the roughly 8.33 ms frame interval is already consumed by the drain alone. Several windows make per-window search slices additive on the same thread.

The derivation transfers the drain's justification incorrectly: its other half was reserved for publication and the platform round trip, not assigned anew as an independent 8 ms allowance for waits. Ticket 50's measured 3.4 ms is a sample, not an upper bound on a native font lookup. `SEARCH_HISTORY_SLICE` is 4,096 lines, explicitly **not a time limit**, and the source derives its estimated cost from measured per-line work on one machine. It neither stops at 4 ms nor preempts one expensive line. The drain checks time between slices, so even it has an indivisible-unit overshoot. These are useful work quotas, not guarantees about wall time.

The five dispositions also do not exhaustively establish boundedness. “Slice” can bound CPU units but cannot bound a stalled read within a piece. “Idle” only describes when a call starts: input arriving 1 ms after a 300 ms warm-up still waits. “Bound at its measured distribution” for D-41 is not a bound. “Stay” needs an explicit lifecycle phase: row 19 is in ordinary turns, and shutdown requests can originate while callbacks still hold control; being on an exit road does not itself prove no heartbeat hold exists.

**Change that fixes it:** State two separate contracts: enforceable admission/work/outstanding-resource limits, and observed wall-time responsiveness targets. Label 16/8/4 as provisional policy choices supported by cited measurements, not derived universal limits. Give a composition inequality covering events, drain, searches across windows, preparation, native calls and instrumentation, with reserved headroom and the maximum non-preemptible unit. If the design intends to enforce aggregate admission, specify a shared remaining-turn allowance and when optional work is deferred; otherwise explicitly disclaim that guarantee and retain D-2's remaining scheduling debt.

Use the earliest relevant active-window deadline on the shared thread, with a capped fallback for no active deadline; do not give every window a fresh allowance. At 120 Hz measure against that deadline rather than merely halving three constants. Record uncontrollable scheduling delay and exceptional native waits separately while still reporting their input latency. Under a machine-wide stall, no local policy guarantees a 16 ms wall-time turn; moving an application wait can nevertheless improve input service when the scheduler runs the owner. Keep pending/deferred/exempt status separate from the final disposition so an unresolved wait cannot be presented as a proven `bound`.

## R3 — High: B2 does not yet specify the accounting needed to make its backstop true

**Exact paragraph:** §5.2, “The vocabulary cannot be complete. A new cross-crate function that waits inside is invisible to Part A until it is added. The backstop is the run-time accounting: its time lands on the enclosing station and shows in a budget line.” Related: B2's goals require a microsecond clock, “a per-turn sum of waits,” and per-run “maximum, count and sum per wait station.”

**Concrete failure sequence:** The unlisted helper in R1 blocks for 40 ms inside an event station classified `Scope` or `Work`. B2's wait total remains zero, and its specified budget-line triggers cover excess wait totals or an individual listed wait's bound. The existing slow-hold path discards the completed record below 500 ms. B2 can meet its named tests and emit nothing for this turn. Merely defining `TURN_BUDGET` does not add the missing whole-turn trigger.

There are two other independent accounting holes. First, `Heartbeat::charge` and `hang_watch_detail` aggregate exclusive time by station/path; two separate 3 ms invocations become a 6 ms station total. That cannot distinguish a compliant pair of calls from one 6 ms call against the 4 ms per-call allowance. Nested work can also reduce a wrapper's exclusive charge below its wall duration. Second, `close_hold` publishes through `try_lock` to a queue capped by `SLOW_HOLDS_KEPT`, incrementing a dropped counter on failure. Reusing that delivery shape does not justify “a budget line goes to the diagnostics log” for every overrun. A 60 Hz stream can produce many more than 32 records between two-second watchdog polls.

**Change that fixes it:** Specify an independent all-turn measurement and overrun trigger, including unattributed/Scope time; it reports an unexplained slow turn without falsely identifying that time as an external wait. B2 must aggregate before the 500 ms early return and independently of successful queue admission. Track individual call duration/count/max at wrapper boundaries, and define inclusive per-call duration versus exclusive union accounting for the per-turn wait total so nested calls neither hide latency nor double-charge it. Use bounded detail delivery with explicit loss counters and persistent summary totals; silence with dropped records is not a clean result. Preserve the existing slow-hold format and expensive sampling cadence.

Acceptance needs deterministic 4,001 µs single-call, two 3 ms calls, sub-millisecond accumulation, 9 ms aggregate waits, a 40 ms unclassified turn, nesting, queue contention/overflow, and an in-progress call that never reaches `park`. The latter remains the watchdog's responsibility. Include overhead measurements under active, overloaded, failed and quiescent operation. B2 correctly identifies the 500 ms problem; these requirements prevent an implementation from nominally fixing it while leaving the same blind spot.

## R4 — High: the hand-off lane cannot be the first fully green conformance instance unchanged

**Exact paragraph:** §3, “Why the hand-off lane is the reference. It is the only lane on the base that already has all six obligations in code: an id, an incarnation, a bound, an order, a set of completions and a wake. Wrapping it changes no behaviour, so the suite's first green run proves the harness rather than a repair.” Claim 4 immediately above requires “a dead worker leaves an observable terminal state.”

**Concrete failure sequence:** Submit A and B; A starts; the worker exits before publishing A. No subsequent submission occurs. `HandoffLane::answers` drains `try_iter`, which does not expose disconnected-versus-empty as an outcome, and the accepted IDs remain in `Pending`. `LANE_GONE` only answers a later submission. The lane has no published terminal outcome for A/B or death wake. A process-level fatal panic path, where applicable, is not a lane-level completion contract. The presentation note already explicitly records this exception.

There are further mismatches with the declaration: `HandoffId` is a counter reset by `start`, with production relying on one application-lifetime lane; an incarnation wrapper must preserve that scope. `turned_away` and the answer channel are unbounded. Delivery drains refusals first, then worker completions, so a later rejected request can be delivered before an earlier admitted request. FIFO applies to admitted execution, not all deliveries. Calling all this simply `Fifo` does not adopt the presentation note's separate execution/delivery obligations unchanged.

**Change that fixes it:** Call hand-off the reference for its **existing partial contract** and declare each failing obligation explicitly. Either repair accepted-request death accounting in a separate prerequisite or carry it as an exact expected failure with a repair ID. The exception harness must fail on unexpected success, a different failure, a skipped adapter, or zero exercised requests; catch-all panic-to-pass is not evidence. Prove passing claims through the real admission/publication/acceptance path and failing claims through a controllably terminated worker. B3 can preserve behavior and remain mergeable, but cannot simultaneously claim full conformance.

## R5 — High: D-41's evidence paragraph can reject the lane for evidence consistent with its intended benefit

**Exact paragraph:** §4's decision block, especially “Evidence that it is not is any of the following” through “present-led holds that coincide to the second with the machine-wide stall beat, where a lane would keep keys alive but the picture would still freeze”. The same block requires low CPU/faults, no fixed wait over threshold in the same line, and a rate comparable to 68 in 161.

**Concrete failure sequence:** After next92, present still blocks for a second during a compositor stall, with a co-occurring title wait. The title exclusion discards this event. Other events are configure-led but include a substantial present wait. Longest-station-only classification discards those present contributions too. The remaining present events coincide with the machine-wide beat and are classified as evidence against D-41—even though keeping input runnable during that wait is D-41's ledger purpose and the presentation note's Q1 accepts frozen pictures on the shared device.

A quieter next92 session can also produce fewer holds simply because it presents fewer frames, changes windows less, or encounters fewer stall beats. 68/161 is a proportion of already selected slow holds, not a rate per presentation, active hour, or beat. Holds between a frame deadline and 500 ms are missing. Low thread CPU means little measured CPU consumption, not proof of a driver wait: a runnable but descheduled thread can look the same. `Paging` is process-wide and has a cached opening baseline; high faults elsewhere do not establish that this particular present was paging, nor that isolation could not help. Correlation to a whole second does not identify the causal wait.

**Change that fixes it:** Recast the paragraph as evidence to classify and prioritize, with “insufficient exposure/instrumentation” as a third outcome. Preserve all material exclusive contributions and their coexistence. Record matching build, workload, windows, presentation attempts, active exposure, successful picture landings, drop counts, and stall-beat exposure; include sub-500 ms distributions after B2. Separate input-dispatch latency/progress from successful present-plus-commit and time to resume pictures. Where attribution matters, use contemporaneous thread scheduling/wait evidence, not CPU/fault counters alone. A matched or interleaved baseline/candidate experiment must establish benefit; comparable session length alone does not.

Configure or WebView-led stalls identify residual work and can lower priority; they do not refute an independent presentation wait. A global pause of all runnable threads predicts no input benefit during that pause; a compositor/driver pause with a runnable window owner predicts possible input benefit. Neither promises fresh pictures. Keep the reviewed presentation note's requirement that pictures actually resume—zero present-led holds achieved by presenting nothing is a failed experiment. Existing next89/next90 evidence supports investigating isolation; the proposed next92 log criterion alone cannot decide its causal benefit or absence.

## R6 — Medium: four lane claims are necessary but do not cover the declared contract

**Exact paragraph:** §3, “One suite, `lane_contract_tests`, runs the same four claims on every adapter”, followed by full-queue response, abandonment, publication-before-wake, and worker death. The instance table calls font `BeforeStart`, observation `PerQuestion`, and computation bounded by “its queue”.

**Concrete failure sequence:** An adapter returns immediately when full, suppresses a closed target's answers, publishes before waking and reports a worker fault. It can still deliver an older answer over a newer one, execute storage commands out of order, publish a completion twice, retain unlimited result bytes, or lose a terminal wake in the consumer's clear-and-recheck race. All four tests pass. Merely replacing old results in a one-slot mailbox is not an exactly-once terminal accounting policy for the displaced request.

The implementations need different declarations:

| Instance | What the source provides | Missing or misdescribed contract |
|---|---|---|
| Hand-off | Request counter, window-owned `Pending`, bounded waiting queue, serial execution, publish then wake | R4's dead-worker/held-answer exceptions; separate delivery order; lane incarnation on restart |
| Font | Numbered `ScanState::requested`, one active walk, `again` coalescing, one offered monospace answer, monotonic adoption against the **adopted** generation | `again` is rescan coalescing, not an implemented cancellation API; state includes one pending round. No explicit per-request superseded/fault terminal accounting or wake-failure policy. Declare the target as the application-wide slot, not the dialog. Preserve its useful behavior rather than inventing cancellation for the adapter |
| Path observation | Separate filesystem worker; path plus `ShellAddress`; publication before `MathReady` | No request sequence or independent shell incarnation, unbounded admission/results, no per-lane worker-death indication; the shared result sender can remain live after one worker dies |
| Computation | Separate math and scaling channels/threads behind `MathWorker`, shared result type/channel; math's explicit stack requirement | “its queue” is not a numeric bound: `MathWorker::spawn` uses `mpsc::channel`. Inventory each job's real generation/acceptance policy, retained bytes, overload, death, replacement and cancellation. Sharing a result enum is not itself the missing safety property |

**Change that fixes it:** Add policy-driven tests for identity/target reuse, execution and delivery order, latest-value supersession, exactly-once terminal accounting, waiting/executing/answer **and byte** bounds, consumer clear-and-recheck, and terminal/fault visibility with a full mailbox or unavailable wake. State what “latest” means: newest requested, started, completed, or adopted. The PSReadLine B5 request is LatestValue in §2/B5 but is grouped under PerQuestion in §3; separate it from path verification. B3 currently names no computation adapter: add one or explicitly leave those obligations as unverified debt. The minimal contract is the presentation note's obligation set with concrete policy tests, not four generic successes.

## Recommendations on the five open questions

1. **D-2 closure:** Close only the explicitly redefined inventory/accounting milestone after corrected B1+B2 acceptance; keep aggregate scheduling, unclassified-effect coverage and unresolved waits as named open debt, rather than declaring a 16 ms guarantee repaid.
2. **Refresh-rate scaling:** Use one shared deadline from the earliest relevant active-window frame/input obligation, capped by a fallback; derive allocations within it and remeasure at 60/120 Hz and across mixed-refresh windows.
3. **Native calls over 4 ms:** Permit explicit measured exceptions with owner, exposure, expiry/review trigger and mitigation debt; keep charging actual latency, since idle scheduling and a measured percentile do not create a bound.
4. **Delayed save receipt:** Yes—show saved only for the matching durable revision receipt, preserve newer dirty edits, and specify failure and bounded-quit recovery; “a turn later” must not promise a maximum completion delay.
5. **Unstoppable macOS watcher:** Permit retention to final process exit only with callback/native-resource lifetime proof and a bounded outstanding-watch policy; ordinary retirement must stay asynchronous and must not free resources beneath a live watcher.
