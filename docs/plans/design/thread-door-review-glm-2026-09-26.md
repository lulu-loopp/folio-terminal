## P2 — Departure 5's "exclude" claims more than the M14 fence excludes

**Note paragraph.** §7 item 5: "the only way to reach a worker-only door off a worker is a fabricated `WorkerCtx`, which `#![forbid(unsafe_code)]` and the M14 fence exclude"; and §2.4's row "`unsafe` fabrication (`transmute`, `zeroed`, `MaybeUninit`, a pointer `read`) | … B§C-5's fence on naming the type inside `unsafe` anywhere else (A1e, M14)".

**Code.** The fence as §9.1 specifies refuses the *names* `WorkerCtx`/`WaitToken` inside `unsafe` blocks, `unsafe fn`s and those expressions. `bt-platform` is the one crate whose `unsafe_code = "deny"` is lowered, and an inference-typed fabrication there — `let x = unsafe { std::mem::transmute(0usize) }; ShellThread::enter(&x)` — writes neither name inside the expression; the type is inferred at `enter`'s parameter, outside the fence. `enter` is public and callable from `bt-platform` itself, so the road exists for that crate's `unsafe` writers.

**Consequence.** Not an accident road — it takes deliberate evasion — but the sentence claims an exclusion the specified check does not establish, and departure 5 partly rests on it. **Obligation.** Narrow the claim, in one of two faithful ways: (a) write the fence's limit as B§R-A writes its others — named fabrication is refused; an inference-typed `transmute` inside `bt-platform`'s `unsafe` remains, is deliberate evasion, and sits below the accident bar the guard targets; or (b) keep a counted role read inside the worker-only door explicitly as telemetry, not contract, claiming no red test for it. ## P4 — The meter's drop guard is justified by mis-citing `during`, whose own documentation refuses the pattern

**Note paragraph.** §7 item 2: "`leave` also on unwind (a drop guard, as `during` keeps its stack balanced)"; §4.4 step 4.

**Code.** `hang_watch::during` (`hang_watch.rs:2511`) is `enter` → `work` → `at(parent)`, deliberately guardless; the neighbouring `enter` states the rule: "Not a guard type: a guard would run on the unwind path too, and the one thing this module must never do is add a `Drop` to a thread that is already in trouble" (`hang_watch.rs:2497–2499`). So `during` does *not* keep its stack balanced on unwind — a panicking `work` leaves the station pushed — and the note's parenthetical claims the opposite of the precedent it cites while proposing for `admitted` exactly the mechanism that precedent refuses: a guard that runs hang_watch-registered code during a panic unwind, where a panic inside `leave` aborts the process.

**Consequence.** Small, but the two shapes are not equivalent and A1a's implementer will copy whichever the note leaves standing.

**Obligation.** Replace the parenthetical with one of two statements. Either the guard is right — then say why the module's rule does not apply to `admission`'s guard (one indirect call and an atomic store is not "work"; the abort-on-panic-in-`leave` trade is accepted and written) — or `during`'s discipline is right — then `leave` is not called on unwind, and the note says what the stack looks like after a panicking admitted call (the station stays pushed; the next hang report names the door, which is arguably the more truthful report). The enter half itself is correctly motivated: naming a never-returning call is what `during`'s `enter`-before-`work` buys today.
