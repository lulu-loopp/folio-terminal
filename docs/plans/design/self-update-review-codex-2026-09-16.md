# Self-updater adversarial review, 2026-09-16

Reviewed `design/self-update` at `c19a9206`, including the complete design and its cited source/document locations. Product code was read only; no Cargo, tests, packaging scripts, application launches, or process termination were performed. Line references below are to this commit. Proposed behavior is distinguished from behavior already implemented.

The separation between checking and installing is sound. The replacement transaction is not yet safe enough to implement: neither platform has a recovery entry point that survives losing the normal executable path, and successful process creation is mistaken for a successful upgrade.

1. **R-1 — blocker — §C Windows 3–5; macOS 6: a crash can remove the only usable launch path.**
   Evidence: `scripts/release/package.ps1:279-297` ships one executable and its sidecars; `crates/bt-app/src/main.rs:118126-118201` enters through that executable and contains no installation recovery path. The proposed ordered renames are individually atomic, not an atomic installation transaction. A live worker's inverse cannot run after its process dies.
   Change: redesign around a durable transaction journal plus a recovery executable/launcher that remains reachable independently of the replaced executable or bundle. Define durable preparation, commit, recovery, and health acknowledgement, with recovery idempotent after interruption of recovery itself. An in-app startup sweep alone cannot repair an executable that cannot start. The following table must become executable fault-injection cases:

   | Boundary reached before death | What the next ordinary start finds |
   | --- | --- |
   | Shared 1–6, including Windows extraction/trust and macOS attach/verification/copy | Old install still starts; partial downloads, mounts, or `.new` trees need owned cleanup. |
   | Shared 7, session saved but no rename yet | Old install still starts; session/sentinel handling must reflect whether exit was clean. |
   | Windows 3, `folio.exe` moved aside | `folio.exe` missing; shortcut/CLI launch cannot execute a sweep. |
   | Windows 4, any subset of the other eight moved aside | Executable missing and old set split across names; still no normal recovery entry. |
   | Windows 5, any prefix moved in | Missing or mixed executable/sidecars; starting the new executable before all files exist is unsafe. |
   | Windows 5 complete, before/after spawn | Complete new set exists, but startup may fail; complete old set needs an independent restorer. |
   | macOS 6, after first rename, before second | Original bundle path missing; `.old` and `.new` exist but ordinary launch cannot recover. |
   | macOS 6 complete, before/after `open` | New bundle at the launch path; old bundle remains, but nothing guarantees the new application starts. |
   | Either platform during inverse operations | Another partial installation; the inverse itself needs durable, retryable recovery. |
   | Either platform during backup deletion | Rollback becomes incomplete; deletion is permissible only after an explicit committed-health state. |

2. **R-2 — blocker — §B failure edges; §C Windows 6–7/macOS 7–8: spawn is not health, and next-start deletion destroys rollback.**
   Evidence: `crates/bt-platform/src/lib.rs:2647-2661` merely constructs a command with `CREATE_NO_WINDOW`; it supplies neither readiness nor a detached-lifetime protocol. `scripts/release/smoke.ps1:3-10` exists precisely because a built executable still needs real startup verification. Spawning `open` is even further removed from proving Folio's readiness. A loader failure, unknown `--await-exit`, GPU initialization failure, immediate crash, or hang can follow a successful spawn.
   Change: retain complete, transaction-named backups until the intended build claims the intended data directory and sends a transaction-bound health acknowledgement after usable startup. A surviving supervisor must restore and relaunch the old version if that fails; specify how it handles a still-running failed child. Do not count `--version`, a helper invocation, or entry into `main` as success. Delete only the recorded backup set, never arbitrary `*.old`. Retain/reconcile backups locked by another instance. Protect session/settings compatibility during trial startup too: `crates/bt-persist/src/migrate.rs:839-842` already documents rejection of future schemas. “Nothing installed was changed” is valid only before mutation or after verified complete rollback; add an explicit recovery-required outcome when rollback fails.

3. **R-3 — blocker — §C relaunch handoff: the proposed wait does not integrate with the actual claim owner.**
   Evidence: `crates/bt-app/src/persist.rs:223-233` caches both `Some(claim)` and `None` forever. Calling it once while the old process lives makes subsequent calls permanently false. Acquiring a separate claim and keeping it makes `is_writer_of` refuse the child itself; dropping it before the ordinary path creates an acquisition race. `crates/bt-platform/src/instance.rs:132-148` uses named-object existence, not abandoned mutex ownership; Unix uses a retained `flock` at `:623-657`.
   Change: provide a single claim-acquisition/adoption API that transfers the successfully acquired guard into the persistence table without dropping it or caching transient failure. Preserve exactly one writer, including concurrent manual launches. At 30 seconds, fail the update handoff explicitly; never “start anyway” or invoke ordinary handover. At `main.rs:118197-118201`, a responsive old instance consumes the request; `launch_wire.rs:614-621` otherwise permits a second, non-writing window. Thus two windows/processes can exist today, although the locks do not allow two simultaneous writers for the same claim. The 2-second budget (`launch_pipe.rs:111`) is an IPC deadline, not evidence that the old instance has exited. Distinguish access-denied/process-query errors from death, handle PID reuse, and carry the canonical data-directory identity and transaction ID across relaunch.

4. **R-4 — blocker — §B close rule; §C shared 7–9: the ordinary quit transaction must precede the destructive commitment.**
   Evidence: `crates/bt-app/src/main.rs:110997-111035` can ask about dirty documents and fail the session write; `:111072-111082` abandons quitting. `:112207-112215` separately handles ordinary window-close events, and `:112427-112429` closes the window. Nothing about a worker running prevents these paths. The claim is held in a static table until process exit (`persist.rs:223-233`), not released just by closing windows.
   Change: complete all cancelable Save/Discard/Cancel decisions before replacement, snapshot every window, confirm the final session generation landed, and prevent new session mutations/admitted launches while committing. Define one application-level update/quit owner, not the presenting window's lifetime. Closing that window during download may cancel the job, but must not strand other windows or lose its outcome. Closing/OS termination/crash during swap must be handled by the recovery protocol in R-1. Starting the ordinary, cancelable Quit only after swapping and spawning leaves an installed new build plus an old process that may refuse to exit.

5. **R-5 — must-fix — §C Windows 1; §F: the extractor rejects the real release archive.**
   Evidence: `scripts/release/package.ps1:472-497` calls `CreateFromDirectory(..., $true)` and expects `folio-$Version/<name>`, not nine bare entries; `docs/RELEASING.md:682-685` explicitly documents that directory. The stable ZIP is byte-for-byte the same archive (`package.ps1:537-543`).
   Change: accept precisely one expected versioned root and its nine regular-file children, stripping that root during extraction. The root uses the manifest version, not the tag's `v`/`-preview` spelling. Reject duplicates, case-colliding names, absolute/drive/UNC paths, traversal, alternate streams, links/reparse entries, and extra roots; bound both individual and total expanded bytes. Exact allowed filenames alone do not bound a ZIP bomb or duplicate overwrites. Test the actual packaging layout as a fixture.

6. **R-6 — must-fix — §C shared 2/Windows 3–5; §D: staging can be on another volume, and the eligibility probe mutates the installation.**
   Evidence: `crates/bt-app/src/persist.rs:1211-1219` places data under roaming APPDATA or Application Support, independently of the executable. `package.ps1:154` likewise imposes no runtime co-location. Moving from APPDATA on C: into a portable install on D: fails without copy semantics; enabling them would make the operation a copy/delete, not a rename. See [Microsoft's MoveFileExW contract](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw).
   Change: download into a private local cache, then fully copy, flush, and verify the staged installation on the destination volume before moving any live file. Reserve space for archive, expansion, and complete rollback set; handle actual write/flush failures as authoritative. `Available` cannot call a probe that renames `folio.exe`, because §B forbids mutation before consent and needs location to decide whether to offer consent. Separate read-only ownership classification and nondestructive staging preparation from commit-time renames. A failed rename can mean sharing violation or existing backup, not simply “folder not ours.” Specify retryable errors and the rename/rollback retry policy independently: `persist.rs:32-47,248` defines five write attempts with a 1.5-second debounce, not five 200-ms rename retries.

7. **R-7 — must-fix — §C “A second Folio”; §D location: serialize by installation identity, not data directory.**
   Evidence: `crates/bt-platform/src/instance.rs:128-136` names the claim from the data directory; `persist.rs:220-232` makes the same distinction. It does not lock the installation. Two isolated data directories, or other login sessions, can therefore update the same binaries concurrently. A second old instance can also start a new shell against newly replaced sidecars; retaining its mapped executable proves less than compatibility of the whole runtime.
   Change: take an installation-scoped transaction lock keyed by canonical filesystem identity; prevent competing commits and cleanup regardless of data directory. Refuse/defer when other users of the installed set cannot safely participate. Record ownership of `.old`/`.new` names and refuse unknown collisions. On macOS derive every path from the actual bundle basename: a running `Folio Test.app` must not cause hard-coded `Folio.app` renames to replace another installation. Resolve aliases/symlinks deliberately and refuse read-only mounted/translocated source locations with an actionable install message.

8. **R-8 — must-fix — §E tag/hash argument: pin the offered tag, but do not equate a tag URL with immutable bytes.**
   Evidence: `crates/bt-app/src/update.rs:319-329` retains only a verbatim tag; `:340-344` returns that exact tag. `:479-482` can replace `latest_tag` while a card is open. `package.ps1:555-568` publishes a separate checksum document, not an authenticated binding between binary version and offer. §E's claim that assets from different releases “both would verify” is wrong when their bytes differ: the hash comparison fails.
   Change: capture the card's tag in an immutable offer/job object and use it for both requests; never reread global latest or reconstruct it from `VERSION`/`RELEASE_TAG`. Validate/encode the tag for URL use and use an opaque staging ID. Replaced asset/hash pairs under a mutable release can disagree: fail before mutation, discard the partial transaction, and offer an explicit retry. If both are replaced consistently, SHA-256 succeeds; verify platform version/architecture and product identity against the offer as well. If byte identity at offer time is required, retain authenticated asset digests/identity or require verified immutable releases. [GitHub immutability](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases) is a separately enabled guarantee, not a property of every tag URL; this review did not establish this repository's setting.

9. **R-9 — must-fix — §C Windows 2; §E Authenticode: specify the full trust decision rather than calling the smoke test equivalent.**
   Evidence: the subject is correctly spelled in `packaging/msix/AppxManifest.xml:39-42`, including `S=mi`. `msix.rs:121-177` compares ordered parsed RDNs, normalizing attribute names/spacing but preserving value case; it is not raw-string equality. `smoke.ps1:351-361` only substring-matches the executable's copyright holder; `:483-495` separately compares the MSIX publisher and both signer subjects. `package.ps1:450-464` also verifies Microsoft's two sidecars.
   Change: validate the running executable's trusted identity, the new executable/MSIX trust chains and timestamp semantics (including RFC 3161), and the MSIX manifest publisher against its verified signer. Use the defined DN comparison, never substring matching or case-folded values. Specify certificate-renewal limits: same subject can survive key renewal, changed subject requires an explicit migration. Validate both ConPTY signatures as packaging does, or use an authenticated manifest covering all installed bytes; unsigned hash text plus two signed Folio files is not an equivalent package authenticity check. Check embedded version and architecture before commit.

10. **R-10 — must-fix — §C macOS 3–5; §E/H: notarization does not identify Folio.**
    Evidence: `scripts/release/macos/notarize.sh:350-367` checks exit status and notarized source; it relies on the release pipeline already knowing what it signed. `scripts/release/macos/sign.sh:238-247` signs then deeply verifies the bundle. Neither `codesign --verify` alone nor acceptance of any notarized Developer ID bundle requires Folio's Team ID and bundle identifier.
    Change: require the expected Developer ID identity/Team ID and bundle identifier independently of Gatekeeper, on the destination copy, with nested-code verification where applicable, architecture and version checks, and an explicit notarization policy. Keep verification both on the mounted source and after `ditto`: copying can fail or retain stale contents if `.new` already exists. Create a fresh destination exclusively. Reassess the copied bundle before committing. Identity verification is mandatory now, not conditional on the disabled-Gatekeeper experiment. Apple's [code-signing requirements](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements) distinguish validity from the caller's required identity.

11. **R-11 — should-fix — §E quarantine; §C macOS 2–8: preserve provenance and give mounted images a recovery lifecycle.**
    Evidence: `scripts/release/macos/dmg.sh:208` uses `ditto`, while `notarize.sh:336-340` staples and validates tickets. These support preserving bundle metadata, not the universal assertion that a copied bundle has no quarantine. Existing `macos_http.rs:492-540` downloads text only, so it supplies no evidence about the new file downloader's quarantine behavior.
    Change: preserve quarantine and other required xattrs, test absent/present quarantine through download, mount, copy, and launch, and report assessment/launch failures without stripping attributes. Record mount ownership and detach on every success/failure/cancellation path; after a crash, recover only that transaction's mount. A failed detach is cleanup debt, not grounds to undo an otherwise healthy install. Bound command runtimes and stderr capture, and check tool exit status, not merely successful spawning. The next launch must know about `.new`, `.old`, and mounted images outside the download directory.

12. **R-12 — note — §A/E HTTP redirects: the existing clients already support the GitHub redirect chain safely with respect to scheme.**
    Evidence: `crates/bt-platform/src/http.rs:39-51` documents WinHTTP's ten-hop, no-HTTPS-to-HTTP defaults; `macos_http.rs:311-329` explicitly permits only HTTPS and at most ten redirects. Thus a 302 to a GitHub asset host is not inherently a failure, including for the checksum fetched with today's `https_get`. `http_portable.rs:40-42` remains an explicit unsupported-platform error.
    Change: preserve these rules in both download arms, test cross-host HTTPS and rejected downgrade/loop cases, and apply the whole-call deadline across redirects. State that “one GET” means one logical fetch with redirected requests. Rewrite the privacy claim “github.com and nothing else” to include redirected asset hosts and any platform trust/notarization network activity; separate these from the check's unchanged fixed API request.

13. **R-13 — must-fix — §E `https_download`; §B progress: specify bounded streaming, unknown lengths, and cancelable waits.**
    Evidence: Windows `http.rs:226-260` grows a response vector; macOS `macos_http.rs:391-402` copies each NSData chunk and accumulates a vector. `http.rs:204-228` checks the budget only after blocking send/receive; macOS waits up to budget plus phase at `:534`. Neither implementation is already a bounded-memory file downloader with prompt cancellation.
    Change: use fixed-size buffers and a bounded sink/queue, with checked byte counters and a strict cap enforced before writing a chunk. Treat missing/unknown Content-Length as `None` (macOS's negative sentinel must not become a huge unsigned value); show bytes received and indeterminate progress, and verify actual EOF/known-length completeness plus hash. Define cancellation latency during DNS, headers, body, hashing, extraction, and verification, not just between chunks. Enforce a monotonic end-to-end deadline or document the bounded overrun; periodic bytes must not defeat it. Handle short writes, disk-full, flush/close failures, and cancellation during finalization without entering Verified. Coalescing every 100 ms needs at most one pending progress wake, not an unbounded event backlog when W stalls.

14. **R-14 — must-fix — §B cleanup; §C shared 2: the sweep is neither a startup protocol nor safely scoped.**
    Evidence: `main.rs:36827-36828` loads/checks state at startup, and `update.rs:680-703` starts only the check; no existing cleanup hook is available. In the design the only enumerated sweep is after a new press, while §B promises it on the next launch. Reusing `<tag>` preserves partial files for the very retry that needs cleaning. `persist.rs:1214` already appends `Folio`, making `<data>/Folio` ambiguous.
    Change: define an off-thread startup recovery pass before any new job, and separate recovery data from disposable download cache. Use private, unique transaction directories and exclusive file creation; never follow links/reparse points out of their owned root. Sweep only proven abandoned disposable transactions, never live jobs or unacknowledged rollback data. Coordinate with the installation lock and bound cleanup work; keep failed deletions as retriable debt. Name the actual path relative to `persist::storage_dir()` exactly once, and avoid roaming large archives by default.

15. **R-15 — must-fix — §D `CHANNEL`; §G ticket 1: packaging happens after compilation.**
    Evidence: `crates/bt-app/build.rs:36-37` embeds COMMIT at compile time; `version.rs:34-65` has VERSION/COMMIT/a synthesized RELEASE_TAG, but no publication fact. `docs/RELEASING.md:298-300` and `:867-870` build before packaging; `.github/workflows/release.yml:87,262` likewise builds first. `package.ps1:154,477` consumes and copies existing binaries. Setting an environment variable only in that packaging step cannot alter the embedded channel.
    Change: if retained, call it an explicit self-update capability and set it in the actual release build invocation, with `rerun-if-env-changed`, exact-value parsing, scoped environment restoration, and packaging verification. A copied release executable retains that bit; an inherited environment can set it accidentally. `RELEASE_TAG`, `!debug_assertions`, and a valid signature each describe narrower facts, not publication or candidate provenance. A simpler honest policy is explicit updater opt-in plus verified identity, with the candidate workflow explicitly disabling it; a package marker also requires the candidate copier to remove/rewrite it and bind it to the executable. Do not claim any binary-only signal distinguishes identical copied bytes. `candidate.sh` is not tracked here and was not found in the searched main checkout; the user-specified copy-from-dist behavior is therefore an input to this review, not a line-verified script claim.

16. **R-16 — must-fix — §B Skip; §F persistence: the existing read-modify-write race can erase a skip.**
    Evidence: `update.rs:479-482` rereads before committing a network result, but the read and write are not one synchronized operation. `:494-501` performs another independent read/write for seen state. A Skip write between the worker's read and write can be lost; atomic file replacement (`bt-persist/src/lib.rs:212-217`) does not make read-modify-write atomic. `KNOWN` is shared at `update.rs:587`, and `main.rs:111918-111924` already repaints every window for check results.
    Change: serialize all check/seen/skip mutations through one owner or lock covering the whole read-modify-write, retain unrelated fields and the cadence timestamp, then publish one coherent snapshot and repaint all windows. Surface a failed Skip persistence rather than claiming it will survive restart. Compare the skipped tag's precedence explicitly if “until a newer tag” is intended; mere inequality reoffers an older still-newer-than-running tag after a release is removed. Loading cached state must suppress the skipped tag even when no request is due; a later higher tag must be eligible. Maintain one process-level offer and reject stale window/job events.

17. **R-17 — must-fix — §B/D card eligibility and verbs: several reachable states have no defined exit or entry.**
    Evidence: `update.rs:680-682` gates the request on the switch, but `:607-611` still loads cached tags. `first_run.rs:22-27` supports the proposed floating geometry, `notice.rs:26-46` supports no dimming/30 px, and `settings.rs:5385,14840` supports the cited row/surface. These are UI precedents, not a process-wide updater policy. §B requires an owned location for Available, while §D wants cards for manager-owned/unwritable locations.
    Change: include the automatic-check switch in automatic-offer eligibility, including cached offers and in-flight results after switching off. Separate informational manager/manual-install offers from installable offers. Specify source and bounds of the highlight line (the check currently stores only `tag_name` at `update.rs:321-323`), no-ordinary-window behavior, focus/keyboard/Escape handling, and priority against other cards. Define Verified → Later: retain staging and provide a discoverable Restart now entry, or discard it explicitly. Do not strand the job behind a once-per-launch gate or suppress a newer tag merely because a stale cached tag consumed that gate. Label the initial verb consistently with the second confirmation: it currently promises a restart but first only downloads. Later must not relight a dot already acknowledged in Settings (`update.rs:355-357`).

18. **R-18 — must-fix — §C W/K split; §G stations: forced session flush can still block the visible window indefinitely.**
    Evidence: `persist.rs:365-385` waits on an unbounded `recv`; `:708-743` uses it in `flush_judged` and can fall back to synchronous disk I/O. `:266-277` explicitly explains why disk work was removed from the window thread. `hang_watch.rs:1440-1465` changes the window heartbeat's station; a station does not make blocking safe.
    Change: W snapshots/serializes and requests a forced write generation, then processes events until its receipt arrives; abort before commit on refusal or an explicit timeout policy, without racing another writer. Keep location probing, download, hashing, extraction, signature tools, swapping, rollback, and cleanup off W. Give W's offer/dispatch, progress/outcome handling, session barrier, and quit transitions distinct attributable stations with restoration on early returns. Give K separate phase/deadline diagnostics; it must not update W's heartbeat to disguise a hang. Add stations to both new AppEvent arms (`main.rs:588-609`) and the non-event press/quit paths.

19. **R-19 — must-fix — §D Homebrew/winget detection: global presence is not ownership, and the winget command names the wrong package.**
    Evidence: `packaging/winget/manifests/w/WeiyiShi/Folio/0.4.0/WeiyiShi.Folio.installer.yaml:3,8-14` already defines `WeiyiShi.Folio`, ZIP/portable, and the versioned root; `docs/RELEASING.md:654-680` documents its layout. `docs/plans/release/winget.md:3-6` is already a submission plan, not a future absent file. `docs/RELEASING.md:1003-1007` identifies the actual Homebrew tap/cask.
    Change: offer `winget upgrade --id WeiyiShi.Folio --exact`. Determine ownership of this canonical install using package receipts/registration and actual roots, including custom install locations and symlink resolution. A leftover Caskroom directory or a separate installed cask falsely disables updating a manually copied Folio; default-prefix-only checks miss managed custom-prefix installs. A portable folder merely named `Microsoft/WinGet/Packages` can falsely match, while custom winget roots can be missed. False positives cost an unusable command/manual work; false negatives mutate a manager-owned install and desynchronize receipts, potentially breaking later upgrades/removal. Represent unknown ownership and fail safely with the releases-page route; do not treat writability as ownership.

20. **R-20 — must-fix — §C sparse MSIX; §H: the cited API has no version field and rollback must include registration policy.**
    Evidence: the function is `msix::registered()` (`msix.rs:258`), not `registration()`. `PackageRegistration` at `:242-250` exposes only `full_name` and `external_path`. `package.ps1:389-396` writes a four-part numeric version; comparing it directly with three-part `version::VERSION` is not the proposed predicate. `msix.rs:305-307` supports replacing registration without remove-first, and `explorer_menu.rs:58-79` supports doing repair on its worker.
    Change: expose/query the package version with a typed comparison to the expected manifest version, preserve absence and external-location ownership, and publish a visible repair-failure state. Delay re-registration until the new build is accepted, or define how rollback restores the old package registration, including downgrade refusal. Do not make a registration failure falsely report that every installed file was unchanged, and do not silently disable a still-present broken registration.

21. **R-21 — must-fix — §F clean-machine plan: the proposed acceptance run cannot exercise the feature.**
    Evidence: `update.rs:31-44` states that no updater shipped in the starting implementation; `:95-98` says anonymous requests cannot see drafts. `cli.rs:406-407` rejects the new flag today. Thus ordinary 0.4.1 cannot perform the proposed in-app update to a private draft 0.4.2. `docs/plans/release/clean-vm.md:611` already names a stronger startup criterion, `first_text_present`, than file mtimes or `--version`.
    Change: start with a signed/notarized updater-capable baseline and an explicitly accessible controlled successor, or a test-only injected release source. Do not edit public production assets to exercise corrupt checksums. Cover usable restored multiwindow startup, immediate child death, hangs, claim timeout, power/process interruption at each boundary, locked rollback files, second volumes, manager ownership, quarantine, and failed session save. Read the actual installed bytes and identity; mtimes alone prove nothing. Make deletion assertions conditional on health commitment, not “the second start.”

22. **R-22 — must-fix — §F missing CPU-only tests: the current fake inverse test assumes away the dangerous failures.**
    Evidence: the design's ten gates at §F cover successful inverse execution but not failure of the inverse or loss of its in-memory history; `persist.rs:223-233`, `update.rs:479-501`, and `main.rs:110997-111082` expose the relevant claim, write, and quit interleavings. Add these deterministic tests using fake clocks, processes, transports, locks, and a durable fake filesystem, plus temporary-file tests where appropriate:

    - `every_crash_boundary_recovers_a_complete_launchable_install`, `recovery_can_itself_be_interrupted`, `rollback_failure_preserves_journal_and_backups`.
    - `spawn_without_health_never_commits`, `early_crash_or_health_timeout_restores_old_build`, `unacknowledged_backups_are_never_swept`, `unknown_old_files_are_never_deleted`.
    - `acquired_claim_is_adopted_without_a_gap`, `transient_claim_refusal_is_not_cached`, `await_timeout_never_hands_over_or_starts_a_nonwriter`, `manual_launch_and_relaunch_have_one_writer`.
    - `two_data_directories_share_one_install_lock`, `locked_backup_blocks_reuse`, `cross_volume_staging_finishes_before_live_renames`, `renamed_bundle_updates_only_itself`.
    - `quit_cancel_or_failed_save_prevents_swap`, `close_during_each_phase_preserves_recovery`, `stale_progress_cannot_revive_a_cancelled_job`, `session_receipt_matches_the_final_snapshot`.
    - `packaged_zip_root_is_accepted`, `duplicate_case_alias_stream_link_and_traversal_entries_are_refused`, `expanded_size_limit_precedes_disk_exhaustion`.
    - `offered_tag_survives_latest_changes`, `mutated_asset_hash_pair_refuses_before_swap`, `validly_signed_wrong_product_or_version_is_refused`, `dn_values_preserve_case_and_order`, `timestamp_policy_accepts_the_packagers_format`.
    - `unknown_length_stream_is_bounded`, `https_redirects_work_and_http_redirects_refuse`, `redirect_loop_and_trickle_body_hit_deadlines`, `cancel_interrupts_idle_wait`, `short_write_disk_full_and_flush_failure_never_verify`, `progress_queue_has_one_pending_wake`.
    - `skip_racing_check_and_seen_keeps_all_fields`, `skip_failure_is_not_reported_as_persistent`, `cached_skipped_tag_stays_hidden_inside_daily_cadence`, `newer_tag_is_offered_after_skip`, `switch_off_suppresses_cached_and_inflight_offers`.
    - `verified_later_has_a_resume_or_discard_path`, `manager_receipt_must_match_this_install`, `candidate_opt_in_is_explicit`, `unsupported_driver_returns_failure_without_panicking_or_downloading`.

23. **R-23 — must-fix — §G three-ticket split: establish recovery contracts first, and do not ship a panic stub.**
    Evidence: `main.rs:118197-118201` and `persist.rs:223-233` make startup/claim changes independently consequential before any swap driver exists. `package.ps1:472-497` shows that even the plan's fake filesystem model must first match the actual artifact. Rust `todo!()` panics; it cannot “report Failed” as §G says. Both platform drivers can have testable injected cores, so ticket 1 is not the only testable ticket.
    Change: keep a shared-core ticket followed by Windows/macOS drivers only after a reviewed recovery/health/claim protocol and packaging-capability contract are part of that core. Drivers may then proceed independently, with each integration gate required before enabling its platform. Ticket 1 can ship harmlessly only with a typed Unsupported/Failed return before network, staging, flush, wait, or mutation, automatic install offers capability-gated off, and all ordinary check/launch behavior unchanged. A visible “Update and restart” that downloads then admits no driver exists is misleading even if it cannot brick files. Include the build/release scripts and release instructions in the ticket file lists; currently none sets the proposed build-time signal at the necessary time.

Verdict: **redesign section C first**, including its §B shutdown/health edges and §F recovery tests. Implement the remaining must-fixes before enabling either platform's updater. The card and check can be built behind a disabled install capability while that redesign is reviewed.
