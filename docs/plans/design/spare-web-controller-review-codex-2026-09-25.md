**Verdict: adopt with changes.** Keep the single, non-replenished spare and the existing window-thread WebView2 ownership. Do not implement the lifecycle and acceptance contract exactly as written: creation, retirement, and failed adoption have gaps that the proposed ten tests can miss. These are conditions of adoption, not evidence that the spare idea should be rejected.

SW-1 through SW-7 are this review's obligation identifiers; they are not existing ledger IDs.

The coordinator's answers are constraints, not outstanding questions: **D-64 remains open, narrowed, for 0.4.6; wgpu device loss alone does not retire the spare; v39 migration infers `Used` from saved session/Recent web-page evidence.** The note and brief must incorporate all three. **P1 — SW-1: retirement must be phase-aware and must intercept recovery before it causes effects.**

Exact paragraphs: §2 **“Retired — one predicate … read after every drive”**, especially **“a state other than `Ready`, or no controller”** and **“the seat's own machine would rebuild; a spare never rebuilds”**; §2 lifecycle table's `Creating` row; §7(c′)'s **“the spare closes on the same event.”**

Failure sequence, ordinary startup: the clock creates a seat; `WebSeat::open` leaves it `EnvironmentPending`, with no controller. Its first `drive` consumes `Environment`, requests the controller, and leaves it `ControllerPending`, still with no installed controller. The stated predicate retires it. Neither a ready-generation comparison nor a blanket `!Ready` test makes sense during this normal creation interval. The headline spare may therefore never become available.

Failure sequence, recovery: with a ready spare, `BrowserProcessExited` or browser `ProcessFailed` enters `WebSeat::drive` → `digest` → `apply(RebuildFromScratch)` → `host.close`, `forget_web_environment`, `start_environment`. Only then does `drive` return to the proposed predicate. Retirement is too late to uphold “never rebuilds.” If a real page also received the event, driving pages first can start a new environment request which the spare's subsequent recovery forgets. `EnvironmentSlot` serializes callers of `ask`; it cannot protect them from an unnecessary `forget` that invalidates their request. A new-version event similarly starts the seat's rebuild wait before the spare owner gets a say.

There is also a different invalidation missing from the predicate: another seat forgetting the process environment does not change this spare's `present_state()` generation/state/controller tuple. `holds_the_process_environment` rejects a later rehost, but that is a handoff guard, not timely retirement while the spare is idle.

Fix: specify phase-specific transitions through the real seat driver. While `Creating`, allow the expected pending states and retire on actual failure, cancellation, or the start deadline. While parked, consume a browser/version invalidation as terminal retirement **before** executing the normal page's recovery effect. Reuse the existing close/effect machinery with an explicit parked-seat recovery policy; do not copy the entire driver. Observe process-environment invalidation at the owner boundary and revalidate eligibility when taking the spare. After adoption, the normal page recovery policy applies. Retirement is idempotent and late controller completions remain owned and closed; they never install or resurrect the spare. Add event-sequence tests with delayed callbacks, including a real page and spare hearing the same browser event, asserting creation/forget counts and parent lifetime, not just predicate outputs. Q2 remains unchanged: a recovered wgpu device loss is not one of these browser invalidations.

**P1 — SW-2: the exit wait has no complete clock/wake path, and orderly failure is omitted.**

Exact paragraphs: §2 **“Driven … ticked in the application-clocks window's turn”** and **“The last window and quit … the run may not end until the spare has let go”**; §5 tests 8 and 10; appendix **“Launch 3 … close before any page.”**

Failure sequence, last-window close: a `Used` profile warms a spare and opens no actual web pane. Closing its terminal window sets `leaving`. `reap_leaving_windows` finds that window's web map empty and removes the window. The added `has_let_go(now)` check can prevent exit, but `about_to_wait_inner` then reaches its empty-registry arm, sets `ControlFlow::Wait`, and returns. There is no application-clocks window left. Unless the spare's own deadline is folded into this arm, the deadline is never revisited. A test which directly calls `has_let_go(deadline)` conceals this hang.

Failure sequence, quit: the retiring branch of `about_to_wait_inner` returns before normal window turns. `FolioApp::advance_retirement` currently ticks only the windows' seats. Adding a predicate to `every_page_has_gone` does not tick the spare. Quit can consequently consume the full outer bound without completing its inner cleanup. This is especially relevant because **`WebHost::close` removes its environment event subscriptions**, including `BrowserProcessExited`; a closing seat cannot rely on receiving a future exit notification through that removed handler. A notification already queued is possible; the deadline must work without one.

Failure sequence, orderly stop: after idle warm-up, a frame-shape rejection enters `FolioApp::fail`. That path reports the failure, closes/clears windows, calls `App::finish`, and exits the loop. `exiting` also returns early for an empty registry. Neither proposed retirement site covers it. A process which previously hosted only terminals now has a live WebView2 child under an unretired hidden parent. `main`'s final `leave_process` bypasses normal Rust destruction on Windows, so “Drop will close it” is not an answer. Conversely, routing every such stop through an extra ordinary 12-second wait changes the current stop timing.

Fix: give spare retirement an application-owned advance/deadline path, called by both quit retirement and ordinary reaping, independent of all visible windows. Preserve that deadline in the empty-registry control flow. Start one absolute run-retirement bound, never restart it on polls, and wait for pages and spare concurrently, not sequentially. Consume `Gone` and actually release owned resources before declaring completion; at the bound, take the explicit abandonment/diagnostic path. Specify the `fail`/`exiting` emergency policy separately, including who closes the controller and who retains the HWND until the final exit. Preserve prompt frame-failure reporting and sentinel finalization; do not resume frame publication or show an interactive quit question. Exercise the existing frame-validator stop path with a ready spare and pin report, session finalization, footer, and process-exit timing against the baseline. No numeric frame-validator timeout was found in the reviewed worktree; the review does not invent one or authorize increasing it.

**Is waiting needed?** Yes, retaining the parent while pumping its teardown is justified by §7.35's measured child-HWND hang, and the new parent has the same obligation. It is not justified as an unconditional sleep until every browser PID disappears. The inner 10-second deadline and outer approximately 12-second bound are backstops, not proof that the browser has exited; spike 59 measured exits as late as 17 seconds. A safe bounded lifecycle and “no remaining runtime process at the exact bound” are different claims. Keep the existing `leave_process` road, verify HWND/process cleanup, and record any browser tail separately. Do not raise an existing gate to make the new path green. A historically web-using profile that opens no page this run acquires a new invisible shutdown cost; it did not already pay a page's wait on that run.

**P1 — SW-3: adoption needs an ownership transaction through every failure, particularly `Lost`.**

Exact paragraphs: §3 step 1 **“`Lost`: the seat is already the pane's … the parent waits out the closed controller's browser-exit wait before it is dropped”**; steps 2–3, which apply fallible setters before insertion; §2 table **“`Adopted` … nothing … terminal.”**

Failure sequence: `take()` removes the whole `Spare` and makes the slot terminal. A rehost step fails and compensation also fails. `WebSeat::rehost` moves the seat's address to the target and calls `on_rehost_lost`, beginning a rebuild. The note moves that seat into the window but says its old parent continues waiting. There is no owner, deadline, or completion signal for this parent in the proposed states: `Adopted` owns nothing; `Retired` owns a closing seat plus parent; the actual seat is now a live, rebuilding pane. It will not emit teardown `Gone` merely because its old browser wait ends. Waiting for that pane's eventual `Gone` can retain the parent for the pane's entire lifetime; dropping the local parent immediately violates the promised wait.

A second failure exists after `Moved`: `set_device_scale` or `set_color_scheme` can return an error before the seat is inserted. The slot is already consumed and the controller is already parented to the target. An early return can leave the controller outside both lifecycle owners. `WebHost` has no general Drop implementation which substitutes for the specified explicit teardown road. `SourceKept` also needs a defined handback from the consumed slot into retirement rather than an informal reassignment to a terminal phase.

Fix: define the handoff as one transaction with explicit resource results for source-kept, moved, rebuilding, and post-move configuration failure. Every return must leave the seat either in the adopting pane's map or in an actively driven retirement owner. Retain an old parent after `Lost` under a named owner with its own release condition tied to the old-controller teardown/bound, not the eventual life of the new page. If retaining that resource requires extending the slot, the table must say so; do not make a second owner of the live seat. Apply the URL/mint to the rebuilding seat without losing it. Route both cold creation and adoption through the existing pane-bookkeeping tail (`leave_preview_buffer_in`, `clear_preview_image_in`, and outcomes), rather than copying only the map insertion. Fault-inject preparation, compensated failure, failed compensation, and both setters; assert exact owners and subsequent pane close/tear-out behavior.

**P2 — SW-4: Q3 needs a contextual migration contract, and the receipt must distinguish memory from disk.**

Exact paragraphs: §1 **“Where … the migration writing `Never`”**, **“Who writes it … does nothing otherwise … once per profile”**, and **“Who reads it … scratch … every first launch make no spare”**; §8 Q3. The coordinator's answer supersedes the `Never`-for-all-upgrades choice.

Failure sequence: upgrade v38 settings with no live web pane but a web page in Recent. A plain `migrate_settings_v38_to_v39(Value)` sees only settings JSON, writes `Never`, and misses that history. Opening a web page is again cold, contrary to Q3. Reading arbitrary files from that migration would instead break the current pure `MigrationStep = fn(Value) -> Value` boundary, and could contaminate settings-bundle import with local startup semantics.

Fix: keep structural migration pure and name the startup reconciliation which completes the v39 upgrade using the already-loaded session. `FolioApp::create` opens `SessionStore` before `SettingsStore`; use that information before restore choices discard/rewrite it and before the warm-up can fire. In this schema **Recent is inside `SessionV1::recent`**, not another file. Inspect typed page records in saved pane/current and pool entries, `RecentSeedV1::Preview`, and `RecentEntryV1::previews` (`RecentPreviewV1::Page`), across windows/tabs, rather than searching strings for `http` or treating an HTML filename as a page. Specify missing/corrupt/future-version and already-v39 behavior; absent trustworthy positive evidence must not manufacture `Used`. Preserve the store's writer-of-record rule. Update the “one writer” architecture claim to account for this migration input, through the same receipt writer.

There is also a write-failure sequence: the first successful commit calls `SettingsStore::store`; the in-memory settings become `Used` even if the write fails. The proposed “if loaded is Used, do nothing” prevents later successful commits from reaching the store's existing failed-write retry logic. Fix the receipt writer to let `SettingsStore` decide whether an unchanged value still needs writing. Test one successful disk transition in the normal case and a failed first write followed by a successful retry, with no writes by a secondary reader process. The statement that `Committed` excludes blank, refused, and unsuccessful top-level navigation is supported by the current machine; retain that exact producer boundary.

**Can someone who never opens web pages pay 91 MB?** With `Never`, no positive saved page evidence, and receipt-preserving import, the design should make zero controller requests: no 91 MB spare tree. Environment-only warming still has ticket 54's small cost. This is a guarantee about the profile's recorded history, not an individual human: a copied profile containing `Used` or saved pages qualifies under Q3. A fresh isolated scratch profile does not warm a controller. A reused scratch profile which successfully opens a page becomes `Used` and does warm on the next launch—the appendix explicitly relies on that. Replace “scratch profiles never warm” with this precise statement, and isolate both settings storage and `LOCALAPPDATA` in the smoke. No new UI switch is needed.

**P2 — SW-5: install acknowledgement is not the warmed condition measured by spike 59.**

Exact paragraphs: §2 table **“`Ready` … `InstallEvents` acknowledged (its `about:blank` navigation issued)”** and the `Creating` construction; §3 step 4 **“never against zero by zero.”**

Failure sequence: the spare is opened without any call that supplies `wanted_bounds`. `WebSeat::open` initializes hidden presence and no bounds. Installation calls `stand_on_the_floor`, but there are still no bounds to send; its acknowledgement then navigates to blank. A page takes the spare immediately after this acknowledgement while the blank renderer/navigation may still be starting. The spike measured warm-up through completed `about:blank`, with scale, bounds, visibility, and commits supplied by its harness. The note has neither reproduced that preparation nor measured its earlier handoff point. A hidden HWND's 800×600 size does not automatically populate a composition controller's bounds.

Fix: specify and drive the spare's initial nonzero controller geometry through the existing placement path, with scale before size and the required compositor commit, keeping the native parent never shown. Define whether “eligible for adoption” means installed or blank-completed. If retaining the earlier condition, measure that case and stop attributing the fully warmed 146 ms distribution to it. For adoption, only **target** bounds satisfy the navigation condition; stale spare `wanted_bounds` must not release the requested page URL. Test adoption before target layout exists, a hidden/background pane, and bounds becoming available later. The deferred address must be released once, through the common `Navigate`/mint/guard path, not on every subsequent presence update.

**P2 — SW-6: the quiet-turn argument assumes an environment callback timing which the actual interface does not guarantee.**

Exact paragraphs: §2 **“Made … answered on the spot … or joins the call in flight”** and §4 **“C is not re-gated on quiet … C follows B within the same quiet stretch.”**

Failure sequence: turn A asks for the environment, but this request is delayed. Turn B is quiet, opens the spare, and joins the request. The user resumes typing. The environment callback arrives during that activity; the spare's next `WebPageSpoke` immediately issues the controller call, which measured a worst hold of 590 ms. The source explicitly supports asynchronous answers, regardless of ticket 54's synchronous measurement. Even a queued immediate answer is not a proof that no input can arrive before its spoke is processed.

Fix: gate the actual spare `CreateController` effect on the existing quiet/restore/run-ending conditions, with an explicit deferred wake, or narrow the design so delayed environment readiness cannot arm spare creation until a newly quiet turn. Leave real page requests responsive to the user's request; do not make them wait behind the spare. Keep one `EnvironmentSlot::ask` path for all three askers. Add a delayed-answer/stir test and a page-open-during-creation test. No second environment request should be caused by competition between the spare and the page; separate controller requests in that case are expected.

**P2 — SW-7: the native acceptance test does not yet cover the adoption contract.**

Exact paragraphs: §3 **“What adoption does, in order”**, especially `take_focus = false` and steps 2–4; **“The link filter and the allowed-file state”**; appendix **“VM smoke (the real controller)”**.

Failure sequence to expose, not a claimed measured failure: warm on one DPI/theme, change theme and move the accepting window to a different DPI, adopt into a visible pane, then type into a page field using IME. A hidden-to-hidden `Moved` result and a quick `NavigationCompleted` do not establish correct first-frame scale, popup origin, keyboard ownership, or candidate-window placement. The present smoke would be green even with a page drawn at the wrong scale or unable to accept text.

The proposed ingredients are mostly correct. `WebSeat::rehost` prepares the target visual; the platform handoff hides, detaches and commits the source, reparents, attaches and commits the target, then updates bounds/presence/position. Keep the spare hidden through this intermediate old-bounds stage. Set the adopting window's authoritative scale and current scheme before its page navigation, invalidate the controller/visual caches through `take_address`, then use the normal placement writer and normal frame commit. Reapplying static `WEB_SETTINGS` and event registrations would be unnecessary and risks duplicate subscriptions. The guard report must travel with the seat. Windows gate closures really do read the shared mint per request, and the `Navigate` effect updates it before calling the engine; keep that entire path. Updating both captured trace labels through a cell in `take_address` is appropriate, including subsequent tear-outs.

Fix the acceptance contract: assert live controller identity/parent and DPI properties after adoption; render a page that reveals CSS size/DPR and colour preference; check nonzero bounds, pane origin, clipping and the first visible frame before any corrective resize. Then change DPI again. Exercise allowed local navigation and a currently-disallowed file navigation through the existing gates, including an iframe/resource callback where the present policy differs; do not invent a stricter file policy. Verify trace lines name the target pane and change again on tear-out. Initialise current shortcut claims before the page can receive keys, and route queued `PageFocus` outcomes through the adopting window. `take_focus = false` only suppresses the explicit focus call; `apply_web_outcomes(PageFocus)`/`settle_the_web_keyboard` still decide what focus the controller may keep. Check address-bar typing, background-pane adoption, click-to-focus, Tab out, a Folio shortcut, and IME composition/candidate placement. There is no need to transfer an old page's composition because the spare is blank and never interactive.

Microsoft documents [parent reassignment](https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/win32/icorewebview2controller?view=webview2-1.0.3650.58#put_parentwindow), and separately documents that [manual rasterization-scale ownership requires app updates and affects popups as well as content](https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/win32/icorewebview2controller3?view=webview2-1.0.3650.58). Those contracts support the mechanism; neither substitutes for the missing visible/cross-DPI product evidence.

**Lifecycle coverage required by the corrected note.**

| Road | Required result / review judgment |
|---|---|
| Never-used profile, repeated launches | Environment stage is allowed; zero spare/controller calls and no receipt write from blank/failure. SW-4 tests the eligibility boundary. |
| Page before spare stage | Existing page opens normally; spare stage finishes without constructing one. Include pending and background pages in “any web map holds a page.” |
| Page while spare is `Creating` | Page cannot take it and need not wait; both ask the same environment slot. Specify the late spare's fate: the current table implies it may later serve another pane. If that is retained, say “first eligible page,” not invariably “first page.” |
| Two panes in one turn | At most one gets the ready controller; the other creates its own. Single-threaded take is sufficient only if ownership is moved before any reentrant platform work; test the real caller, not just two slot takes. |
| Environment failure / no callback | Retire once, one spare diagnostic, release parent under the defined bound; real pages retain their existing failure card/retry road. No warm retry loop. |
| Two builds, one UDF | Preserve common options and `EnvironmentSlot`; `0x8007139F` remains an ordinary environment/controller failure. A spare in build A now keeps the browser/options resident before any visible page, extending the interval in which build B can hit the existing conflict. Do not describe timing/exposure as literally unchanged. Never kill the other build's browser or reset the shared folder. |
| Browser exit/version change/environment forgotten | Terminal retirement while parked, no speculative recovery request or stale handoff (SW-1). After adoption, normal page recovery and tear-out continue. |
| wgpu device loss | Keep the spare, per Q2. Its null-device compositor does not share the recovered wgpu surface. Test that it remains adoptable afterwards; an actual browser failure remains SW-1. |
| DPI/theme change | A parked controller need not follow every window. Adoption receives target values; after insertion the existing window update paths apply. Native evidence is SW-7. |
| Non-last window close | Spare remains app-owned. Its clock follows whichever window drives application clocks; it must not keep references to the closed window's compositor. |
| Last-window close / explicit quit | Concurrent bounded retirement, sentinel at the existing save/finish boundary, pumping even with zero windows (SW-2). |
| Frame failure / unexpected loop exit | Explicit emergency ownership/exit policy and unchanged validator obligations, not an accidental Drop after the pump stops (SW-2). |
| `Moved` / `SourceKept` / `Lost` / setter failure | One lifecycle owner for every seat, pending callback, compositor and parent; no detached local value lost on `?` (SW-3). |

**What the ten red tests actually establish.** Keep the behavioral cases, but a missing symbol or a changed source spelling is not a red behavioral assertion. The note's list is ten groups, not ten individual tests; report actual selected/executed counts.

| Proposed group | Property versus shape; required correction |
|---|---|
| 1 — never used | Good behavioral property if the real clock/door records zero controller construction. A flag helper alone is insufficient; include fresh, upgraded without pages, failed navigation and import. |

| 3 — page already open | Good decision test. Feed pending/background/multiwindow pages from the same inventory the product reads. |

Assert controller identity and recorded door calls through adoption, not the name of a new method. |
| 6 — size before URL | Good property if driven through placement and the real effect executor. Cover stale spare bounds, unsized target, hidden target and repeated placement; a bare `adopt(url, false)` test cannot prove those inputs are correct. |

Before the VM, headless tests can establish the transition graph, single environment request, one-shot consumption, ordering of recorded effects, failure ownership, deadline wake folding, migration and receipt writes. They cannot prove actual COM reparenting, first-frame rendering, focus/IME, native child-window destruction, runtime process tails or the claimed latency. CI green alone therefore cannot close SW-7 or certify teardown safety.

One **expanded VM smoke session** can supply that native evidence. Retain the three launches, but wait for an observed spare-ready marker rather than assuming 12 seconds makes it ready. Cover a fresh Never launch and a seeded Used launch; visible cross-DPI adoption after a theme change; input/IME and current file gates; second-pane creation; a post-adoption tear-out; close while Creating and while Ready; explicit quit as well as last-window close; and a frame-validator orderly stop with a parked spare. Use headless fault injection for the rare rehost/version/failure branches rather than expecting a VM to hit them by chance. Record the hidden parent HWND, controller/parent identity, relevant browser PID association, creation/adoption stations, first visible page and navigation times, sentinel removal, footer and process exit. Time the unadopted shutdown as well as the adopted case. Do not make “no descendants at exactly 12 seconds” a purported consequence of a 17-second measured browser tail. A VM unable to exercise distinct source/target DPI leaves that acceptance condition open.

**Ticket size and two-day decision.** Keep this as **one atomic feature ticket**, conditionally M; no split is required merely because it spans platform, app and persistence. The receipt, admission, adoption and retirement must ship together, and a flag-only or spare-only partial merge would not deliver the reviewed feature safely. The present brief's ten groups plus its current smoke are insufficient. Amend the state/ownership contract and test matrix before dispatch, keep the existing controller, placement and teardown implementations shared, and run the visible/cross-DPI and exit cases early enough to stop within the window. This is not approval for an unrelated shutdown/recovery redesign under ticket 60. If closing SW-1–SW-3 reveals a larger prerequisite, split that prerequisite for 0.4.6 and move the feature with it.

The release gate remains the owner's: **not CI-green in two days → 0.4.6**; CI-green without the required VM evidence is also not merge-ready. Do not extend the window, weaken tests, or merge a partially enabled feature to retain 0.4.5. Update D-64 to open/narrowed for 0.4.6, including first-ever pages, pages which arrive before readiness, and all pages after the spare is consumed. Adjust the changelog's unconditional “first one … appears in a fraction of a second” to acknowledge an available, successfully adopted idle-prepared spare.

The three highest-priority corrections are **SW-1 (phase-aware retirement before recovery effects), SW-2 (application-owned teardown pumping and explicit orderly-stop handling), and SW-3 (complete ownership across failed handoff).** With those and the stated migration/native gates resolved, the spare is a supported, bounded extension of the existing design.
