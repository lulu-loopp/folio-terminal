1. **F-1 — Blocker — The retained recovery table bypasses health and forgets unsuccessful recovery.** Obligations R-1, R-2, R-22.

   **Exact paragraphs:** R.1, “the idempotent decision table of §C.6”; §C.6, row `Flipped, no health | this process is to_version | write health, delete the recorded backups, remove journal`; row `Failed / RolledBack | — | show the sentence once, then remove the journal`; and §C.5, “P deletes exactly the recorded backup set … removes the RunOnce entry, journals Healthy”.

   **Failure sequence:** On Windows, P finishes moving the new set into `C:\Folio`, persists `Flipped`, and the machine loses power before N has started. At the next logon the new-version applier executes `--update-recover`; it is itself `to_version`. The table allows it to acknowledge health and delete `backup/` without claiming the intended data directory or drawing anything. An ordinary N start also runs this table before handover/first text, so it can delete the backup and then crash initializing its first pane. The same premature-health path exists on macOS if startup finds the journal. Separately, a locked file makes rollback fail, P writes `Failed` and retains backups as §C.5 requires; the next recovery invocation follows §C.6 and removes the journal that names those backups. A power cut during post-health backup deletion also has no specified row for `Flipped` with persisted health or for `Healthy` with cleanup outstanding.

   **Change:** Make recovery discovery incapable of manufacturing health. Only the normal N startup path, after the recorded data-directory claim, compatible reads and first text, may emit a transaction-bound health receipt; a headless helper never may. Serialize that receipt with P's deadline/rollback decision through one transaction owner. Persist an irrevocable `Healthy` decision **before** deleting any rollback data or recovery entrance. Separate pre-mutation failure, rollback-incomplete, rollback-complete and committed-cleanup-pending; only verified complete restoration may retire a failed transaction. Specify idempotent rows for every persisted state, including health present, partial cleanup and unsupported journal versions. Test a power cut before/after each receipt, decision, deletion and journal retirement. Merely naming `every_crash_boundary_recovers…` does not make the present table satisfy it.

2. **F-2 — Blocker — A `!` RunOnce value is neither a durable registration nor a retry-until-repaired service.** Obligations R-1, R-14.

   **Exact paragraphs:** C5, “the `!` prefix makes Windows delete a RunOnce value only after its command completes, so a recovery interrupted at logon runs again at the next logon”; retained §C.4, “writes … RunOnce … and journals Flipping, fsync”; R.4's RunOnce row, “Windows after a completed run”.

   **Failure sequence:** P writes the value, flushes `journal.json`, moves `C:\Folio\folio.exe` into `backup/`, and power fails before the registry hive's lazy flush. The durable filesystem journal cannot make an unflushed registry value durable; the launch path is missing and no logon command repairs it. In another run, the registered recovery process starts, encounters a still-locked destination, records an incomplete rollback and exits nonzero (or crashes). Its execution has ended without repair; `!` does not encode “keep this until Folio's journal says Healthy or RolledBack.” The next logon therefore cannot be assumed to retry. E4's self-termination test is not a substitute for a contract covering nonzero exit, process crash and machine power loss separately.

   **Change:** Flush and check the recovery registration before the first destructive move, with explicit failure handling. Use a recovery entrance whose lifetime the transaction owns until durable completion—such as a transient persistent logon registration with its own undo, or an independently installed launcher—rather than claiming `RunOnce` guarantees successful recovery. A wrapper that can die has the same problem unless another durable entrance survives it. Keep the applier and journal until that entrance is safely retired. Validate the fully quoted command's length, since RunOnce documents a 260-character limit and this command repeats an arbitrarily long portable root. Define the user scope: HKCU for user A does not repair a shared installation when only user B logs on. Either provide a reachable per-install repair route or explicitly restrict unsupported shared-install cases before mutation. [Microsoft's Run/RunOnce contract](https://learn.microsoft.com/en-us/windows/win32/setupapi/run-and-runonce-registry-keys) describes deletion timing, not Folio transaction success; [RegFlushKey](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regflushkey) distinguishes visibility from persistence.

3. **F-3 — Blocker — The macOS transaction loses its stable lock, discoverable journal and durable backup.** Obligations R-1, R-6, R-7, R-14.

   **Exact paragraphs:** C6's three macOS bullets: “system's item-replacement directory”, “flock … on … the bundle directory itself”, and “journal … Folio's data root … update/<txn>.json”; C7, “The one residual”; R.3, “one stat, and work only if a journal exists”.

   **Failure sequence:** P locks the directory inode at `/Applications/Folio.app`, then swaps it with the staged bundle. That lock now protects the **old** bundle at the staging path. A second process opening `/Applications/Folio.app` opens the **new** inode and can acquire an independent exclusive lock while P still awaits health. With another user/data root it also sees no journal; with the same root it can incorrectly enter F-1's health row. Separately, P swaps and power fails before health; the new app has a loader failure and the temporary replacement directory containing the old bundle is purged. There is now neither a runnable recovery process nor a retained old installation. Adding a LaunchAgent that points into the same purgeable directory does not fix this. Even with a healthy new app, the retained §C.6 install-root lookup does not find `~/Library/Application Support/Folio/update/<unknown-txn>.json`; no replacement discovery/index protocol is given.

   **Change:** Define a stable installation identity and lock object **outside both exchanged bundles**, shared by every actor allowed to mutate that installation and unchanged across a swap. Define an installation-to-transaction locator, including how a second data root/user discovers an unfinished job; do not key identity only by the shared `/Applications` parent. Put rollback material and an independently runnable recovery helper in durable storage on the required volume, with ownership, permissions and uninstall cleanup. Temporary space may hold the download/expansion, not the sole rollback copy. Journal both bundle identities/digests and decide which side of a swap is present from those identities, with filesystem durability ordering. Then add the LaunchAgent and its registration/retry/retirement protocol. Its storage and discovery are part of Q5, not an implementation detail. If this contract cannot land, leave macOS self-update disabled. [Apple documents item-replacement directories as temporary](https://developer.apple.com/documentation/foundation/filemanager/searchpathdirectory/itemreplacementdirectory?language=objc), and [flock locks the opened file](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/flock.2.html), not the pathname a later open will resolve.

4. **F-4 — High — The Windows package is not authenticated as a set; C4 expands the gap to arbitrary future files.** Obligations R-8, R-9, R-5.

   **Exact paragraphs:** C4, “The new set is what the archive holds”; C8, the paragraph specifying checks on the executable, package and two Microsoft sidecars; retained §E, “the hash is the integrity check and identity is checked separately”; U-15's `mutated_asset_hash_pair_refuses_before_swap` gate.

   **Failure sequence:** An attacker able to replace a release's ZIP **and** `SHA256SUMS.txt` retains the real signed `folio.exe`, `folio.msix`, `conpty.dll` and `OpenConsole.exe`, changes `folio-here.cmd` or `uninstall.cmd`, then recomputes the ZIP hash. Every specified identity/version/hash check passes. The replaced command runs when its ordinary entry point is used. Alternatively the attacker adds an unknown regular DLL/configuration file to the new set; C4 installs it even though no signature binds it to Folio. Whether that particular DLL is loaded depends on the executable's imports/search behavior; the modified shipped `.cmd` counterexample requires no such assumption. `package.ps1` signs only the EXE/MSIX and `SHA256SUMS.txt` is unsigned. The sparse MSIX contains identity/resources, **not** the external executable or the other ZIP members, so its signature does not close this gap.

   **Change:** Authenticate a manifest/catalog covering the exact canonical filename, digest and size of **every** installed member, plus product, version, architecture and package-format compatibility, under a trusted release identity. It can travel inside the ZIP, preserving two network fetches. Reject unlisted/missing members and protect reserved updater/marker names. Publish and verify this artifact in the release scripts before enabling old clients that will need to consume it. An unsigned manifest beside an unsigned checksum is not a fix. Retain Authenticode checks as additional checks. In particular, `package.ps1 -Sign` delegates its sidecar checks to `sign.ps1::Assert-Signature`, which checks validity/timestamp and prints the subject; it does not enforce that the signer is Microsoft or that the signed file is the intended ConPTY component. Do not mistake that release-side provenance assumption for a downloaded-file identity predicate. The checksum fetched from the same release is sufficient for accidental corruption/mismatched downloads over the trusted transport; it supplies no independent authenticity against release-asset replacement. Repository immutability helps distribution operations but cannot replace the signed binding. The U-15 paired-mutation test currently has an accepted counterexample and must use it.

5. **F-5 — High — Equal publisher DNs do not establish continuity of the signing principal or product.** Obligation R-9.

   **Exact paragraph:** C8, “then the leaf subject compared as a parsed DN … against the running folio.exe's own leaf subject … A changed subject is a refusal”; C1, “the successor is the same publisher's Folio”.

   **Failure sequence:** Assume an attacker can supply the release bytes and has a different trusted code-signing certificate with the **same complete parsed DN**, not merely the same CN. They sign a malicious `folio.exe` with the offered VERSIONINFO and architecture, obtain a valid timestamp, and sign a matching-publisher MSIX. C8 accepts it even though the signing principal/key lineage differs. A self-signed certificate absent from the machine's trust roots, an expired untimestamped certificate, or a certificate sharing only CN but differing in another compared RDN does **not** pass; the design should state these boundaries. A timestamp establishes when a signature was made, not that its signer owns Folio. Likewise, another product legitimately signed by the same publisher is not identified solely by a version and architecture.

   **Change:** Keep full chain/signature/timestamp validation but bind continuity to a durable authenticated publisher identity and bind product to F-4's signed manifest. Artifact Signing provides a subscriber identity-validation EKU with a unique full OID under `1.3.6.1.4.1.311.97.` specifically for durable identity pinning; compare the full identity value from the trusted installed build under the appropriate trusted chain, not just the prefix. Confirm the actual release certificates carry it and define an authenticated migration for identity-resource changes. A separate pinned update-signing public key is another defensible contract. Do not pin each short-lived leaf fingerprint/public key. Correct the factual wording: certificates have 72-hour validity and are renewed daily, not necessarily once per release; multiple releases can share a certificate. Verify an old correctly timestamped release after its leaf expires, and specify revocation/offline/error policy. [Microsoft's certificate-management documentation](https://learn.microsoft.com/en-us/azure/artifact-signing/concept-certificate-management) explains both rotation and durable identity.

   **Trust root:** Today it is the OS trust store/Authenticode policy plus the identity extracted from the already trusted installed executable; GitHub/TLS controls delivery. On macOS it is Apple's certificate trust plus the trusted installed bundle's designated requirement. “Read from self” is a continuity bootstrap, not an independent proof that the initial copy was genuine. A compromised initial binary can replace its own policy. Adding F-4's authenticated release binding makes that installed trust anchor cover the complete successor rather than four selected files.

6. **F-6 — High — Lock transfer and launch admission have no protocol; probes do not exclude a second process.** Obligations R-3, R-7.

   **Exact paragraphs:** §C.2, “Take the installation lock”; §C.3, “O spawns P detached and then exits”; §C.4, P “holds the installation lock” and claims the data directory then “immediately releases it”; §C.6, lock held means “do nothing at all”; E3, “exclusive open of folio.exe”.

   **Failure sequence:** O holds the Windows no-sharing lock through `Prepared`. P cannot independently open that same lock until O exits; no inherited-handle transfer or acknowledged acquisition is specified. After O exits, a manually launched process can win the lock, read `Prepared`, and delete `staging/<txn>/set` under §C.6 before P acquires it. Later, if P wins, another Folio with a different APPDATA can start immediately after P's exclusive-open probe closes, or after the new `folio.exe` is moved in but before its sidecars. Its startup sees a held installation lock and “does nothing”, then proceeds into a mixed install. The original data-directory probe does not exclude that process. On macOS, `flock` is advisory even before F-3's swap issue.

   **Change:** Specify O→P lock ownership transfer and persist an apply-intent/handshake state before O exits, so no sweeper mistakes an accepted restart for disposable `Prepared` work. Require every ordinary launch to participate in installation admission: a destructive transaction must defer/refuse startup before settings, sidecars or handover are used; it must not mean “skip recovery and continue.” Track existing users of the installed set independently of data-directory claims, and refuse/defer when they cannot quit safely. Test two APPDATAs, two logon sessions, a manual start between every probe and move, and a sweeper winning the handoff race. Do not solve this by killing unrelated Folio instances or terminal children.

7. **F-7 — High — Rollback lacks both a live-child policy and a data-compatibility boundary.** Obligations R-1, R-2, R-4.

   **Exact paragraphs:** §C.5, “N exits, crashes, or the deadline passes … reverses the flip … then relaunches the restored old build”; its health paragraph, “read settings and session without a future-schema refusal”; §C.4's invariant that a complete copy always exists.

   **Failure sequence:** N hangs before first text while retaining its executable mappings and the data-directory claim. At 90 seconds P tries to restore files and relaunch O. Windows can refuse a rename; on macOS swapping names does not terminate N or release its claim. The old process cannot acquire the intended data directory. Another failure needs no persistent hang: N migrates/writes `settings.json` or `session.json` to a newer schema, then dies before health. Restoring the old binaries leaves O unable to read the new data. Interrupted rollback also needs its own construction: restoring backup files by move while discarding replaced new files can leave no complete tree after a later move fails. A full inverse that first preserves the complete new set avoids that particular loss, but the current phrase “reverses the flip from what is on disk” never specifies which algorithm or how its partially completed inverse is recognized.

   **Change:** Define trial startup as a bounded, transaction-owned process with admissions/data mutations constrained until commitment. Retain a real process handle/identity and a graceful-stop/escalation policy for the child P created; wait for claim release before restoration/relaunch. A manual healthy process needs its own coordination and cannot be indiscriminately killed. Require backward-compatible writes throughout the trial or isolate/checkpoint the affected data with an explicit, race-free restore/commit protocol. Preserve a complete immutable rollback source until restoration is verified, or explicitly replace I1 with a per-file reconstruction invariant and prove interrupted rollback against it. `RollingBack` must reconcile actual old/new digests, not blindly invert the last operation again.

8. **F-8 — High — The old inventory belongs to O, but the applier is the new build; the journal does not state the cross-version contract.** Obligations R-1, R-5, R-23.

   **Exact paragraphs:** C4, “the old binary performs the flip”, and “The old set is the running build's own shipped list”; C5, “Prepare writes the verified new folio.exe twice”; §C.1's journal has only `files:[…]` and `v:1`.

   **Failure sequence:** O is 0.4.6 and shipped `uninstall.cmd`; 0.4.7 removes that file and adds `helper.dll`. P is the staged 0.4.7 executable. If “running build's own shipped list” is evaluated in P, it does not back up the old-only `uninstall.cmd` and can mistake a pre-existing user `helper.dll` for a shipped old file, overwriting it. After a crash a recovered old build may use yet another list. Even if the implementer correctly passes O's list, the journal currently does not distinguish old shipped names, actually present old files, new files, their digests and pre-existing collisions. Recovery cannot safely reconstruct that information from P's compile-time constant. A future P with an incompatible journal/argv protocol can also refuse only after O has quit.

   **Change:** O records immutable old/new inventories, old presence, digests, file types and collision decisions under the installation lock before `Prepared`; P and every R consume that record, never recompute old ownership from themselves. Define a versioned O/P/N/R protocol and reject incompatibility before quit. Prove the helper's headless startup without installed sidecars before mutation, including the next version gaining a loader dependency. Prefer a known-good independent recovery executable/protocol for the rescue entrance: a second copy of an unproven new executable is physically independent but still shares its loader/early-start failures. Test adding/removing a filename, an old-only file during rollback, an unknown pre-existing name, and a future incompatible journal.

9. **F-9 — High — macOS identity is improved, but a recorded Gatekeeper rejection is not acceptance and ticket presence is not validation.** Obligation R-10.

   **Exact paragraphs:** C7, “Gatekeeper's assessment is recorded, not required”; U-11, “the stapled ticket's presence”; C7, “the seal and the stapled ticket are what let Gatekeeper accept it offline”.

   **Failure sequence:** A correctly Developer ID-signed successor satisfies the running bundle's designated requirement and carries the expected version, but is unnotarized, has an invalid ticket, or is explicitly rejected by the current assessment policy. Prepare records the rejection and still reaches `Verified`; after replacement the normal launch is refused, or launching `Contents/MacOS/folio` directly succeeds without proving the Finder/Gatekeeper launch users rely on. U-11 checking only that ticket bytes exist cannot establish valid offline notarization. `notarize.sh` currently treats post-stapling rejection as a release failure; the updater weakens that boundary.

   **Change:** Keep verification against the trusted running bundle's complete designated requirement—it gives identity continuity without a repository Team ID constant, provided the requirement really anchors Developer ID, Team identity and Folio's identifier. Independently validate notarization/ticket binding on the copied bundle. Distinguish assessment disabled/unavailable from an explicit rejection; do not silently accept an enabled policy's rejection. Specify supported in-process/runtime APIs rather than assuming end users have Xcode's `stapler`. Cover a copied notarized bundle, an invalid/missing staple, explicit rejection, disabled assessment, nested code, and first offline launch on a machine without a cached ticket. Code validity and notarization are distinct policies in [Apple's code-signing guidance](https://developer.apple.com/library/archive/technotes/tn2206/); repository `notarize.sh` supplies the release-side expected behavior.

10. **F-10 — High — “No marker → Ours” is safe only after marker delivery and negative ownership evidence are established.** Obligations R-15, R-19.

    **Exact paragraphs:** C2's classification paragraph, “no marker → Ours”; its assertion, “A copy of a managed folder carries its marker”; C2's winget paragraph; U-1, “read once at start”; U-2, “The owner pushes the two manifests”.

    **Failure sequence:** 0.4.6 is installed through a still-unmodified Scoop/Homebrew manifest, or Homebrew copies the new bundle but `postflight` fails before writing the xattr. The signed build starts with no marker, passes the write probe and self-updates inside the manager-owned installation. winget always takes this path unless U-4 lands. On macOS, a metadata-stripping copy/restore over a still-managed destination loses the custom xattr while leaving signed bundle contents intact; its absence cannot prove unmanaged provenance. An xattr read error or unsupported filesystem is also not “attribute absent”. A metadata-preserving drag-copy may retain the marker and produce the intended conservative false positive; that case must be measured, not generalized to every copy.

    **Change:** Make U-2's **published and tested external manifests**, U-4 and the marker reader prerequisites to enabling, with a plan for existing/unmarked installations. Treat failed/unsupported marker reads as `Unknown`, and complete exact-install manager evidence before declaring `Ours`; preserve the owner's no-path-guess rule. The winget ARP record is appropriate: check package/source/type evidence and canonical target/install identity across the relevant hives/views and custom locations, not an arbitrary uninstall entry with the same display name. Specify precedence when evidence conflicts, and revalidate the installation/ownership under the commit lock after a long `Verified → Later` wait. [winget's PortableARPEntry source](https://github.com/microsoft/winget-cli/blob/master/src/AppInstallerCommonCore/PortableARPEntry.cpp) explicitly records install location, target path, installer type and package/source identifiers.

    **macOS marker verdict:** A custom xattr on the top-level bundle is a reasonable candidate, not inherently a broken seal. Apple's [QA1940](https://developer.apple.com/library/archive/qa/qa1940/_index.html) specifically discusses resource-fork/FinderInfo attributes; it does not establish that every custom xattr invalidates a signature. It also does not guarantee preservation of this attribute. Extend E1 to write it **after** signing/notarizing/stapling, verify code and ticket, assess/launch offline before cache warming, and exercise Finder drag-copy, rename, `ditto`, Brew upgrade/reinstall and a copy that discards metadata. Do not re-sign or strip quarantine to make the test pass. Keep markers out of the public ZIP/DMG and reserve `folio-install.json` against archive payload injection. If preservation/negative evidence is insufficient, use an exact-install manager receipt or durable manager registry as a fallback; absent metadata alone cannot carry the policy.

11. **F-11 — High — The dependency graph can enable a platform without its ownership or recovery prerequisites.** Obligation R-23.

    **Exact paragraphs:** R.6 “Order”; U-22 “Everything above merged”; U-23 “As U-22 … after U-21”; U-17 “The recovery entrances”.

    **Failure sequence:** Follow the explicit DAG: U-1, U-6–U-10, U-13–U-19 and U-22 can complete without U-2 or U-4. Windows then enables against no published markers and no winget classifier, producing F-10. The macOS chain U-20 → U-21 → U-23 does not require U-17 or U-1; its new bundle can be enabled without startup recovery/ownership wiring. At lower levels U-13 promises C1 capability/C11 classification but depends only on U-6, U-14's managed row depends only on U-13, U-16 spawns P but has no declared journal/helper interface prerequisite, and U-12 records mount ownership without depending on the journal. Each author must invent an interface, silently defer promised behavior, or import another ticket.

    **Change:** Replace “Everything above” with one explicit DAG and per-ticket input/output interfaces. Establish classification types (U-1), transaction/protocol types (reworked U-8) and the durable recovery contract first. U-2 consumes U-1's format; U-3 requires that evidence be available before first-run decisions. U-13/U-14 consume the classification/capability interfaces, with a typed pending state and offers off until evidence arrives. U-12/U-16 consume the transaction and handoff interfaces. Both apply drivers and enabling tickets require platform recovery entrances; U-22 requires U-2/U-4 and U-23 requires U-1/U-2 plus the revised macOS recovery work. Add publication/verification of F-4's authenticated package metadata before either consumer gate. Assign ownership of actually adding `clean-vm.md` §4.4; the briefs currently tell U-22 to run a checklist none explicitly writes. The coordinator can still merge small, inert pieces after the 0.4.5 tag, but no ticket should advertise behavior it can only acquire from an undeclared dependency.

12. **F-12 — Medium — Removing the filename allowlist requires a complete Windows namespace and extraction budget contract.** Obligation R-5.

    **Exact paragraph:** C4's new-set bullet, “regular files only … at most … 32 … 200 MB expanded … every refusal of §E kept”; U-9's archive tests.

    **Failure sequence:** An archive carries `folio.exe` and `folio.exe.` or a name ending in a space: simple case-collision checking sees different strings while ordinary Windows path handling can alias them. Device names such as `NUL.txt`, separator variants, or inconsistent central/local ZIP names similarly need defined refusal before a file is created. A ZIP advertises a tiny uncompressed length but emits more than 200 MB; checking only directory metadata does not bound expansion. A signed future archive adds the regular file `folio-install.json` to an unmarked installation; unless reserved, it becomes package-supplied channel evidence. A legitimate new release exceeds the old updater's fixed cap or requires nested directories: it is correctly refused, but cannot be made consumable merely by changing the new build's constants.

    **Change:** Retain the existing traversal/absolute/drive/UNC/ADS/duplicate/link/reparse refusals; do not claim those were removed. Add a canonical Windows filename grammar, device/trailing-dot/space and alias rejection, reserved metadata names, checked byte counters on **actual decompressor output before writes**, bounded metadata allocation/name lengths, integrity/truncation checks, and a cancellation/time bound through expansion. Exclusively create destinations under directory handles that cannot escape through existing links; validate destination collisions before the first install move. Specify whether the 32-entry count includes the root directory entry. Add adversarial fixtures and an authenticated format/minimum-updater field so an unknown *ordinary* file can be installed without executing it or understanding its semantics, while an unsupported layout routes to manual update. Run each release through the oldest supported updater parser/caps, not just its own packager.

13. **F-13 — Medium — Signature validity is capability, not release eligibility; signed candidates already have a route to exist.** Obligation R-15.

    **Exact paragraphs:** C1, “On macOS a candidate bundle is ad-hoc signed … and only a release is Developer ID signed and notarized”; “A signed candidate, should one ever exist”; C10's signed candidate baseline; Q4.

    **Failure sequence:** A manually dispatched `release.yml` run has the six macOS signing/notary inputs. The existing workflow deliberately produces a Developer ID-signed, notarized artifact even though it publishes nothing. A tester runs that candidate from a writable unmarked folder. When a higher public version appears, C1/C11 offer an update that replaces the test build after the tester presses it. The version comparison still prevents arbitrary downgrade; this is loss of test-channel separation, not a silent update or proof that signing happened accidentally. On Windows `sign.ps1 -OutDir` similarly permits signed non-public builds.

    **Change:** Decide eligibility separately from cryptographic authenticity. My Q4 recommendation is a release/test capability flag or equivalent signed policy, default off for candidates, plus mandatory identity verification; a controlled candidate explicitly enables the updater for the clean-machine test. The signal must be set before signing (and before compilation if embedded), not by packaging an already compiled EXE. Restore the required CI/build/package/smoke changes to the ticket set and verify defaults in both workflows. If the owner intentionally chooses “every signed candidate may update to public”, retain C1 but explicitly document and test that policy; remove the incorrect claim that the existing pipeline inherently distinguishes candidates. Authenticating only ad-hoc versus Developer ID is not that distinction.

14. **F-14 — Medium — “One bounded journal write” on the window thread has no bounded latency and creates a second transaction writer.** Obligations R-18, R-22.

    **Exact paragraph:** R.3 health row, “window (one bounded journal write)”; §C.5, “N writes health … into the journal, fsyncs, and signals P”; U-8 architecture impact, “none (pure)” despite fsynced writes and OS locks.

    **Failure sequence:** N draws first text, then its window thread blocks flushing `.folio-update/journal.json` on a slow synced drive. P's 90-second timer expires and persists `RollingBack`; N's eventual whole-journal write can publish an older `Flipped` snapshot with health and overwrite that decision unless an ordering protocol exists. Even without the lost update, N's window freezes on an external write, violating ARCHITECTURE §5's lane contract. A byte bound is not an I/O latency bound.

    **Change:** W emits a transaction-bound readiness event and remains runnable. One transaction owner serializes durable state; a worker or P persists the accepted health decision and returns a receipt. Define how late acknowledgements race the rollback deadline, including refusal after rollback intent. Keep `update_txn::decide` pure and inventory the actual journal/lock/file operations under their doors and storage lane. Update U-16's baseline too: current `SessionWriter::wait_for` already uses `SESSION_SAVE_BUDGET`, and ARCHITECTURE §5.3 row 16 explicitly permits ordinary quit to proceed on timeout; updating must require a successful named receipt without silently changing ordinary quit's existing timeout ruling.

15. **F-15 — Medium — Package-manager cleanup needs an executable lifecycle contract, not just hook names.** Obligations R-19 and C3's uninstall-hook promise.

    **Exact paragraphs:** C3's Scoop bullet, “Its exit 2 … and scoop then abandons its uninstall”; its Homebrew bullet, “uninstall_preflight … must_succeed: false”; U-2's hook goal/tests.

    **Failure sequence:** Folio A in another folder is running, so the cleanup door for Scoop copy B refuses with exit 2; Scoop's subsequent running-process check is about B's install directory. A bare native invocation need not propagate that exit as a terminating PowerShell error, so B can still be removed with its cleanup refused. Conversely, on Homebrew an uninstall hook can execute during upgrade; without a proven distinction it removes integrations while Brew is merely replacing Folio. A structured hook lacking writable paths can have its home-directory cleanup denied, then `must_succeed: false` lets uninstall complete while marks remain. The marker nevertheless claimed an uninstall hook capable of undoing those marks.

    **Change:** In Scoop, explicitly interpret the door's exit code and invoke the manager's abort/error mechanism when removal must stop; test refusal caused by this copy and by another copy. Preserve the `$cmd -eq 'uninstall'` update guard. Specify and test the actual Homebrew DSL/version, resolved installed `appdir` (including custom app locations), required write scope, upgrade behavior and reportable best-effort failures. Current [Scoop uninstall source](https://github.com/ScoopInstaller/Scoop/blob/master/libexec/scoop-uninstall.ps1) calls the hook and then performs its own process check; that check is not Folio exit-code propagation. The [Homebrew cookbook](https://docs.brew.sh/Cask-Cookbook#stanza-flight_steps) documents structured flight steps and sandbox write grants. Its temporary third-party compatibility means the legacy hook name alone is not grounds to reject this private tap; the missing lifecycle proof is. Test the rendered and installed manifests, not only text preservation in the renderer.

16. **F-16 — Medium — The identity tests cannot produce a production-trusted positive fixture merely by making a certificate in the test.** Obligations R-9, R-10, R-21, R-22.

    **Exact paragraphs:** U-10, “fixtures signed in the test with a certificate made in the test; the real WinVerifyTrust runs”; U-11, “real Security.framework calls on CI macOS over bundles signed in the test”.

    **Failure sequence:** U-10 makes a local self-signed certificate and uses the production system-trust policy; the positive renewal test fails because its chain is untrusted, and it has no production-valid RFC 3161 timestamp. Installing a root globally to get a green test changes the machine and still does not prove real Artifact Signing behavior. On macOS, self/ad-hoc-signed fixtures can exercise refusals but cannot manufacture an Apple Developer ID chain that satisfies the genuine installed app's designated requirement. With no prescribed fixtures, independent tickets either cannot pass or quietly relax the production predicate.

    **Change:** Separate pure policy fixtures from platform verification tests. Use narrowly scoped custom test trust where an API supports it, otherwise disposable test machines with explicit test roots/TSA; never silently change the developer's system trust. Keep real timestamped release fixtures across certificate renewal and real signed/notarized Mac fixtures for positive production-policy integration. Add the same-DN/different-identity negative case and expired-leaf/valid-timestamp positive case. Gate U-10/U-11 against the appropriate environment rather than promising all positive tests can be synthesized on ordinary CI. Power-fault acceptance must use disposable environments; the production Mac mini is not a power-cut target.

17. **F-17 — Medium — Pre-Prepared cleanup and Verified resume contradict the journal lifecycle.** Obligations R-11, R-14, R-17.

    **Exact paragraphs:** §C.2 writes `Prepared` only at step 7; §B promises death during download/staging is “swept by the startup pass”; §C.6's `Prepared` row unconditionally deletes staging/cache, while its closing paragraph says “two launches old”; §B says Verified → Later retains a resumable job.

    **Failure sequence:** P has not yet been started: K downloads 100 MB or successfully mounts a DMG and then O dies before `Prepared` is written. Startup's “journal absent → done” leaves the orphaned transaction/mount. There is also a cut between successful attach and recording the returned mount path. In a different run the reader chooses Later at `Verified`, exits normally and immediately restarts; §C.6 deletes the prepared set on that first start, so the promised resume entry disappears instead of surviving two launches. On macOS the random journal filename makes even discovering these cases unspecified.

    **Change:** Persist an owned transaction allocation/Preparing record before external resources are acquired; define recovery of each resource-acquisition intent, including identifying a mount when attach succeeded before its result was persisted. Keep cleanup debt until it is actually discharged. Distinguish deferred verified work from abandoned preparation and define the launch-age owner, resume/discard rule and lock release/reacquisition. Preserve a valid deferred transaction on the first subsequent launch and revalidate it before applying. Test each acquisition/persistence gap as well as download/extract cancellation; do not sweep unacknowledged rollback data with these disposable resources.

18. **F-18 — Medium — MSIX renewal can retarget another installation and can be lost after health.** Obligation R-20.

    **Exact paragraphs:** U-19, “re-register when the registered version is older than the manifest's four-part one”; R.4, “only after Healthy, only if already registered”; §C.5 retires the journal at Healthy.

    **Failure sequence:** Copy A owns the current per-user sparse registration. Copy B in another folder updates to a newer version. `msix::registered()` returns A's registration, and the proposed version-only test re-registers it against B, moving the Explorer integration without a request to do so. Even for A, a process death after health/journal deletion but before the registration worker runs loses the only trigger to reconcile the old registered version. U-19's two tests cover neither sequence.

    **Change:** Compare the returned canonical `external_path` with this transaction's install identity and serialize renewal with existing registration/removal operations; absence or a different owning copy is not a renewal request. Retain durable post-commit repair debt or reconcile it through the existing integration owner on startup. Treat failure as integration repair, never rollback of an already healthy binary transaction. Add two-copy ownership and crash-after-health-before-registration tests.

The crash-boundary acceptance matrix below is the minimum concrete replacement for the broad claim that §C.6 is already idempotent. Each row needs process death and durable-storage interruption cases; “power cut” includes losing writes not covered by the stated persistence barriers. A process kill alone cannot verify filesystem/registry durability.

| Boundary | Windows result required | macOS result required |
|---|---|---|
| Transaction directory allocated; partial checksum/archive download | Old install starts; owned partial files are discoverable without `Prepared`; no apply permission inferred. | Old bundle starts; transaction locator finds disposable download state. |
| Extraction or DMG attach, before resource record completes | Reject/sweep only exclusively owned partial outputs; no links escape staging. | Recover the attach-intent gap and detach only the transaction's image; preserve unrelated mounts. |
| Verification/copy/flush, before `Prepared` | Partial `set/` or `applier/` cannot become eligible; old install untouched. | Partial copied bundle cannot become eligible; old bundle untouched. |
| Durable `Prepared`; Later/normal exit; cancelled or failed quit | Resume/discard according to one age rule; no destructive step and no false Failed claim. | Same, with a discoverable transaction outside the sealed bundle. |
| Successful session receipt; P spawn/lock handoff before destructive intent | Either old starts, or P alone owns apply; a manual launch cannot sweep its payload. | Same, with a stable lock that will survive the later exchange. |
| Recovery entrance registration and persistence, before first move | Failure to make the entrance durable aborts before mutation; long paths and user scope are handled. | Durable helper/backup/locator and logon entrance exist before exchange. |
| Each old file moved to backup | Independent R reconstructs a complete approved set using journal inventories, never a guessed current-build list. | Not applicable to a single bundle exchange; no two-rename fallback. |
| Each new file moved into install | R remains outside the moving set; ordinary launches cannot use a partial set. | Not applicable to individual payload files; all copied bundle bytes were durable before swap. |
| Swap completed but phase update absent | Actual identities/digests determine the side of the flip; no version-only false health. | Same; the lock still serializes the destination, and the old bundle is not purgeable. |

| Every backup/helper deletion and recovery-hook removal after commitment | Healthy is already durable; partial cleanup is debt; no rollback using a partly deleted backup. | Same, including LaunchAgent retirement and cleanup of its durable helper. |
| Post-health MSIX/integration repair and final journal retirement | Repair is scoped to this copy and survives interruption without changing another copy's registration. | Only transaction-owned integration/cleanup state is retired; other installations remain untouched. |

The earlier Velopack rejection still follows from the inspected spike: its lack of durable recovery/health and its process-killing behavior do not solve these failures. These findings require a corrected custom recovery protocol, not a return to that applier. The narrower UI, tag-pinned URLs, no-download-before-press rule and separate platform enabling gates remain sound choices.
