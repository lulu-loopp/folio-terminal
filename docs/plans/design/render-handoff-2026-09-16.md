## A. Decision and ownership

Choose a small presentation lane per window, with **one pending CPU frame per window, one active frame, and one process-wide preparation permit**. Keep application composition, glyph preparation, render-pass encoding, surface creation/configuration, and compositor work on the window thread. The lane acquires a texture, sends its view to the owner for encoding, then submits the returned command buffer and presents the texture it retained. Every exchange is asynchronous; a busy lane causes coalescing, never a window-thread wait. This adds one acquire/encode exchange but avoids moving the whole renderer, its mutable font machinery, and its application-facing state into an actor. It also avoids an extra offscreen image and copy. The current render pass needs the acquired view, so a finished surface command buffer cannot simply be queued before acquire (`crates/bt-render/src/lib.rs:9283-9299`, `crates/bt-render/src/lib.rs:9332-9351`). The shared device/queue/font system/atlas live together today (`crates/bt-render/src/lib.rs:4163-4184`); the preparation permit preserves their existing serial frame lifetime across windows. This is the minimum ownership split proposed in DeepSeek's verification, with the missing acquire/encode handshake made explicit (`perf-verify-deepseek-2026-09-16.md:24`).

The review's broader latest-frame renderer handoff remains a possible later change; moving whole composition would also move the P-2 cost but requires a substantially wider API boundary. UI text measurement already borrows the shared GPU context, and font changes invalidate renderer caches and shared math textures (`crates/bt-app/src/main.rs:43098-43109`, `crates/bt-render/src/lib.rs:8318-8343`). Neither approach justifies moving the compositor: GLM correctly retains owner-thread commit; DeepSeek's suggestion to move that COM work in its final P-1 paragraph is not adopted (`perf-verify-glm-5.3-2026-09-16.md:19`, `perf-verify-deepseek-2026-09-16.md:26`).

| Operation / resource | Proposed owner and boundary |
|---|---|
| Window, HWND/NSView, compositor, native visual tree | Window thread throughout creation, use, and destruction. |
| Surface creation, configure, `configured_size`, generation | Window thread, only with the surface returned and the global preparation permit held. |
| Surface acquire | That window's lane; sole temporary ownership of the surface is transferred to it. |
| CPU frame composition, shaping, atlas preparation, uploads | Window thread, once a candidate is admitted; GPU preparation only under the global permit. |
| Render-pass encode / `encoder.finish()` | Window thread on `Acquired`, using the frozen prepared frame and returned view. |
| Queue submit, including empty failure drains | Lane. No submit in a live window's UI callback. |
| Surface texture present / discard | Same lane that acquired it. No `SurfaceTexture` crosses back to the owner. |
| DComp `set_covered_size` and commit | Window thread after a terminal lane completion reports that present returned. |
| `close_the_frame` / atlas trim or repair | Window thread exactly once after the attempt's resources have been released by the lane, before another preparation. |
| Receipt timestamps | Lane stamps submit return and present return; owner retains trigger and identity and publishes the completed receipt. |
| Presented-picture state, hit-test picture, resize debt | Window thread after the matching completion and successful owner commit. |

Current evidence for the split: `RedrawRequested` calls `redraw` inline, which enters the common funnel and synchronous renderer (`crates/bt-app/src/main.rs:112175`, `crates/bt-app/src/main.rs:100575-100587`, `crates/bt-app/src/main.rs:100159`). Acquire, submit, and present are at `crates/bt-render/src/lib.rs:10705`, `crates/bt-render/src/lib.rs:9792-9804`; latency remains 1 at `crates/bt-render/src/lib.rs:4665`. Retained frames and resize frames use that same funnel (`crates/bt-app/src/main.rs:100127-100132`, `crates/bt-app/src/main.rs:100372-100383`, `crates/bt-app/src/main.rs:97568`).

## B. Handoff, capacity, and ordering

### Payload and state

The waiting slot holds a CPU candidate, never a prepared atlas frame, encoder, or acquired texture. Replace the existing waiting slot rather than adding a second frame queue; today's `LatestFrameSlot::publish` replaces its pending frame indiscriminately (`crates/bt-render/src/lib.rs:1536-1555`). The new slot must distinguish an ordinary candidate from a protected resize candidate.

Short type sketch; names are proposed, not existing APIs:

```rust
struct FrameKey { window_epoch: u64, device_epoch: u64, surface_gen: u64, seq: u64 }
enum FrameKind { Ordinary, Retained, Resize { expected_grid: GridSize } }
struct FrameIntent { key: FrameKey, kind: FrameKind, trigger: FrameTrigger, picture: OwnedPicture }
enum ToLane { Acquire(SurfaceLease), Submit(FrameKey, CommandBuffer), Drain(FrameKey), Abort(FrameKey), Stop }
enum ToOwner { Acquired(FrameKey, TextureView), Completed(Completion), Stopped }
```

`OwnedPicture` captures terminal frames, stable tab/seat identities, seat rectangles/clips, focused status, content and layout revisions, and the data needed to credit painted revisions. The existing `SeatFrame` carries seat/clip plus borrowed frame data and cannot be stored across callbacks as-is (`crates/bt-render/src/lib.rs:4969-5014`). Retained candidates reference the last acknowledged content picture and carry a new chrome/animation intent; animation time and transforms are sampled when admitted, so a busy interval produces the current animation position rather than replaying queued ticks. The current retained path explicitly re-samples transforms (`crates/bt-app/src/main.rs:100271-100278`).

Preparation produces a UI-owned `PreparedFrame`: owned draw buffers, frozen clear/ground/viewport/scissor parameters, text-renderer state, trace counters, and the original picture identity. Move or reserve the prepared glyph renderers and viewport until encoding finishes; do not later read mutable live renderer fields to finish an older frame. The ground upload currently occurs after acquire and must be included in this preparation split (`crates/bt-render/src/lib.rs:9300-9331`). All remaining scene inputs used by the pass must likewise be captured. The lane receives only surface/queue/device handles, frame identity, control data, and eventually a finished command buffer; it does not borrow `GpuContext`, `WindowRenderer`, `Window`, or a compositor.

There is one pending slot **per window**, not one per producer, pane, or frame source. An active attempt is outside that slot. Across windows, a fair owner-thread scheduler grants one global preparation permit, from the first GPU upload through completion/atlas close. Thus there is at most one prepared/acquired frame process-wide; other windows may hold one CPU candidate each. This deliberately preserves shared-atlas serialization instead of allowing independent lanes to overwrite another frame's glyphs. Idle lanes sleep. A stalled lane can delay every window's picture, but cannot stop their event dispatch; per-window atlas isolation is outside this ticket.

Use a fixed-capacity control mailbox in each direction and an edge-triggered `AppEvent::RenderLaneReady(window_epoch)` wake. Phase progression allows at most one undrained normal reply. Fault/stop state must remain observable independently of a full reply cell. Publish reply state before sending the wake; the UI drains available state nonblockingly, clears the wake flag, then rechecks it to prevent a lost wake. The UI must not call blocking `send`, `recv`, or acquire a mutex held over a driver call; if a small mailbox lock is contended, defer and retain the wake obligation. Condvar/channel waits are allowed on the lane. Handle proxy closure through stop state, not repeated wake attempts.

### One attempt

1. The owner admits a candidate when the lane is idle and the global permit is available. Validate the picture and resize barrier, freeze its metadata, and prepare GPU resources. New ordinary publications can now replace only the waiting CPU candidate.
2. Still on the owner, configure if needed, immediately after preparation, then increment the surface generation for every actual configure, including same-size recovery. Keep `configured_size` as the actual size and a separate monotonic generation as identity; size alone cannot distinguish a rebuild. Finalize the dispatched `FrameKey.surface_gen` here; a waiting candidate names a logical layout/resize identity, not a promise that a future configure already happened. The current resize only records requested size and configuration is delayed until after preparation (`crates/bt-render/src/lib.rs:7959-7979`, `crates/bt-render/src/lib.rs:9278-9283`, `crates/bt-render/src/lib.rs:10656-10695`).
3. Transfer the surface lease to the lane. It calls acquire, retains the `SurfaceTexture`, creates the view, places `Acquired` in the reply cell, and wakes the owner. The owner returns to normal event processing while acquire runs.
4. On `Acquired`, the owner checks the full key, records the existing pass against that view and the frozen prepared state, finishes the encoder, drops its attachment-view reference, and sends `Submit`. No temporary Rust borrow or unfinished render pass survives the handler's return. A superseded ordinary *pending* frame can disappear; this active frame cannot be replaced mid-attempt.
5. The lane submits, stamps submit return, presents its retained texture, and stamps present return immediately. It releases texture/view/command-buffer references and returns the surface with `Completed`. It cannot acquire another image until the owner's completion processing grants the next lease.
6. The owner closes the prepared atlas frame exactly once, performs the matching coverage update and commit for any returned present, records completion, and releases the global permit. It then services protected resize work or the latest waiting candidate. A failure in commit is terminal/recovery work, not permission to mark a picture presented.

The surface lease is an ownership token, not `Arc<Mutex<WindowRenderer>>`. All configure, create/rebuild, auxiliary submit/readback, and GPU-cache mutation paths must participate in the process permit. CPU-only font measurement and input/session work may continue. Font/DPI changes that discard prepared resources become deferred renderer updates; their requested values can still be recorded immediately. The current readback separately submits and metric adoption clears shared textures, so treating only `present_frame` as GPU work would be insufficient (`crates/bt-render/src/lib.rs:8019-8062`, `crates/bt-render/src/lib.rs:8335-8343`). Do not stage another frame's uploads while the active lane can submit them.

### Coalescing and the resize barrier

| Situation | Required decision |
|---|---|
| Ordinary pending A, newer ordinary B for the same admitted generation | Replace A with B, including B's trigger; count A as coalesced. |
| Active frame A, newer ordinary B | Keep A immutable; put/replace B in the one pending slot. |
| Ordinary pending frame, new resize intent | Remove the ordinary candidate; give geometry admission priority. |
| A resize frame exists in the pending slot or active attempt | Pin that exact frame/grid/geometry until a complete present and commit; ordinary work records dirty state and cannot evict it. |
| More physical sizes arrive while a resize frame is pinned | Update one scalar `desired_extent`/DPI request; do not make another resize frame or apply another grid transition yet. |
| Resize attempt skips, loses text, or needs surface repair | Keep its CPU picture and barrier; retry under the same logical resize identity, with a new surface generation if configured. |

Bounded memory and a nonblocking event loop cannot promise one frame for every raw `Resized` callback. **Coalesce raw size requests before admitting a resize frame; never coalesce an admitted resize frame.** Apply layout/grid/DPI transitions only when this window's prior attempt has completed and its previous resize barrier is satisfied. The newest raw desired extent then produces the next newly projected grid. Until then, keep the previous complete image scaled and update the native window skirt immediately; the current handler already distinguishes window size from the later swapchain size and documents the scaled-image fallback (`crates/bt-app/src/main.rs:97484-97499`, `crates/bt-app/src/main.rs:97563-97567`).

For example: active ordinary G0, requests S1/S2, then an animation tick => finish/commit G0, admit one resize for S2, pin its newly projected G1, and refuse a retained G0 candidate. If S3 arrives while G1 is pinned, G1 still completes before S3 becomes a frame. G0 never presents *after G1's configure*. This makes the linearization point explicit: a raw OS extent is a request; successful configure admits a surface generation. Resize bursts cannot manufacture an unbounded FIFO of mandatory frames.

Keep the current focused-grid `frame_matches_grid` gate and carry its expected grid with the barrier, not in a mutable global value read by a late completion (`crates/bt-app/src/main.rs:100441-100449`, `crates/bt-app/src/main.rs:116495-116498`). Validate all captured seat geometry against the same surface generation as well. Clear resize debt only for the matching complete `Presented` plus successful commit. Handle every producer of the existing resize debt, including structural seat geometry and delayed leaf reflow, not just `WindowEvent::Resized` (`crates/bt-app/src/main.rs:64738-64743`, `crates/bt-app/src/main.rs:83974-83978`). A shell-less window still needs an extent barrier even without a terminal grid (`crates/bt-app/src/main.rs:97558-97561`).

### Commit and “the frame on the glass”

Never put the compositor on the lane; preserve its window-thread COM apartment ownership. The present/commit ownership warning is explicit at `crates/bt-app/src/main.rs:100118-100125`; the device and actual COM commit are at `crates/bt-platform/src/lib.rs:3541-3554` and `crates/bt-platform/src/lib.rs:4545-4547`. The completion event replaces the synchronous call stack as proof that present returned. Its immutable configured extent feeds `set_covered_size`, immediately followed by commit. Do not use the newest requested extent or a newer renderer configuration.

Preserve the existing coverage history: `set_covered_size` deliberately uses the previous presented size, and the funnel requests another redraw while the skirt remains (`crates/bt-platform/src/lib.rs:3940-3946`, `crates/bt-app/src/main.rs:100189-100206`). Every actual present, including `PresentedWithoutText`, must receive this owner commit, even if newer content arrived while it was in flight (`crates/bt-app/src/main.rs:100172-100178`). Skips have no frame commit. Native window-size skirt commits remain their separate existing operation (`crates/bt-platform/src/lib.rs:4538-4544`).

“On the glass” is the app's **last acknowledged published picture**, not a hardware scanout claim: present returned and, on Windows, its owner commit succeeded. Only then install that frame's pane snapshots and captured revisions. Today's success arm writes current content revision, uses the current active tab, updates each leaf, and clears resize debt synchronously (`crates/bt-app/src/main.rs:100598-100606`, `crates/bt-app/src/main.rs:100647-100666`). Async completion must instead credit the captured identities/revisions, never newer ones. Keep newer dirty/output debt when revisions differ; do not mark a newly focused tab seen because an old tab finished. Store the acknowledged picture's layout with its hit-test frames. Drain ready completions at UI dispatch boundaries before pointer hit testing where possible.

`PresentedWithoutText` commits the partial picture but does not establish the intended terminal picture or satisfy resize debt; keep an explicit incomplete-picture state and the owed candidate. This preserves the current distinction instead of falsely licensing retained redraw (`crates/bt-render/src/lib.rs:1627-1650`, `crates/bt-app/src/main.rs:100668-100687`). Old completions after device/window replacement may release resources but cannot publish into the replacement epoch.

## C. Platform and failure contracts

### wgpu threading: use the dependency actually in this checkout

This repository uses **wgpu 30.0.0**, not 0.2x (`Cargo.toml:200`, `Cargo.lock:5196-5197`); only 30.0.0 wgpu API sources are installed in the inspected registry. Its native assertions make `Surface`, `Queue`, `Device`, and `SurfaceTexture` `Send + Sync` (`wgpu-30.0.0/src/api/surface.rs:267-268`, `wgpu-30.0.0/src/api/queue.rs:18-19`, `wgpu-30.0.0/src/api/device.rs:23-24`, `wgpu-30.0.0/src/api/surface_texture.rs:16-17`).

There is no `SurfaceTexture::present` method in this version's impl (`wgpu-30.0.0/src/api/surface_texture.rs:21-27`). `Queue::present` consumes the texture and documents submit-before-present, with no acquire-thread restriction (`wgpu-30.0.0/src/api/queue.rs:367-379`; also the [versioned public API](https://docs.rs/wgpu/30.0.0/wgpu/struct.Queue.html#method.present)). Do not invent a 0.2x rule or use older docs as the contract for this build. This design nevertheless keeps acquire, present, and discard on one lane, so it does not depend on cross-thread presentation.

`Surface::configure` can wait for GPU idle, submissions during it can fail validation, and an old live `SurfaceTexture` makes configure panic (`wgpu-30.0.0/src/api/surface.rs:103-118`). The global permit and returned surface lease prevent those races, but **configure itself remains a potential UI stall**. Also fix the current suboptimal branch's immediate configure while it still holds the acquired texture: present the usable suboptimal frame first, release it, then ask the owner to reconfigure before the next attempt (`crates/bt-render/src/lib.rs:9289-9292`).

### Atlas and upload lifetime

The current wrapper calls `close_the_frame` outside every compose exit, not merely after success (`crates/bt-render/src/lib.rs:8438-8479`). Its success arm trims and clears the repair latch; the first textless frame replaces the atlas; other outcomes trim; device loss bypasses atlas work (`crates/bt-render/src/lib.rs:6726-6751`). Glyphon's trim empties the in-use set (`glyphon-0.12.0/src/text_atlas.rs:219-220`, `glyphon-0.12.0/src/text_atlas.rs:334`). Preserve that complete policy.

The UI owns a once-only close obligation from the start of GPU preparation. It pays it after the lane has submitted/presented or drained/discarded the attempt and returned its resources, before another window prepares. An error before dispatch closes locally; if it staged uploads on a live device, route an empty `Drain` through the lane first. Never trim when a frame is merely enqueued, and never let a pending-frame overwrite create an atlas obligation. Submit return is not GPU completion; subsequent atlas writes remain ordered after the preceding draws on the same queue. wgpu stages writes until the next submit (`wgpu-30.0.0/src/api/queue.rs:143-155`).

### Failure matrix

| Failure / event | Lane action | Owner action |
|---|---|---|
| Timeout / unavailable | Count failure, empty-submit staged uploads, return `Skipped` and surface. | Close atlas attempt, preserve picture debt, use existing retry policy. |
| NotVisible / Occluded | Same empty submit and release, return `SkippedNotVisible`; no present. | Close attempt, keep CPU debt, release global permit, request no retry solely because of this completion. |
| Outdated / surface lost | Empty submit while device is live, return `Reconfigure` and released surface. | Configure/recreate under the permit on the owner; keep the resize picture pinned and increment surface generation. |
| Suboptimal texture | Encode/submit/present normally; mark `reconfigure_after`. | Commit the returned present, then repair before any next acquire; no live texture at configure. |
| Text preparation refused | Submit/present the existing partial-picture policy. | Commit, run atlas repair, retain debt and existing bounded textless retry policy. |
| Validation / encode error | Release any texture; drain staged writes if device remains live; return terminal error. | Close once; enter failure handling, never publish a successful frame. |
| Device lost during acquire/submit/present | Observe shared loss latch before and after calls; report device epoch and whether present already returned. No deliberate further submission on a known lost device. | Freeze admissions across all windows, retire/join old lanes, then run existing recovery with fresh epochs. Preserve CPU pictures; skip old-atlas repair. |
| Window closes with acquired texture | Stop has priority over pending work. If awaiting encode, discard after owner releases its view; if already inside submit/present, finish that call before releasing resources. | Keep window/compositor alive through returned completion and lane join; cancel visual debt only because this window is retiring. |

This preserves the existing absorbed-failure drain before skip/reconfigure/fatal classification (`crates/bt-render/src/lib.rs:10631-10652`) and its policy mapping (`crates/bt-render/src/lib.rs:3961-3966`). Guarding a newly noticed device loss avoids submitting over a known dead device, as the existing drain rationale requires (`crates/bt-render/src/lib.rs:10623-10630`). A completion records `present_returned` separately from a later loss/error: if present returned while the original surface/compositor still exists, deliver its commit before teardown; do not claim a healthy complete picture after loss.

The loss callback currently records an `Arc<OnceLock<String>>`, and recovery rebuilds every window's surface through the UI-owned target factory (`crates/bt-render/src/lib.rs:5930-5939`, `crates/bt-app/src/main.rs:108334-108353`). Add a coalesced recovery wake; do not rely on another render request discovering loss. Delay the existing recovery pilot until old lane ownership is settled; preserve its retry policy, which currently runs through `recovered_from_a_lost_device` (`crates/bt-app/src/main.rs:111082-111129`). A callback never reconstructs a surface or touches the compositor.

### macOS prerequisite: indirect AppKit access counts

Keep `window_surface_target`, owned-view creation, clearing old layers, surface creation, and configuration on the main/window thread. The current target names Folio's own NSView; reconstruction clears its layers, and renderer documentation records the main-thread assertion in `from_ns_view` (`crates/bt-app/src/main.rs:116190-116198`, `crates/bt-app/src/main.rs:116223-116230`, `crates/bt-platform/src/macos_impl.rs:950-953`, `crates/bt-platform/src/macos_impl.rs:1033-1043`, `crates/bt-render/src/lib.rs:4580-4594`). The macOS compositor retains the NSViews and its commit currently returns `Ok(())` (`crates/bt-platform/src/macos_compose.rs:301-315`, `crates/bt-platform/src/macos_compose.rs:712-713`).

**The installed Metal backend is not ready for a literal “no AppKit on the lane” contract.** Acquire walks the layer's delegate to `NSView.window`, then sends `NSWindow.occlusionState`, without a main-thread check (`wgpu-hal-30.0.0/src/metal/surface.rs:18-32`, `wgpu-hal-30.0.0/src/metal/surface.rs:307-323`). A `Send + Sync` assertion does not remove those calls. AppKit view operations carry threading restrictions ([Apple thread-safety documentation](https://developer.apple.com/library/archive/documentation/Cocoa/Conceptual/Multithreading/ThreadSafetySummary/ThreadSafetySummary.html)). Do not ship an off-main acquire with this backend unchanged, and do not dispatch synchronously back to AppKit from acquire.

Stage 2 must first supply a pinned dependency fix: move the visibility observation to the UI owner, expose a per-surface thread-safe visibility value to Metal acquire, and replace the backend's AppKit traversal there. Prefer an upstream fixed release if its exact source meets this contract; otherwise use a narrow, documented vendored wgpu-hal patch and a safe bt-render bridge. The lane may call Metal/CAMetalLayer drawable operations, but never AppKit, including through dependencies. Surface creation/configuration remains on the UI; no native view pointer enters a lane message.

Initialize visibility on the UI before dispatch, update it on both occlusion transitions and native show/hide/minimize transitions, and refresh it on a genuine invalidation before retrying hidden debt. Return the same NotVisible policy when false. Preserve `Occluded(false)` publishing a frame and preserve “skip without self-redraw”; add the true-transition tracking needed by the new observation boundary. Today the false arm republishes and the true arm is deliberately ignored (`crates/bt-app/src/main.rs:112298-112311`); `ask_again_after(SkippedNotVisible)` returns false (`crates/bt-app/src/main.rs:107756-107774`). A raced hide can still make `nextDrawable` slow; that wait belongs on the lane. Metal presentation itself uses a command buffer/drawable path (`wgpu-hal-30.0.0/src/metal/mod.rs:802-824`).

### Panic and shutdown

Contain a lane panic only to report it and retire safely, never to continue using possibly inconsistent renderer resources. A bare `catch_unwind` is insufficient: today's panic hook invokes a fatal callback after writing the report, and that callback hides windows and leaves the process (`crates/bt-app/src/main.rs:117698-117711`, `crates/bt-app/src/main.rs:117715-117739`). Add an explicit thread-local “inside render-lane unwind boundary” marker, analogous in purpose to the existing narrowly contained math exception. For that scope, the hook records diagnostics and lets unwind reach the lane boundary; it must not call native UI from the lane. Publish a durable `LaneFault`, wake the owner, stop admission process-wide, release owner-held views, join the finished lane, and enter controlled fatal teardown. Retire the entire context instead of attempting atlas repair after an uncertain driver panic; no later frame can reuse its in-use set. Keep ordinary panic policy unchanged. Never reuse a panicked GPU session merely because the thread was joined.

Ordinary close is asynchronous: mark stopping at the shared `let_go_of_this_window` teardown door, drop unprepared pending work, answer an outstanding `Acquired` with abort, release its view, and continue pumping. The current common teardown starts at `crates/bt-app/src/main.rs:101350`; retirement removes the window at `crates/bt-app/src/main.rs:109282`. Extend `reap_leaving_windows` so removal requires both existing page-retirement eligibility **and** a finished lane; call `join()` only after `JoinHandle::is_finished()`, then drop the returned surface, then the compositor/native window. The browser timeout must never waive the lane lifetime requirement (`crates/bt-app/src/main.rs:109264-109282`).

Audit every bulk removal too: quit `Exit`, fatal `fail`, and `exiting` currently clear the registry (`crates/bt-app/src/main.rs:110953-110967`, `crates/bt-app/src/main.rs:111190-111197`, `crates/bt-app/src/main.rs:112386-112403`). Controlled exit must finish stopping/joining lanes before reaching those clears or `event_loop.exit()`. If an external event-loop exit makes pumping impossible, the stopping protocol must terminate without needing further UI encoding; a final join precedes field destruction. That exceptional shutdown join can block on an unreturning driver call. Rust cannot safely cancel it: keep the window and surface alive and let the watchdog report the wedge, rather than detach the lane and drop its native owner. No normal redraw/resize/input callback waits for a lane.

## D. Observability and tests

Keep the meaning of the two receipt latencies: `event_to_submit = lane_submit_return - original_trigger` and `event_to_present = lane_present_return - original_trigger`. The latter is still API call completion, not scanout or DComp commit. Their difference continues to isolate the post-submit present call, provided the two lane timestamps immediately bracket it. These are today's receipt definitions and stamping points (`crates/bt-render/src/lib.rs:1498-1514`, `crates/bt-render/src/lib.rs:9792-9804`). Async queue time and the acquire-to-encode wake gap now contribute to event-to-submit; enqueue time must never masquerade as submit time.

Emit `BT_PERF_TRACE present` once per returned present from the owner completion path, with captured source/retained identity, `window_epoch`, device/surface generations, sequence, outcome/text completeness, and `trace_schema=2`. Include textless actual presents with their outcome; skips/coalesces have separate records and no invented present receipt. Keep source stamps attached to the candidate that actually wins coalescing. Preserve the existing source metrics' limitations from `perf-review-2026-09-16.md:39-43`; add a raw resize-request stamp so deferred resize admission is observable without silently changing the older Resize origin.

Add durations for pending wait, UI preparation, UI configure, lane acquire, acquire-reply-to-encode-start, UI encode, submit, present, completion-delivery lag, owner commit, and total event-to-commit. Count coalesced CPU candidates, raw size requests folded before admission, pinned-resize retries, and outstanding frame age. Freeze frame diagnostics with the attempt; never read another frame's counters at completion. The current renderer's `acquire_us` combines configure/acquire/view creation and its frame record contains combined `submit_present_us` (`crates/bt-render/src/lib.rs:9278-9299`, `crates/bt-render/src/lib.rs:9825`, `crates/bt-render/src/lib.rs:9861-9864`); schema 2 must split those buckets explicitly.

Change `since_previous_us` to the difference between successive lane present-return timestamps for that window, and add `since_previous_commit_us` on the owner. Today it uses `Instant::now()` in `trace_present`, after the synchronous funnel (`crates/bt-app/src/main.rs:100240-100267`). Using completion-handler arrival time would turn event-loop delays into false animation frame intervals. Neither new interval proves scanout cadence; use presentation telemetry/video for that experiment.

The UI watchdog keeps its own stations. Rename/document `Present` as CPU preparation/encoding where appropriate, add scoped `SurfaceConfigure` and `PresentCommit`, and restore the prior station after each call. **No UI “waiting for render lane” station** is added to normal work: there is no such wait. The existing heartbeat is global and its `at` API explicitly describes the window thread (`crates/bt-app/src/hang_watch.rs:1250-1265`); lane threads must not write it. Scoped attribution already has `enter`/restore support (`crates/bt-app/src/hang_watch.rs:1268-1288`).

Add a separate atomic lane-progress record per window: native/Rust thread identity, frame key, stage, stage-entered time, and last-completed sequence. Stages distinguish Idle, Acquire, AwaitOwnerEncode, Submit, Present, AwaitOwnerCommit, Stopping, and Stopped. The watchdog samples these even when the UI heartbeat is healthy; active driver-call stalls report the lane, while overdue owner acknowledgments report the protocol/owner stage. Idle and a visibility-suspended resize are not hung. Record shutdown ownership waits separately if forced exit reaches the final join. The existing watchdog samples the UI and captures its thread stack (`crates/bt-app/src/hang_watch.rs:1736-1745`, `crates/bt-app/src/hang_watch.rs:1803-1828`, `crates/bt-app/src/hang_watch.rs:1905-1907`); extend its report facts and capture target rather than calling `WM_NULL` on a worker with no message pump.

## E. Expected effect and measurement boundaries

The owner's supplied next68 result is the motivation: 90–120 ms present calls on 177/217 slow animation frames and 53/98 slow keyboard frames. Those counts are owner-provided, not rederived against a changing file. An inspected next68 example is `D:/Developer/trace/next68/stderr.log:274`: 103.473 ms event-to-present minus 2.520 ms event-to-submit = 100.953 ms in present. The read-only snapshot taken here was 8,628,930 bytes, SHA256 `460aeab74343f2091cdff947f0e6aba137acb45ba0b70ae06085d5937f0927dd`; it is a later growing prefix and is not the review's next67 dataset.

The comparison baseline below is the review's fixed-prefix Phase-1 table, in milliseconds (`perf-review-2026-09-16.md:21-35`). The source order matches the four owner-facing latency metrics; its separate owner-supplied p90s were 97.2 / 77.5 / 24.0 / 61.9 ms, from another sample, so do not mix those populations with this table.

| Source | Baseline event-to-present p50 / p90 / max | Expected effect, not a numeric forecast |
|---|---|---|
| Keyboard | 20.335 / 111.517 / 296.867 | Input dispatch and PTY progress stop inheriting another frame's acquire/present hold. Surviving frames still pay lane wait and their own GPU calls; pre-render input/echo work remains. Neither p90 nor max is guaranteed to fall. |
| Expose | 6.010 / 74.692 / 223.179 | Pointer handlers and animation clocks keep running while the lane stalls; pending ticks collapse to the latest state. Light-load p50 may rise by wake/encoding hops. API-present tails can remain high. |
| PtyOutput | 10.620 / 24.759 / 124.628 | Draining/publication can progress during presentation; fewer stale output frames await service. GPU occupancy and CPU composition still bound visual progress. |
| Resize | 13.857 / 61.880 / 129.942 | Event callbacks can record sizes immediately; admitted resize pictures are ordered and cannot be displaced. Waiting for an older attempt, configure's idle wait, and the pinned present can keep or increase this latency. |

Moving a wait does not remove it from a receipt that still measures actual present return. Do not subtract p90 present cost from p90 total. The review's event-to-submit p90s (83.084 / 12.147 / 14.181 / 44.894 ms) illustrate the other work already present, not predicted post-fix latencies (`perf-review-2026-09-16.md:32-37`, `perf-review-2026-09-16.md:113`). Coalescing also changes the sample population, so report attempted/coalesced/completed counts and outstanding age beside quantiles.

Animation intervals can lose pump-induced extra gaps and stale-frame catch-up; input and animation state should track current time during a GPU wait. A 100 ms present call still caps that lane's actual picture progress for roughly that interval, and this design's two UI wake points add scheduling overhead. Smooth physical animation is therefore an experiment, not a promised consequence. P-2 preparation, configure, native commit, and other UI work remain possible stalls; the review measures preparation separately (`perf-review-2026-09-16.md:119-125`).

## F. Stage-2 implementation order and size

1. **Resolve the macOS dependency prerequisite first.** Record the exact wgpu-hal change and source audit. If vendoring is necessary, change root `Cargo.toml`/`Cargo.lock`, a documented `vendor/wgpu-hal` patch, and the safe visibility bridge in `crates/bt-render`; UI native visibility observation belongs in `crates/bt-platform/src/macos_impl.rs`. Do not edit a Cargo registry cache. Existing patches are listed at `Cargo.toml:258-260`.
2. **Build the pure protocol and fake-lane tests.** Add `crates/bt-app/src/render_handoff.rs` for candidate admission, resize barriers, fair global permit scheduling, epoch/revision checks, and terminal obligations. Replace/wrap the waiting-slot use in `main.rs`; keep one waiting picture, not two. Add the minimal transport/worker module `crates/bt-render/src/present_lane.rs` and message types.
3. **Split renderer phases mechanically.** In `crates/bt-render/src/lib.rs`, extract `compose_frame` into preparation and encode-against-view, then lane submit/present; retain a synchronous adapter for isolated offscreen/probe callers. Refactor `configure_surface_if_needed`, `handle_surface_failure`, `acquire`, and `close_the_frame` around the explicit lease/attempt lifecycle. Preserve pass order and shader/alpha behavior (`crates/bt-render/src/lib.rs:8487`, `crates/bt-render/src/lib.rs:9278-9351`, `crates/bt-render/src/lib.rs:9791-9805`, `crates/bt-render/src/lib.rs:10631-10705`).
4. **Integrate one application funnel.** Replace synchronous `present_seats_and_commit` with enqueue/admit plus completion/commit handlers. Route `redraw`, `present_retained_picture`, resize/DPI/seat-reflow admission, `AppEvent`, and `user_event` through it. Move all success accounting from call return to captured completion. Keep the skirt and native placement work on the owner (`crates/bt-app/src/main.rs:100142`, `crates/bt-app/src/main.rs:100280`, `crates/bt-app/src/main.rs:100425`, `crates/bt-app/src/main.rs:97475`, `crates/bt-app/src/main.rs:111702`).
5. **Close lifetime gaps before enabling the lane.** Gate readback/font-cache mutation/new-surface setup through the global permit; integrate device loss, the narrowly scoped lane panic boundary, normal retirement, quit/fail/exiting, and epoch invalidation. Do not leave an alternate synchronous live-window present or an unjoined drop path.
6. **Add trace and watchdog support.** Update `trace_present` and renderer phase timing; extend `crates/bt-app/src/hang_watch.rs` with separate lane records, correct owner stations, and reports. Keep the existing UI heartbeat semantics and watchdog reporting infrastructure.
7. **Validate the implementation in its own stage.** Run the named CPU-only protocol tests and existing relevant resize/occlusion/atlas-policy tests; check bt-render/bt-app on supported targets. Then perform the explicit Windows/macOS experiments below under stage-2 authorization. This design stage runs none of those commands or applications.

Estimate: roughly 1,500–2,500 new/changed handwritten lines across protocol/transport, app integration, tests, and diagnostics, plus about 600–1,000 lines mechanically extracted from the existing frame function. A narrow Metal dependency change adds tens to low hundreds of semantic lines; vendored upstream source volume is separate. This is a medium cross-cutting change, not a three-call thread spawn. A backend API redesign would require revising the estimate.

Leave PTY drain budgets, formula detection/typesetting, P-2 cache optimization, shaders, render order, alpha modes, latency=1, present mode, and existing device-retry budgets alone. CPU projection remains on the owner. Keep offscreen probe semantics available but prevent their auxiliary queue work from racing a live lane. The experiment must isolate ownership changes from swapchain tuning.
