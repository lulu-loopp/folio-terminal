# Review: "Leaving no trace — how Folio is removed, on every channel"

Reviewer: GLM (independent), 2026-09-20. Design: `docs/plans/design/clean-uninstall-2026-09-20.md` @ 81fa9c03.
Scope read: shell_integration.rs, attention_hooks.rs, attention_codex.rs, attention_copilot.rs, psreadline.rs, explorer_menu.rs, cli.rs, update.rs, docs/install.md, packaging/. Web sources cited inline.

## Verdict up front

**GO WITH CHANGES** — the three-layer shape is right (layer 0 is the only foundation that covers the zip/winget/trash channels), but layer 1 as written rests on one false claim about existing code ("everything else calls functions that exist" — the X-mark removers remove by *mark*, not by *path*, so the ownership rule of §3.3 is new code, not reuse), and layer 0 has a two-copy hole that defeats its own rule. Details below; slicing verdict in §3.

---

## 1. Breaking it — layer by layer

### Layer 0 (marks degrade harmlessly)

**L0-1. MUST-FIX — Claude Code hooks: two copies make the "upgrade to guarded form" self-defeating.**
Situation: the owner's own set-up — copy A and copy B both installed, both wrote hooks (`install_into` at `attention_hooks.rs:344` first calls `remove_from`, which removes **any** entry containing `attention claude-code:` regardless of path, then writes its own exe's path). Copy A upgrades to the guarded form: it rewrites the hook to guard A's path. Now B's hook entries are *gone* (A's `remove_from` took them) and only A's guarded line remains; when A is deleted, B is silently unintegrated — B's Settings row still reads "Installed" only if B's path is the one in the file, which it no longer is. What happens: the second copy loses its integration without any uninstall at all. Defeats: §3 rule 1 and §3 rule 3 — the upgrade path itself is a writer that must be ownership-aware, and the design only makes the *remover* ownership-aware.
Fix direction: the guarded-rewrite must be mark-scoped AND path-scoped (rewrite only groups whose command names this copy), and install must not cannibalise another live copy's groups — append a second group instead (the `hooks.<event>` array holds multiple groups; `install_into` at `attention_hooks.rs:391` already appends, but the leading `remove_from` wipes the other copy's).

**L0-2. MUST-FIX — guarded `$PROFILE` line: the same probe-cost rule forbids the design's one-line guard on slow machines.**
The guard `if (Test-Path <script>) { . <script> }` is one line and one `Test-Path` — fine (§3.6 budget met). But the *upgrade of existing installs* ("the next time Folio runs") needs the profile path, which comes from `profile_probe` (`shell_integration.rs:1136`) — asked of the shell, once per process, only when a PowerShell pane exists. A user who installed the line and never opens a PowerShell pane in Folio again keeps the unguarded line forever. What happens: the population the design most wants to fix (people who deleted the folder but kept `%APPDATA%`) is exactly the population that never runs Folio again — **the upgrade only reaches people who still run Folio**, and layer 0's whole point is the people who don't. This is not fixable inside the app; it is fixable only by making the *default* line guarded at write time (which the design does) plus accepting that pre-0.4.3 unguarded lines survive until layer 1.2's Apps entry or the user runs the door — say so in the design; today it reads as if existing installs get healed.

**L0-3. MUST-FIX — Codex `notify` cannot be guarded at all: it is argv, not a shell string.**
`notify = ["<abs>\folio.exe", "attention", "codex:agent-turn-complete", "--json"]` (`attention_codex.rs:200` `program_for`). Codex spawns argv[0] **directly** (VERIFIED from the array shape and codex's documented "program + arguments" model — see Q1); there is no shell to put an existence test in, and candidate (b) "a tiny stable launcher outside the app folder" is the only in-band guard — the design rejects it. So for Codex the design has *no layer-0 answer at all*; §2 layer 0 lists "Agent hooks" as if the three families share a problem shape. They do not. Either accept "codex prints/logs one spawn failure per turn until layer 1" as the documented answer (and verify how loud it is — Q1), or reconsider the launcher for this one family. As written, T-B "starts with the investigation in §5 Q1" is the whole ticket — say what happens if the investigation answers "no silent form exists".

**L0-4. NOTE — Copilot's guard costs a second process on Windows.** Copilot runs the `powershell` column as a PowerShell command string (module header quotes upstream's field table, `attention_copilot.rs:45-53`). A guard `if (Test-Path …) { & … }` is one line in the same PowerShell — no extra process, budget met. On macOS the `bash` column gets `test -x … && …` — also one line. Copilot is the easy one; the design never says so, and T-B's per-platform-per-agent table should.

**L0-5. MUST-FIX — PSReadLine patch under OneDrive-redirected Documents.** `documents_directory()` (`psreadline.rs:852`) follows the known folder, which OneDrive redirection moves. Two consequences the design's class O/R list misses: (a) layer 1's removal of "nine files under the user's PowerShell modules" must go through the *known folder*, not a composed path — the code already does; the design should say the ownership test (`installed_copy`, `psreadline.rs:970`, by build stamp `2.4.6-bt.*`) is the *only* safe test, since the folder is user-writable and shared with the machine's own modules; (b) `remove_dir_all` on a OneDrive-synced folder can fail on a synced placeholder/lock — the cleanup must report it and exit non-zero, which the design's exit rule already covers, but the `--purge` "when requested, ALL of it is (both roots)" rule needs the same one-line-per-refusal reporting.

**L0-6. NOTE — toast identity `Folio.Terminal` is listed as "deliberately never removed" but is an R mark under the design's own rule §3.2.** Every mark gets an undo; this one is cheap (delete one `AppUserModelId` key). Either remove it in the door or write the exemption into §3 with its reason (notifications history?), otherwise the design contradicts itself.

### Layer 1 (the door and its entrances)

**L1-1. BLOCKS — the ownership rule is not "generalised from `explorer_menu`"; it contradicts the X-mark removers as they exist.**
`attention_hooks::remove_from` (`attention_hooks.rs:403`) and `attention_codex::remove_from` (`attention_codex.rs:268`) recognise ours by the substring `attention claude-code:` / verb+family — **by mark, not by path**; `attention_hooks.rs:56-62` says so as a deliberate rule ("a user who moves Folio, or who runs two builds of it, still has one set of entries that this can recognise"). The design's §2 layer-1 ownership test ("a hook naming ANOTHER existing copy's path is left alone; one naming a path that no longer exists is removed") is a *different* rule and requires new code in all three removers (parse the command's first word, compare against `current_exe` and the disk). The claim "The only NEW removal code is the `$PROFILE` line remover; everything else calls functions that exist" is false as written. This BLOCKS only because the ticket will be cut from that sentence; the fix is to strike it and name the three ownership tests as new code with the same `same_path` (`explorer_menu.rs:631`) machinery.

**L1-2. MUST-FIX — `CLAUDE_CONFIG_DIR`/`CODEX_HOME`/`COPILOT_HOME` pointing elsewhere at uninstall time than at install time.** All three config paths are read from the *current environment* (`attention_hooks.rs:79`, `attention_codex.rs:109`, `attention_copilot.rs:214`). Hooks written under a `CLAUDE_CONFIG_DIR` that is no longer set at uninstall time are in `~/.claude/settings.json`... no — they are in the *old* directory, and the cleanup will look in the *default* one and report "nothing to remove", exit 0. What happens: marks survive the door. Defeats §3 rule 2 ("every mark has a non-interactive undo"). Fix: the door must enumerate both the current-env path and the default path for each family (two candidate files per agent), and the Claude Code one additionally has no other registry of past config dirs — accept and document the limit, but scan at least default+current.

**L1-3. MUST-FIX — config file malformed/locked at uninstall time: the door exits non-zero and the folder is still deleted by entrance 1/2's "then deletes the folder".** `apply_to` refuses on `Standing::Unreadable` (`attention_hooks.rs:466`) — correct for install, fatal for uninstall: a malformed `settings.json` (which Folio refused to write into, so it isn't even Folio's damage) means the hook entries inside it survive, and the Apps-entry command (§2 entrance 2) then deletes the folder anyway → back to layer 0's worst case with no app left. The door's contract must be: X-mark removal failure does not block folder deletion but **does** print the path and the reason and exit non-zero — and `--uninstall-cleanup`'s "non-zero exit only when a removal was attempted and refused" already says this; the *entrances* must not treat non-zero as "abort the uninstall".

**L1-4. MUST-FIX — cleanup while Folio is running.** The door must refuse (or degrade) when another Folio holds the mutex: `--purge` deleting `%APPDATA%\Folio` under a live instance destroys its settings writes; deleting the WebView2 root under a live renderer is Q5's question. Design says "no hand-off to a running instance" but not "refuses when one is running". One sentence needed, plus the `--purge` case explicitly waits/fails per Q5.

**L1-5. NOTE — settings data lost that the user wanted: `--purge` deletes `settings.json.rejected-*` and hang reports — fine. But `%TEMP%\folio\clipboard` is *live clipboard content*; purging it while the user expects to paste from Folio's clipboard history loses data with no prompt. The checkbox in entrance 1 must name clipboard history explicitly, not "settings and data".

**L1-6. NOTE — standard (non-admin) user:** everything in §1 is HKCU/per-user; the sparse package registration is per-user; no elevation anywhere. VERIFIED — `read_state`/`RemovePackageAsync` path in `explorer_menu.rs` is the same one the non-elevated Settings row uses. No issue; worth one line in the ticket so nobody adds elevation later.

**L1-7. MUST-FIX — entrance 1's self-delete: a path with a trailing backslash or non-ASCII through `cmd`.** Q3 details below; the design's own text names the hazards but the slicing puts T-D (the button that triggers self-delete) in 0.4.4 while T-C (`uninstall.cmd`, same self-delete primitive) is 0.4.3 — the primitive must land with T-C, tested, not twice.

**L1-8. NOTE — entrance 2's Uninstall entry after "unzip beside the old folder".** Two zips, two folders, one HKCU Uninstall key name: the second copy's registration overwrites the first's `UninstallString` (or must be refused). Q2 answer below proposes the key name derived from the folder so two copies coexist; design must pick, because the owner runs two copies.

**L1-9. NOTE — macOS translocation/quarantine.** A zip-installed app run from the Downloads folder translocates to a random `/private/var/folders/...` path; `current_exe` there is *not* the user's copy. Hooks written from a translocated run would embed the translocated path (gone next boot) — the mark is then "a path that no longer exists", which layer 1's rule removes as nobody's, and layer 0's guard keeps silent. Actually fine — but the design should note the DMG/cask builds (the only supported mac channels) never translocate; only the unsupported zip-on-mac path does. `xattr -d com.apple.quarantine` is not needed by the design (no self-delete via shell on mac).

**L1-10. NOTE — /Applications owned by another user:** moving to Trash needs write on the .app; if another admin user owns it, Finder asks for a password — the design's "moves itself to the Trash" must fall back to `osascript`-free `NSWorkspace.recycleObjects` failure reporting. Minor; cover in T-D's test plan.

### Layer 2 — no findings beyond Q2's (the deferral to 0.4.5 is right; see §3).

## 2. The open questions

**Q1 — how each agent executes a hook, and the failure the user sees.**

- **Claude Code** — VERIFIED from the hooks reference (https://code.claude.com/docs/en/hooks): the *shell form* (command as a string) runs under `sh -c` on macOS/Linux; on Windows under **Git Bash**, falling back to **PowerShell** where Git Bash is absent; an optional `shell` field pins the interpreter; the *exec form* (`args` present) spawns directly with no shell. Failure surface: a hook that fails to start is non-blocking **but surfaced** — the transcript shows `Failed with non-blocking status code: …`. So candidate (c) "accept the agent's own handling" is refuted, and `quoted_program`'s comment (`attention_hooks.rs:321`, assumes cmd) mis-models Windows: `if exist` is cmd syntax and works in *neither* Git Bash nor PowerShell. The current unguarded string survives both shells (a double-quoted string in command position is the command name in both), but no *guard* satisfies both — `test` is not a PowerShell command, `Test-Path` is not a bash one. **Proposed command strings** (guard costs no extra process — the shell Claude Code already spawns does the test):
  - Windows: pin `"shell"` to PowerShell (guaranteed present; Git Bash is not) and write `if (Test-Path "<abs>\folio.exe") { & "<abs>\folio.exe" attention claude-code:<event> --json - }` — exit 0 when missing, naturally silent. T-B must confirm the field's accepted values against the live hooks reference.
  - macOS/Linux: `test -x '<abs>/folio' && '<abs>/folio' attention claude-code:<event> --json - || true` — the `|| true` tail is REQUIRED: without it a missing exe makes the line exit 1, which Claude Code surfaces as a failure notice — the guard would be noisier than the thing it guards.
  - Caveat: the `--json -` tail applies only to turn-end rows (`command_for_on`, `attention_hooks.rs:299`); keep that branch.
- **Codex** — VERIFIED from the config reference (`notify`: `array<string>`, "Command invoked for notifications; receives a JSON payload from Codex" — https://learn.chatgpt.com/docs/config-file/config-reference) and the open-source spawn path (argv via `Command::new`, payload appended — https://github.com/openai/codex, codex-rs): **no shell, no in-band guard possible**. What the user sees when the program is missing: UNKNOWN (documented nowhere I could find) — the one item T-B's investigation must measure on a real machine; the design should name the fallback if it turns out loud (layer-1 removal only, plus "run `folio --uninstall-cleanup` before deleting" documented for scoop/cask, where a hook exists).
- **Copilot CLI** — VERIFIED from upstream's field table (quoted at `attention_copilot.rs:45-53`): `bash` runs on Unix, `powershell` on Windows, as a command string; timeouts are "logged and skipped". Proposed: Windows `if (Test-Path '<abs>\folio.exe') { & '<abs>\folio.exe' attention copilot:<event> }`; Unix `test -x '<abs>/folio' && '<abs>/folio' attention copilot:<event> || true` (same exit-code caveat as Claude Code).
- **"Is `async: true` enough?"** — No: VERIFIED that `async` moves the hook off the turn's critical path but the failure *notice* still appears in the transcript. Guard Claude Code + Copilot as above; for Codex, measure and write the answer into T-B.

**Q2 — Settings ▸ Apps entry from a portable zip.** VERIFIED acceptable: many portables (VS Code User Setup, Obsidian) register per-user Uninstall keys; the requirements are the documented Registry conventions — DisplayName, DisplayVersion, Publisher, InstallLocation, UninstallString, QuietUninstallString, NoModify=1, NoRepair=1, SystemComponent absent (https://learn.microsoft.com/en-us/cpp/windows/uninstall-registry-key). Keys the design must add: **the key name must be unique per copy** (`Folio (<folder>)` or a hash of the folder) or two copies fight over one entry; `DisplayVersion` must be rewritten on every launch (the "existing self-repair on folder move" the design leans on is in `explorer_menu.rs::reassert_wanted`, not here — a NEW repair path for the Uninstall key must be named, since `InstallLocation` goes stale after a move or an unzip-beside upgrade). INFERRED: winget validation of *portable/zip* packages ignores vendor uninstall keys (winget tracks its own symlinks — https://learn.microsoft.com/en-us/windows/package-manager/winget/install); no conflict expected, but the Apps entry will make `winget uninstall` *and* the Apps entry both available — the design should say the door dedupes (running cleanup twice must be a no-op, which rule §3.2's idempotent removers already give).

**Q3 — self-delete on Windows; Trash on macOS.**
- Windows VERIFIED-technique (standard, used by installers and self-updaters): spawn a detached `cmd.exe /c timeout /t 2 & rd /s /q "<folder>"` — must (a) quote the path (spaces, non-ASCII are fine inside quotes; a trailing backslash before the closing quote escapes it — strip it), (b) not have the folder as any process's CWD (`rd` fails on a directory that is a current directory — the detached cmd must `cd /d %TEMP%` first), (c) accept that AV heuristics sometimes flag self-deleting executables: mitigation is the same command every uninstaller uses; there is no documented Microsoft pattern to avoid it. `MoveFileEx(PENDING_DELETE)`-style deferred delete does not work for directories. The design should specify: `cd /d "%TEMP%"` + retry loop `rd /s /q` up to N times with delay, and report leftovers as "delete these files" in the exit message (the last honest fallback; not a defect under the owner's principle because the *marks* — the costly part — are already gone).
- macOS VERIFIED: a notarised, non-sandboxed app may move itself to the Trash via `NSWorkspace.recycleObjects(...)` without a prompt (Finder-authored move; no TCC prompt for Trash). No gatekeeper interaction. (https://developer.apple.com/documentation/appkit/nsworkspace/1533461-recycleobjects — the API's own contract; "detailedBeforeURL" errors are returned, not prompted.)

**Q4 — ownership for X marks.** Answer: one line in §3.3 plus L0-1/L1-1 above — the rule must be: *a mark is this copy's iff its command's first word names this copy's executable (`same_path`); a mark naming a live other copy is left and *reported* ("left: another Folio at <path> is using it"); a mark naming a missing path is removed*. Second copy finding the first's hook already installed: the Settings row must say "installed by another copy at <path>" rather than "Installed" (today `state()` answers by mark and would claim it).

**Q5 — WebView2 folder under purge.** VERIFIED from WebView2 docs: the user-data folder can be deleted only when no `msedgewebview2.exe` child remains (https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/user-data-folder). Practical answer: after Folio exits its last window the children can outlive it by seconds; the door should retry with a short bound and then report "left: %LOCALAPPDATA%\Folio\WebView2 (in use)" and exit non-zero per the design's own rule. Two Folio copies share the same user-data folder name — a second running copy blocks purge; detect via the existing single-instance mutex? NOTE: two copies *each* run their own WebView2 with the same UDF → both must be closed; the door cannot know, so the retry-and-report answer is the honest one.

**Q6 — what is missing from §1.** Found in code, not in the inventory: (a) `$PROFILE` **backups** — `<profile>.bak-<date>` beside the profile (`shell_integration.rs:1453`) and `settings.json.bak-*`, `config.toml.bak-*` beside each agent config (`attention_hooks::land`) — class X leftovers the door should name but not delete (they are the user's pre-Folio copies); (b) `~/.copilot/hooks/folio.json.bak-*` presumably same; (c) the winget portable **symlink** in `%LOCALAPPDATA%\Microsoft\WinGet\Links\folio.exe` and winget's own package folder — a channel mark winget owns; `--uninstall-cleanup` running under `winget uninstall` is fine, but a user running the door *manually* on a winget install leaves a dead symlink (report it); (d) macOS: the design's five locations omit `~/Library/WebKit/`, includes it — ok — but check `~/Library/Saved Application State/io.github.lulu-loopp.folio.savedState` (listed) and **`~/Library/HTTPStorages`** (listed). Nothing else found in the crates read.

**Q7 — package-manager policies.**
- scoop VERIFIED: manifests support `pre_uninstall`/`post_install` scripts in the JSON manifest (https://github.com/ScoopInstaller/Scoop/wiki/JSON-manifests; https://github.com/ScoopInstaller/Scoop/wiki/App-Scripts-Automatic) — but **bucket review practice disfavours heavy scripts**; a two-line `pre_uninstall` calling `folio.exe --uninstall-cleanup` is within existing examples (some buckets ship similar). The `post_install` channel marker is fine. UNKNOWN: whether the *maintainer's* bucket rules add restrictions — the bucket is self-hosted, so self-imposed only.
- Homebrew cask VERIFIED: `uninstall_preflight` is a real, documented stanza (Ruby block run before uninstall, lazily evaluated — https://docs.brew.sh/Cask-Cookbook) — correct choice; a `zap` stanza listing the five paths is the audit-clean shape for "remove everything" (same cookbook). NOTE: `uninstall_preflight` requires a recent Homebrew — pin nothing, but test on the version brew.sh ships.
- winget VERIFIED: the published manifest is `InstallerType: zip` + `NestedInstallerType: portable` (packaging/winget/manifests/w/WeiyiShi/Folio/0.4.0) — the winget repository validation has **no pre/post-uninstall hook** for this type (no such field exists in the manifest schema, https://aka.ms/winget-manifest.installer.1.12.0.schema.json) — the design's reading is right; layers 0+1.2 cover it, and a portable alias symlink remains (Q6 c).

## 3. Slicing

- **Move earlier (0.4.3):** (1) T-E's *door registration*, not the full Settings UI — the hook-writes-outside moment is when the Apps entry is needed; a user who turns on hooks today and deletes the folder tomorrow has no discoverable door, and 0.4.4 is a release later. Minimum: write the HKCU Uninstall key in the same press that writes the first X mark (small, testable, no UI); the Settings ▸ About button can wait. (2) The self-delete *primitive* (Q3) belongs with T-C's `uninstall.cmd`, not T-D — same code, tested once. (3) **Telling existing users the door exists** — missing from the design altogether: 0.4.3's release note must carry one line ("deleted the folder? run this once") and `docs/install.md`'s rewrite is in T-C but no channel *reaches* upgraders; the first-run card is once-only and existing users never see it. Consider the update-check notifier (update.rs) surfacing it once, or the Settings ▸ About line in 0.4.3 as text.
- **Can wait:** T-D's full button UI; layer 2 (installer/updater) — correctly bundled with 0.4.5.
- **Missing altogether:** (a) a **test plan that touches no real machine** — the repo's own `BT_POWERSHELL_PROFILE` / `BT_PSREADLINE_DOCUMENTS` sandbox doors (`shell_integration.rs:1143`, `psreadline.rs:396`) and the env-var config dirs (`CLAUDE_CONFIG_DIR` etc.) give a full harness; the design should name them and add the same door for the Uninstall-registry key (HKCU under a test subkey); (b) **release-note wording** (per the repo's publicity rules, one line, no drama); (c) what `--uninstall-cleanup` says on a **Mac** (design is Windows-heavy; the Mac door's text should name the five `--purge` locations); (d) exit-code table for the door (0 / 1 attempted-and-refused / 2 running-instance) so scoop/cask hooks can log meaningfully; (e) L0-2's admission that pre-0.4.3 unguarded `$PROFILE` lines are healed only by the door.
- **0.4.3 scope is too big as one slice** given L1-1 turns three removers into new ownership-aware code: split T-C into T-C1 (door + profile remover + ownership for Claude Code hooks) and T-C2 (codex/copilot ownership + package-manager hooks), each shippable.

---

## Verdict

**GO WITH CHANGES** — required before the ticket:
1. Strike "the only new removal code is the `$PROFILE` remover"; specify per-family ownership tests as new code (L1-1, Q4).
2. Give Codex an explicit layer-0 answer or a documented acceptance (L0-3).
3. Make the guarded-line upgrade ownership-aware across two copies (L0-1) and state the pre-0.4.3-line limit (L0-2).
4. Door contract: config-dir fallback paths (L1-2), unreadable-config non-blocking of folder deletion (L1-3), running-instance refusal (L1-4).
5. Move the Uninstall-key write and the self-delete primitive into 0.4.3; add the existing-user notification and the sandboxed test plan (§3).

The shape — degrade first, one door second, installer last — is right, and layer 0's framing ("no uninstall path can be relied on") is the correct foundation for a zip-first product.
