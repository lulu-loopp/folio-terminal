## P-1 — synchronous swapchain present blocks the event thread

**Verdict: CONFIRMED.**

Reopened: `crates/bt-app/src/main.rs:111446`, `:100187-100345`, `:99910-99927`, `:99957-99965`, `:100203-100212`; `crates/bt-render/src/lib.rs:9631-9645`, `:8278-8284`, `:9118-9139`, `:10477-10496`, `:4506`, `:1457-1479`.

**Claim vs code.** Every present is dispatched on the winit event thread: `WindowEvent::RedrawRequested => runtime.redraw()` (main.rs:111446); `redraw` calls `present_seats_and_commit` inline (main.rs:100337), which calls `renderer.present_frame` inline (main.rs:99927). `present_frame` → `compose_frame` unconditionally (bt-render lib.rs:8284). Inside, on that same thread: `gpu.queue.submit([encoder.finish()])` (lib.rs:9632), then `gpu.queue.present(texture)` (lib.rs:9635), stamped at `present_called_at` (lib.rs:9640). Acquisition is likewise synchronous: `configure_surface_if_needed` + `self.acquire()` + `create_view` between `rectangles_prepared_at` and `surface_acquired_at` (lib.rs:9122-9139), where `acquire` is `surface.get_current_texture()` (lib.rs:10479). `PresentReceipt::latency` derives `event_to_submit = submitted_at - trigger.occurred_at` (lib.rs:1471), so the log's `event_to_present_us - event_to_submit_us` is exactly the wall time of the `queue.present` call — the review's reading is precise, including its caveat that this is call completion, not scanout. `desired_maximum_frame_latency = 1` confirmed at lib.rs:4506.

**Measured cost — reproduced exactly.** Recomputed over the fixed prefix: 2458 present records (Expose 1064 / Keyboard 298 / PtyOutput 1082 / Resize 14). Among ≥50 ms records, post-submit time exceeds half of total for **111/150 Expose, 27/69 Keyboard, 65/75 PtyOutput, 1/2 Resize** — identical to the claim. Spot lines match the log: :3987 (128.209 ms total, 5.570 to submit, 122.639 after), :3334 (133.790/14.962/118.828), :295 Resize (129.942/14.392/115.550), :907 Keyboard max (296.867 total, 0.224 after submit — correctly not claimed for P-1).

**Cost class.** Blocking GPU/platform calls on the event thread — not O(visible) or O(document) work, not file I/O. It delays every later event in the pump (same-thread dispatch), which is the review's stutter mechanism. Real on all four owner-felt paths.

**Fix.** The capacity-one latest-frame handoff matches the composition side's existing pattern (`pending_frames.take()` main.rs:100188, publish main.rs:64947-64950), so ordering discipline already exists in-house. It is the correct structural fix but not small, and three in-repo contracts must survive it: (1) present→`set_covered_size`→`commit` ordering — "whoever owns the DirectComposition device owns the commit... a present without its commit is... a screen that never changes again" (main.rs:99888-99896, commit at :99963), so the lane must not take the compositor and the commit must stay serialized after present; (2) the resize contract `frame_matches_grid` (main.rs:100203-100212) requires the presented frame to be the newly projected grid — a latest-frame lane may not drop a resize present; (3) surface ownership moves with the lane (bt-render lib.rs:10478). Flag-only changes (latency=2) are smaller but are experiments, exactly as the finding says; the trace shows call-duration stalls, not proven queue depth.

**Missed.** Nothing material on this path. The review already bounds what the receipt excludes (the DComp commit at main.rs:99963 is named in Phase 1) and already separates the acquire bucket (lib.rs:9122-9139) from pure acquisition. The single caller funnel (`present_seats_and_commit`, "the only call to `WindowRenderer::present_frame` in `bt-app`", main.rs:99895-99896) means one lane covers composed, retained and resize presents alike — no fourth path to audit.

## P-2 — every present reshapes chrome text and recreates transient GPU geometry

**Verdict: CONFIRMED.**

Reopened: `crates/bt-render/src/lib.rs:8767-8771`, `:8803-8808`, `:8518-8573`, `:8682-8702`, `:11892-11941`, `:12669-12722`, `:10008-10013`, `:9118`/`:9694`; `crates/bt-app/src/main.rs:100128-100151`.

**Claim vs code.** `compose_frame` has no unchanged-frame early-out (lib.rs:8278-8284), and the retained caller funnels through the same door (main.rs:100139), so every present — including an unchanged picture with only a hover/fade/caret change — executes: `shape_preview_body` per preview body per frame (lib.rs:8771; per-paragraph buffers at :12701); `shape_chrome_labels` (lib.rs:8803), which builds a fresh cosmic-text `Buffer::new(font_system, ...)` per label (lib.rs:11930-11931), sets text (:11940) and runs `buffer.shape_until_scroll(font_system, false)` (:11941) — no retention anywhere; per-seat `create_buffer_init` for ground/rects (lib.rs:8518-8524, :8530-8536); status and math-overlay buffers created **unconditionally**, with `empty_rect.as_slice()` dummy contents when empty (:8545-8556, :8562-8573); icon lists `.iter().cloned().partition(...)` (lib.rs:8695-8698) then `icons.to_vec()` again inside `prepare_chrome_icon_draws` (:10013). The `rectangles_us` field is `rectangles_prepared_at - math_prepared_at` (lib.rs:9694), and both shaping sites (:8771, :8803) sit inside that interval, so it really is the broad preparation bucket — as the finding states.

**Measured cost — reproduced exactly.** `rectangles_us` over the prefix: Keyboard 3.993/5.092/163.463 ms (p50/p90/max), Expose 4.026/4.880/119.713, PtyOutput 4.232/5.020/70.707, Resize 1.088/3.621/4.014 — all four rows match. The cited extreme reproduces: log line 1070 carries `rectangles_us=163463` inside a 177.819 ms renderer (`total_us` max for Keyboard) with the paired present at :1071 showing 272.146 ms event latency.

**Cost class.** O(drawable chrome labels + preview paragraphs + visible per-seat geometry) — visible-bounded, not document-sized; CPU shaping plus GPU resource creation, all synchronous on the event thread, every present. The ~4 ms median at 60 Hz is a real quarter of the frame budget; the maxima overlap P-1 waits inside the same bucket, and the finding correctly refuses to split them.

**Fix.** Retain shaped text by content/font/width revision and reuse growable buffers — correct, but not the whole saving, and not all of it is "smallest": two strictly smaller, risk-free slices exist inside the finding's own citations — skip the dummy empty buffers (create only when data is non-empty, lib.rs:8545-8573) and drop the second icon clone (pass the slice, lib.rs:10013). The text-shaping retention is the larger half and must invalidate on DPI/font/width changes (configuration sites exist at lib.rs:4506-4507's neighborhood for surface config; font/DPI keys flow through `session.set_font_size_subpixels` etc., main.rs:34108-34110).

**Missed.** The glyph atlas is trimmed after **every** presented frame: `present_frame` calls `gpu.close_the_frame(&outcome)` (bt-render lib.rs:8318), and the `Presented` arm runs `self.atlas.trim()` (lib.rs:6572-6574), which empties glyphon's in-use set each frame. So even with shaped `Buffer`s retained by revision, `prepare_chrome_text_atlas` (lib.rs:8820, :8784) must re-run per frame to re-register glyphs, and that prepare time stays inside `rectangles_us`. The review's "upper bound, not a guaranteed saving" hedge covers this numerically but never names the trim as the reason the bound is loose — a fix scoped only to shaping would leave this cost on the books.

## P-3 — whole-visible-screen image/path scans repeat per feed and twice per publication

**Verdict: CONFIRMED.**

Reopened: `crates/bt-term/src/session.rs:2891`, `:3003`, `:9694-9840`, `:9845-9867`, `:9934-9945`, `:2641-2665`, `:2731-2812`, `:2854-2860`, `:7617-7618`, `:687`; `crates/bt-app/src/main.rs:34112`, `:64783-64842`, `:64848-64855`, `:64908-64931`.

**Claim vs code.** All four traversals verified. (1) Per feed: `feed_at` ends with `self.reconcile_live_image_paths(false, &vec![false; self.live_rows.len()])` (session.rs:3003); the only gate is `detect_image_paths` (:9695), which the app sets `true` by default (main.rs:34112). With `INLINE_IMAGE_BANDS = false` (session.rs:687) the band gates are skipped (`band_gates && ...` at :9705), so the alternate-screen exclusion does **not** apply — confirmed, and 2205 of 2458 traced frames are `alt=1`, so the dominant workload runs exactly this path. Detection (:9708) walks every live row via `for_each_live_logical_line` (:9845-9867, fresh text/boundaries per row) and `detected_live_image_links` walks all rows again (:9936-9945). (2) Per publication: `viewport_frame` decoration calls `frame_image_references` once (session.rs:7618 → :2855 → :2641-2665 → `collect_frame_line_references`, cell-map rebuild at :2743 and detection at :2809), then the app immediately re-scans the same frame for hover storage (main.rs:64840) — the double scan is even documented in-tree: "The session scanned the same frame once more when it painted the resting dots inside `viewport_frame`" (main.rs:64833). The unchanged-skip gate sits after all of it (main.rs:64908); it fired 439 times in the prefix (`skip=unchanged` lines), each after the full preparation. Matching additionally searches stored records linearly per candidate (session.rs:9752-9762), as claimed.

**Cost class.** O(visible rows × columns) pure CPU on the event thread, four full traversals per feed-and-publish cycle, no I/O — visible-bounded, not document-sized, with temporary strings/vectors per row. The finding correctly claims source-proof only ("milliseconds are not isolated"); nothing in the logs contradicts or supplements that.

**Fix.** For the frame-side double scan, "compute once and return/cache with the frame" is the smallest correct fix **only as a return-value variant** — `decorate_image_reference_affordance` returns the references it already computed, or `viewport_frame` returns them beside the frame. The in-tree comment records a design objection to the other shape of this fix: "collapsing the two would mean hanging the scan on the session as state, which is the very kind of thing this affordance was rebuilt to be rid of" (main.rs:64834-64835); a return-based reuse honors that objection, a session-state cache does not. Reuse is exact, not approximate: the app's scan at :64840 reads the frame before `apply_hover_marks` (:64848-64855) mutates it, and hover marks change only underline bits, not text or hyperlinks, so decoration-time references are already the right answer; the `verified` bit (session.rs:2803) cannot go stale between the two scans because worker batches land at turn boundaries, not mid-publish. The feed-side "scan damaged lines only" proposal is heavier than needed — see below.

**Missed.** The per-feed call passes `create_and_retire = false` (session.rs:3003) and an all-false stability vector, so in that call the entire detection pass feeds only the record-matching loop (:9746-9790): creation needs `create_and_retire && candidate.stable` (:9791-9792, false on both counts) and retirement returns early (:9821-9823). When no `LocalPath` records exist on the current screen/generation — `existing` empty (:9711-9742), the common case on this workload — every detected candidate is matched against an empty list and discarded. A guard on "no existing live records" before :9708 removes the per-feed whole-screen scan without any content-keyed cache or damaged-line bookkeeping, which is smaller than the finding's proposed feed-side fix and breaks nothing (record creation and retirement happen in the other call site, `schedule_visible_artifacts` → `schedule_live_artifacts`, session.rs:7634-7646, which passes the real stability vector).
