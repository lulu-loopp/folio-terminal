## 1. The state model (§3, §11.5, §11.8)

**F1 — The one-second forward-clear eats the most common wait.** §11.5: *"a clear with `ClearScope::All` also clears waits minted within one second after it."* `UserPromptSubmit` is `ClearScope::All` (`attention_map.rs:199-213`), and a prompt whose first tool call needs permission produces a `PermissionRequest` routinely *within* a second of the submit — an instant `ls` approval is the ordinary case, not a race. The rule as written clears that live, legitimate wait: no notification, no Waiting row, agent silently blocked — the headline scenario fails in the common case. **BLOCKS-DESIGN.** Smallest change: forward-clearing applies only to turn-*ending* clears (`Stop` / `StopFailure` / `SessionEnd`), never to `UserPromptSubmit` — a submit causally precedes its own turn's waits, so it has no inversion to forgive; the inversion the rule was written for is exactly `Stop`-before-`PermissionRequest`.

**F2 — The tolerance is asymmetric: `begins_turn` after its own `Stop`.** §11.5 tolerates a wait minted after its clear, but the unordered pipe (one `folio.exe` per event, no sequence number or timestamp anywhere on the wire, `attention_wire.rs:92-102`) inverts both directions. If `UserPromptSubmit` lands after the `Stop` of the *same* turn, the ledger enters Working with every clear already spent; nothing else is coming (the turn is over), and no Working reaper exists — the only expiry in the ledger is `WaitClock` for waits (`attention_wire.rs:307-371`). Row breathes Working until the next turn or pane close. **MUST-DECIDE-BEFORE-TICKET 2.** Smallest change: extend the same one-second tolerance symmetrically (drop a `begins_turn` arriving within 1 s after that pane's turn-end), and state the residual honestly.

**F3 — Working after `kill -9` never clears, for hook-rich agents too.** §11.5's Exited bullet rests on "root-process death always [knowable]" — but the pane's root is the *shell*; the agent is a grandchild, and a killed Claude Code fires no `Stop`/`SessionEnd` hook and is not root death. The no-process-walker ruling (§11.8, third rung dropped) forbids obtaining the evidence. So a `kill -9`'d agent's row shows Working forever (until the pane closes). Kimi F6 raised the shape of this; §11.5 answered stuck *Waiting*, not stuck *Working*. **MUST-DECIDE-BEFORE-TICKET 2.** Smallest change: rule that Working clears on OSC 133 command-end where shell integration is on (a returned prompt *is* turn-over evidence), and add one line to §11.8's floor: without it, a killed agent's row holds Working until the pane closes — said, not discovered.

**F4 — A denied permission leaves Waiting standing for the rest of the turn.** §11.5 says Waiting inherits the shipped clears. The permission-wait receipt is `PostToolUse` gated to answered credentials (`attention_map.rs:256-267`, gate at `attention.rs:1288-1296`); a **Deny** executes no tool, so no `PostToolUse` fires, and the wait stands until the user submits or the turn ends — which can be many minutes of a still-working turn, with the row pulsing "Waiting" while nothing waits. **NOTE.** Smallest change: record the staleness window in §11.5 (Stop eventually clears it), or treat the first subsequent `PreToolUse`-class evidence… there is none today — so record it.

**F5 — §11.8's floor table promises a row its own recognition rule forbids.** The floor row says a hookless, OSC-silent vendor (Kimi, OpenCode, Hermes, GLM, Gemini CLI) gets "the mark and the title"; two bullets later: *"Nothing else lists an agent."* A zero-signal agent hand-typed into a shell pane can never produce a row, so that mark has no host. The only consistent reading is that such a row exists only for a Folio-launched dedicated pane (`pane.kind` known by construction) — which §11.8 never says. **MUST-DECIDE-BEFORE-TICKET 2/3.** Smallest change: one sentence — a zero-signal vendor gets a row only in a dedicated pane; hand-started with no hook and no OSC it is as invisible as WSL, and §11.8's table should say so in the same breath.

## 2. §12.1 and §12.2 — the cases the two rules don't decide

**F6 — "Focused" in §12.2 is undefined at exactly the seam §12.1 opened.** §12.1's whole argument is that focus is a keyboard fact, not an eye fact. §12.2 then clears the dot when "that pane gains focus." The shipped `Settle { active, focused }` means *window* focus (`main.rs:25403-25406`, `notify.rs:108`). Concrete break: user focuses pane A, alt-tabs to a browser; the turn ends. §12.1 sends a system toast — transient, and Focus Assist can eat it. If §12.2's "focus" is pane-level, the pane is still the window's focused leaf, so it *never wears the dot*: the user returns to badge 0, no dot, and a Done that survives only as a state word on a row possibly scrolled below the rail's 50 % fold (the sticky rule, §12.4.1, is recommended only for Waiting). Arrival was spent on a toast nobody saw, and the debt was never recorded. **MUST-DECIDE-BEFORE-TICKET 4/5.** Smallest change: the dot's focus is "the pane is the focused leaf **and** its window holds desktop focus" — exactly the `Settle{active, focused}` the frame already computes; panes of an unfocused window all wear their dots.

**F7 — Which states raise a notification is never said, and the storm math depends on it.** §11.7.1/§12.1 say "an agent that needs the person." Is Done a need? Failed? If every turn end of every agent raises an expandable notification, five agents finishing a wave is five popups. The new surface has **no** rate, stacking, or coalescing rule (the quota toasts have nine; this one has none). The shipped latches — once-per-episode (`attention.rs:1501-1522`), once-per-turn, 64/s bucket (`attention.rs:1690-1728`) — bound the *ledger*, not this surface. **MUST-DECIDE-BEFORE-TICKET 4.** Smallest change: name the raising states (suggest Waiting + Failed; Done only under the existing *Agents ▸ Turn finished* switch) and adopt the toast host's discipline verbatim: stack don't merge, one per episode, auto-leave on the master's 3.4 s unless hovered or armed.

**F8 — Auto-leave versus the reply field, and the 1004 flip.** §12.1: "a notification leaves by itself." §11.7.3 arms it with a text field. Once the keyboard is in the field the pointer may be anywhere, so the toast rule "hover stops the clock" does not protect it — the user is mid-sentence, the timer expires, the notification vanishes, and §12.4.4's "kept" text is kept *in a dismissed window*. Second break in the same gesture: clicking the reply field moves the keyboard owner off the shell, and the pane's child hears `CSI O` (`main.rs:18692-18719` — precisely the area of today's focus fix, `33a1eb86`); TUIs that redraw on focus change will visibly flinch, and where focus goes after send/cancel is unspecified. **MUST-DECIDE-BEFORE-TICKET 4.** Smallest change: an armed or focused reply field pins the notification (no auto-leave); sending or cancelling returns the keyboard to the pane it came from; arming the field does not change the pane's 1004 report (the report flips only if the user clicks *into the pane*).

**F9 — Four undecided edges of §12.1/§12.2, one line each.** (a) **Which window hosts the notification** for an agent in another, possibly minimised window (§12.4.5 lists those rows in every window's rail; the click-through must cross windows — the toast path already resolves `w=<hwnd>&t=&s=` routes with graceful misses, `main.rs:84678-84730`; say the in-app surface reuses it). (b) **Pane closes mid-display**: the notification, its expansion and its reply field target a dead leaf; the toast path degrades gracefully, the new surface needs the same rule — die with the pane. (c) **Mute scope**: does muting an agent suppress Failed, the dot, the badge contribution? A muted agent that then fails is precisely where silence is wrong; mute must scope to the *notification*, never the dot or Failed. (d) **Mid-display hand-over**: Folio loses foreground while an in-app notification is up — re-raise as a system toast or die quietly? Today `desktop_reach` decides once, at arrival (`notify.rs:233-246`); the new surface needs the transition rule. **MUST-DECIDE-BEFORE-TICKET 4** (four one-line rulings in §12).

## 3. Reply in the notification (§11.7.3)

**F10 — Auto-Enter pastes into a draft the user forgot, and submits it in their name.** TUI agents keep unsubmitted input; the user leaves "please also fix the" half-typed in Claude's box and walks away. A notification reply lands at the caret and Enter submits *draft + reply* as one prompt the user never saw whole. There is no wire fact for "the input box is empty," so the gate cannot be evidence-based — and "what is not knowable is not shown" is the design's own rule. This also defuses the disarm/send race (an in-flight `PermissionRequest` arriving after the check) — with Enter, that race answers a prompt by proxy; without Enter, it leaves visible text. **BLOCKS-DESIGN.** Smallest change: the reply is a bracketed paste **without Enter** — "put this in the box" — and submission stays with the user on arrival. If the owner insists on Enter, it must be gated on a per-vendor "input known empty" fact that does not exist today; say that instead of pretending the gesture is safe.

**F11 — "Verifiably waiting for free text" is unverifiable for the OSC lane, and wrong for Elicitation.** The offer rule is: no Permission/Quota wait, and a turn boundary observed. Two breaks. (i) OSC-lane/hookless agents: an OSC 9 announcement supplies the "turn boundary," but a `Proceed? [y/N]` from a child program is invisible to the ledger — the reply (even without Enter, per F10) splices prose into a confirmation the user never saw; with Enter it answers it. (ii) `WaitKind::Elicitation` is not excluded by the rule, but elicitations are not necessarily free text — MCP elicitation is schema-driven and can be a choice list; pasting prose into a choice UI is garbage input. **MUST-DECIDE-BEFORE-TICKET 4.** Smallest change: the offer is per-vendor, not per-ledger-state — Claude Code and Copilot (hook-observed boundary, no standing wait) and Codex after `stop`; never for OSC-lane/hookless; Elicitation excluded until a recorded payload proves free text.

**F12 — Three implementation facts that must become ticket-4 acceptance criteria.** (i) Multi-line: `sanitize_paste` maps `\n`→`\r` and bracketing is conditional on the child's 2004 mode (`input.rs:796-832`, `main.rs:118756`) — into an unbracketed child a multi-line reply submits itself line by line; flatten to one line or refuse multi-line when 2004 is off. (ii) The send must route through the answer path (`AnswerKind::Paste` exists, `attention.rs:545`; `answer_attention`, `main.rs:25467-25494`) or the ledger never spends the wait and the notification's own state lies. (iii) The send must name `PasteTarget { tab, seat, incarnation }` and pass `live_paste_target` (`main.rs:830-835`, `101074`) or a restarted agent in the same seat eats the reply. **NOTE.**

## 4. Drag out → second interactive view (§11.7.4)

**F13 — The section's only open question is the chassis; the interactive half has five unruled functional questions and no precedent.** "Not new machinery" is true for rendering (`focus_thumb` is a read-only *text* re-projection at 10 Hz, `focus_thumb.rs:1092-1136`) and the chassis (`float.rs` has exactly two tenants, no terminal tenant, `float.rs:1373-1377`). Everything interactive is new, and each item below is a ruling, not a detail:

- **Keyboard/focus.** One keyboard per tab today; the 1004 truth is "seat is the tab's focused leaf ∧ owner is a shell" (`main.rs:18692-18719`). A float is not a shell owner, so by default the child hears `CSI O` *while receiving keystrokes* — in the exact machinery today's fix just touched. Does typing in the float flip `focused_leaf` (evicting the docked pane's caret), or does the float hold a second keyboard?
- **Scroll ownership.** One session, one scroll offset: does the float share it (scrolling the float scrolls the docked pane under the user's eyes) or hold a second view offset (new state, against the "one PTY one size" simplicity the section argues from)?
- **Mouse reporting.** The SGR/button latch is one per window (`main.rs:12920`); two views of one tracking program share a gesture slot, and coordinate translation needs the float's rectangle (`live_viewport_mouse_hit`, `main.rs:19626-19644`).
- **IME.** One composition per window, candidate list placed from the keyboard-holding pane's frame (`main.rs:18228-18663`, `62442-62468`); the float needs its own `ImeCaretSource` rung or candidates land on the docked pane.
- **Lifecycle.** `close_pane`/`close_tab` never touch the float host (`main.rs:55478-55581`, `40703-40810`), and a preview float whose source tab closes is *not* swept — `preview_tab_index` even falls back to the **active** tab (`main.rs:56497-56514`). That is a latent bug for previews; for a terminal float holding a live session reference it becomes a wrong-pane bug with a process attached.

**MUST-DECIDE-BEFORE-TICKET 7.** Smallest change: five one-line rulings appended to §11.7.4 (suggested: float focus flips `focused_leaf` and 1004 follows the keyboard, not the dock; the float shares the session's scroll offset; mouse forwards only from the view under the pointer — the latch is already per-gesture; IME places at the focused view's cursor; closing the source pane closes the float). Query replies (DA/DSR/colour/XTVERSION) are safe by construction — session-owned, drained to the one PTY regardless of views (`main.rs:37237-37291`) — and the section may say so.

## 5. The protocol and tiers (§6, §11.9, §12.4.7)

**F14 — The revision-checked write has no scope, no revision source, and no error shape.** Three gaps. (i) **Scope:** §12.4.7's last sentence ties the rule to web driving ("this binds when that ticket is written"), but ticket 8 ships acting verbs — open preview, split, type-into-created-pane — in 0.5. Either the revision rule binds them (then every addressable thing needs a revision *now*) or it doesn't (then the ruled copy "Folio refuses the stale write" describes 0.6 while the verbs ship in 0.5). (ii) **Source:** nothing on the wire or in the ledger is a monotonic revision today — no sequence numbers, no timestamps (`attention_wire.rs:92-102`); `screen_revision` exists per seat but answers render damage, not "the person touched this." And "touched" is undefined: if focus or looking bumps the revision, any navigation refuses every pending agent write (false-refusal storms); it must bump on state/content change only. (iii) **Shape:** the read-modify-write window is two CLI process spawns apart — seconds. Refusal must return the current revision so the retry costs one read, and that error belongs in §6's structured-error list. **MUST-DECIDE-BEFORE-TICKET 8.** Smallest change: rule that in 0.5 the revision rule binds exactly the mutating verbs ticket 8 ships; revision = a per-addressable-thing counter bumped on state change, never on focus; add the stale-write error to the protocol.

**F15 — The action log: no bound number, and its producers ship three tickets before it.** §11.9 says "size-bounded" with no size — an agent-day is thousands of actions, so the ticket needs the number (and whether the bound is per app or per window) under CONVENTIONS §十 rule 5. Sequencing: §2.5's counts are queries over this log, but the events that feed them (wait raised/cleared, notification shown, pane focused) are produced by tickets 2/4/5 while the log lands in ticket 8 — either a minimal append sink rides in ticket 2, or "count the interruptions" is not demonstrable in the first 0.5, which §2 lists as a headline claim. Also *unverified*: the claimed removal hook `folio --uninstall-cleanup --purge` — I found no evidence of such a flag before the tree became unavailable; if it does not exist, it is a ticket-8 deliverable, not a reference to existing behaviour. **NOTE.**

## 6. Quota (§4.5, §11.8)

**F16 — "Most-used first" has no store, and GLM F20 was never answered.** §4.5 rules the panel's ordering; §11/§12 never address persistence (GLM F20). Usage history and the per-account readings must survive restart, or "most-used first" is unimplementable as ruled — the action log is agents-only and holds no payloads, so quota readings are not actions and have no home. **MUST-DECIDE-BEFORE-TICKET 6.** Smallest change: persist the small `{account, window, percent, resets_at, fetched_at}` table §7 already names, plus a use counter, in the same data folder; or re-rule the ordering as "in-use first, then last-known within this run" and say readings are per-run memory.

**F17 — Poll-sourced Limited lags, and Done-vs-Limited precedence on one row is unruled.** Codex/Kimi readings arrive on 5–10 min polls, so a quota-stuck Codex turn actually *ends* (notify fires with a last message) and shows **Done** — with quotable words that say "you've hit your limit" — until the next poll moves the row to Limited. §11.5 rules Failed-beats-Limited but not Done-vs-Limited: if Limited replaces Done, the unread debt (the thing the badge counts) is hidden behind a quota fact. **NOTE.** Smallest change: state the poll-latency in §11.8's floor, and extend §11.5's precedence sentence — suggest the row keeps an unspent Done over Limited, with the quota fact living on the chip and panel.

**F18 — "In use" = a listed row burns silently for hand-started hookless agents.** §11.9 adopted GLM F16's "a listed row exists" definition without stating its consequence: with F5's recognition floor, a hand-started hookless agent (Kimi CLI — the vendor with the *most readable* quota) has no row, so its account is never "in use," so §4.5's 80 %/exhausted toasts can never fire while it burns quota, and its row can never show Limited. **NOTE.** Smallest change: one sentence in §11.9 — accounts whose only sessions are unlisted never toast; the panel still shows their readings on open.

**F19 — The marks pipeline lost its ticket.** Old §8 ticket 0 owned "the marks pipeline and `TRADEMARK.md` review"; the §11.10 table dropped it, but §4.9's rulings stand — official marks, `#p-claude` replaced *when this lands*, monochrome-follows-`currentColor`, per-vendor guideline review — and ticket 1 (Recent view) already draws "a small mono agent mark per row." No ticket owns the marks; ticket 1 has an unstated dependency on them. **MUST-DECIDE-BEFORE-TICKET 1.** Smallest change: fold the marks pipeline into ticket 1 (its first consumer) or restore it to ticket 2's foundations.

**F20 — A second installer hides inside ticket 6.** The Anthropic statusLine shim (wrap-or-refuse, §11.8) is the entire model/context/quota source for the flagship vendor, and it has the install/uninstall/trust shape that `attention_codex.rs` and `attention_copilot.rs` each treat as a careful slice of their own. Bundled into "chip, panel, toasts," ticket 6 is the biggest ticket in the sequence while reading as a UI ticket. **NOTE.** Smallest change: split it — 6a the statusLine lane (reader + wrap/refuse + account attribution), 6b the chip/panel/toasts consuming 6a and the Codex/Kimi readers.

**F21 — Cross-window ledger ownership for moved panes, and the badge's sum scope.** §11.3 made the rail application-wide; shipped features move panes and tabs between windows (`move_pane_to_new_window` `main.rs:79235`, `move_tab_to_window` `main.rs:76714`, drag handover). The ledger addresses panes as `Site { tab: usize index, seat }` (`main.rs:25362-25365`) — a positional index inside one window's runtime. A pane moved mid-wait: which window's ledger owns the wait, which badge counts it, does the wait survive (the capability rides the leaf; delivery scans leaves, `main.rs:25720-25724` — across windows or per window?)? And §12.2's "the badge is the sum of the panes' dots" — this window's panes or the app's? **MUST-DECIDE-BEFORE-TICKET 3.** Smallest change: two rulings — the badge sums its own window's dots (the rail carries the rest, per §11.3), and a moved pane's ledger state travels with its leaf, re-sited, same capability.

**F22 — What to cut, and testability.** Ticket 7 (drag-out) is the cut candidate for the first 0.5: it is "the one genuinely new mechanism," its chassis question is only a recommendation (§12.4.2), F13 lists five unruled functional questions, and nothing depends on it. The rest are each independently shippable and testable without a real agent: 1 (files column, synthetic paths), 2 (synthetic wire lines — the wire already has byte-level tests), 3 (ledger-driven), 4 (synthetic ledger events; reply acceptance needs a TUI child, and the repo already drives real PowerShell in tests), 5, 6 (a fake vendor child serving quota JSON), 8 (CLI against a live instance). **NOTE.** Smallest change: move ticket 7 to the "not in the first 0.5" row beside select-and-comment/web driving, or adopt F13's five rulings as its gating questions.

## 8. The owner's new question: select text in an agent's conversation, comment to that agent

**Do the two conflict? No.** Copy-on-select completes on mouse release (`finish_local_selection` → `should_copy_on_select_release`, `main.rs:96241`, `19866-19872`); the selection *persists* after release. A comment act that hangs off the persisted selection never touches the release gesture, so the clipboard behaviour is untouched.

**Cleanest functional model:**

- **Affordance:** an explicit act on an existing selection — a context-menu entry / small popover button on the selection, "Comment to agent ▸", listing this tab's agent rows (the rail already knows them), plus an optional keyboard chord. Not a modifier-on-release: that is a hover secret of exactly the kind the `⌄` lesson (§4.2) banned, and it would fight copy-on-select for the same gesture.
- **What is written:** the selected text in a fenced quote block, plus the pane's title as provenance — **no line references**. Scrollback lines have no stable coordinates (they shift under freeze/reflow), so a line number would be a guess, and guessing is what CONVENTIONS §一 forbids. Truncated at a stated bound (it travels as paste bytes, not wire payload, so the bound can be generous — but bounded).
- **No auto-Enter.** A comment is a composition aid, not an answer; the agent may be mid-turn, and in some TUIs Enter mid-turn is an interruption. This aligns with F10's recommendation for §11.7.3 itself: one write path, paste-only, submission always the user's.
- **Alt-screen:** with mouse reporting on, a plain drag is forwarded to the agent and selects nothing (`route_forwarded_mouse_button`, `main.rs:19737-19786`); Shift-drag already forces local selection (`main.rs:19746`), and `copyable_rows` already reads the alternate grid (`session.rs:8481-8495`). So the affordance works identically in alt-screen via Shift-selection, and writes into the same input box — subject to F11's evidence gate (never for OSC-lane/hookless agents).
- **Scrollback vs live:** selections already span frozen/staging/live via `ContentAnchor`, and `selection_text()` (`session.rs:8610-8640`) is the single source of the text — nothing new. Note that the paste scrolls the pane to live (`paste_text` already does); acceptable, but state it.
- **In the first 0.5? Yes, this variant.** It is ticket 4's write path minus Enter plus one menu row — cheap, and it serves the attention story directly: pointing at output is the cheapest form of precision. The preview/page element variant (old ticket 6 — pickers, file:line mapping, PDF rects) stays in 0.5.x as ruled. If the owner takes F10 (paste-only replies), the terminal comment and the reply become *one* mechanism with two entry points, which is the strongest argument for including it.

## UI suggestions (advisory only)

- With no Allow/Deny and no activity line, the one-line row's right edge is under-used; the turn clock could live there permanently, not only while Working.
- The expanded notification's reply field deserves a visible "paste only, you submit" hint if F10 is adopted — one glyph or placeholder, no sentence (§11.4).
- A muted agent could show a dimmed mark rather than a mute badge; the state word already carries the facts.
- Consider letting the notification's collapse corner host the drag-out affordance; a phone-style card suggests the gesture anyway.
- The sticky Waiting row (§12.4.1) could share the ask strip's 2 px `--warn` edge as its only ornament.
- In the glance card, "go there · stop" would read better as a verb pair with stop visually secondary.
- The quota chip's three-state colour (dim/warn/err) is a candidate for the same "one ring, one meaning" discipline as §12.3 — a gauge that is full-red only when everything is spent reads naturally.
- The Recent view's mono marks (ticket 1) will set the house style for vendor marks at small sizes before the rail does; rule its look first and let the rail inherit.
