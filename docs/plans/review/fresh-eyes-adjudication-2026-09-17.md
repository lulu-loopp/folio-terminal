# Adjudication of the three fresh-eyes reviews of the live decoration subsystem

Three independent whole-subsystem reads exist for this subsystem: `fresh-eyes-glm-2026-09-17.md`, its verification `fresh-eyes-glm-verify-deepseek-2026-09-17.md`, and `fresh-eyes-kimi-2026-09-17.md`. They disagree on one claim. This records the reading of the code that settles it, what two or more of them agree on, and what only one of them raises.

## Refuted: D1, "a DL or partial-scope scroll wipes every live record"

The first review's D1, and the "D1 — CONFIRMED" in its verification, are wrong. `apply_removed_rows` (session.rs:11050) builds `removals` from the row directives it is handed and returns `Ok(0)` at `if removals.is_empty()` (11084) *before* the `invalidate_all_live_decorations()` at 11092. Those directives come from the rule table in `crates/bt-term/src/lifecycle.rs`: its three non-catch-all rules all require `screen == Primary` and `scope == FullScreen`, so every alternate-screen removal, every `Partial` scope and every cause other than `NormalScroll`/`Resize` — which is every `CSI M` (`RemovalCause::DeleteLines`) and every non-top-anchored region scroll — falls through to `RowAction::Ignore` (lifecycle.rs:97-103) and contributes no removal. The wipe is reachable only for Primary + FullScreen + Resize-cause removals outside a resize epoch: Primary + FullScreen + NormalScroll sets `preserve_full_screen_scroll` (session.rs:10181), and a removal inside a resize epoch goes to `rebase_vendor_owned_rows` instead (10196). The third review states this outcome directly in its closing paragraph.

## Re-checked, and also not standing: the section-2 "stale alternate context under DL"

The first review's section 2 says a DL that removes a fence-bearing row leaves `alternate_detection_context` stale, because the context is advanced only in the NormalScroll + FullScreen arm (session.rs:10163-10178). The gating is as described; the conclusion does not follow. That context is the parser state immediately *before* grid row 0 — `live_initial_detection_context` hands it to the scan as the checkpoint for the first grid input (6056-6069) — so it models exactly the rows that have left the screen through row 0. A `CSI M` deletes rows in place and pulls the rest up; those rows never pass above row 0, and feeding them to the context would assert a fence that is no longer anywhere on the grid. A region scroll whose top is not row 0 is the same case. So there is nothing for the context to hear, and advancing it only on rows that leave through row 0 is the correct rule rather than a gap.

## Agreed by at least two of the three

Park/restore (`?1049h`/`?1049l`) destroys every live record and re-detects after a fresh stability interval, so leaving a full-screen program flashes the source of every formula on the primary screen. Primary idle has no off-band preservation at all, so a window-less primary repaint that moves a formula's rows drops the record outright. The off-band re-anchor ran on every feed turn with only an empty-queue early-out — fixed on this branch. A record removed for cause while a repaint window was open was projected back at that window's close — fixed on this branch. "Window open" is kept as both a flag and a snapshot, and different predicates read different ones. Two byte-identical blocks can never be re-anchored off-band, because `exact_live_source_match` requires the source to be unique on the grid.

## Raised only by the third review — UNVERIFIED

Off-band cap eviction at `MAX_OFFSCREEN_RECORDS` (`retain_offscreen_record`, session.rs:6810) drops the oldest record whatever its state, and evicting the last stale-pending record flips `has_pending_resize_relayout` and with it `offscreen_preservation_active` mid-gesture. A theme change drops both the artifact and the stale artifact, so an unchanged block shows source until its relayout lands. Every published frame rebuilds the whole grid's text through `schedule_live_artifacts` → `live_detection_context` even with no math anywhere on the screen. On the last of these: the memo this branch adds for the off-band question keys on the grid alone, while the arming question also depends on the per-row stability vector and each row's candidate signature, so gating it would need those in the key as well. Not implemented here; scheduled after the release.
