# 视频文件预览 —— 立项摸底（2026-08-26，只读，未改任何代码）

**这份文件不是方案，是账。** 它回答四个问题：这台机器上什么能播、这栋房子有哪些门要开、悬停卡上那张首帧从哪里来、一段视频在播的时候跟终端的其余部分怎么相处。每条断言带出处（`file:line` 或官方 URL）；拿不到一手证据的写「未验证」。

## 0. 先说三件已经被量过的事

立项之前必须知道：**这张单子在 2026-08-25 被开过一次，一半被否，一半落了地**（`docs/DESIGN.md:2973` §7.16）。那次不是猜的，是在本仓 release、隔离 `APPDATA` 的实机上量的，四张截图为证。

1. **顶层导航一个视频都播不出来。** 双击 `clip.mp4` 与 `screencast.webm`，座位开出来、头/脚/地址栏都在，正文是 `WebErrorStatus · ConnectionAborted` 的「did not respond」卡。**机理**：WebView2 没有浏览器 UI，对一个顶层媒体响应它没有 viewer，于是把它变成一次**下载**；而 `crates/bt-platform/src/webview.rs:1311-1331` 的 `DownloadStarting` 处理器**无条件** `SetCancel(true)`，导航因此以 `ConnectionAborted` 收场。PDF 之所以不同，是因为 WebView2 **自带** PDF 阅读器。
2. **同一份文件放在一张普通本地页里用 `<video controls>` 播得好好的**：有控件、有进度条、`0:06 / 0:06`；页上顺手打印的 `canPlayType` 是 `mp4=maybe webm=maybe m4v=maybe mov=`（空串）。**所以编解码没有任何问题，问题在托管形态。**
3. 因此 `preview::PAGE_EXTENSIONS` 停在 `[html, htm, pdf]`（`crates/bt-app/src/preview.rs:178`），并且**钉了两条红门**：`preview.rs` 的 `no_video_spelling_is_a_page_until_something_hosts_it_inside_one`，与 `crates/bt-app/src/main.rs:110115` 的 `a_video_takes_the_document_lane_at_every_door`（四扇门各一条断言）。这两条测试的存在意味着：**任何让视频进页道的改动都会当场红**，这是设计，不是障碍。

§7.16 ⑤ 已经把「唯一还开着的路」写死了：**本窗自己铸一张托管页，把视频当子资源交给它**——并列出六个必须由用户裁决的问题。本文档在这些之上补技术账，并**新增一条 §7.16 当时没有考虑的路线**（第 1.4 节 Media Foundation Media Engine），它绕开全部六问。

## 1. 格式与引擎

### 1.1 WebView2 的引擎身份

WebView2 Evergreen Runtime 与 Microsoft Edge 是同一套 Chromium 二进制：官方原文 "The WebView2 Runtime contains modified Microsoft Edge binaries"（<https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/browser-features>），且 "binaries for Microsoft Edge and the Evergreen WebView2 Runtime are **hard-linked together** when they are on the same version"、"The Evergreen Runtime is **preinstalled onto all Windows 11 devices**"（<https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/evergreen-vs-fixed-version>）。**推论：Edge 能播的，这一席就能播；不需要任何额外安装就有 H.264/AAC。**

### 1.2 容器 / 编码矩阵（Windows 11 stock，无任何额外安装）

| 容器 / 编码 | `<video>` 内联能否播 | 依据 |
|---|---|---|
| **MP4 + H.264 + AAC** | **能** | Edge 官方排障表 `H.264 (AVC) — Supported`（<https://learn.microsoft.com/en-us/troubleshoot/microsoft-edge/development/video-playback-issues>）；MDN 容器表 MP4/AVC/AAC = Yes（<https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Formats/Containers>）；**本仓实测** `canPlayType('video/mp4') = maybe`（§7.16 ①） |
| **WebM + VP8/VP9 + Opus/Vorbis** | **能** | MDN 容器表；**本仓实测** `canPlayType('video/webm') = maybe`，且 `screencast.webm` 在页内播出（§7.16 ①） |
| **`.m4v`** | **能** | **本仓实测** `canPlayType('video/x-m4v') = maybe`（§7.16 ①） |
| **AV1（WebM 或 MP4）** | **能，默认软件解码** | Chromium 以 dav1d 为默认 AV1 解码器（<https://chromium.googlesource.com/external/github.com/videolan/dav1d/+/HEAD/README.md>）；Edge 排障表 "AV1 \| Supported \| Hardware decode support depends on the device and GPU"。**不需要 Store 的 AV1 Video Extension**——那个扩展是给走 Media Foundation 的系统应用（照片、电影和电视）用的，浏览器自带解码器。 |
| **HEVC / H.265（MP4）** | **条件支持，默认不能指望** | Edge 官方排障表逐字：`H.265 (HEVC) \| Conditionally supported \| Requires a valid HEVC Video Extension and a working HEVC decoder path.`，并说明 "For HEVC (H.265) media, Edge relies on the Windows platform `MediaFoundationVideoDecoder` path."。修法是从商店装 HEVC Video Extensions（<https://apps.microsoft.com/detail/9n4wgh0z6vhq>）。免费 OEM 版与付费版是否等价：**未验证**（只有二级来源）。 |
| **MKV（Matroska）** | **不能** | Chromium 的媒体 MIME 白名单（`media/base/mime_util_internal.cc`）不含 `video/x-matroska`（<https://chromium.googlesource.com/chromium/src/+/master/media/base/mime_util_internal.cc>，子 agent 转述，**未逐字核对**）；MDN 容器表根本没有 Matroska 这一行。底层 FFmpeg 的 demuxer 与 WebM 共用，技术上能解，但容器识别层没开。**本仓未实测 `.mkv`**（§7.16 只测了 mp4/webm）。 |
| **MOV（QuickTime）** | **不能** | **本仓实测** `canPlayType('video/quicktime') = ""`（空串 = 明确不支持，§7.16 ①）；MDN 容器表 QuickTime 一行只列老版 Safari。这是本报告里唯一一条同时有官方文档与本机实测的否定结论。 |
| **AVI / WMV / FLV** | **不能** | 三者均不在 MDN 支持容器表，也不在 Chromium MIME 白名单中。 |

**推荐的准入表（如果走页道）**：`mp4`、`m4v`、`webm`。`mov` / `mkv` / `avi` / `wmv` **不进**，落回文档道那张诚实的「无法预览」卡——这正是原单子自己写的「能播的才进，播不了的仍落卡」。

### 1.3 `file:` 直开 vs 自铸一张页

**Blink 里确实有一个 `MediaDocument` 类**（`third_party/blink/renderer/core/html/media/media_document.cc`，<https://chromium.googlesource.com/chromium/src/+/refs/heads/main/third_party/blink/renderer/core/html/media/media_document.cc>）：它给顶层媒体响应合成一个 `HTMLVideoElement`，无条件加上 `controls` 与 `autoplay`，并把 `<source>` 指向文档 URL。

**但这条路在 WebView2 嵌入模式下不通，且这不是推测。** 本仓实机测量（§7.16 ①）：顶层 `.mp4` 与 `.webm` 都没有变成 `MediaDocument`，而是变成了一次下载，被 `DownloadStarting` 拦掉。**实测优先于源码阅读**：Chromium 有这个类不代表 WebView2 这个宿主会用它。

**结论与推荐：只能自铸一张 HTML 托管页。** 除了「实测只有这条能走」以外，自铸还买到四样东西：

1. **外观可控** —— `MediaDocument` 不执行任何脚本、不接受任何配置，`controls`+`autoplay` 是硬编码的；而本产品对每个表面的定妆有自己的规矩（`docs/DESIGN.md` §7.1.5b 起的整条 UI 线）。
2. **能读到时长与进度** —— 但注意：`crates/bt-platform/src/webview.rs:1078` 与 `:1090` 把 `IsWebMessageEnabled` 与 `AreHostObjectsAllowed` **双向关死**（「a local page opened out of the files column is read, and nothing in this product offers it an object, a method or a channel」）。页要把 `duration` / `currentTime` 报回宿主，就得开其中一扇门——**这是一条安全纪律的改动，属于必须裁决的事**，不是实现细节。
3. **右键菜单已经是关的** —— `webview.rs:1104` `SetAreDefaultContextMenusEnabled(false)`，所以 `<video>` 自带的「下载 / 播放速度 / 画中画」右键菜单不会冒出来；要不要这些能力得自己在页里做。
4. **失败有自己的话说** —— 一份编码不认识的 mp4，页可以画自己的一行字，而不是把浏览器的错误卡端到用户面前。

**壳页放哪里**：目前 `CreateCoreWebView2EnvironmentWithOptions` 传的是 `None::<&ICoreWebView2EnvironmentOptions>`（`webview.rs:750-757`），**没有** additional browser arguments，**没有** 自定义 scheme 注册。所以可选形态是（a）写一份临时 `.html` 到 UDF 旁边、由本进程管清理；（b）`SetVirtualHostNameToFolderMapping`。注意 §7.14b 曾**否决**过 (b)，但否决理由是「它的前提（WebView2 读不了 `file:` 文档）不成立」，**不是原则性反对**；用在这里前提不同（这里要的是同源，不是可读性）。`data:` URL 壳页**不可行**：不透明源加载不了 `file:` 子资源。以上三条形态的可行性**均未在本机实测**。

### 1.4 第四条路：不用浏览器（本节是 §7.16 没有考虑过的）

Windows 自带 **Media Foundation Media Engine**，它就是 HTML5 media element 模型的 COM 版：`IMFMediaEngine` 的方法逐个映射到 `HTMLMediaElement` —— `Play`/`Load`/`SetSource`/`GetDuration`/`CanPlayType` 官方原文都写着 "corresponds to … of the HTMLMediaElement interface in HTML5"（<https://learn.microsoft.com/en-us/windows/win32/api/mfmediaengine/nn-mfmediaengine-imfmediaengineex>，Remarks：「The IMFMediaEngine interface contains methods that map to the HTML5 media elements」）。它有三种模式：frame-server（交出未压缩帧）、rendering（自己渲染音视频）、audio-only。

关键在于 `IMFMediaEngineEx::EnableWindowlessSwapchainMode` + `GetVideoSwapchainHandle`（同上 URL；<https://learn.microsoft.com/en-us/windows/win32/api/mfmediaengine/nf-mfmediaengine-imfmediaengineex-getvideoswapchainhandle>）—— **这栋房子已经有一整套 DirectComposition 视觉树**（`Win32_Graphics_DirectComposition` 已启用，`crates/bt-platform/Cargo.toml:41`；`WebHost` 的每个 pane 就是这样摆的）。`IDCompositionDevice::CreateSurfaceFromHandle` 收一个由 `DCompositionCreateSurfaceHandle` 造出来的句柄（<https://learn.microsoft.com/en-us/windows/win32/api/dcomp/nf-dcomp-idcompositiondevice-createsurfacefromhandle>）。

**「Media Engine 的 windowless swapchain 句柄可以直接喂给 `CreateSurfaceFromHandle`」这条配对，官方文档没有明写——未验证，需要一次 spike。** 但如果成立，它的价值很大：

- **绕开全部六问**：没有壳页，所以没有「地址栏显示什么」「`session.json` 存哪个」「`Mint::path_and_tail_of_file_url` 的反函数性质还成不成立」这些问题——视频就是一个文件，走文档道的一个新 view，跟图片、跟 git graph 一个待遇。
- **不动 `PAGE_EXTENSIONS`，两条红门一条不红。**
- **不新增一个包**（`windows` crate 加 feature，见 §3.2）。
- 容器覆盖面**不同**：MOV 走 MF 的 MPEG-4 source 是能读的（见 §3.3），WebView2 不能——但 MKV 两边都不行。

代价也要说清楚：那是**自己实现一个播放器的外壳**（播放/暂停/进度条/音量/全屏/键盘），而页道方案里这些是 `<video controls>` 白送的。**这是本单最大的一处取舍，建议由用户裁。**

（如果将来真要「在浮窗里播」这样的动词，正确的位置是 pane 头的 `⌄` 菜单，不是文件行菜单——见 memory 的 ⌄ 菜单裁决。）

### 2.5 地址判决对 `.mp4` 路径现在判什么

`crates/bt-app/src/webhost.rs:1069` `judge_address(input, engine)`：

1. 空 → `Draft`
2. `local_page_path(trimmed)` → `LocalPage(path)` —— 这一步问的就是 `preview::path_names_a_page`（`webhost.rs:1091-1096` 的注释：「`preview` owns "is a file with this name a page"」）
3. 否则走 `address_bar()` 的 scheme 判决

**`D:\shots\clip.mp4` 落在第 3 步，而 `webnav::classify_scheme` 会把 `D:` 读成一个未知 scheme 并拒绝** —— 所以今天在地址栏里敲一个 `.mp4` 路径，得到的是 `AddressVerdict::Refuse`，字段画红线。这与 `webhost.rs:4772` 那条已有断言一致：`judged(r"D:\Developer\notes.md") == AddressVerdict::Refuse`。

**推论**：只要视频进了 `PAGE_EXTENSIONS`，地址栏**自动**开始接受 `.mp4` 路径 —— 一个字都不用改，而且这正是 §7.16 ⑤ 里「地址栏显示什么」那一问的来处。如果走 §1.4 的原生路线，地址栏一切照旧（视频不是页，就不该出现在页的地址栏里）。

### 2.6 终端里裸路径识别是否已把视频扩展名算「文件」

**已经算了，一行都不用改。** `crates/bt-transcript/src/paths.rs:1298` `PrintedPathLinks::candidates_in`：

```rust

```

`accepted` 闭包是 **`|_| true`** —— 没有任何扩展名白名单。绝对路径（`detect_absolute_path_candidates`，`paths.rs:195`）与 `file://` URI（`paths.rs:629`）同样无白名单。是否画下划线只取决于 `verdicts` 里那个 bool（`paths.rs:1320` `is_verified`），也就是 **worker 问过磁盘、磁盘说在**（`main.rs` 的 `MathWorkerRequest::VerifyPath` → `bt_term::path_exists`）。这正是 2026-08-20「裸文件路径识别扩全部文件，存在才 verified」那条裁决的落地。

**所以**：终端里印出的 `D:\shots\clip.mp4` 今天已经是一条可点的链接；点它（「点=留窗内」裁决）走 `open_preview_at` → `Document` 道 → 「这种文件类型没有预览」卡。这张卡就是本单要换掉的东西。

## 3. hover 卡缩略图（首帧）

### 3.1 三个候选的判决

**(a) WebView2 离屏 `<video>` seek 后 canvas 截帧 —— 否，且理由已经在本仓量过。**

`crates/bt-app/src/web_thumb.rs:32-38` 的模块头（W2 片⑥ 的落账）：

> **A hidden WebView never completes a capture.** Measured on 2026-08-20, re-measured twice on 2026-08-22, and re-measured again at card scale by gate 11: the completion handler is simply not called.

**(b) 纯 Rust 解码 —— 没有。诚实地说，一条都没有。**

### 3.2 `windows` crate 的 feature 账（问题里点名要验证的那条）

- 已启用 34 个 feature（`Cargo.toml:18-101`）。逐项核对：
  - `Win32_Media_MediaFoundation` —— **未启用**
  - `Win32_Media` —— **未启用**

### 3.3 Media Foundation 能读什么

官方权威表 [Supported Media Formats in Media Foundation](https://learn.microsoft.com/en-us/windows/win32/medfound/supported-media-formats-in-media-foundation)（**注意：该页最后更新 2018-05-31，只覆盖出厂内建，不含后来的 HEVC/VP9/AV1**）：

| 容器 / 编码 | MF 免加装 | 与 WebView2 的差异 |
|---|---|---|
| MP4 / H.264 / AAC | 内建 | 一致 |
| **MOV** | **内建** —— `.mov` 与 `.mp4`/`.m4v`/`.m4a` 同属 MPEG-4 File Source | **不一致**：WebView2 明确不能（`canPlayType=""`） |
| AVI、WMV/ASF | 内建 | 不一致：WebView2 不能 |
| HEVC | 需 Store 的 HEVC Video Extensions（[H.265 / HEVC Video Decoder](https://learn.microsoft.com/en-us/windows/win32/medfound/h-265---hevc-video-decoder)，最低 Windows 10） | 一致（Edge 本来就走 `MediaFoundationVideoDecoder`） |
| VP9 | **未验证** —— 官方 medfound 没有 VP9 解码器参考页；业界说法是 Store 的 VP9 Video Extension | 不一致：WebView2 自带 |
| AV1 | **未验证** —— 同上，业界说法是 Store 的 AV1 Video Extension | 不一致：WebView2 自带 dav1d |
| **MKV / Matroska** | **不在官方容器表里**（该表只有 3GP/ASF/ADTS/AVI/MP3/MPEG-4/SAMI/WAVE 八种）。第三方要专门写 Matroska Media Source 才行，这反证系统没有内建。**未验证到官方否定性文档，但缺席的证据链可靠。** | 一致：两边都不行 |

**这个错位本身是一条要写下来的规矩**：能画首帧的集合与能播的集合**不相等**。`.mov` 会画得出首帧但播不了；`.webm`/AV1 播得了但首帧未必画得出。悬停卡承诺的是「看一眼」，双击承诺的是「播」，两者用不同的表是**诚实**而不是不一致——但必须显式写下来并各钉一条红门，否则下一个人会以为其中一张表漏了。

### 3.4 抓帧的 API 路径

标准链条（**必须在 `crates/bt-platform` 里实现**：`unsafe_code = "deny"` 是 workspace 级的，根 `Cargo.toml:43`，`bt-platform` 是唯一的破例，`crates/bt-platform/Cargo.toml:103-104`；而 `bt-app` 根本没有 `windows` 依赖，`crates/bt-app/Cargo.toml:18-60`）：

1. `CoInitializeEx` → `MFStartup` —— [Initializing Media Foundation](https://learn.microsoft.com/en-us/windows/win32/medfound/initializing-media-foundation)：「For every call to **MFStartup**, your application must call **MFShutdown**.」
2. `MFCreateSourceReaderFromURL` —— <https://learn.microsoft.com/en-us/windows/win32/api/mfreadwrite/nf-mfreadwrite-mfcreatesourcereaderfromurl>：「You must call CoInitialize(Ex) and MFStartup before calling this function.」
3. 建 reader 时设 `MF_SOURCE_READER_ENABLE_VIDEO_PROCESSING = TRUE`，然后 `SetCurrentMediaType` 要 `MFVideoFormat_RGB32`。**官方文档正好点名了这个用例** —— <https://learn.microsoft.com/en-us/windows/win32/medfound/mf-source-reader-enable-video-processing>：

   > "If this attribute is TRUE, the source reader can perform … Conversion from YUV to RGB-32 … These operations are performed in software, and are not optimized for playback. **This feature is intended for applications that process a small number of frames—for example, to create a video thumbnail**…"

   同页 Remarks 的约束：开了它，`MF_SOURCE_READER_D3D_MANAGER` 与 `MF_READWRITE_DISABLE_CONVERTERS` 必须是 FALSE。
4. `IMFSourceReader::SetCurrentPosition` seek —— <https://learn.microsoft.com/en-us/windows/win32/api/mfreadwrite/nf-mfreadwrite-imfsourcereader-setcurrentposition>：**不保证精确**，通常落到目标之前最近的关键帧，要精确得自己 `ReadSample` 往前走。
5. `ReadSample` → `IMFSample::ConvertToContiguousBuffer` → `IMFMediaBuffer::Lock` → 字节 → 交给 `bt-app` 一块 RGBA。
6. **官方参考实现就叫 VideoThumbnail**：<https://learn.microsoft.com/en-us/windows/win32/medfound/videothumbnail-sample>，源码 <https://github.com/microsoft/Windows-classic-samples/blob/main/Samples/Win7Samples/multimedia/mediafoundation/VideoThumbnail/Thumbnail.cpp>。

**取哪一帧**：不要取 0.0 秒——很多视频第一帧是黑场。VideoThumbnail 示例的做法是 seek 到片长的某个比例。**取 1/10 处还是固定 1 秒，是产品决定，建议在片里定死一个数并写进注释。**

**耗时**：Microsoft Learn 一个数字都没给。**未验证，必须自己基准**。参照物是本仓已有的两个数：`CapturePreview` 的同步 ask 是 0.115 ms、引擎侧等待 84 ms、PNG 解码+重采样 18 ms（`web_thumb.rs:16-24`）；PDF 首页光栅走的是同一条 decoration worker。

### 3.5 线程与 apartment —— 本片唯一的架构新东西

官方 [Media Foundation and COM](https://learn.microsoft.com/en-us/windows/win32/medfound/media-foundation-and-com)：

> "Work queues always have multithreaded apartment (MTA) threads … Therefore, it is recommended to call **CoInitializeEx** with the **COINIT_MULTITHREADED** flag."
> "Media Foundation does not marshal single-threaded apartment (STA) objects to work queue threads … Applications will have an easier time if they interact with Media Foundation from an MTA thread, but it is possible with some care to use Media Foundation from an STA thread."

**本仓现有的三处 `CoInitializeEx` 全是 STA，且全在事件循环线程上**：`crates/bt-platform/src/lib.rs:3150`（Taskbar）、`:3453`（Notifier）、`:4837`（文件选择器）。它们的 SAFETY 注释都写着「runs on the window's own event-loop thread, which is the thread that owns the HWND and the apartment」。

所以本片会引入**这栋房子里没有的东西：一条后台线程 + `COINIT_MULTITHREADED`**。这不是问题，但要说清楚谁负责配对 `MFShutdown` / `CoUninitialize`（官方原话：「decide up front which thread uses Media Foundation … and who owns the corresponding shutdown responsibilities」）。

**落在哪条 worker 上**：现成的是 `MathWorkerRequest` 那条 decoration lane（`main.rs:960-1010`），PDF 首页就在上面（`main.rs:864` `raster_peek_page` → `pdf::first_page`）。可以照抄，也可以像 `preview.rs` 模块头写的那样另起一条（「a slow file cannot sit behind a slow directory」）。**建议另起一条**：一段一小时的 4K 视频的 seek 可能是几百毫秒，把它排在公式渲染和 PDF 光栅前面会拖慢两个已经很快的东西；而且 decoration worker 那条线程今天不是 MTA，把它整条改成 MTA 会影响它上面所有其它任务的 COM 语义。

### 3.6 卡的形状 —— 已经有一个逐字同构的先例

`.pdf` 那张卡（2026-08-25）是：`PeekBodyKind::Facts` → 请求 `MathWorkerRequest::PeekPage { path, fit, known }` → worker 上 `raster_peek_page`（`main.rs:864`，带 mtime 缓存，`PeekPageOutcome::Unchanged` 省掉重画）→ `DecorationWorkerCompletion::PeekPage` 回到事件线程 → 卡上画首页 + 两条事实。`raster` 是 `Option`，`None` 就画空底 + 那两行仍然为真的字（`main.rs:854-856` 的注释：「which is the card's whole degradation path」）。

视频卡：`PeekBodyKind::Frame` → `MathWorkerRequest::PeekFrame { path, fit, known }` → `bt_platform::video_first_frame(path, w, h) -> Option<Raster>` → 同一条回程。**两条事实**建议是：**时长** 与 **分辨率**（都能从同一次 `IMFSourceReader` 打开里顺手拿到：`MF_PD_DURATION` / `MF_MT_FRAME_SIZE`）。`None` 的降级路径与 PDF 逐字相同——一段 MF 读不了的 `.mkv` 画空底加两行字，而不是崩、也不是回到「无法预览」。

## 4. 播放与终端的关系

以下每条都对**页道方案**（§1.3）与**原生方案**（§1.4）分别成立与否。

### 4.1 音频

- **页道**：`ICoreWebView2_8` 提供 `get_IsMuted` / `put_IsMuted` / `get_IsDocumentPlayingAudio` 与两个 changed 事件（<https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/win32/icorewebview2_8>，自 1.0.1072.54 起）。本仓已经在用 `ICoreWebView2_4`/`_12`/`_15`/`_18`/`_28`（`webview.rs:1267/1311/1356/1379/1827`），**加 `_8` 是同一种 cast，零新依赖**。
- **切到别的 tab 会怎样**：后台 tab 的页被 `SetIsVisible(false)`（§7.8 ⑧；`webview.rs:1655`）。官方对 `IsVisible` 的说明是：「If `IsVisible` is set to `FALSE`, the WebView2 is transparent and is not rendered.」并且「There are CPU and memory benefits when the page is hidden. For instance, Chromium has code that throttles activities on the page like animations」（<https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/win32/icorewebview2controller>）。**文档只说不渲染、会节流，一个字都没说停音频 —— 所以要假设它还在响。未验证，必须实测。** 这是一条真实的产品风险：切走一个 tab 之后终端里还在放声音，而那个 tab 你看不见。
- **原生方案**：`IMFMediaEngine::Pause` / `SetMuted` 是我们自己调的，没有黑盒。
- **哪种是对的行为，要裁**：切走就暂停？还是继续放（像浏览器 tab）？还是继续放但在 tab 上挂一个「正在响」的标？（本产品已有一整套 tab 状态点的分类学，`DESIGN.md:924` §7.1.5b 七态，`IsDocumentPlayingAudio` 天然可以接到那套上去。）

### 4.2 焦点与键盘

- 页道下键盘按 `webhost::claimable_chords`（`webhost.rs:3465` 附近）分配：页拿到焦点时本窗认领哪些和弦是一张表。`Space` 今天不在认领表里，所以它会到页里 —— `<video>` 的 `Space` = 播放/暂停，**白送**。
- 但**「任何信息或操作不得只经 hover 可达」以及键盘等价路径**是 §7.1.5 ⑤ 的硬约束，播放/暂停/seek 必须有键盘路径。页道白送一套（浏览器的 `<video>` 默认键位）；原生方案要自己写一套并进 `shortcuts.rs` 的表。
- `AreBrowserAcceleratorKeysEnabled` 与全屏：`F11` 属于浏览器加速键。本仓没设过这个开关（`webview.rs` 的 `configure()` 里只设了五项）。视频全屏要不要走 `F11`、走 fullscreen API 还是走本产品自己的聚焦模式，**未决**。

### 4.3 `Ctrl+滚轮`

`webhost.rs:2870-2874` 的原话：

> **`Ctrl`+wheel is empty everywhere else in this window** — there is no type-size zoom in this product and a picture zooms on the bare wheel — so nothing is being taken from anything by claiming it over a page.

页道下 `Ctrl+滚轮` 会缩放整张托管页（连带缩放 `<video>` 的显示尺寸），语义上说得过去但有点怪：用户想缩的是画面。**图片是裸滚轮缩放**（同一句注释），视频与图片更近，**建议裸滚轮 = 缩放画面**，与图片对齐；`Ctrl+滚轮` 在页道下是白送的、在原生方案下是空的。要裁。

### 4.4 注意力块

**不相干，而且是结构上的不相干。** `crates/bt-app/src/attention.rs` 全文没有一处提 web/page；注意力的信号源是 A1 的 `OSC 1337;RequestAttention` 与 A3 的管道（`DESIGN.md:924` §7.1.5b 的勘误段），全部来自**会话**。一段视频不是 agent，不产生 turn-end，不进队列。**唯一需要写下来的是「不进」这件事本身**（照 §7.16 ③「这是一个钉着的否，不是一处空白」的做法钉一条）。**但音频是个例外**：如果采纳 4.1 那条「在 tab 上挂正在响的标」，那就碰到了 §7.1.5b 的状态点分类学 —— 那套有「一点一断言、按严重度取一」的规矩，新增一个通道要按那套规矩来，不能自己发明一个点。

### 4.5 撕出浮窗

**已经通了，不用做。** §7.14a/§7.14b（`DESIGN.md:2985` 起）刚落地了「页跟着 pane 进浮窗」：`main.rs:5028` `a_page_still_has_a_pane(floated, seat_stands, replaced)`，配合 `main.rs:72006-72012` 的注释——

> **A page that has been popped out has not lost its pane; it has taken it with it**（§7.14a）。

所以页道方案下撕出去自动继承。原生方案下视频是 `PreviewView` 的一个变体，走的是 document/picture 那条已经支持浮窗的路。**两条路都不欠这一项。**

### 4.6 pane 关闭必须停播放（不持尸）

**结构上已经保证了，页道方案零成本。** 链条：

`main.rs:71987` `advance_web_page` 每一轮算出 `orphaned`（座位离开树、或有别的东西落在它上面；判据是 `main.rs:5028` `a_page_still_has_a_pane`）→ `WebSeat::close`（`webhost.rs:3059`）→ `WebHost::close`（`webview.rs:2037`）→ `controller.Close()`。而官方对 `ICoreWebView2Controller` 的说明是「if all references to the CoreWebView2Controller go away, the WebView is closed」。**引擎没了，播放当然停了，不会有尸体。**

**原生方案要自己保证**：`IMFMediaEngine` 有 `Shutdown`，drop 的时候必须调，且必须与 `MFShutdown` 分清层级。这是原生方案要新写的一条纪律，也是它比页道贵的地方之一。

**还有一个页道方案独有的坑**：`SetIsVisible(false)` 的 tab 切换不是关闭。切走一个正在放视频的 tab，引擎还在，`advance_web_page` 不会把它算成 orphaned（它的座位还在树上）。这正是 4.1 那条音频风险的机理。

## 5. 最小可交付切片

### 5.1 建议：片 ①「视频有一张脸」—— 不碰页道，不需要六问的任何一问

**范围**：

1. 清掉 `main.rs:4943-4951` 那段与代码矛盾的注释（见 §0.1）。
2. `preview.rs` 新增 `VIDEO_EXTENSIONS` 与 `PreviewFtype::Video`，chip 上印 `video`。表的内容按 §3.3 的 **MF 覆盖面**定（`mp4`/`m4v`/`mov`/`webm`/`mkv` 都进，因为进这张表只意味着「本窗认得这是一段视频」，不意味着能画出首帧、更不意味着能播）。
3. `bt-platform` 新增 `Win32_Media_MediaFoundation` feature 与一个函数：`video_first_frame(path, fit_w, fit_h) -> Option<VideoGlance>`，带回**一张 RGBA 首帧 + 时长 + 分辨率**。三样一次打开就都有了。
4. 新起一条 worker lane（§3.5），照 `raster_peek_page` 的 mtime 缓存形状（`main.rs:864`）。
5. 悬停卡新增 `PeekBodyKind::Frame`，与 `Facts` 同构：首帧 + 两条事实；`None` 时空底 + 两行字。
6. 预览 pane 上，`PreviewFtype::Video` 从 `Refused(Type)` 改成同一张首帧卡的大号版本（首帧 + 时长 + 分辨率 + 已有的 `Open in default app` 按钮），**不播**。

**为什么这是「一片」**：它一个字都不碰 `PAGE_EXTENSIONS`、不碰 `preview_open_lane`、不碰 `Mint`、不碰 `session.json`、不碰地址栏、不碰 `↗`。§7.16 ⑤ 那六个必须用户裁的问题**一个都不需要回答**。两条红门（`no_video_spelling_is_a_page…` 与 `a_video_takes_the_document_lane_at_every_door`）**一条都不红** —— 视频仍然走文档道，只是文档道上多了一张有内容的脸，正如 `.pdf` 在文档道之外多了一张 `Facts` 脸。

**它值不值得单独上**：值。今天鼠标停在一个 `.mp4` 上得到的是「这种文件类型没有预览」；片 ① 之后得到的是一张能认出这是哪段片子的画面 + 多长 + 多大。这就是 hover 原则（§7.1.5 ⑤「查询 hover 化」）说的那种东西。而且它是**两条播放路线的公共前置**：无论最后走页道还是原生，首帧与时长都要有。

**它买不到的**：不能播。这必须在验收时说清楚，不能让人以为片 ① 就是「视频预览」做完了。

### 5.2 片 ②（需要用户先裁）：能播

两条路，**先裁路线，再排片**：

- **路线 A（页道 + 自铸壳页）**：要回答 §7.16 ⑤ 的六问，外加本文档新提的三条 —— 壳页放哪/谁清（§1.3）、`IsWebMessageEnabled` 要不要为进度条开一条缝（§1.3）、后台 tab 的音频怎么办（§4.1）。工作量集中在「身份」而不在「播放」，因为播放是 `<video controls>` 白送的。
- **路线 B（Media Foundation Media Engine + DComp）**：绕开全部六问（视频不是页，所以没有页的身份问题），但要先做一次 spike 验证 `EnableWindowlessSwapchainMode` 的句柄能不能进 `IDCompositionDevice::CreateSurfaceFromHandle`（**未验证**，§1.4），然后自己造一整套播放控件与键盘表。

**我的倾向：先做片 ①，同时用一天做路线 B 的 spike。** 理由是路线 B 如果成立，它把「视频」这件事整个留在文档道里，与图片、与 git graph 同构，不需要动本产品最贵的那套东西（页的身份、地址栏、mint、session）；而路线 A 的六问每一问都是一次裁决 + 一次落账。但这条判断依赖一个未验证的技术前提，所以是 spike 而不是结论。
