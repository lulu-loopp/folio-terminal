# M1.8 resize 视觉稳定性

基线为 `cd9f1e9`。本片只收紧 resize 的 viewport、收割、合成与呈现边界，不回退 M1.7 的
vendor 单一所有权、最终尺寸 coalescing、矩形防御和 WT 级内容语义。

## 真机 trace 定性

原始 `BT_RESIZE_TRACE` 共 14 个事务、876 次本地 resize、947 次 frame publish；3 次非空
harvest，宽度分别为 `[21]`、`[14,14,14]`、`[15]`。这证明 S3 确实经过窄宽 vendor harvest，
但旧格式只记录 harvest 宽度与 frame 矩形，未记录 WRAPLINE、viewport 状态、layout width 或
cursor 投影，因此不能诚实地区分 S4 的“合成错拼”和“投影错宽”。M1.8 扩展 trace：harvest
记录每行 `continues`；frame 记录 layout width、Bottom/Anchored、offset 与 cursor。确定性双回放
同时断言 `layout_columns == columns`。

## 实现边界

- viewport 是显式 `Bottom | Anchored(ScrollAnchor)` 双态。只有滚动 API 能从 Bottom 进入
  Anchored；resize/reflow 只按 `ContentAnchor` 的逻辑行与行内 offset 重找视觉子行。staging
  定稿通过 `HistoryDocument` 的真实 G3 mapping 迁为 history anchor，不做文本匹配。
- `Resized` 不再先把上一张网格主动画到新 swapchain。renderer 先准备新投影 frame，紧邻
  acquire/submit 才配置 surface；app 另有运行时门拒绝尺寸不等于新 grid 的待呈现 frame。
- 同一次 `finish_resize_transaction` 返回的是一个有序 vendor 网格批次，批内使用 normal capture
  按 WRAPLINE 重接；批尾调用 `finalize_all_candidates`，所以任何延续都不能跨到下一批。
- `ViewportFrame::validate_shape` 现在把 `layout_key.width_cells == frame.columns` 作为硬门。
  prompt echo、cursor、IME/renderer 均消费同一 `ViewportFrame`；Bottom 下不会再把冻结副本与
  live echo 因 resize 制造的 offset 拼在同一画面。

## 自动回归

- 六行内容的 shrink/harvest/widen 全程保持 Bottom、offset 0、无 `N lines below`。
- Anchored 宽→窄后逻辑 offset 不变，并仍落在顶部视觉行；staging anchor 用 G3 mapping 定稿。
- `narrow → harvest → widen` 验证同批两个 WRAPLINE fragment 定稿为一个可重排逻辑行；独立测试
  验证批尾强制切断。
- 收割后 prompt echo、cursor cell anchor、frame/layout width 一致；扩展 trace 双次回放逐事件相等。
- app 的 atomic-present gate 明确拒绝旧 grid frame，renderer 的 layout-width 门明确拒绝错宽 frame。

协调者的真拖连续截屏（锚线位移和帧间字宽）仍是最终人工 oracle；自动测试不冒充像素终审。

## R2：极限 shrink → grow 后冻结/live 接缝

2026-07-18 的新 trace 把此前未覆盖的两行初始内容场景定性为本地网格与 ConPTY 最终 viewport
的 resize 路径分叉，而不是一次被丢弃的 ConPTY 重绘：

- `transaction 3` 从 `104×26` 经 66 次本地尺寸变化，最低到 `11×3`，最终停在 `30×9`；
  vendor mutable tail 最高 7 行，最终仍有 2 行。
- ConPTY 因 final-size coalescing 只收到一次 `30×9`；从 `PtyResizeRequest` 到
  `TransactionEnd` 没有 `PtyChunkArrived`，sidecar 1.25 没有 grow 回填 VT 批次可供丢弃。
- 旧实现收割 `widths=[30,30], continues=[true,false]`。按同一尺寸序列确定性回放，这两行是
  `Did not find path entry D:\App` 与 `\Base\anaconda3\bin`；它们本应利用 final viewport 的
  空白容量留在 live grid。收割后一次向上滚动的最大 offset 恰为 2；被移出 viewport 的两个
  live 尾行全空，所以这就是错误 `2 lines below` 的来源。
- 收割前 cursor 为 `(1,9)`；在 final-width 上重新评估 final-height 后 cursor 为 `(3,9)`，与
  完整四个视觉行的 viewport 组成一致。随后 PowerShell recall 继续写在提示符的同一逻辑行。

最终 PTY resize 边界现在先在 vendor 内把 transaction history 全部拉回一个临时扩展 viewport，
再仅按最终高度收缩一次。这不匹配文本，也不猜测 shell 内容；唯一依据是 vendor 自有 row、
WRAPLINE 和 cursor。归一化后仍不适配的行才允许在 quiescence 时进入冻结转录。归一化会立即
发布一帧，并写入 `VendorReconcile { history_before, history_after, cursor_* }` trace 事件。

`N lines below` 另加独立防线：位移出去的纯空 live 尾行只是矩形容量，不计作隐藏内容；若
content rows below 为 0，则不显示状态文案。

## 拖窗预算钉：为什么它不再用毫秒计价（resize-pin-audit 片，2026-08-19，已落地）

`resize_drag_200_frames_stays_within_the_sparse_and_full_budget` 是 `6133230` 一起加进来的。
那次提交在**每一个 sparse 拖窗帧**上放了新工作（空白尾扫描 + 第二次
`reconcile_resize_transaction_to_viewport`），同时从拖窗路径上**拿掉**了三件必须不许回来的
每帧工作：vendor history 的 `Vec<Row<Cell>>` 整份 clone、为根本不在屏上的 semantic input
region 重建的整屏 `String`、以及对没人 stage 过的行做的 staging retain。钉子挡的是这一族。

原来的口径是 200 帧的**墙钟总和**（sparse 75 ms / full 50 ms / 合计 120 ms），三个数字除了
这条测试本身没有任何地方记过，是一次单跑测量被冻成的常量。它不诚实：

| 条件（同一台 24 核机器，同一个二进制，2026-08-19） | sparse 总和 min–p50–max | 结果 |
|---|---|---|
| 单独跑 ×20 | 40.1 – 41.4 – 43.4 ms | 20/20 绿 |
| 整个 bt-term 套件里 ×20 | 63.8 – 71.4 – 103.5 ms | **8/20 红**（机器是空的） |

full 臂 0/20 红、合计臂 1/20 红——吵的只有 sparse 一条。把每帧单独计时后，方差的位置很清楚：

| 条件 | 帧 p50 | 帧 p90 | 帧 p99 | 帧 max |
|---|---|---|---|---|
| 单独跑 | 352–360 µs | 415–525 µs | 515–1100 µs | 0.80–1.41 ms |
| 套件内 | 235–377 µs | 783–1147 µs | 1.54–2.50 ms | 1.54–4.60 ms |

**方差全在尾巴上**，而 200 个样本求和会把整段拖窗里 OS 发出的每一次抢占都收进来，当成代码
做的功报出去。套件内的中位数甚至常常**更快**（235 µs vs 355 µs）——忙机器是升频的机器，空
机器上一条孤立的测试线程跑在降频的核上；总和照样更差，因为它由尾巴支配。这就是“总和不是在
量算法”的直接证据。19 路 `cargo build` 压着时，sparse shrink 帧中位数还会再翻到 1006 µs，
所以**任何绝对墙钟数字在这台机器上都稳不到 1.8 倍以内**。

不动的是这 200 帧向分配器要了多少：sparse `128 942 382` 字节 / `107 432` 次分配，
full `38 212 398` 字节 / `34 129` 次分配——**四种负载条件下 90 次运行逐字节相同**。

于是钉子改用三种货币计价，按可信程度排序（实现见测试本身的 `DragHeapCounter`、`DragArm`
与 `median_paired_shrink_shape`）：

1. **堆用量**（精确，主钉）。每帧字节数与分配次数，留 ~12% 余量。上面那三件“不许回来”的
   每帧工作全都是堆用量退化，藏不进 12%。
2. **形状**（同一次运行内的**配对**相对量）。两条臂逐帧交错跑，所以每一个样本都是相隔几微秒
   的两次测量；取 100 个 shrink 帧各自的 sparse÷full 的中位数。时钟在比值里约掉，负载在配对
   里约掉。这一步不是修辞：同样这个比值，**按两段分开测是 3.62–7.74，配对之后是 2.62–3.90**，
   而它所依赖的绝对中位数在同一批运行里仍然动了 1.9 倍。取 shrink 半边而不是全部 200 帧，是
   因为两个半边是两种工作量（sparse 的 grow 回去只要 ~40 µs），混在一起的中位数正好落在双峰
   之间来回跳。预算取 6，比最差的 3.90 还宽一半；对着日常的 3.5，它仍然会在 sparse shrink 帧
   涨七成的时候报出来。
3. **天花板**（唯一剩下的绝对数，不是预算）。它是“再慢就不叫慢而叫坏了”的那条线，位于这台
   机器被 19 个 `rustc` 压着时最差中位数的 3 倍处（sparse 3 ms / full 1 ms）。

三条臂各自证明过会红，并且证明过另外两条在同一次注入下不会红——CONVENTIONS §三“断言要能
失败”落到本条上就是这张表：

| 注入的退化 | 堆 | 形状 | 天花板 |
|---|---|---|---|
| 撤掉 `reanchor_semantic_input_regions_after_resize` 的提前返回（`6133230` 的真实修复之一） | **红 3/3**，sparse 128.9→214.1 MB、107 432→186 230 次，逐次同一句话 | 绿（两臂一起变慢，3.09×） | 绿 |
| vendor `sparse_primary_width_shrink` 分支里 ~0.5 ms 无分配忙循环（shrink 帧 ×1.9） | 绿（逐字节不变） | **红 3/3**，7.94–8.30× | 绿 |
| 每一个 resize 帧上 ~3.5 ms 无分配忙循环（两臂等量） | 绿 | 绿（比值 1.14） | **红 2/2**，中位数 4.57 / 6.49 ms |

顺带：同一个病在同一个 crate 里还有一处——`session.rs` 的
`wide_same_content_repaint_fingerprint_overhead_is_bounded` 也是“一段 16 次对着几秒之后另一段
16 次”求商，2.25× 的天花板，在本次 20 次套件循环里红了 2 次而单跑从不红。它按同样的办法改成
逐次配对取中位数（天花板一个字没动，因为动的不是标准而是测量）：配对后读数 1.42–1.44、最差
的单次 1.55；往 `session.feed` 里塞 ~7 ms 无分配忙循环，读数 2.54 > 2.25，仍然会红。

墙钟数字仍然逐次打印在 `BT_RESIZE_BENCH` 行上（总和、shrink 中位数、帧 p50/p90/max、堆），
只是不再当断言用——读日志的人看得到真实分布，而门不会为调度器的脾气而红。
